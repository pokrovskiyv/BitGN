## T+0:00 — Window opens

### Phase 1 — Reconnaissance (target: 10 min)

Goal: preview the blind task set without burning agent attempts.

```bash
cd pac1-py

# Quick mode: just task IDs + metadata (no trials created)
uv run python sample_tasks.py --out /tmp/recon-quick.md

# Live mode: sample first 10 tasks with full instructions
# SAFETY: verify the final benchmark allows repeated trials before --live on all 100
uv run python sample_tasks.py --live --limit 10 --out /tmp/recon-sample.md
```

**Human scan in `/tmp/recon-sample.md`:**
- New task families (calendar, messenger, multi-modal, scheduling)?
- New injection patterns or threat vectors?
- New required-reference patterns (different from practice)?
- Instance identifier format changes (e.g., `acct_###` → `ACCT-###`)?
- File layout hints (AGENTS.md mentions new directories)?

**Decision gate:** if nothing unfamiliar → skip to Phase 2. If new families
observed → note them for Phase 4 (hot-patch), still proceed.

### Phase 2 — Canary (target: 10 min)

Goal: prove the pipeline works on 3 diverse tasks from the blind set.

```bash
# Pick 3 tasks of different apparent shapes from the recon sample
# Example: one CRUD-like, one inbox-like, one security-looking
make task-final TASKS='<pick from recon>'
```

**Observe in the log:**
- Per-task score (aim for 3/3)
- `VERIFIER: AGREE` / `DISAGREE` lines — count disagreements
- `GATE BLOCK`, `GATE PASS`, `CHECKPOINT` fires — all expected?
- `SEMANTIC-STAGNATION` fires — fire-once each, no infinite loops?
- `SECURITY WARNING` fires — matches actual threats?
- Cost ≈ $0.50-1.50

**Decision gate:**
- Canary 3/3 → go to Phase 5 (skip diagnose/patch)
- Canary 2/3 → go to Phase 3 (diagnose the one failure)
- Canary 1/3 → go to Phase 3 (harder diagnosis) or Phase 7 (revert profile)
- Canary 0/3 → **STOP**, run escape hatch (see §Escape Hatches)

### Phase 3 — Diagnose (target: 10 min, only if Phase 2 failed)

Goal: identify the failure family.

```bash
# Check the canary eval report (auto-generated by main.py)
ls -lt docs/eval/run-*.md | head -3
cat docs/eval/run-<latest>.md
```

Match failures to the 8 failure families from `.claude/agents/generalization-analyst.md`:

| Family | Signature |
|---|---|
| `wrong_outcome` | score_detail says "got OUTCOME_X expected OUTCOME_Y" |
| `missing_side_effect` | "expected write/delete to <path> not found" |
| `grounding_miss` | "answer missing required reference '...'" |
| `no_answer` | "no answer provided" / `OUTCOME_ERR_INTERNAL` |
| `security_miss` | "expected DENIED_SECURITY got OK" |
| `security_fp` | "expected OK got DENIED_SECURITY" |
| `parse_failure` | "LLM FAILURE after 3 attempts" |
| `budget_exhaustion` | hit max_steps / `report_budget_exhaustion` |

**Decision gate:**
- Single family dominant → Phase 4 (targeted hot-patch)
- Mixed failures, no pattern → skip Phase 4, proceed to Phase 5 as-is (patching won't help a random-variance failure)
- Infrastructure failure (parse_failure cluster, ERR_INTERNAL ≥2) → Phase 7 (revert profile)

### Phase 4 — Hot-patch (target: 15 min, only if Phase 3 identified a family)

Goal: ONE targeted fix that generalizes, not a task-specific hack.

**Apply the Commander Rule 1-5 filter from `.claude/agents/commander.md`:**
1. No task IDs in code
2. No new `task_type` conditionals (extending existing is OK)
3. No hardcoded paths/IDs from task instructions
4. Addresses a family, not a single instance
5. Defer variance check to post-run

**Patching options in order of preference (fastest → slowest):**

**A. Prompt fragment edit (0 restart)** — `workspace/prompts/fragments/*.md`
```bash
# Fragments are re-read on every decide_strategy() call — no restart needed
vim workspace/prompts/fragments/<family>.md
# Continue running / resume without kill
```

**B. HINT env var (requires restart but minimal change)**
```bash
# HINT is read at Python startup in strategy.py — requires restart
# Useful for a blanket rule to add to every prompt
HINT='<new structural rule>' make run-final
```

**C. classify.py regex addition (requires restart)** — new task family
```python
# Add to classify.py:
_NEW_FAMILY_SIGNALS = re.compile(r"\b(pattern1|pattern2)\b", re.IGNORECASE)
# Plus a new branch in classify_task() — keep it behavioral, no task-specific literals
```
Then commit and restart: `git add pac1-py/classify.py && git commit -m "feat: add <family> classification" && make resume-final`

**D. verify.py / agent_loop.py structural change (requires restart + care)**
Only if A-C don't fit. High regression risk. Commit before and after.

**DO NOT:**
- Edit `domain_fs.py` (RPC contracts)
- Change `settings.py` model/backend mid-window (use env vars instead)
- Add new regex to `defend.py` without checking for false positives against canary

### Phase 5 — Full soak (target: 25 min)

Goal: run the complete blind task set once.

```bash
# Clean state check
git status --short
cat pac1-py/.run_progress.json 2>/dev/null && rm pac1-py/.run_progress.json

# Full run
make run-final

# Monitor in a second tmux pane
tail -f docs/run_history.json  # wait for the final record to land
```

**Watch for:**
- Progress logs show "Parallel mode: 4 workers"
- Each task prints its score
- Final line: `FINAL: <pct>%`
- Cost logged in last line
- Eval report auto-generated at `docs/eval/run-<timestamp>.md`

**Failure modes:**
- `KeyboardInterrupt` / killed → `make resume-final`
- `ConnectError` on one task → other tasks continue, resume the failed one
- `ERR_INTERNAL` cluster ≥3 → likely API rate limit, retry with `PARALLEL=2`
- Cost spike >$20 → investigate before retrying

### Phase 6 — Triage (target: 15 min)

Goal: decide SHIP / ITERATE / REVERT based on the soak result.

```bash
# Auto-compile wiki (already runs via hook, but verify)
python3 compile_wiki.py

# Read the eval report
cat docs/eval/run-<latest>.md

# Optional: invoke triage-benchmark-update skill for diff vs prior run
# (runs as Claude skill — `triage-benchmark-update` is available in user scope)
```

**Apply the verdict framework from the plan file §9:**

```
score >= 90% → SHIP
score in [80%, 90%) → CONDITIONAL SHIP (review failure pattern)
score in [65%, 80%) → ITERATE (one family-level patch, one more soak)
score < 65% → REVERT PROFILE (env flip to Qwen3 on Nebius, no code revert)
ERR_INTERNAL cluster ≥ 3 → REVERT regardless of score
unresolved regression on previously-stable tasks → ITERATE or REVERT
```

### Phase 7 — Iterate or escape (target: 25 min, only if Phase 6 decides ITERATE/REVERT)

**If ITERATE:**
- Apply one Phase 4 patch based on Generalization Analyst recommendation
- Commit
- `make resume-final` (faster) OR full `make run-final` (cleaner baseline)
- Return to Phase 6 with new score

**If REVERT:**
- Execute the relevant escape hatch (see §Escape Hatches)
- Re-canary: `make task-final TASKS='<known stable>'`
- If canary passes → full run again
- If canary fails → escalate to a deeper rollback

### Phase 8 — Submit & freeze (target: 5 min)

```bash
# Verify final score was persisted
tail -1 docs/run_history.json | python3 -m json.tool | head -20

# Tag the finals-ready commit
git tag finals-ready-$(git rev-parse --short HEAD)
git push --tags  # only if you push — otherwise just local

# Lock the final profile state
cp pac1-py/.env.final pac1-py/.env.final.lock
chmod 444 pac1-py/.env.final.lock
```

Final-ready marker: update `docs/final/release-notes.md` header
`**Status:** PRE-SOAK DRAFT` → `**Status:** FINAL (frozen at <SHA>)`.

## Escape Hatches

Ordered from least-disruptive to most-disruptive. Apply the smallest that fixes
the problem.

### E1 — Reduce parallelism (soft)

API rate-limited or sporadic ConnectError?
```bash
make run-final PARALLEL=2   # half pressure
make run-final PARALLEL=1   # sequential, slowest but safest
```

### E2 — Env flip to Qwen3 (no code revert)

Sonnet underperforms or Haiku verifier over-rejects?
```bash
# Edit pac1-py/.env.final
PRIMARY_LLM_BACKEND=nebius
PRIMARY_MODEL_ID=Qwen/Qwen3-235B-A22B-Thinking-2507
# Keep VERIFIER_MODEL=claude-haiku-4-5 if Haiku was helping, else VERIFIER_POLICY=off
make run-final
```
**Pros:** Reuses all P0 code structural improvements. No git revert. **Cons:** Different backend, different cost profile, possibly different parse failure rate.

### E3 — Revert P0 cycle

A P0 change introduced a regression?
```bash
git revert 1a4680d          # the agent-team P0 cycle commit
make run-final              # re-run on the rolled-back state
```
This keeps `4acbe7e` (scaffold) + `182e30b` (evidence-based fallback) intact.

### E4 — Emergency revert to scaffold

P0 + 182e30b both misbehaving?
```bash
git checkout 4acbe7e        # Codex scaffold, no P0 fixes
make run-final
```
Only the bare Sonnet+Haiku pipeline with no behavioral fixes.

### E5 — Last-resort revert to Qwen3 baseline

All of the above failed?
```bash
git checkout 8071f87        # pre-P0 Qwen3 commit (75% → 92.5% cycle)
# Edit .env.final to Qwen3+Nebius
make run-final
```
This is the commit that scored 92.5% on practice with Qwen3. Known-good baseline but no P0 security fixes.

## Anti-Overfit Reminders

Repeat to yourself before every patch in the window:

1. **Task IDs rotate in the final.** Today's `t05` is not tomorrow's `t05`. Never write code that names a specific task ID.
2. **Task text references are instance-specific.** `acct_009.json` in practice might be `acct_042.json` in final. Never hardcode entity IDs.
3. **The grader's ground truth is opaque.** You cannot see why a task failed — only whether it did. Don't over-fit to guessed reasons.
4. **Variance is the enemy, not peak.** A fix that adds 5pp peak but 8pp variance is a NET LOSS on 100 independent tasks.
5. **When in doubt, don't patch.** The cost of a rushed bad patch is higher than the cost of accepting a 1-task regression.
