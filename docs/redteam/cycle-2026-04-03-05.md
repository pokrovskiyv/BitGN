# Red Team Report — cycle-2026-04-03-05

**Fix analyzed**: commit 38ea2f7 — changes `call_llm` invocation in `agent_loop.py:81` from 4 arguments to 5, inserting `""` as `system_dynamic` to match the refactored `llm.py` signature: `call_llm(system_static, system_dynamic, messages, model, nextstep_type)`. The entire composed prompt from `strategy.py` now flows through `system_static`; `system_dynamic` is always the empty string `""`.

**Scope**: Three attack scenarios targeting the semantic, regression, and security implications of routing the full system prompt into the cacheable `system_static` parameter with an empty `system_dynamic`.

---

## Attack 1 — Semantic: Empty-String Concatenation Artifact in Nebius Backend

**Vector**: In `_call_openai_compat()` (llm.py:114), the system message is built as:

```python
system = (system_static + "\n\n" + system_dynamic).strip()
```

When `system_dynamic` is `""`, the expression becomes `(prompt_text + "\n\n" + "").strip()`. The `.strip()` call removes the trailing `\n\n`, so the final system message is identical to calling `.strip()` on the original prompt alone. There is **no concatenation artifact** — no stray newlines, no double-spacing at the end.

For the Anthropic backend (`_call_api`, llm.py:189-194):

```python
static_text = system_static.strip()
dynamic_text = system_dynamic.strip()
system_blocks = [{"type": "text", "text": static_text, "cache_control": {"type": "ephemeral"}}]
if dynamic_text:
    system_blocks.append({"type": "text", "text": dynamic_text})
```

When `system_dynamic` is `""`, `dynamic_text` becomes `""` after `.strip()`, the `if dynamic_text:` check is falsy, and no second block is appended. The system message is a single cached text block containing the full prompt. This is functionally identical to the previous 4-arg behavior where the whole prompt was passed as the single system argument — there is no behavioral change.

**Edge case explored**: Could a model respond differently to a single system block vs. two blocks (static + dynamic) when the content is identical? The Anthropic API treats multiple system blocks as concatenated text with the same semantic role. Since there is now only one block, there is no boundary for the model to misinterpret. This is actually slightly cleaner than two blocks.

**Rating**: **BLOCKED** — No behavioral change. Both backends produce byte-identical system messages compared to the previous 4-arg call pattern. The `.strip()` in the Nebius path and the truthiness check in the Anthropic path both correctly handle the empty string. No attack surface.

## Attack 2 — Regression: Consistency with second_opinion.py and Dead Prompt-Split Design

**Vector**: Does `second_opinion.py` already use the 5-arg pattern, and does the fix create any inconsistency in how `call_llm` is invoked across the codebase?

`second_opinion.py:67` calls:

```python
verdict = call_llm(verifier_prompt, "", messages, model, VerifierVerdict)
```

This is exactly the same 5-arg pattern with `""` as `system_dynamic`. Both call sites are consistent: `agent_loop.py:81` and `second_opinion.py:67` both pass `""`. No caller uses a non-empty `system_dynamic`.

**Design debt identified**: The CLAUDE.md (pac1-py) still documents: *"Prompt split -- ExecutionStrategy splits prompt into system_prompt_static and system_prompt_dynamic."* But the actual `ExecutionStrategy` dataclass in `strategy.py:20-24` has only a single `system_prompt: str` field. The `system_prompt_static` / `system_prompt_dynamic` split described in the docs was either never implemented or was removed in an earlier refactor. The current `""` default for `system_dynamic` is a workaround for this: the split exists in `llm.py`'s function signature but not in the strategy layer.

This is not exploitable, but it is a latent regression risk: if someone reads the CLAUDE.md documentation and tries to implement the split by adding `system_prompt_static` and `system_prompt_dynamic` fields to `ExecutionStrategy`, they would need to update both `agent_loop.py` and `second_opinion.py` call sites. The current code provides no compiler/linter enforcement that both call sites stay in sync — a future refactor could easily update one but not the other.

**Concrete regression check**: The fix changes only `agent_loop.py:81`. All other callers of `call_llm` (`second_opinion.py:67`) already used the 5-arg signature. No existing functionality is broken. The `llm.py:221-230` dispatcher correctly routes to either backend. The `BaseModel` return type is unchanged.

**Rating**: **BLOCKED** — No regression. Both call sites are consistent. The fix correctly aligns `agent_loop.py` with the already-refactored `llm.py` signature. The documentation drift in CLAUDE.md is a housekeeping issue, not a security or correctness concern.

## Attack 3 — Security: Full Prompt in Cached system_static Enables Cache-Poisoning Amplification

**Vector**: With the entire system prompt (base + task-type addon + outcomes + reasoning + security sections + hints + target references) now in `system_static`, the Anthropic backend marks it all with `cache_control: {"type": "ephemeral"}`. This means subsequent calls within the same task reuse the cached prompt tokens. The cache key is derived from the exact text content.

**Attack scenario**: An adversary cannot directly poison the Anthropic prompt cache — the cache is scoped to the API key and the exact byte sequence of the cached content. There is no cross-tenant or cross-request cache pollution possible through the Anthropic API. The cache is a performance optimization, not a shared state.

**However**, consider the inverse: the fact that the entire prompt is cached means that if the prompt itself were compromised (e.g., via A-Evolve mutation of `workspace/prompts/system.md` or fragment files), the compromised prompt would be cached and used for all subsequent LLM calls within that task. This is identical to the pre-fix behavior — the prompt was always loaded once per task and reused — so the caching does not change the blast radius of a prompt mutation.

**More subtle angle — cache key stability across tasks**: Since `strategy.py` composes the prompt from the same fragment files for tasks of the same type, two consecutive `communication` tasks would have the same `system_static` content (assuming no A-Evolve mutation between tasks). The Anthropic cache could serve the cached prompt from task N to task N+1, saving input tokens. This is purely beneficial — it reduces cost and latency. There is no security implication because the cached content is the agent's own system prompt, not user-controlled data.

**The real question — should dynamic content be in system_dynamic?**: The composed prompt from `strategy.py` includes `target_section` (strategy.py:106-107), which contains path references extracted from the task text:

```python
target_section = f"\nTarget references from task: {hints_str}. Prioritize these."
```

These `target_hints` are derived from the task instruction via regex (`_extract_target_hints` in classify.py:100-102). If the task text contains attacker-controlled path-like strings (e.g., `../../../etc/passwd`), they flow into `target_section`, then into `system_prompt`, then into `system_static`, and finally into the cached prompt block. This means attacker-controlled content is placed into the highest-privilege position in the message hierarchy (system prompt) AND cached.

However, the `target_hints` extraction uses a restrictive regex (`_PATH_HINTS` in classify.py:92-96) that matches only simple path patterns (`word/word.ext`) and known directory names (`outbox`, `inbox`, `contacts`, `calendar`). It does not capture arbitrary text. The extracted hints are interpolated into a fixed template string, not executed. The model sees them as routing guidance, not as instructions. And the existing system prompt's instruction hierarchy (`system prompt > task instruction > file content`) means the model should not elevate these hints above its core rules.

**Rating**: **BLOCKED** — The Anthropic prompt cache is API-key-scoped and content-addressed. Placing the full prompt in `system_static` does not create a new attack surface. The `target_hints` inclusion in the cached block is a minor concern but is mitigated by restrictive regex extraction and the instruction hierarchy. An adversary cannot exploit the caching mechanism to inject, modify, or amplify prompts across tasks or sessions.

## Recommendations

1. **P3 — Update stale CLAUDE.md documentation**: The pac1-py CLAUDE.md line 21 references `system_prompt_static` and `system_prompt_dynamic` fields on `ExecutionStrategy` that do not exist. Update to reflect the actual single `system_prompt` field and the `""` convention for `system_dynamic` at the `call_llm` boundary. This prevents future contributors from attempting to implement a split that diverges from the current architecture.

2. **P3 — Consider materializing the prompt split**: If the Anthropic prompt caching benefit is significant (cost reduction from caching the stable base prompt across tasks of different types), consider splitting `ExecutionStrategy` into `system_prompt_static` (base prompt + outcomes + reasoning, stable across task types) and `system_prompt_dynamic` (task-type addon + security section + target hints, varies per task). This would maximize cache hit rates on the Anthropic backend. Current behavior — caching the full composed prompt — only gets cache hits for consecutive tasks of the identical type with identical target hints. This is a cost optimization, not a correctness issue.

3. **P4 — Add a type signature comment**: The `call_llm` function accepts `system_dynamic: str` but every caller passes `""`. Consider adding a comment or TODO at the call sites noting the unused parameter, so future reviewers understand this is intentional and not an oversight.
