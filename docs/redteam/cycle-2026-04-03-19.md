# Red Team Report: Cycle 2026-04-03-19

**Commit**: fac8a38
**Change**: `pre_completion_gate()` in `verify.py` rejects `OUTCOME_NONE_UNSUPPORTED` when `tool_call_count < 2` (step 0 or 1), forcing the model to make at least 2 tool calls before claiming UNSUPPORTED. Shares the `completion_gate_count` cap of 2 with all other gates.

---

### Attack 1: Bounce Through UNSUPPORTED into Unchecked OUTCOME_OK (PARTIAL)

**Vector**: The model attempts UNSUPPORTED at step 0. The gate rejects it (`completion_gate_count` = 1). The model then does one read (step 1) and immediately submits `OUTCOME_OK` with fabricated results -- no actual work done.

At `tool_call_count=1`, the `OUTCOME_OK` gate (`step < 2`) fires and rejects (`completion_gate_count` = 2). The model does one more read (step 2) and submits `OUTCOME_OK` again. Now `completion_gate_count == 2`, so `pre_completion_gate` is **skipped entirely**. However, the evidence challenge (`outcome_challenged`) and criteria gate (`check_criteria`) still fire independently since they are outside the `completion_gate_count` guard.

**Verdict: PARTIAL** -- the UNSUPPORTED gate burns 1 of 2 gate budget slots, leaving less headroom for other gates (inbox reads, cumulative threats, contacts check). But the evidence challenge and criteria gate are unaffected since they have their own one-shot flags. The real risk is limited to tasks where the inbox/communication/threat-count gates would have caught a bad outcome on attempt 3+.

---

### Attack 2: Two Tool Calls Then Immediate UNSUPPORTED (BLOCKED)

**Vector**: The model calls `tree /` (step 0) and `list /` (step 1), then submits `OUTCOME_NONE_UNSUPPORTED` at `tool_call_count=2`. The gate checks `step < 2` which is `2 < 2 = False`, so the UNSUPPORTED gate does not fire. The model claims the task is unsupported after only superficial filesystem exploration.

However, after the gate passes, the evidence challenge fires: "VERIFY: You chose OUTCOME_NONE_UNSUPPORTED. Provide evidence... UNSUPPORTED -> name the capability you lack." The model must justify the claim. If it cannot cite a missing capability, the challenge nudges it toward OUTCOME_OK. Additionally, for `analysis` and `search` tasks, the separate `tracker._reads` gate (line 148-155) blocks UNSUPPORTED if no files were actually read -- and `tree` and `list` do not register as reads in `WriteTracker`.

**Verdict: BLOCKED** -- the step threshold is easy to satisfy, but the downstream evidence challenge and the task-type-specific reads gate provide defense in depth. A model doing only tree+list on an analysis task still gets caught.

---

### Attack 3: Shared Gate Budget Starvation via Inbox Task (PARTIAL)

**Vector**: An `inbox_processing` task where the model tries UNSUPPORTED at step 0 (gate fires, `completion_gate_count` = 1), then reads one inbox file and tries UNSUPPORTED again at step 3. This time the UNSUPPORTED step gate passes (`3 >= 2`), but the inbox "read ALL listed inbox files" gate fires (`completion_gate_count` = 2). The model reads one more file, then submits `OUTCOME_NONE_CLARIFICATION` -- skipping `pre_completion_gate` entirely since `completion_gate_count == 2`.

The CLARIFICATION outcome triggers the evidence challenge (one-shot, fires once). The model provides a vague justification. The second opinion verifier also fires for CLARIFICATION outcomes on inbox tasks. So two independent checks remain.

**Verdict: PARTIAL** -- the UNSUPPORTED gate consumed one gate budget slot that could have been used by the inbox-specific gate on a later attempt. But the evidence challenge and second opinion verifier are independent and still protect against unjustified CLARIFICATION claims. The damage is bounded to scenarios where a third gate attempt would have been needed.

## Summary

| # | Attack | Verdict | Risk |
|---|--------|---------|------|
| 1 | Bounce UNSUPPORTED -> burn gate budget -> unchecked OK | PARTIAL | Low-Medium |
| 2 | Two superficial calls then UNSUPPORTED | BLOCKED | Low |
| 3 | Gate budget starvation on inbox tasks | PARTIAL | Low |

**Assessment**: The fix is narrowly scoped and low-risk. Unlike the reverted `_MIN_STEPS` gate (cycle-18), this version only targets one specific outcome (`UNSUPPORTED`) at a very early threshold (`< 2`), which limits the gate budget consumption problem. The main weakness remains the shared `completion_gate_count` -- any gate that fires reduces headroom for others. Consider not incrementing `completion_gate_count` for quality gates (early-OK, early-UNSUPPORTED) so the budget is reserved for security-critical gates (inbox reads, cumulative threats).
