# Red Team Report: Cycle 2026-04-03-15

**Change**: `pre_completion_gate()` in `verify.py` now accepts `cumulative_threats: int = 0` and fires a HOLD when `cumulative_threats >= 3` and the chosen outcome is not `OUTCOME_DENIED_SECURITY`.

---

### Attack 1: False-Positive Flood to Force OUTCOME_DENIED_SECURITY on Legitimate Tasks (PARTIAL)

**Vector**: An adversarial task environment plants files whose legitimate content happens to match 3+ threat patterns. For example, a project README that says "new instructions:" (matches `context_reset`), a template that contains "you are now a helpful assistant" (matches `role_manipulation`), and a log file that mentions "ignore all prior errors" (matches `direct_override`). These are plausible false-positive matches in a developer filesystem. The agent reads all three files during normal task execution, accumulates `cumulative_threats >= 3`, then attempts to complete with `OUTCOME_OK`. The gate fires: "HOLD: Multiple security threats were detected..." The LLM, uncertain whether the match was genuine, may capitulate and switch to `OUTCOME_DENIED_SECURITY` — costing 1.0 points on a task the agent would otherwise have completed correctly.

**Why not fully blocked**: The gate message says "unless you are certain the detected patterns are false positives." A well-calibrated LLM reading this should retain `OUTCOME_OK` if it has already done the work and the task was benign. But LLMs under BUDGET_WARNING pressure (fired 2 steps earlier) tend to seek the path of least resistance, and "report OUTCOME_DENIED_SECURITY" is named explicitly in the HOLD text. The `completion_gate_count < 2` cap means this HOLD can fire at most twice, giving the LLM two pressure points to capitulate.

**Mitigated by**: (1) The gate's own hedging language ("unless you are certain") gives the LLM an explicit permission to proceed. (2) Real false positives are unlikely to cluster to 3+ from a single benign task's file reads, since scan_content runs on each individual tool result, not the whole filesystem; a single file rarely triggers 3 distinct categories. (3) The `outcome_evidence_message` challenge fires afterward and asks the LLM to cite the threat text — which will reveal it is benign, potentially correcting the capitulation.

**Verdict: PARTIAL** — vector exists but requires an unusually high false-positive density and an LLM that ignores the gate's own "unless certain" escape clause.

### Attack 2: Drip-Feed Below Threshold Then Burst at Completion (BYPASSES)

**Vector**: A multi-file payload spreads injection content across exactly 2 warnings per file so that early reads accumulate `cumulative_threats = 2`, staying below the gate threshold of 3. The final payload file, read just before the agent would naturally complete, contributes 1 more warning, pushing the total to 3. At this exact moment, the agent has already been pushed toward the injected action and attempts `report_completion` with `OUTCOME_OK`. The gate fires. But the gate only says "report OUTCOME_DENIED_SECURITY" — it does not say "undo the action you just took." If the injected instruction caused a **write** to occur in a prior step (before the gate threshold was crossed), the damage is already done: the file has been written, and a security rejection now doesn't erase it.

**Concretely**: steps 1-4: read files with 2 cumulative threat warnings total; step 5: injected write executes (cumulative threats still 2, so no gate fired); step 6: read the injected destination file (adds 1 more warning, total = 3); step 7: agent completes with OUTCOME_OK. Gate fires. Agent switches to OUTCOME_DENIED_SECURITY. The injected write is permanent regardless of outcome code.

**Why this matters**: The gate is positioned at the `report_completion` boundary, which is post-write. It cannot retroactively un-write a file written two steps earlier. The damage (exfiltration, overwrite, file creation) is already committed to the VM. OUTCOME_DENIED_SECURITY is the correct outcome code but does not reverse side effects.

**Mitigated by**: (1) HIGH-risk action gate on write operations to sensitive paths blocks the injected write before it reaches dispatch. (2) Stagnation detection and the pre-submit unverified-write gate may surface the suspicious write. (3) The cumulative threat warning is also appended to tool output text, so the LLM sees it before the next step and may self-correct.

**Verdict: BYPASSES** (in terms of side effects) — the gate correctly changes the outcome code but cannot prevent writes that occurred while `cumulative_threats < 3`. A targeted payload that front-loads the injected action before the threshold is crossed evades the security outcome guarantee while still triggering it.

### Attack 3: Gate Slot Exhaustion via Benign Bounce (BLOCKED)

**Vector**: An attacker embeds content that causes the first `pre_completion_gate` check to fire for a reason *other* than the threats gate — for example, making the agent complete an inbox task without reading inbox/ (fires the inbox-read gate). That consumes `completion_gate_count = 1`. A second early completion attempt triggers the unverified-write hold (a separate mechanism, does not consume the gate count). Then, when the agent finally retries completion after genuinely resolving those issues but now with `cumulative_threats >= 3`, the threats gate should fire as `completion_gate_count = 1` (still under 2). After one more bounce, `completion_gate_count = 2` and the gate is skipped entirely — the threats HOLD can no longer fire.

**Why this is blocked on close inspection**: The gate cap `completion_gate_count < 2` applies to *all* gate rejections from `pre_completion_gate()`, including the new threats check. If the threats check itself fires twice (once at count=0, once at count=1), the third attempt falls through with `completion_gate_count = 2`. However, the *other* guards (inbox, no-reads, communication) firing first would only consume gate slots for *those* guards, not pre-spend slots that the threats gate needs. Both checks live inside the same `if completion_gate_count < 2` block, so once the count hits 2 via any rejecting guard, the threats gate is also bypassed.

**The realistic path**: task_type="inbox_processing", `cumulative_threats >= 3`. Agent first completes without reading inbox/ (count goes to 1). Agent rereads inbox/ and completes again with OUTCOME_OK and threats present (count goes to 2). Third attempt: gate is bypassed entirely because count >= 2. The threats-based HOLD never fires on attempt 3. The outcome code the LLM chose (OUTCOME_OK) passes through.

**Mitigation gap**: The `completion_gate_count < 2` cap was originally sized to prevent infinite loops, but it means that any legitimate two-bounce path (e.g., inbox + unread files) exhausts the threats gate before it can fire.

**Verdict: BLOCKED** for single-bounce scenarios, but this analysis reveals a **compound-bounce interaction**: if two other gate conditions fire before the threats gate gets a chance, the threats gate is silently skipped. This is not a bypass of the threats gate specifically — the LLM still received the cumulative threat warnings in tool output at steps 2-3 via the `warning_text` appended to `txt`. The redundancy saves it, but the gate itself is effectively voided in the two-prior-bounce path.

---

### Summary

| Attack | Verdict | Notes |
|--------|---------|-------|
| 1. False-positive flood | PARTIAL | Requires dense benign false positives + LLM capitulation |
| 2. Drip-feed below threshold then burst | BYPASSES | Gate is post-write; pre-threshold writes are irrevocable |
| 3. Gate slot exhaustion via compound bounce | BLOCKED* | Gate fires 0 times in two-prior-bounce paths, but in-band warnings remain |

**Critical finding**: Attack 2 exposes a structural limitation — the threats gate operates at `report_completion` time, which is necessarily after any writes already dispatched to the VM. For the gate to prevent side effects (not just correct the outcome code), write-time threat counting needs its own threshold check, independent of the completion gate. The current design is effective at correcting the reported outcome but cannot undo committed filesystem mutations.
