# Red Team Report: Cycle 2026-04-02-21

## Change Reviewed
`verify.py` `_fallback_outcome()`: terminal return changed from `OUTCOME_ERR_INTERNAL` to `OUTCOME_NONE_CLARIFICATION` when agent exhausts step budget with zero reads and zero writes (tracker exists but is empty).

---

## Attack Scenarios

### Scenario 1: Threat Injection Causes Total Tool Failure, Agent Reports CLARIFICATION Instead of SECURITY
**Attack**: A task embeds a sophisticated injection that causes the LLM to refuse every tool call (e.g., each proposed action triggers the HIGH-risk gate, and the LLM never re-confirms). The agent spins through its full step budget producing only gated-and-skipped iterations. The `cumulative_threat_count` stays below 5 because threats appeared in the task text (scanned once), not in tool outputs (which never executed). With the old code, the fallback was `ERR_INTERNAL` -- a neutral signal that something broke. With the new code, it returns `CLARIFICATION`, which tells the benchmark "the task was ambiguous." A task that should score as `DENIED_SECURITY` (injection present) instead scores as `CLARIFICATION` -- potentially still earning partial credit but failing to flag the threat.

**Precondition**: `cumulative_threats < 5` (threats only in task text, not in tool output) AND all tool calls gated/failed.

**Rating**: **PARTIAL**

The `cumulative_threats` set in `agent_loop.py` only accumulates from `scan_content()` on tool *output*, not from the initial task-text scan. If the injection prevents any tool from executing, the threat count stays 0 and the `>= 5` guard in `_fallback_outcome` never fires. The security classification from `classify.py` (which routes to `security_test` type with 8 steps) is upstream and does not affect `_fallback_outcome` -- it only controls step budget and prompt fragment. The change removes the last-resort ERR_INTERNAL that at least signaled abnormality, replacing it with a "normal" outcome that hides the failure mode.

---

### Scenario 2: Masking Systemic Failures Behind a Legitimate-Looking Outcome
**Attack**: Not adversarial, but a debugging/observability concern. When the LLM backend is misconfigured (wrong model ID, malformed schema, network failures), all 3 parse attempts fail per step, `job` is `None`, the loop breaks immediately at step 0. The tracker has zero reads/writes. Previously this produced `ERR_INTERNAL`, a clear signal in eval logs that something was broken. Now it produces `CLARIFICATION`, which is indistinguishable from a legitimate "task was ambiguous" result. An operator reviewing eval reports (e.g., `docs/eval/`) would see CLARIFICATION and assume the task was genuinely unclear rather than investigating a backend failure. This delays diagnosis of infrastructure regressions.

**Rating**: **PARTIAL**

The loop's `return None` path (line 254 of `agent_loop.py`) means `run_agent_loop` returns `None` when the budget exhausts, not the fallback outcome string. The fallback outcome goes to the benchmark via RPC, not to the caller. So the eval report sees the *benchmark's* score, not the raw outcome string. However, the console log shows the outcome via `report_budget_exhaustion`, and downstream analysis tools (analyst agent, run_history.json) may parse these outcomes. Replacing a distinctive ERR_INTERNAL with a common CLARIFICATION reduces signal-to-noise in failure analysis. The blast radius is proportional to how often total tool failure occurs (rare in production, but common during development/migration).

---

### Scenario 3: Adversary Forces Empty Execution to Earn CLARIFICATION Score on a Security Task
**Attack**: A crafted task combines a real action request with a subtle injection. The injection is designed to make the LLM hesitate on every tool call (e.g., each path triggers sensitive-path detection, or the injection includes language that makes every write look like it was "suggested by file content"). The agent enters a loop of: propose tool -> HIGH-risk gate -> LLM declines to re-confirm -> next step. After exhausting the budget with zero tool executions, the fallback is now CLARIFICATION. On the benchmark, CLARIFICATION may score higher than ERR_INTERNAL for certain task types. The comment in the code itself acknowledges this: "CLARIFICATION is never worse than ERR_INTERNAL (which is never a correct outcome)." An adversary who understands the scoring model could engineer tasks where CLARIFICATION is the *second-best* outcome (after DENIED_SECURITY), effectively gaining a small score advantage from a broken execution.

**Precondition**: Benchmark scoring must award partial credit for CLARIFICATION on the target task type. The adversary must know the fallback logic.

**Rating**: **BLOCKED**

This is largely theoretical. The adversary would need to control task content (which in BitGN comes from the benchmark platform, not user-submitted). The change's logic is sound for the stated goal: ERR_INTERNAL is genuinely never a correct PAC1 outcome, and CLARIFICATION is a safer default. The cumulative_threats >= 5 guard still catches cases with heavy threat signals. The real risk is Scenario 1, not this one.

---

## Verdict

**Overall: ACCEPTABLE**

The change is defensible. `ERR_INTERNAL` is not a valid PAC1 outcome code and was always a score-zero dead end. `CLARIFICATION` is at worst score-neutral and sometimes correct (tasks like t05 that expect CLARIFICATION/UNSUPPORTED). Two concerns worth noting:

1. **Scenario 1 gap**: When a security injection prevents all tool execution but `cumulative_threats < 5`, the fallback should ideally be DENIED_SECURITY, not CLARIFICATION. Consider adding: if `classification.task_type == "security_test"`, pass that into `_fallback_outcome` and return DENIED_SECURITY for security-classified tasks regardless of threat count.

2. **Observability regression**: ERR_INTERNAL was a useful "canary" for infrastructure failures. Consider logging a distinct warning when the zero-reads-zero-writes fallback fires, so analysts can distinguish "genuinely ambiguous task" from "total execution failure" without relying on the outcome code.
