## Findings

### Finding 1: LLM Parse Error Rate Is High (empty plan_remaining_steps_brief)
**Type**: Budget Waste / Structural
**Evidence**: The log shows repeated Pydantic parse failures of the same type across many tasks. The most frequent is:
```
LLM parse error (attempt 1/3): 1 validation error for NextStep
plan_remaining_steps_brief
  List should have at least 1 item after validation, not 0
```
Observed at: t02 step_3, t03 step_8, t11 step_6, t13 step_8 (twice, attempt 1/3 and 2/3), t17 step_7, t18 step_15, t19 step_13.

Each parse error costs one retry attempt (~10–30s of additional subprocess time). The second most common failure is the "4 validation errors for NextStep" (missing `current_state`, `plan_remaining_steps_brief`, `task_completed`, `function`) which appears at t02 step_3, t09 step_1, t11 step_7, t17 step_8, t19 step_13, t22 step_13, t24 step_5. This occurs when the model outputs a bare `report_completion` object without wrapping it in the `NextStep` envelope.

**Confidence**: HIGH
**Impact**: 7–10 wasted retry rounds observed per run. Each retry adds ~20–55s latency (because attempt 2/3 involves an extra LLM call). Across 25 tasks this accumulates to estimated 3–8 minutes of wasted runtime per full run. Does not cause task failures in the 09 log (retries recover), but adds context length bloat and increases risk of hitting the `max_steps` budget prematurely.

### Finding 2: Repeated `tree -L 2 /` + `cat AGENTS.md` Auto-Init on Every Task
**Type**: Redundant Read
**Evidence**: Every single task in the run begins with the identical 3-step auto-init sequence:
```
AUTO: tree -L 2 /
AUTO: cat AGENTS.md
AUTO: context
```
This is by design (hardcoded `must` list in `agent.py` lines 377–386), but the cost is non-trivial for the CRM environment where the tree output is large (30+ lines listing 10 accounts, 10 contacts, 20 invoices, 10 opportunities, 10 reminders). The entire AGENTS.md content is also re-transmitted on every task. For 25 tasks this means 25 full tree + AGENTS.md transmissions, each ~1KB of context in the conversation, growing cumulative context cost.

Additionally, in tasks t12–t17 (CRM tasks with large filesystems) the auto-init tree is very long. Several tasks then also read README files they just saw in the tree, e.g. t14 reads `/outbox/README.MD` in step 2 after already having seen the outbox directory structure in the auto-init tree.

**Confidence**: HIGH
**Impact**: ~3 steps of context overhead per task are unavoidable but the pattern of reading the same READMEs repeatedly (outbox/README.MD read in t11, t12, t17 separately) wastes 1–2 steps per CRM email task.

### Finding 3: Subprocess Timeout Still at 120s — Confirmed Risk for Sonnet-4-6
**Type**: Timeout
**Evidence**: `pac1-py/agent.py` line 212: `timeout=120`. The eval report for cycle 10 explicitly states: "The Optimizer's analysis was correct" regarding the `timeout=120` issue. In the 09 log, retry attempts frequently show 29–56s per step for complex tasks (t09: 29183ms, t13 step_8: 35857ms for attempt 2/3, t17 step_8: 22193ms). Some steps push very close to 60s (t03 step_6: 55599ms). Under high API load, a complex task step requiring structured JSON output could exceed 120s and crash the agent with `subprocess.run` timeout.

The 09 log does not show any actual timeout failures (all ran clean at 60%), but the 10 run showed CRM tasks failing at step_1 with empty JSON — a symptom of `claude -p` returning an empty `result` field, which can occur both from API degradation and from timeout-induced truncation.

**Confidence**: HIGH
**Impact**: Risk of cascading empty-JSON failures on CRM tasks during API contention. Each timeout = task failure (0.0 points). The 10-run regression lost 5 tasks this way. Reverting to 120s preserves safety but leaves the risk open.

## Recommendations

Ordered by confidence and impact:

1. **Fix LLM parse error pattern** (HIGH confidence, 3–8 min/run waste): The `plan_remaining_steps_brief` empty list error occurs because the model returns `[]` when it considers the task complete and no more steps are planned. The `NextStep` schema requires `MinLen(1)` but the model legitimately has nothing to say. Fix: change the schema constraint to `MinLen(0)` or provide a fallback value like `["task complete"]` via a validator. Alternatively, add to the FORMAT CORRECTION message that `plan_remaining_steps_brief` must always contain at least one string (e.g., `"done"` or `"task complete"`).

2. **Raise subprocess timeout to 150s** (HIGH confidence, prevents CRM task failures): The reverted 120→180s change was correct in principle. The 180s value may be too aggressive for normal tasks. A middle value of 150s reduces the risk of CRM task empty-JSON failures under API contention while keeping overall run time reasonable. This was specifically noted as a valid optimization in the eval report ("consider applying in the NEXT cycle if the benchmark run is clean").

3. **Fix t03 card naming** (HIGH confidence, 4% score gain): Add guidance in the `crud.md` or `multi_step.md` fragment: "When creating a distill card from an inbox file, the card filename should match the source file's date-prefixed basename pattern (e.g., `2026-03-23__hn-walmart-chatgpt-checkout.md`)." This is deterministic and directly maps to a 1-point gain.

4. **Inbox: read the message before loading channel rules** (MEDIUM confidence): Add guidance in the `multi_step.md` fragment or `system.md`: "For inbox tasks, first read the inbox message to identify its type (direct email vs. channel message), then load only the relevant documentation. Skip channel file reads for plain email messages." This saves 3 steps in ~40% of inbox tasks.

5. **Short-circuit contact-not-found search** (MEDIUM confidence): Add a guidance note that if a full-name search in contacts returns empty, skip the surname-only retry and go directly to OUTCOME_NONE_CLARIFICATION. Full-name miss is sufficient signal.

6. **Include outbox README inline in CRM prompt fragment** (MEDIUM confidence, small): The outbox format is stable and short. Include it directly in a CRM-specific prompt fragment rather than requiring the agent to read it on every email task.
