The new `_MIN_STEPS` gate (step < 4) fires inside the `completion_gate_count < 2` cap, sharing the same counter with inbox-read, contacts-search, and cumulative-threat gates. Worst case: 2 gate holds total across all gates, not 2 per gate.

**Verdict: No budget exhaustion risk.** The gate uses `tool_call_count` (actual dispatched calls), not `step` (loop iterations). An agent that reads AGENTS.md + tree + task file already has 3 tool calls from boot before attempting completion. The gate only catches agents that skip exploration entirely — exactly the problem pattern seen in t28 (2 tool calls, completed at step 3) and t30 (3 tool calls, wrong answer at step 3).

## Waste Pattern: Gate Holds Without Productive Recovery

t25 in R89: 28 steps consumed, only 4 tool calls dispatched. The agent spent 24 iterations in gate/challenge loops without making progress. This is not caused by the new gate but by the existing outcome-evidence and cumulative-threat gates interacting with a model that cannot satisfy them. The new min-steps gate will not worsen this — it fires early (step < 4) and the cap is shared.

## Tuning Recommendation

**No parameter changes needed.** Confidence: **HIGH**.

The min_steps=4 threshold is conservative — boot_messages alone typically produces 2–3 tool calls. The gate only blocks genuinely premature completions (the t28/t30 pattern). The shared `completion_gate_count` cap of 2 prevents runaway holds. Communication (tightest budget at 18) retains 13–14 productive steps, sufficient for read-contacts-write-verify flows.
