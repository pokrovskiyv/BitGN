## Waste Patterns

### 1. Parse failures in t03: retry correction partially failing on `MinLen(1)` (RESIDUAL)

**Observed**: cycle 4 eval report notes t03 had 5 LLM parse failures — "3 empty JSON + 2 plan_remaining_steps_brief MinLen(1)". The retry correction message (applied in cycle-07) was designed to fix the nesting structure and the empty-list problem by injecting a concrete example:

```
"plan_remaining_steps_brief": ["<next step>"]
```

The fact that 2 of 5 failures still hit `MinLen(1)` on `plan_remaining_steps_brief` indicates the correction is not always read/applied on the first corrective retry. The 3 "empty JSON" failures are a separate upstream issue — the `claude -p` subprocess returned an empty or non-JSON result.

**Root cause split**:
- 3 "empty JSON": `_call_cli` received an empty `result` field from `claude -p`. This can happen when `claude -p` times out (120 s), returns a non-JSON response, or produces an empty output. The `_extract_json` function would return an empty string, causing `model_validate_json("")` to raise `ValidationError`. This is NOT a format correction problem — it is an infrastructure/timeout problem.
- 2 "MinLen(1)": The LLM produced valid JSON structure but with `plan_remaining_steps_brief: []`. The correction message example (`["<next step>"]`) was present but the LLM interpreted `<next step>` as a literal template and emitted an empty list instead.

**Estimated waste**: 5 extra LLM calls on t03 alone. More importantly, the task scored 0.00 after completing with OUTCOME_OK, suggesting the real failure was a side-effect error (wrong file content or missing read-after-write), not the parse failures directly.

**Confidence**: MEDIUM — the parse failure count is documented in the eval report; the "empty JSON" root cause is inferred from the CLI backend path.

### 4. `claude -p` subprocess timeout producing empty JSON (NEW)

**Observed**: 3 of t03's 5 parse failures were "empty JSON", consistent with `claude -p` returning an empty `result` field. The subprocess timeout is set at 120 s. If the CLI model (claude-sonnet-4-6) takes longer than 120 s for a complex reasoning step, the subprocess completes with no output, `_extract_json("")` returns `""`, and `model_validate_json("")` raises, consuming a retry slot.

**Current model**: `claude-sonnet-4-6` is now the default (changed from haiku-4-5 in commit `32ca4bf`). Sonnet reasoning steps are longer than Haiku. The 120 s timeout was set when haiku-4-5 was default; it may be undersized for sonnet on complex steps.

**Estimated waste**: Each timeout consumes 120 s of real time before the exception is raised. 3 empty-JSON failures = up to 6 minutes wasted on t03 alone (3 attempts × 120 s each if each timed out). Even if not all hit the full timeout, this is the most expensive per-event waste in the run.

**Confidence**: MEDIUM — the mechanism is clear; whether all 3 empty-JSON events were timeouts vs. empty responses from the model is not confirmed without subprocess stderr inspection.

## Tuning Recommendations

### Rec 1: Increase `subprocess.run` timeout from 120 s to 180 s for sonnet

**Confidence**: HIGH

**Change**: In `pac1-py/agent.py`, `_call_cli` function, change the `timeout=120` argument to `timeout=180`. This gives claude-sonnet-4-6 an additional 60 seconds per step before the subprocess is abandoned and an empty-JSON parse failure is triggered.

**Rationale**: The model was switched to sonnet-4-6 (commit `32ca4bf`, flagged as "perf: switch default model") but the subprocess timeout was not updated to match sonnet's longer generation time. Haiku-4-5 typically responds in 5–30 s; sonnet-4-6 can take 60–120 s on complex structured output steps. 3 of t03's 5 failures were "empty JSON" — consistent with timeout-induced empty results.

**Expected impact**: Eliminates up to 3 timeout-induced parse failures on t03. If t03's OUTCOME_OK result was valid but a side-effect check failed, reducing retry noise may reveal whether the task itself is structurally broken. No risk of regression — increasing timeout only delays failure discovery, never prevents correct results.

**File**: `/Users/vitalypokrovskiy/Projects/BitGN/pac1-py/agent.py`, line 213: `timeout=120` → `timeout=180`

**Risk**: LOW — longer timeout increases worst-case per-step latency from 360 s (3 retries × 120 s) to 540 s (3 retries × 180 s), but only when the model genuinely takes long. Happy-path performance is unaffected.
