## 1. t01: Budget Exhaustion — Confirmed Root Cause

**Failure:** Missing deletes of 3 files in `02_distill/`. Budget runs out before all deletes complete.

**Step accounting for bulk-delete with HIGH-risk gating:**

Each delete of a HIGH-risk path costs **2 steps**: one step triggers the gate (`continue`, no dispatch), the second step re-issues the command to confirm. With 3 files to delete plus initial tree/context reads and final report:

| Action | Steps consumed |
|--------|---------------|
| Auto-init (tree + AGENTS.md read) | ~2 |
| Task read / plan | 1 |
| Per-file: gate challenge | 3 (one per file) |
| Per-file: confirmed delete | 3 |
| Read-after-write (verify.py: unverified_writes) | 0 (deletes not tracked as writes) |
| Pre-completion gate / outcome challenge | 1–2 |
| report_completion | 1 |
| **Total** | **11–12** |

Current `crud_delete` budget = **16**. That should be enough — but the `high_risk_gated` set only blocks once per path (line 130–132 of agent_loop.py). After the first gate, the second attempt dispatches immediately. So the real bottleneck is not per-delete gating cost, but likely the agent making redundant tree/list/read calls to re-locate files.

**Finding:** The gate cost is bounded at 1 extra step per unique path. Budget is not the structural blocker. The real issue is the agent spending extra steps on re-discovery (tree, list, re-read) between each delete. On a stochastic free-tier model, this variance spills over budget.

**Recommendation (HIGH confidence):** Raise `crud_delete` budget from **16 → 20**. The cost of extra steps on simple delete tasks (false-pass scenario) is low — the agent will still report_completion when done. The benefit is covering the re-discovery overhead that a weaker/noisier model like qwen3.6-plus adds.

## 2. Gate Waste: HIGH-Risk Gates Cost 1 Step Per Unique Path

**Code path (agent_loop.py lines 130–132):**
```python
if effective_risk == "high" and cmd_path not in high_risk_gated:
    high_risk_gated.add(cmd_path)
    continue
```

This is correct behavior — subsequent calls to the same path go through immediately. No change recommended here; it's already optimized.

**However**, the MEDIUM-risk gate (risk_level == "medium") does **not** block with `continue` — it appends a VERIFY message but dispatches immediately on the same step. This means medium-risk operations pay a message-injection cost but no step cost. This is fine and by design.

## 4. Redundant Read Analysis

From `agent_loop.py` and `verify.py`: the WriteTracker enforces read-after-write (any write with no subsequent read triggers a HOLD). This creates a structural pattern of 1 extra read per write. For tasks with multiple writes, this is a necessary cost, not waste.

**Potential redundancy:** The auto-init phase (lines 60–63 of agent_loop.py) reads AGENTS.md unconditionally in `domain.boot_messages(client)`. If the LLM also calls `read AGENTS.md` explicitly as its first action, that's a duplicate. However, the boot_messages result is injected into the initial message history as a pre-seeded user message — the LLM should not need to re-read AGENTS.md. Whether it does depends on model behavior.

**Recommendation:** No code change. This is a model discipline issue. The `reasoning.md` fragment already mandates using `current_state` to quote the source — if AGENTS.md is in boot_messages, the agent should reference it from memory. Monitor via logs; only act if t01/t24 traces confirm duplicate reads.
