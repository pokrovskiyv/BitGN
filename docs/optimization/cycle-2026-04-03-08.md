## Finding 1: HIGH-risk gate does NOT block execution (HIGH)

**Analysis**: CLAUDE.md specifies 3-level risk gating: "HIGH = DANGER message that blocks execution via `continue`". The actual implementation at agent_loop.py:106-109 appends a VERIFY message to the conversation but **does not `continue`**. The tool executes immediately in the same loop iteration regardless of risk level.

This means:
- `delete` (risk_level="high") executes without re-confirmation.
- `move` (risk_level="high") executes without re-confirmation.
- Sensitive-path writes (escalated to "high") execute without re-confirmation.
- The gate message arrives in the LLM's history *after* the tool already ran -- it cannot prevent the action.

The MEDIUM gate has the same issue (warn-then-execute is the stated design, so this is correct for MEDIUM). But for HIGH, the spec says block and force re-confirmation.

**Impact**: Security tasks (t07, t25, t28, t29 -- all flaky at 50-75%) where injections try to trigger deletes or sensitive writes are not blocked. The agent may delete files or overwrite protected paths on the first attempt, before the LLM sees the warning. This contributes to the binary-flaky pattern on security detection tasks.

**Recommendation**: Add `if effective_risk == "high": continue` after the gate message append. This skips dispatch and forces the LLM to re-issue the command (or choose a different action) on the next iteration. The MEDIUM path stays as-is (warn but execute).

```python
if effective_risk != "low" and not domain.is_completion(cmd):
    gate_msg = action_gate_message(tool_name, cmd_path, risk_level=effective_risk)
    print(f"{CLI_YELLOW}GATE{CLI_CLR}: {gate_msg}")
    messages.append({"role": "user", "content": gate_msg})
    if effective_risk == "high":
        continue  # block dispatch, force LLM re-confirmation
```

**Confidence**: HIGH (verified: no `continue` after HIGH gate in current code)

## Finding 2: `pre_completion_gate()` remains dead code -- next priority to wire in (HIGH)

**Analysis**: Carried forward from cycle-2026-04-03-05 Finding 2. `report_budget_exhaustion()` was wired in, but `pre_completion_gate()` was not. It provides 5 completion guards:

1. **OUTCOME_OK after 1-2 steps** -- prevents premature completion without doing work.
2. **Inbox: never read inbox/** -- forces agent to actually look at inbox before completing.
3. **Inbox: read ALL listed inbox files** -- catches partial inbox processing (needs `record_list()` wired in too).
4. **Analysis/search: no reads before CLARIFICATION** -- prevents lazy "I don't know" answers.
5. **Communication: no contacts/ before CLARIFICATION** -- prevents lazy "can't find recipient" answers.

Gates 2, 4, and 5 directly address flaky failure patterns: t14 (CLARIFICATION instead of OK, 50%), t17 (CLARIFICATION instead of OK, 75%), t21 (OK instead of CLARIFICATION, 25%).

**Wiring requirements**:
- Import `pre_completion_gate` in agent_loop.py.
- Call it before the outcome evidence challenge, with a max-2-attempts counter to prevent budget exhaustion.
- Wire `tracker.record_list()` calls for "list" tool results (currently `record_list` is defined but never called).

**Recommendation**: Wire `pre_completion_gate()` with attempt cap. Add `record_list()` tracking for list tool results.

**Confidence**: HIGH

## Finding 4: WriteTracker.record_action() and StagnationDetector.record_action() exist but are unused (LOW)

**Analysis**: Both `WriteTracker` and `StagnationDetector` have `record_action()` convenience methods that consolidate the inline tracking logic currently duplicated in agent_loop.py:159-174. The agent_loop uses manual `if hasattr(cmd, "path")` / `if tool_name == "write"` blocks instead of calling these methods.

Current code (agent_loop.py:159-174):
```python
if hasattr(cmd, "path"):
    if tool_name == "write":
        tracker.record_write(cmd.path)
    elif tool_name == "read":
        tracker.record_read(cmd.path)
    elif tool_name == "delete":
        tracker.record_delete(cmd.path)
elif tool_name == "move" and hasattr(cmd, "to_name"):
    tracker.record_write(cmd.to_name)
```

This could be replaced with:
```python
tracker.record_action(tool_name, cmd)
stagnation.record_action(tool_name, cmd)
```

**Impact**: No behavioral change. Pure cleanup -- reduces 15 lines to 2 and removes logic duplication between agent_loop.py and verify.py.

**Confidence**: HIGH (verified: `record_action()` logic matches inline code exactly)

## Finding 7: `security_posture` from strategy is computed but never consumed (OBSERVATION)

**Analysis**: `ExecutionStrategy.security_posture` is set based on task type and threat level (standard/hardened/paranoid) and returned from `decide_strategy()`. However, `agent_loop.py` never reads `strategy.security_posture`. It is used only in `strategy.py` to decide whether to append the security prompt fragment -- the value itself is not consumed downstream.

This means the "paranoid" vs "hardened" vs "standard" distinction affects only prompt composition (whether `security.md` fragment is included). It does NOT affect runtime behavior (step budget, gate sensitivity, threat scanning aggressiveness). This is fine as-is -- the prompt composition is the primary lever. But if future cycles want to vary gate behavior by security posture (e.g., lower the HIGH gate threshold in paranoid mode), the field is already available.

**Impact**: None currently. Observation only.

**Confidence**: HIGH
