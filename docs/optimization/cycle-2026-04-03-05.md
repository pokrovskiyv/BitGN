## Finding 1: `second_opinion.py` is DEAD CODE -- never imported or called (HIGH)

**Analysis**: `second_opinion.py` defines `needs_second_opinion()` and `get_second_opinion()` with a `VerifierVerdict` model. However, **no file in the codebase imports from `second_opinion`**. Grep across all of `pac1-py/` for `import.*second_opinion` and `from.*second_opinion` returns zero matches. The `agent_loop.py` main loop has no reference to second opinion at all.

This means:
- The eval report's finding that "Second opinion fires for ALL inbox outcomes including OK" is **incorrect** -- it fires for nothing because it is never called.
- The `workspace/prompts/fragments/verifier.md` prompt (1,873 bytes) is loaded by `second_opinion.py` but never actually used.
- The optimization concern from `cycle-2026-04-03-03` about verifier LLM cost was analyzing phantom code.

**Impact**: No runtime cost (it is dead code). But the file creates false analysis -- multiple optimizer cycles have discussed its cost impact based on the assumption it was wired into the loop.

**Recommendation**: Either (a) delete `second_opinion.py` and `workspace/prompts/fragments/verifier.md` to remove confusion, or (b) wire it into `agent_loop.py` at the completion gate if the second-opinion behavior is actually desired. Do NOT leave dead code that misleads future optimizer passes.

**Confidence**: HIGH (verified via grep -- zero imports)

## Finding 2: `pre_completion_gate()` is DEAD CODE -- defined in verify.py but never called (HIGH)

**Analysis**: `verify.py` defines `pre_completion_gate()` at line 110, which implements the inbox checks the eval report flagged ("pre_completion_gate inbox checks have no attempt cap -> can exhaust budget"). However, `agent_loop.py` does NOT import or call `pre_completion_gate`. The import list at line 13-20 of `agent_loop.py` imports `BUDGET_WARNING`, `StagnationDetector`, `WriteTracker`, `action_gate_message`, `merge_grounding_refs`, `outcome_evidence_message` -- but NOT `pre_completion_gate`.

The agent loop implements its own inline pre-submit checks (unverified writes at line 109-113, outcome evidence challenge at lines 116-124), but these are a subset of what `pre_completion_gate()` provides. Specifically, the following gates defined in `pre_completion_gate()` are **never executed**:

1. Inbox "never read any file from inbox/" gate (line 119-125)
2. Inbox "read ALL listed inbox files" gate (lines 127-139)
3. Analysis/search "no reads before CLARIFICATION" gate (lines 140-148)
4. Communication "no contacts/ search before CLARIFICATION" gate (lines 149-154)
5. "OUTCOME_OK after only 1-2 steps" gate (lines 114-117)

**Impact**: The eval report's finding about "no attempt cap" on inbox checks is moot -- these checks never run. However, the inbox completeness gate (gate #2 above) would be genuinely useful: it forces the agent to read all inbox files before completing. The agent currently can complete after reading only a subset of inbox messages, which contributes to inbox task failures (t18, t23, t24).

**Recommendation**: Wire `pre_completion_gate()` into `agent_loop.py` at the completion path (before the outcome evidence challenge). Add an attempt counter (max 2 gate rejections per task) to prevent budget exhaustion. This is a HIGH-value fix for inbox tasks specifically.

**Confidence**: HIGH (verified via grep -- zero calls)

## Finding 3: `report_budget_exhaustion()` is DEAD CODE -- agent_loop.py has inline duplicate (MEDIUM)

**Analysis**: `verify.py` defines `report_budget_exhaustion()` (lines 236-266) which uses the intelligent `_fallback_outcome()` heuristic (considers cumulative threats, task type, read/write state). However, `agent_loop.py` does NOT call this function. Instead, it has an inline budget exhaustion handler at lines 187-199 that always sends `OUTCOME_ERR_INTERNAL` regardless of task state.

Compare the two approaches:

| Aspect | Inline (agent_loop.py:187-199) | verify.py report_budget_exhaustion() |
|--------|-------------------------------|--------------------------------------|
| Outcome | Always ERR_INTERNAL | Task-aware: OK/CLARIFICATION/SECURITY based on state |
| Threat awareness | None | cumulative_threats >= 5 -> DENIED_SECURITY |
| Write awareness | None | has_writes -> OUTCOME_OK (partial completion) |
| Read awareness | None | has_reads -> OUTCOME_NONE_CLARIFICATION |
| Grounding refs | None | All consulted paths |
| Steps summary | `["budget"]` | Dynamic summary of reads/writes |

The inline handler costs the agent 2+ points per run on tasks that exhaust budget. The `_fallback_outcome()` heuristic was implemented (and previously analyzed in cycle-2026-04-02-20) to fix exactly this -- but it was never wired in.

**Impact**: t01 (persistent ERR_INTERNAL, 0/2 on Nebius) and t24 (ERR_INTERNAL in R67) would benefit from the smarter fallback. If the agent read files but ran out of steps, CLARIFICATION is a better guess than ERR_INTERNAL. If it wrote files, OUTCOME_OK is often correct. This could recover 1-2 tasks per run.

**Recommendation**: Replace the inline budget exhaustion handler in `agent_loop.py` lines 187-199 with a call to `report_budget_exhaustion(domain, client, tracker, classification.task_type, cumulative_threats)`. This is a safe swap -- the function already handles all edge cases.

**Confidence**: HIGH

## Finding 4: `handler.destructive` gate silently fails -- ToolHandler has no `destructive` field (MEDIUM)

**Analysis**: `agent_loop.py` line 102 checks `handler and handler.destructive`:

```python
if ((handler and handler.destructive) or is_sensitive) and not domain.is_completion(cmd):
```

However, `ToolHandler` in `domain_protocol.py` is defined as:

```python
@dataclass(frozen=True)
class ToolHandler:
    model: type[BaseModel]
    execute: Callable[[Any, BaseModel], Any]
    format: Callable[[BaseModel, Any], str]
    risk_level: RiskLevel = "low"
```

There is **no `destructive` field** on `ToolHandler`. Accessing `handler.destructive` on a frozen dataclass raises `AttributeError`. Since `handler` is truthy (looked up from the registry), the short-circuit does not skip it -- `handler.destructive` is always evaluated.

**Consequence**: This line crashes with `AttributeError` for ANY tool call where the handler exists in the registry (write, read, delete, move, tree, list, search, etc.). The exception propagates up through `run_agent_loop()` and is silently swallowed by the broad `except Exception` in `main.py:248`, ending the task with no `report_completion`.

**Caveat**: `agent_loop.py` is marked as modified in the working tree (`M pac1-py/agent_loop.py`). This `handler.destructive` check may have been introduced in uncommitted changes after R66. If R66 ran with the committed version (without this line), the crash would not have been observed. **If the current working-tree version is run, it WILL crash on the first tool dispatch for every task.**

**Recommendation**: Replace `handler and handler.destructive` with `handler and handler.risk_level in ("medium", "high")` which uses the existing `risk_level` field. This is the simplest fix -- `risk_level` is already set to "medium" for write/mkdir and "high" for delete/move. Alternatively, add `destructive: bool = False` to `ToolHandler` but this requires updating all handler registrations.

**Confidence**: HIGH (verified: frozen dataclass without field raises `AttributeError`)

## Finding 5: `expand_search_result()` is defined but never called from agent_loop (LOW)

**Analysis**: `FilesystemDomain.expand_search_result()` (domain_fs.py lines 366-388) implements zero-result auto-retry by splitting multi-token search queries. The method is defined in the `DomainProtocol` interface and implemented by `FilesystemDomain`. However, `agent_loop.py` never calls `domain.expand_search_result()` after search dispatch.

**Impact**: The agent does not benefit from automatic search broadening. When a multi-token search returns 0 results, the agent must manually retry with simpler queries, consuming additional loop steps. For search-type tasks (budget: 15 steps), this wastes 1-3 steps per failed search.

**Recommendation**: Wire `expand_search_result()` into agent_loop.py after the dispatch+format section, before appending to messages. LOW priority -- the agent can self-correct by trying different search terms.

**Confidence**: MEDIUM (method exists, protocol requires it, but never invoked)
