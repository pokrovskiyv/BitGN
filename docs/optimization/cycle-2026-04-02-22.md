## Finding 1: crud budget increase from 10->14 is generous -- 14+3=17 may be over-budgeted

**Analysis**: The previous cycle raised crud from 10 to 14 to fix t02/t30 budget exhaustion. The historian report recommended 10->12. The actual jump to 14 gives 17 effective steps for a simple CRUD task. The minimum crud path is: plan(1) + read-target(1) + write(1) + gate-VERIFY(1) + read-after-write(1) + report(1) + evidence-challenge(1) = 7 steps. Even with sensitive-path double-gating (HIGH risk blocks + confirm = 2 extra), criteria check (1 extra), and folder-format-hint overhead, 15 steps (base=12) would suffice. Two extra steps (14 vs 12) add buffer but are unlikely to convert any additional tasks.

**Recommendation**: Not urgent. 14 is safe and does not cause harm -- unused steps are simply not consumed (no cost per unused step). If the 14-step budget proves too loose and encourages stagnation on crud tasks in future runs, consider pulling back to 12. For now, leave it.

**Confidence**: MEDIUM (observation, no action needed)

## Finding 2: _COMPLETION_RESERVE of 3 is appropriately sized but can cascade to 5

**Analysis**: The completion gate cascade in `agent_loop.py` lines 135-188 can trigger up to 5 sequential gates on a single completion attempt:

1. `pre_completion_gate()` -- early OK rejection, inbox-must-read, analysis-must-read, comms-must-search (1 step)
2. Unverified writes HOLD -- fires when `completion_gate_count <= 2` (up to 2 steps across two attempts)
3. `check_criteria()` -- fires once (`criteria_challenged` flag) (1 step)
4. Communication CLARIFICATION redirect -- fires once (`outcome_challenged` flag) (1 step)
5. Outcome evidence challenge -- fires once (`outcome_challenged` flag) (1 step)

In the worst case (inbox_processing on first attempt), the agent could burn: pre_completion(1) + unverified-hold(1) + criteria(1) + evidence(1) = 4 gates on a single attempt. However, the flags `outcome_challenged` and `criteria_challenged` are one-shot, and `completion_gate_count <= 2` caps the unverified-writes hold. In practice, a single completion attempt triggers at most 2-3 gates because the flags overlap.

The _COMPLETION_RESERVE of 3 covers the typical case. The risk is: if the agent first attempts completion at step `max_steps - 4` and gets gated 3 times, it reaches the BUDGET_WARNING at `max_steps - 2`, attempts again, gets 1 more gate, and exhausts the budget. This 4-gate scenario is theoretically possible but rare.

**Recommendation**: No change. The reserve of 3 is a reasonable tradeoff. Raising it to 4 would reduce the "working" budget for every task type, which is a worse tradeoff than the rare 4-gate cascade.

**Confidence**: HIGH (no action needed)

## Finding 3: BUDGET_WARNING at max_steps-2 is correctly positioned

**Analysis**: The warning fires at `i == strategy.max_steps - 2` (line 75 of agent_loop.py), which means there are exactly 2 iterations remaining (the current one where the warning is injected, and one more). The message says "Only 2 steps remain. You MUST report_completion NOW." This gives the agent 2 LLM calls to submit and potentially retry if the first submission is gated.

Position analysis:
- At `max_steps - 2`: warning injected as user message, then LLM sees it and (hopefully) submits. If the submission is gated by evidence challenge (`outcome_challenged` = one-shot), the agent has exactly 1 more iteration to resubmit. This works.
- If moved to `max_steps - 3`: agent has more time, but it also delays the urgency signal when the agent is productively working.
- If moved to `max_steps - 1`: no room for a gated retry -- any gate triggers budget exhaustion.

**Recommendation**: No change. Position is optimal.

**Confidence**: HIGH

## Finding 4: folder_format_hint() makes a hidden RPC call inside the gate path

**Analysis**: In `agent_loop.py` line 125, when a write gate fires, `folder_format_hint()` is called. This function (in `hints.py` lines 12-15) executes a `Req_List` RPC to the VM to inspect the folder contents. This RPC is invisible to the step counter -- it does not consume a loop iteration. However, it adds latency to every gated write. More importantly, the hint content is appended to the gate message that the LLM sees, which means the LLM gets free information (folder format, README existence, inbox stem) without spending a step.

This is actually a net positive optimization -- it front-loads information that the agent would otherwise need 1-2 steps to discover (list folder + read README). The LLM API cost is negligible (the hint is short text appended to the gate message).

**Recommendation**: No change. This is a good implicit optimization. Consider extending this pattern to other tools if similar "free context" can be injected.

**Confidence**: HIGH (observation only)

**Recommendation**: These regressions are outside the optimizer's scope (they need prompt tuning or model improvement, not budget/loop changes). Flag for the Architect.

## Finding 6: HIGH-risk gate double-step cost could be reduced with dir-level auth caching

**Analysis**: When a HIGH-risk tool call fires (agent_loop.py lines 116-132), the loop injects a VERIFY message and calls `continue`, consuming the iteration without executing the tool. The agent must re-issue the same command on the next iteration to confirm. This costs 2 iterations per HIGH-risk action.

However, there is already a `high_risk_confirmed_dirs` set (line 72) that caches dir-level authorization. Once a tool+dir pair is confirmed, subsequent HIGH-risk calls to the same directory are auto-confirmed (line 116-117). This means the double-step cost only applies once per directory per tool type.

For crud_delete tasks (27 effective steps), a single delete confirmation costs 2 of 27 steps (7%). For crud tasks doing a sensitive-path write, it costs 2 of 17 steps (12%). The dir-level caching mitigates repeated operations.

**Recommendation**: No change. The existing dir-level auth cache already addresses the multi-file case.

**Confidence**: HIGH

## Bottom Line

The step budget system is in a healthy state after the crud 10->14 increase. No task types are detectably over-budgeted to the point of causing stagnation, and no task types are under-budgeted for budget-exhaustion failures in the latest run. The 5 regressions in run-2026-04-02-21 are all outcome-selection errors (wrong outcome code chosen by the LLM), not resource exhaustion. The completion gate cascade, BUDGET_WARNING position, and _COMPLETION_RESERVE are all well-calibrated.

The primary optimization opportunity is NOT in the step budget system -- it is in the security detection path (t09, t25, t27, t28 are persistent 0% win-rate tasks expecting DENIED_SECURITY) and outcome-selection prompt quality (volatile tasks flipping between runs). These are Architect-domain issues.
