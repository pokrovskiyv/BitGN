## Finding 2: second_opinion makes a full LLM call that doubles cost for gated completions

**Analysis**: `second_opinion.py` spawns an extra `call_llm()` for every completion attempt on inbox_processing, DENIED_SECURITY, or CLARIFICATION outcomes. This is an invisible cost -- it does not consume a loop step, but it does consume API tokens and adds latency.

On the free-tier OpenRouter backend this was negligible ($0.00 per run). On Nebius, each second-opinion call processes the full verifier prompt + task text + recent evidence (potentially 4 tool outputs). With Qwen3-235B-Thinking at ~$0.002/1K input tokens, a typical 4K-token verifier call costs ~$0.008. If the agent attempts completion 2-3 times per task (common with gate cascades), that is $0.016-$0.024 per task in verifier overhead.

For 31 tasks, the verifier could add ~$0.50-$0.75 to total run cost -- modest but not negligible on a per-cycle basis.

More importantly, the verifier adds 3-8 seconds of latency per completion attempt. For tasks that get gated 2-3 times, this adds 10-24 seconds of wall-clock time.

**Recommendation**: No code change. The verifier provides value (prevents false security denials). Monitor actual Nebius costs after the backend switch; if verifier overhead exceeds 15% of total run cost, consider throttling it to fire only once per task (currently fires once via `second_opinion_used` flag -- this is already correct).

**Confidence**: MEDIUM

## Finding 3: boot_messages() makes 3 RPC calls per task -- this is correctly outside the loop

**Analysis**: `FilesystemDomain.boot_messages()` issues tree(level=2), read(AGENTS.md), and context() before the task loop begins. These 3 calls are NOT counted against the step budget (they execute before `range(strategy.max_steps)`). This is the correct design.

However, each boot sequence re-sends the full tree + AGENTS.md + context as 3 separate user messages at the start of the conversation. As the conversation grows (later steps), these 3 boot messages are replayed on every LLM call as part of the full message history. On Nebius (no prompt caching), this means:
- Boot messages: ~3K-5K tokens
- Replayed on every step: 3K-5K tokens x max_steps

For a 28-step inbox_processing task, boot messages contribute ~84K-140K tokens of repeated input. On Nebius at ~$0.002/1K input tokens, that is $0.17-$0.28 per inbox task just for boot message replay.

On the Anthropic backend, this is mitigated by `cache_control: ephemeral` on the system prompt (but boot messages are user messages, not system messages -- so they are NOT cached).

**Recommendation**: For Nebius, consider consolidating the 3 boot messages into a single user message to reduce message overhead. This does not save tokens (same content) but reduces OpenAI SDK overhead per message. The real optimization would be to move boot content into the system prompt (where Anthropic can cache it), but that requires restructuring and is not urgent.

**Confidence**: LOW (observation only, no action this cycle)

## Finding 4: expand_search_result() auto-retries with per-token searches -- hidden cost on Nebius

**Analysis**: `FilesystemDomain.expand_search_result()` (domain_fs.py lines 367-388) fires when a search returns 0 results AND the query has 2+ tokens. It splits the query and issues N individual search RPCs (one per token). This is free in terms of step budget (does not consume a loop iteration) but adds N RPC calls to the VM.

On the free-tier OpenRouter, this was invisible. On Nebius, the additional RPC latency (100-200ms per search call) adds up for multi-token queries. If the agent issues 3-4 search queries per task and each triggers an auto-retry, that is 6-16 extra RPC calls per task.

This is a net positive feature (it helps the agent find information it would otherwise miss), but worth monitoring on Nebius for latency impact.

**Recommendation**: No change. Monitor after backend switch.

**Confidence**: LOW
