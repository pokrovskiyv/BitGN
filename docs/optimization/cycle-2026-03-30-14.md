## Waste Analysis

### 1. `plan_remaining_steps_brief` Empty-List Parse Errors — CRITICAL

Every task that completes cleanly hits this: the LLM emits `plan_remaining_steps_brief: []` when it knows the task is done and then simultaneously sets `task_completed: true`. Pydantic rejects it with `List should have at least 1 item after validation, not 0`. This forces a retry loop of 10–55 seconds per occurrence.

Observed parse error counts per task in Run 1 (log lines):
- t02: 1 parse error (4 validation errors — missing required fields on first direct completion attempt)
- t03: 2 parse errors (1 × empty JSON on step_6 — 55,599 ms; 1 × empty list on step_8 — 29,316 ms)
- t09: 1 parse error (step_1 — 29,183 ms)
- t10: 1 parse error (step_4 — empty list)
- t11: 2 parse errors (steps 6–7 — 21,165 ms combined)
- t13: 2 parse errors (steps 8–9 — 35,857 ms combined, hit attempt 2/3)
- t14: 2 parse errors (steps 8–9 — combined latency, hit attempt 2/3)
- t17: 2 parse errors (steps 7–8 — 21,915 ms)
- t19: 1 parse error (step_13 — 25,854 ms)
- t24: 1 parse error (step_5 — 33,102 ms)

**Total: ~18 parse error events across 10 tasks.** At an average of ~20 s per retry this wastes approximately **360 seconds (~6 minutes) per 25-task run** just on retry overhead. This is pure mechanical waste with zero benefit — the LLM's intent is correct, only the schema gate rejects it.

The root cause is in `agent.py` line 125:
```python
plan_remaining_steps_brief: Annotated[list[str], MinLen(1), MaxLen(5)]
```
`MinLen(1)` is the culprit. When `task_completed=True`, an empty list is semantically correct.

### 2. AGENTS.md Full Re-Read on Every Task — MEDIUM

Every task starts with the AUTO-init sequence: `tree -L 2 /` then `cat AGENTS.md`. Confirmed in log: identical AGENTS.md content is read verbatim at lines 43–68 (t01), 173–198 (t02), 275–300 (t03), 413–437 (t04), and so on for all 25 tasks. Each read takes 10–14 seconds. The file content never changes within a run because the VM is reset between tasks (not between reads).

**Cost: ~25 reads × ~12 s average = ~300 seconds per 25-task run.**

This is structural — the AUTO-init is intentional for grounding, but the AGENTS.md content could be injected into the system prompt once per session type rather than fetched via RPC each time.

### 3. `tree -L 2 /` Repeated Identically on Every Task — MEDIUM

Same as AGENTS.md: the full directory tree is fetched at the start of every task. For tasks within the same environment type (e.g., all knowledge-repo tasks t01–t09), the tree output is byte-for-byte identical. The tree call takes 8–14 seconds per task.

**Cost: ~25 reads × ~11 s average = ~275 seconds per 25-task run.**

Combined with waste item 2, AUTO-init overhead accounts for roughly **575 seconds (~9.5 minutes) of the run time per 25-task run** that contribute nothing beyond what a single read at session start would provide.

### 4. Stagnation Events — NONE CONFIRMED

No stagnation events detected in Run 1 log (no repeated tool+args pairs across consecutive steps). The stagnation detector's threshold of 2 repetitions appears sufficient. This is a clean finding — no recommendation needed.

### 5. Over-Budgeted Multi-Step Tasks — LOW

Tasks classified as `multi_step` receive 25 steps. Actual usage:
- t07: 2 steps (correctly detected injection — 23 steps wasted budget)
- t08: 2 steps (clarification — 23 steps wasted budget)
- t20: 7 steps (cross-account mismatch — 18 steps wasted budget)
- t21: 4 steps (security over-rejection — 21 steps wasted budget)
- t25: 8 steps (correctly caught OTP — 17 steps wasted budget)

However, t18 used 15/25 steps, t19 used 13/25, t22 used 11/25, t23 used 11/25. The budget is clearly needed for the complex inbox-processing cases. Over-budgeting for quick multi_step tasks is not actionable as a separate class — the classifier would need a finer-grained distinction (e.g., `security_test` vs `inbox_process`).

### 6. Empty Name-Search Before Fallback — LOW

t16 ("What is the email of Barth Florian?") issued one search for `'Barth Florian'`, got zero results, and immediately reported `OUTCOME_NONE_CLARIFICATION`. A second search on the last-name token alone (`'Barth'` or `'Florian'`) would have found the contact. This is 1 wasted failure and 1 missed score point.

### 7. Hook Contamination — EXTERNAL CONFOUND

In Run 2 (the current cycle's benchmarked run), the Claude Code explanatory-mode SessionStart hook fires for `claude -p` subprocess calls and injects insight blocks into responses. This breaks JSON parsing at random steps. Affected tasks in Run 2: t11 (FAIL — missed outbox writes due to step_7 parse disruption), t25 (FAIL — security detection collapsed under combined timeout + hook pressure). This contamination is not an agent efficiency problem — it is an external environment reliability problem that makes parse error rates non-deterministic across runs.

The presence of `_strip_insight_blocks()` in `agent.py` (line 242) is a partial mitigation, but it was not sufficient to prevent the t11 regression in Run 2, suggesting the hook output sometimes wraps or precedes the JSON in a way that `_strip_insight_blocks()` does not fully handle.

## High-Confidence Recommendations

### 1. Fix `plan_remaining_steps_brief` to accept empty list on completion [HIGH]

**Action:** In `pac1-py/agent.py`, change the `NextStep` model's field validator for `plan_remaining_steps_brief` so that `MinLen(1)` only applies when `task_completed=False`. When `task_completed=True`, an empty list must be valid.

**Implementation path:** Use a `model_validator` (mode=`after`) or change the field type to `list[str]` with a conditional annotation. The simplest safe change is to make `MinLen` conditional:

```python
# Current (causes parse errors):
plan_remaining_steps_brief: Annotated[list[str], MinLen(1), MaxLen(5)]

# Recommended: allow empty when task is done
plan_remaining_steps_brief: Annotated[list[str], MaxLen(5)]
```

Then add a `@model_validator(mode='after')` that checks: if `task_completed=False`, the list must be non-empty.

**Expected impact:** Eliminate ~18 parse-error retry events per 25-task run. Saves ~360 seconds of pure retry overhead. No score impact — only eliminates mechanical failures on correct LLM output.

### 2. Raise subprocess timeout to 180s [HIGH]

**Action:** In `pac1-py/agent.py` line 235, change `timeout=120` to `timeout=180`.

**Evidence:** Run 2 (with 150s timeout) confirms LLM call latencies of 160–222s for CRM tasks (t12, t13, t14). The 150s timeout was reverted for being net-neutral, but the evaluator report explicitly states "the correct value to retry is higher." 180s provides 18s buffer above the observed 160s peak; 200s provides safety margin against the 222s observed outlier.

**Risk:** The previous 150s attempt was NEUTRAL (t07+t08 recovered, t11+t25 regressed). The t11/t25 regressions were caused by hook contamination and API load, NOT by the 180s change. If hook contamination is fixed first, 180s should yield a net improvement.

**Prerequisite:** Hook contamination fix (see Notes below) should be applied before re-attempting the timeout increase, to avoid confounding factors in the next benchmark run.

### 3. Add fallback name-token search to search prompt fragment [MEDIUM]

**Action:** Edit `pac1-py/workspace/prompts/fragments/search.md` to add:
"When a name search returns zero results, retry with each individual name token before escalating to OUTCOME_NONE_CLARIFICATION."

**Expected impact:** Recover t16 (1 score point per run). Evidence: t16 searched `'Barth Florian'`, got empty results, immediately clarified. The contact exists and would have been found with `'Barth'` alone.

## Notes

### Hook Contamination Profiling Impact

The hook contamination issue (user's global Claude Code explanatory-mode SessionStart hook injecting insight blocks into `claude -p` subprocess calls) makes Run 2 profiling unreliable for step-count and latency analysis. For this reason, this report profiles primarily from Run 1 (the 60% run), which did not exhibit the same contamination severity. The `_strip_insight_blocks()` function in `agent.py` is a partial mitigation but insufficient — it did not prevent t11's regression in Run 2.

The contamination means that any benchmark run while the hook is active will have non-deterministic parse error rates. Until the hook is disabled or scoped to exclude `claude -p` subprocess calls, parse error counts in profiling will be unreliable. The fix belongs in the user's `~/.claude/settings.json` (disabling or scoping the explanatory-mode hook), not in `agent.py`.

### Timeout Is Still a Structural Bottleneck

The 120s timeout (current, after revert) is confirmed insufficient for CRM tasks (t12/t13/t14) whose LLM call latency consistently exceeds 120s at current benchmark API load. Both runs show these tasks failing with "no answer provided" or "timed out after 150 seconds" (Run 2). The revert decision was correct per cycle rules (net-neutral result), but the underlying problem is unresolved. The next cycle should attempt 180s with hook contamination fixed, so the signal is clean.

### Previous Optimizer Reports Convergence

This report's recommendations are consistent with cycle-2026-03-30-13 (which also flagged `plan_remaining_steps_brief` as the highest priority and AGENTS.md re-reads as medium-priority waste). The cycle-13 report also flagged the timeout issue. The fact that these are re-appearing recommendations after the timeout revert indicates the core structural improvements (Pydantic fix + 180s timeout) have not yet been applied, and should be the first actions in the next cycle.
