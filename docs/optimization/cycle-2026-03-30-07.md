# Optimization Report: Cycle 2026-03-30-07

## Input

- Eval report: `docs/eval/run-2026-03-29-22.md` (60% score, 15/25 tasks)
- Log: `/tmp/cycle-run-2.log` (4359 lines, 25 tasks, 162 total steps)
- Agent code: `pac1-py/agent.py`, `pac1-py/classify.py`, `pac1-py/strategy.py`, `pac1-py/verify.py`

## Waste Analysis

### 1. Bare report_completion JSON Causes All Three Retry Exhaustion Failures
**Observed**: Tasks t10, t12, and t20 all failed identically: the LLM emitted a JSON object with `{"tool": "report_completion", ...}` at the top level rather than wrapping it inside a `NextStep` envelope (`{current_state, plan_remaining_steps_brief, task_completed, function}`). The pydantic validation error on attempt 1 reads "Field required: current_state, plan_remaining_steps_brief, task_completed, function". Attempt 2 gets the same 4-field error. Attempt 3 fixes 3 of the 4 but fails on `plan_remaining_steps_brief` being an empty list. All three attempts are then exhausted.

The retry correction message (`FORMAT CORRECTION: Your previous response was not valid JSON...`) does not explicitly instruct the model to wrap the action inside a `function` key of a `NextStep` object — it describes the fields of `NextStep` but leaves the nesting relationship ambiguous. The LLM interprets the correction as "emit the action directly" rather than "nest the action under `function`".

**Estimated waste**: 3 tasks × 3 retry attempts × ~15 s each = ~135 s wasted. More critically, 3 tasks score 0.00 (3 points lost) because no answer is ever submitted.
**Confidence**: HIGH — log confirms identical failure signature across t10, t12, t20. The validation error text is present verbatim in the log.

### 2. Stagnation on Delete-After-Delete Pattern (5 stagnation events, 4 tasks affected)
**Observed**: The stagnation detector fires 5 times across the run. In every case the pattern is identical: agent successfully deletes a file, then on the very next step attempts to delete the same path again (the path is already gone, so `NOT_FOUND` is returned). The stagnation nudge fires, the agent re-lists and continues. Affected tasks: t01 (2 events), t02 (1 event), t03 (1 event), t22 (1 event).

This is a specific sub-pattern: `Req_Delete` always returns `{}` on success (no confirmation content), so the LLM has no positive signal that the deletion occurred. On the next step it re-submits the same delete because it cannot distinguish "deleted" from "had an error and returned empty". The `WriteTracker` already catches reads, but delete success is not positively acknowledged in the tool output.

**Estimated waste**: Each stagnation event burns 1 extra step (the duplicate delete) plus 1 correction step (re-list), totaling ~2 wasted steps per event × 5 events = 10 steps wasted (~130 s). For t01 (crud_delete, 12-step budget), the 2 stagnation events consumed 4 steps — leaving only 8 for actual work. t01 ran all 12 steps and never called `report_completion`.
**Confidence**: HIGH — pattern is visible in every STAGNATION line in the log and directly maps to `Req_Delete` returning `{}`.

### 3. Sequential Single-File Reads in Search-by-Scan Tasks (t12: 10 steps, score 0)
**Observed**: Task t12 (find Alex Meyer's email) used all 10 steps attempting to locate a contact. The agent's strategy was: search once (no results), read README, then read contact files one at a time — reading only 1-2 files per step due to the single-path `Req_Read` model. Steps 3-10 each read one or two contact files (`cont_001` through `cont_010`). The search at step_1 returned nothing useful, so the agent fell back to brute-force sequential reads. With 10 files to check and only 8 remaining steps after search+README, the agent ran out of budget before completing the scan.

This represents over-reliance on search when the search index may not have the desired content, and no bulk-list-then-read strategy.
**Estimated waste**: 10 steps fully consumed with 0 points. The task is inherently solvable in ~5 steps: list contacts, batch-read 2-3 at a time, report. The search failure sent the agent into a step-intensive fallback.
**Confidence**: MEDIUM — the 10-step budget for search tasks is likely too tight when a search miss forces a full file scan. However, this also requires the agent to make smarter decisions about batch reads.

### 4. AGENTS.md Re-Read on Every Task (25 × fixed overhead)
**Observed**: The auto-init sequence (agent.py lines 375-384) unconditionally runs `tree / -L 2`, `read AGENTS.md`, and `context` before every task. The AGENTS.md content is appended to the message history as a `[FILE DATA]`-wrapped user message on every task, even though it is static across all 25 tasks. For crud tasks with a 10-step budget, 3 of those budget "message slots" are consumed before the agent loop starts — but because these precede the loop counter, they don't consume steps, they consume context window tokens. For every 25-step task, AGENTS.md content appears verbatim in steps 1-25 worth of history.

Based on log timing, the auto-init sequence costs ~35-45 ms total (fast Protobuf calls, not LLM calls) so latency is not the concern. The concern is context window growth: AGENTS.md and tree output together add ~2-4 KB to every LLM call's message history. By step 20 of a multi_step task, the first three messages in history are always stale grounding context that duplicates what was already internalized.
**Estimated waste**: Low immediate impact (no current failures from context overflow). Estimated 200-400 extra tokens per LLM call × 162 steps = ~32,000-65,000 extra tokens across the run. This is a latency cost only if context hits limits.
**Confidence**: LOW — no current failures attributable to this pattern. Relevant only as a future scaling ceiling.

### 5. Retry Correction Message Grows History Without Helping (6 retry events observed)
**Observed**: When a retry is triggered (attempt > 0), a correction message is appended to `retry_msgs` (agent.py lines 413-422), which is a copy of `messages` plus the correction. However, `retry_msgs` is a local variable — if the retry succeeds, `messages` is updated with the successful `job.model_dump_json()`, not the correction. This is correct behavior. But on failure across all 3 attempts, the exception propagates and the correction is silently discarded. There is no mechanism to learn from the correction across tasks.

More materially: the correction message uses the wrong framing. It says "respond with a JSON object containing exactly these fields" but describes `NextStep`'s fields, not the nested `function` key relationship. The LLM consistently fixes 3 of 4 missing fields (current_state, task_completed, plan_remaining_steps_brief) but still fails on wrapping the action into `function`.
**Estimated waste**: 6 first-attempt failures × 1 wasted LLM call each = 6 extra LLM invocations (~90 s). 2 full retry-exhaustion events → 0 answers submitted for t10 and t12.
**Confidence**: HIGH — the specific pydantic error "List should have at least 1 item after validation, not 0" on attempt 3 shows the correction partially worked (added fields) but still failed on `plan_remaining_steps_brief` being empty rather than the nesting issue.

### 6. t20 Regression: "process" Reclassification Changed System Prompt (1 point lost)
**Observed**: t20's task text is "process the inbox". In cycle 1 it was classified as `crud` (10 steps, `_CRUD_ADDON` prompt) and scored 1.00. In cycle 2 the `process` keyword was added to `_MULTI_STEP_SIGNALS`, so t20 is now classified as `multi_step` (25 steps, `_MULTI_STEP_ADDON` prompt). The task failed with retry exhaustion at step 12 — the same bare-JSON failure signature as t10 and t12.

The reclassification itself is not the root cause of the failure — retry exhaustion is. However, the reclassification changed which system prompt the model received, and "process the inbox" with 25 steps and the multi-step addon appears to have prompted a longer reasoning chain before the final answer, which reached the retry-exhaustion failure mode. Under the old crud classification with 10 steps, the agent completed faster and happened to not trigger the bare-JSON bug.
**Estimated waste**: 1 regression point. The t20 failure is a secondary effect of the bare-JSON retry bug, not of the reclassification itself.
**Confidence**: MEDIUM — the failure signature is identical to t10/t12, strongly suggesting the retry bug is the proximate cause. But can only be confirmed by re-running t20 with the bug fixed.

## Top Tuning Recommendation

**Change**: Rewrite the retry correction message in `agent.py` (lines 416-422) to explicitly show the required nesting structure. The current message describes the top-level fields of `NextStep` but does not illustrate that the action must go inside a `"function"` key. The fix is to add a concrete minimal example to the correction:

```
"FORMAT CORRECTION: You must respond with EXACTLY this JSON structure:
{
  \"current_state\": \"<one sentence>\",
  \"plan_remaining_steps_brief\": [\"<next step>\"],
  \"task_completed\": false,
  \"function\": { <your action object with tool field here> }
}
The action object (report_completion, read, write, etc.) goes INSIDE the \"function\" key.
Do NOT emit the action at the top level. No markdown. Only raw JSON."
```

This targets the exact failure mode seen in t10, t12, and t20: the LLM emits the action at the top level instead of nesting it under `function`.

**Expected saving**: 3 tasks currently failing due to this bug (t10, t12, t20). Fixing it recovers at least 2 confirmed retry-exhaustion failures (t10, t12) and likely the t20 regression. Expected score improvement: +2 to +3 points (60% → 68-72%).
**Confidence**: HIGH — the failure signature is identical in all three tasks, directly traceable to the retry correction message not specifying the nesting structure.
**Risk**: LOW — the change is purely to the correction message string in agent.py. It does not affect the happy path (no retry triggered), does not change classification or strategy, and is trivially reversible.

## Secondary Recommendation

**Change**: Emit a non-empty delete confirmation in `_format_result` for `Req_Delete` success. Currently `dispatch` returns `{}` for deletes, and `_format_result` falls through to `json.dumps({}) = "{}"`. Returning a brief confirmation string (e.g., `"deleted: /path/to/file"`) would give the LLM a positive signal that the operation succeeded, preventing the re-delete stagnation pattern.

**Expected saving**: Eliminates the 5 observed stagnation events. For t01 (crud_delete, 12-step budget), saving 4 wasted steps from 2 stagnation cycles likely unlocks the ability to call `report_completion` within budget. Potential +1 point.
**Confidence**: MEDIUM — stagnation pattern is confirmed in logs. Whether t01 would succeed within budget is uncertain, but eliminating the wasted steps increases the probability.
**Risk**: LOW — adding confirmation text to delete output does not affect any other tool path.
