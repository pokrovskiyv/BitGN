## Waste Patterns

### 1. `record_list()` is never called -- inbox completeness gate is dead code (CARRIED FORWARD, 3rd cycle)

This has been flagged in cycle-09, cycle-12, and cycle-15. The inbox gate at `verify.py:126-137` checks `tracker._lists` to ensure all inbox files were read before completion, but `agent_loop.py` never calls `tracker.record_list()` after a `list` tool dispatch. The gate is dead code.

**Impact:** The strong inbox completeness check ("read ALL listed inbox files") never fires. Only the weak check ("never read any inbox/ file") fires. This affects t24 (DEAD, 0% -- missing outbox writes, likely from incomplete inbox processing) and potentially t23 (FRAGILE, 17% -- unexpected file writes from partial inbox processing).

**Why it keeps getting deferred:** Each cycle has had a higher-priority fix. But this is now the oldest open item and has the highest expected value of any single code change.

**Fix location:** `agent_loop.py`, after the dispatch block (line ~172), when `tool_name == "list"`. Extract entry names from the result and call `tracker.record_list(cmd.path, [e.name for e in result.entries])`. The result object has `.entries` with `.name` attributes (confirmed in `domain_fs.py:_fmt_list`). However, this requires access to the raw protobuf result, which is currently only used for formatting. The fix needs to happen between dispatch and formatting, or the result needs to be stored.

### 2. `expand_search_result()` is never called -- zero-result search retry is dead code

`FilesystemDomain.expand_search_result()` in `domain_fs.py:366-388` implements automatic per-token retry when a multi-word search returns 0 results. This is defined in the `DomainProtocol` interface but never invoked from `agent_loop.py`. On a free-tier model that sometimes constructs poor search queries, this could save 1-3 steps per failed search.

**Impact:** When the model searches for "project status update" and gets 0 results, it wastes a step. The auto-retry would split into 3 sub-searches ("project", "status", "update") and return merged results. This is most relevant for search (budget 15) and analysis (budget 20) tasks.

### 3. Duplicate tracking code in agent_loop.py

`agent_loop.py` lines 213-228 manually dispatch tracking calls (`tracker.record_write`, `tracker.record_read`, `tracker.record_delete`, `tracker.record_write` for move). Meanwhile, `WriteTracker.record_action()` (verify.py:48-58) and `StagnationDetector.record_action()` (verify.py:74-80) encapsulate this same logic. The loop should call `tracker.record_action(tool_name, cmd)` and `stagnation.record_action(tool_name, cmd)` instead. This is not a performance issue but makes it harder to add new tracking (like `record_list`) because changes need to happen in two places.

### 4. HIGH-risk gate `continue` burns a step on the model side

When `effective_risk == "high"` and the path hasn't been gated before (line 130-132), the loop does `continue` -- skipping dispatch and consuming a loop iteration. The model made an LLM call that produced a plan, but the action was blocked. The gate message is appended, and the model retries on the next iteration. For `delete` and `move` operations (both HIGH risk), this costs 1 step + 1 LLM call per unique path.

On tasks with multiple deletes (t01: "delete 3 files in 02_distill/"), this costs 3 extra steps (one per unique path). With crud_delete budget of 12, that leaves 9 steps for actual work, minus other gate overhead. This is the tightest scenario.

**Observation:** t01 is FRAGILE at 17% with failure mode "incomplete deletes -- misses 3 files in 02_distill/". The HIGH-risk gate burning 3 steps on a 12-step budget is a plausible contributing factor. The model needs to: tree(1) + read AGENTS.md(boot) + list dir(1) + read files(3) + delete files(3, each gated=6 steps) + read-after-write verification(3) + completion(1) = 18 steps minimum for a 3-file delete. Budget is 12. Even without verification, it's 15. **The budget is structurally insufficient for multi-file delete with HIGH-risk gating.**

## Recommendations

### 1. Wire `record_list()` in agent_loop.py (HIGH confidence, HIGH impact)

**What:** After dispatching a `list` tool call, extract entry names from the result and call `tracker.record_list()`.

**Why:** Enables the inbox completeness gate (verify.py:126-137) which has been dead code for 3 cycles. This is the strongest guard against incomplete inbox processing -- a pattern seen in t24 (DEAD) and t23 (FRAGILE).

**Risk:** Low. The gate already exists and is tested. The only change is feeding it data. Worst case: gate fires on a non-inbox task (no harm, just 1 extra step).

**Estimated impact:** +0.5-1.0 pts on mean (t24 recovery worth 1.0, partial t23 help).

**Implementation note:** Requires access to the raw dispatch result before formatting. The loop currently only stores the formatted string. Suggest capturing the result object: `result = domain.dispatch(client, cmd)` is already on line 169. Add `if tool_name == "list" and hasattr(result, "entries"): tracker.record_list(cmd_path, [e.name for e in result.entries])` after line 173.

### 2. Increase crud_delete budget from 12 to 16 (HIGH confidence, MEDIUM impact)

**What:** Change `_STRATEGY_TABLE["crud_delete"]` from `(12, "hardened", True)` to `(16, "hardened", True)`.

**Why:** The step budget analysis in Waste Pattern 4 shows that multi-file delete tasks with HIGH-risk gating are structurally infeasible within 12 steps. A 3-file delete requires ~15-18 steps with gating + verification. t01 (FRAGILE, 17%) fails specifically with "incomplete deletes" -- it runs out of budget before finishing all deletions.

**Risk:** MEDIUM. Previous cycle (cycle-09) established DO_NOT_REPEAT for "crud 10->14 increase" but that was for regular crud, not crud_delete. crud_delete is a distinct key in the strategy table with different failure modes. The increase from 12 to 16 is conservative and specifically targeted at multi-file delete scenarios where HIGH-risk gating consumes extra steps.

**Note on DO_NOT_REPEAT:** The crud 10->14 increase was harmful because it added unnecessary steps to simple single-file CRUD tasks, causing the model to ramble. crud_delete tasks are structurally different -- they have a clear minimum step count driven by the number of files to delete * 2 (gate + delete) + verification. 16 steps accommodates up to 4 file deletes with gating.

**Estimated impact:** t01 moves from FRAGILE (17%) toward UNSTABLE (50%), +0.3 pts on mean.

### 3. Wire `expand_search_result()` in agent_loop.py (MEDIUM confidence, LOW impact)

**What:** After search dispatch returns 0 results, call `domain.expand_search_result(client, cmd, result, txt)` to auto-retry per token.

**Why:** Saves 1-3 wasted steps on failed multi-word searches. Most relevant for search and analysis tasks on the free-tier model which constructs imprecise queries.

**Risk:** Low. The method is already implemented and tested. Extra RPC calls are cheap (in-VM).

**Estimated impact:** +0.1-0.2 pts on mean.

### 4. Consolidate tracking into record_action() calls (LOW confidence, maintenance)

**What:** Replace manual tracking dispatch in agent_loop.py (lines 213-228) with calls to `tracker.record_action(tool_name, cmd)` and `stagnation.record_action(tool_name, cmd)`. Add `record_list` handling to `record_action`.

**Why:** Reduces code duplication and makes it easier to add new tracking (like the `record_list` fix in item 1). Not a performance improvement but reduces the surface area for bugs.

**Risk:** Very low. Pure refactor.
