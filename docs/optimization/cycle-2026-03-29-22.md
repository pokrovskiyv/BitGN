## Waste Patterns Identified

### 1. Broad Exception Retry (affects all 25 tasks, wastes 0-360s per infrastructure failure)

The retry loop in `agent.py` (lines 410-417) catches `Exception` rather than `(pydantic.ValidationError, ValueError)`. When the failure is an infrastructure error (binary not found, timeout, network issue), all 3 retry attempts are wasted -- the error cannot self-heal. The Red Team report (Attack 5) independently flagged this as "PARTIAL" inefficiency.

**Observed impact**: 13 retry events across 10 tasks. Without logs distinguishing validation errors from infrastructure errors, some fraction of these may have been non-validation retries that burned time with zero recovery potential.

### 2. Misclassified "process" Tasks Exhaust Step Budget (affects t19, t22, t23 -- 3.0 points lost)

The Analyst report identifies that tasks containing "process the inbox" are classified as `crud` (10 steps) instead of `multi_step` (25 steps). All three run exactly 10 steps without reaching `report_completion` -- every step beyond what was needed to explore the environment is wasted because the agent never had enough budget to finish.

**Observed impact**: 30 steps consumed across 3 tasks with zero output. If classified as `multi_step` at 25 steps each, the additional budget costs nothing on success (unused steps are free) but removes the hard cap that causes guaranteed failure.

### 3. Mandatory 3-Step Auto-Init on Every Task (affects all 25 tasks)

The auto-init sequence in `agent.py` (lines 375-384) always runs `tree / -L 2`, `read AGENTS.md`, and `context` before the agent loop begins. These consume 3 message slots in the conversation history. For `crud` tasks with a 10-step budget, this means the LLM receives 3 grounding messages before its first reasoning step -- effectively using ~30% of context on orientation for simple tasks.

**Observed impact**: Not directly causing failures, but adds fixed overhead. For the 8 tasks classified as `security_test` (8-step budget), auto-init consumes 37.5% of message slots before the agent starts reasoning.

### 4. Full History Replay Per LLM Call (affects all tasks, scales with step count)

The agent uses stateless conversation replay (`agent.py` line 404 loop): the full `messages` list is sent on every `call_llm()` invocation. For tasks reaching 20-25 steps, the prompt includes all previous tool outputs verbatim. With verbose tree/read outputs from early steps, later calls carry significant dead context weight.

**Observed impact**: No observed failures from this pattern yet, but it is the primary scaling bottleneck. Tasks at 25 steps with large file reads will approach the context window limit as task complexity grows.

### 5. Retry-Exhausted Tasks Produce No Partial Credit (affects t03, t07, t13)

When all 3 retries fail on a step, the exception propagates to `main.py` and the task gets 0 score with no `report_completion`. The agent may have completed useful work in prior steps but receives no credit because it never submitted an answer.

**Observed impact**: 3 tasks scored 0.00 after exhausting retries. If a fallback `report_completion` were emitted before the exception, partial credit might be recoverable.

## Recommendations

### 1. Narrow Retry Catch to Validation Errors Only -- Confidence: HIGH

Change `agent.py` line 411 from `except Exception` to `except (pydantic.ValidationError, ValueError)`. Infrastructure errors should fail fast. This eliminates wasted retry attempts on non-recoverable failures and reduces worst-case per-step latency from 360s to 120s.

**Expected impact**: Faster failure on infrastructure errors. Zero score risk -- validation retries are unaffected.

### 2. Add "process" to Write and Multi-Step Signals -- Confidence: HIGH

Already recommended by the Analyst. Add `process` to `_WRITE_SIGNALS` and `_MULTI_STEP_SIGNALS` in `classify.py`. This reclassifies "process *" tasks from `crud` (10 steps) to `multi_step` (25 steps).

**Expected impact**: t19, t22, t23 get sufficient budget. Potential +3.0 points. No downside -- unused steps cost nothing.

### 3. Add Graceful Fallback on Retry Exhaustion -- Confidence: MEDIUM

When all 3 retries fail, emit a `report_completion` with `OUTCOME_ERR_INTERNAL` and a summary of completed steps before raising the exception. This lets the evaluator score partial work.

**Expected impact**: Potential partial credit recovery on t03, t07, t13. Exact point gain depends on whether prior steps produced scorable output.

### 4. Truncate Error Log Messages to 200 Characters -- Confidence: LOW

Per Red Team Attack 4, error messages from failed validation can leak raw LLM responses to logs. Truncating to 200 characters reduces information leakage without affecting debugging value.

**Expected impact**: Reduced log noise. Minor security hygiene improvement. Zero score impact.

### 5. Consider Context Summarization for Long Tasks -- Confidence: LOW

For tasks exceeding 15 steps, early tool outputs (tree, list results) become stale context. A future optimization could summarize or drop earlier message content after it has been superseded by more recent reads. This is a structural change and should be deferred until tasks actually hit context limits.

**Expected impact**: Deferred. No current failures attributable to context overflow, but this is the ceiling for scaling to harder benchmarks.

## Summary

The two highest-impact changes are narrowing the retry catch (eliminates wasted retries on infrastructure errors) and adding "process" to the classifier signals (unblocks 3 tasks worth 3.0 points). Both are low-risk, data-backed, and should be implemented in the next Architect cycle. The remaining recommendations address edge cases and future scaling.
