## Waste Analysis

### Finding 1: Inbox completion gates stack up to 4+ steps per attempt

**Observed**: For `inbox_processing` tasks (max_steps=28), a single completion attempt can burn up to 4 steps before the RPC fires:

1. `pre_completion_gate` -- inbox-specific "read all inbox files" check (fires every attempt, no dedup flag)
2. Unverified writes HOLD (capped at `completion_gate_count <= 2`)
3. `outcome_evidence_message` -- inbox-specific DENIED_SECURITY or CLARIFICATION challenge (fires once via `outcome_challenged`)
4. `needs_second_opinion` -- always True for inbox_processing (fires once via `second_opinion_used`, costs 1 extra LLM call)

If the agent attempts completion twice (common: first rejected by evidence challenge, second passes), that is 5-6 steps consumed by gates alone out of a 28-step budget. The new inbox-specific DENIED_SECURITY evidence challenge from the Architect's latest commit adds one more potential gate step.

**Impact**: t23 and t24 fail with wrong outcomes. If these tasks are reaching completion with the wrong outcome and the gates are not correcting them (challenge fires but agent doubles down), additional gate steps are pure waste. If gates are correcting outcomes (t25, t28 now pass), the cost is justified.

**Confidence**: MEDIUM -- without per-task step logs, the exact gate-step count per failing task is inferred from code structure.

---

### Finding 2: `pre_completion_gate` for inbox has no attempt cap -- can loop indefinitely

**Observed**: The inbox-specific gate in `pre_completion_gate` (verify.py lines 119-139) checks two conditions: (a) did agent read any inbox/ file, and (b) did agent read ALL listed inbox files. These gates have no `completion_gate_count` cap -- they fire on every completion attempt. If the agent keeps trying `report_completion` without reading the remaining files, each attempt burns 1 step + 1 LLM call with zero progress.

Compare with the unverified-writes HOLD (line 146 in agent_loop.py) which has `completion_gate_count <= 2` -- after 2 attempts it stops gating. The inbox read-all-files gate has no such limit.

**Impact**: In worst case, an agent stuck in a loop of "try to complete -> gated -> try again" can exhaust the remaining budget. This is a stagnation pattern that the StagnationDetector cannot catch (it tracks tool calls, not completion attempts).

**Confidence**: HIGH

---

### Finding 3: `folder_format_hint` fires a hidden VM `list` call inside the write gate

**Observed**: In agent_loop.py line 127, when a write is gated (MEDIUM or HIGH risk), `folder_format_hint(client, domain, cmd_path, tracker)` fires. This function (hints.py line 14) calls `domain.dispatch(client, Req_List(...))` -- a real VM RPC that is invisible to step counting, stagnation detection, and the WriteTracker. Confirmed: the previous cycle flagged this as a suspicion; it is now verified as a real `list` RPC.

**Impact**: Low direct waste (the list call is fast), but the hint text ("read README.MD for format") appended to the gate message can cause the agent to spend 2 extra steps reading a README and re-attempting the write. For simple writes where format is already known, this is unnecessary indirection.

**Confidence**: LOW (the hint is often useful; wasteful only when agent already knows the format)

---

### Finding 4: Second opinion LLM call fires for every inbox task regardless of outcome

**Observed**: `needs_second_opinion()` returns True for all inbox_processing tasks unconditionally (second_opinion.py line 32). This means even OUTCOME_OK completions for inbox tasks pay an extra LLM call (~1-2s latency + token cost). For the 6 inbox tasks in the benchmark, that is 6 extra LLM calls minimum.

**Impact**: At ~$0.002/call on Nebius, the direct cost is negligible. The real cost is (a) the extra step consumed if the verifier disagrees with a correct answer, and (b) latency. t18 over-executes (OK instead of CLARIFICATION/SECURITY) -- if the second opinion AGREED with the wrong OK, it wasted a step confirming a bad answer without improving it.

**Confidence**: MEDIUM

---

### Finding 5: t01 (0% across 4 runs) and t30 (computation: expected 820, got 750) are structural

**Observed**: t01 has never passed in any run on any backend. t30 consistently produces the wrong number. These are not step-budget or gating issues -- they are either classification misroutes or model capability gaps.

**Impact**: 2 tasks (6.5pp) that no pipeline optimization will recover. t01 needs root cause (run in isolation with verbose logging). t30 needs investigation of whether the model can do the required arithmetic.

**Confidence**: HIGH

---

### Finding 6: Average 9.0 API calls/task confirms most tasks finish well within budget

**Observed**: 279 API calls / 31 tasks = 9.0 avg. Most task types have budgets of 15-28 steps. This means passing tasks typically use 6-12 steps. The surplus budget is consumed only by failing tasks that exhaust their allocation or by gate sequences.

**Impact**: Confirms that step budgets are generally adequate. No blanket budget reduction needed. The waste is concentrated in the gating overhead on inbox tasks, not in the base step counts.

**Confidence**: HIGH

## Summary

At 22/31 (71%), the pipeline is efficient for passing tasks (avg 9 steps vs 15-28 budget). The primary waste source is **completion gate stacking on inbox tasks**: `pre_completion_gate`'s inbox-specific checks have no attempt cap and can loop indefinitely, unlike the unverified-writes HOLD which caps at 2 attempts. The highest-leverage fix is adding a `completion_gate_count` parameter to `pre_completion_gate` and capping inbox gates at 2-3 attempts. Secondary: skip the second-opinion LLM call for OUTCOME_OK on inbox tasks to avoid confirming correct answers at the cost of a step. The two structural failures (t01, t30) need root cause investigation outside the optimizer scope.
