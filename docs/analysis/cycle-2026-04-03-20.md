### Root Cause: HIGH-risk gate on delete consumes 2 iterations per file

**Classification**: PROTOCOL — budget insufficient due to risk gate overhead
**File**: `pac1-py/agent_loop.py` line 150 (GREEN zone)
**Generalizability**: HIGH — affects ANY crud_delete task with multiple files

Chain of events:
1. `domain_fs.py` assigns `delete → risk_level="high"`
2. `agent_loop.py` HIGH-risk gate blocks first attempt (`continue`), adds path to `high_risk_gated` set
3. Model re-issues delete → already in set → falls through to dispatch
4. **Each unique file delete costs 2 loop iterations instead of 1**

Budget math for t01:
- 2 list calls = 2 iterations
- 7 deletes × 2 iterations (HIGH gate) = 14 iterations
- Total exploration: 16 iterations, but budget is only 12
- Agent completes 5 of 7 deletions before budget exhaustion

### Why this is NOT a repeat of Cycle 2026-04-02-22

The old "crud step budget increase" was tested BEFORE the HIGH-risk gate on delete was introduced:
- **2026-04-02-22**: Budget increase 10→14 / 12→24. HIGH-risk gate didn't exist yet (added 2026-04-03 at `a495a6e`). Each delete cost 1 iteration. Budget wasn't the bottleneck.
- **THIS fix**: Different mechanism — reduces per-delete iteration cost from 2 to 1 by downgrading risk for authorized deletes. Doesn't change any budget numbers.

### Recommended Fix

When `classification.requires_delete == True`, downgrade delete effective risk from HIGH to MEDIUM. The task classification (trusted input from benchmark platform) already authorizes deletions.

In `agent_loop.py`, after computing `effective_risk`:
```python
if effective_risk == "high" and tool_name == "delete" and classification.requires_delete:
    effective_risk = "medium"
```

Effects:
- MEDIUM risk: VERIFY message sent (model warned) but dispatch proceeds in same iteration
- Each delete costs 1 iteration (down from 2)
- Budget math: 7 deletes + 4 lists + 1 report = 12 iterations = exactly fits budget
- Non-delete tasks: unchanged (HIGH-risk gate still blocks)
- Sensitive-path writes: unchanged (separate `is_sensitive` check)
