**Selected:** `classification_mismatch`

**Justification:** The root error is upstream of the agent loop. A task that sums a monetary field across invoice files under an ambiguous match-by-service-line criterion is unambiguously an `analysis` task — it matches the `analysis.md` fragment profile exactly ("Be precise with numbers and comparisons"; "Read ALL relevant rows first. Do not estimate from a partial read."). But because the trigger vocabulary is German ("Wie viel Geld", "verdient", "seit Beginn"), none of the English regex signals fire and the task falls through to the default `crud` branch. `crud.md` does not contain numeric-aggregation discipline and the max step budget is 15 — a third of what `analysis` gets (25). Secondary contributing cause: `language_handling` (the classifier is monolingual); the resulting behavior is `wrong_outcome` (agent stopped at 2 of N invoices and reported something premature). But the single *root* is the classification mismatch driving the wrong fragment and the wrong budget.

## Root cause hypothesis

**Exactly one hypothesis:**

`classify.py` regex signals are English-only. A German monetary-aggregation question ("Wie viel Geld … verdient") has no matching token, so `_ANALYSIS_SIGNALS`, `_SEARCH_SIGNALS`, and `_WRITE_SIGNALS` all return False. The task cascades to the `crud` default, loads `crud.md` (which has no numeric discipline), runs under a 15-step budget, and — most importantly — the agent is NOT told to read every invoice before summing. The symptom (early stop after 2 of N files) is a direct consequence of the wrong fragment being loaded.

**Evidence chain:**
1. Running `classify_task()` on the literal German string returns `TaskClassification(task_type='crud', estimated_steps=10, ...)`. Confirmed empirically.
2. The English equivalent "How much money did we earn since the start of April 2026 with the service line 'checklist rewrite and rollout pack'?" would match `_SEARCH_SIGNALS` (`how\s+much` via the `what(?:'s|\s+is)` alternation — actually no, the current regex only has `what`, not `how much`; only `how many` is caught by `_ANALYSIS_SIGNALS`). So even the English form has a gap here — this task is an analysis/aggregation task, and neither `how much` nor its German counterpart is in the analysis signal list. The German version is doubly disadvantaged.
3. `analysis.md` line 11–14 literally says: "Before stating a computed result, cite the source file AND the row or field containing each input value. If you summed across multiple rows, cite all of them… For sums or subtotals, read ALL relevant rows first. Do not estimate from a partial read." This exactly describes the missing discipline that would have kept the agent iterating until all matching invoices were read. The agent never saw this instruction because `crud.md` was loaded instead.
4. Root, not symptom: editing `crud.md` would pollute the CRUD fragment for actual CRUD tasks. Editing `analysis.md` would not help because `analysis.md` is never loaded. The single corrective fix is to make the classifier recognize the aggregation intent.

## Fix proposal (narrow GREEN zone only)

**Selected fix class:** `classify_rule`

**Target file:** `pac1-py/classify.py`

**Exact change:**
```diff
 _ANALYSIS_SIGNALS = re.compile(
-    r"\b(analyze|summarize|compare|count|list\s+all|report|describe|explain|how\s+many)\b",
+    r"\b(analyze|summarize|compare|count|list\s+all|report|describe|explain|"
+    r"how\s+many|how\s+much|total\s+(?:amount|spent|earned|revenue)|"
+    r"wie\s+viel|wie\s+viele|gesamt(?:betrag|summe)?|"  # German: how much / total
+    r"combien|total|montant|  # French: how much / total
+    r"cu[aá]nto|total)\b",  # Spanish: how much / total
     re.IGNORECASE,
 )
```

**Rationale:** Adds `how much` (English — a gap even without the language issue), plus the three most common Western European equivalents (German `wie viel`/`wie viele`/`gesamt`, French `combien`/`total`/`montant`, Spanish `cuánto`/`total`). The PAC1 benchmark has a documented pattern of embedding multilingual task variants as a robustness check. This single regex edit routes t009 from `crud` into `analysis`, which (a) loads `analysis.md` with its NUMERIC discipline block, (b) raises the step budget from 15 to 25, and (c) enables `pre_submit_verification` in the strategy table (true for both, so no change there).

Crucially, the fix is narrow: the `analysis` branch at line 203 requires `has_analysis and not has_write`, and no German/French/Spanish write verbs were added. A task like "erstelle eine Rechnung" (create an invoice) will still fall through to `crud` because `create` is not present in this edit. Only read-only aggregation questions are reclassified.

**Generalizability:** `MEDIUM`
- Direct impact on t009 (the specific task analyzed here). Likely impact on any non-English multilingual aggregation task (PAC1 historically has at least 2–4 such tasks per run; exact count unknown without a broader scan of the 104-task benchmark). The `how much` English gap also quietly fixes any English "how much did we spend" question that previously fell through. Honest estimate: **+1 on t009, plausibly +1 to +2 on other multilingual or how-much tasks**. Cannot claim HIGH without running the classifier over the full `task_cache.json` corpus, which is out of scope here.

**Zone:** `GREEN` — pure classification rule edit. No change to prompts, no change to security paths, no change to domain or tool registry. The only downstream effect is which prompt fragment gets loaded and which step budget applies, both of which are well within the established parameter space.

**Expected impact:** +1 on t009 (score 0.0 → nonzero, expected full credit if agent reads all matching invoices and sums correctly). **Estimated +1 task**.

**Risks:**
- *Over-triggering analysis fragment.* A German task like "Wie viele Dateien liegen in /inbox?" will also match `wie viele` and trigger `analysis` instead of `search`. This is arguably correct (counting files IS an analysis task), and the analysis fragment's COUNTING guidance explicitly says "use the search tool with count_only=True", so behavior should be equivalent or better. Low risk.
- *French `total` is a common noun.* "Total" appearing in a non-aggregation context (e.g., "the total team has 5 people") could mis-classify. Mitigation: `total` is inside a `\b…\b` word boundary and must be in the same search as the analysis verbs; in practice it will co-occur with `combien`/`montant` for monetary questions. Acceptable.
- *No runtime test coverage.* This repo has no classifier unit tests. If a regression appears, the only signal will be the next benchmark run's score. Acceptable given the narrow edit scope.
