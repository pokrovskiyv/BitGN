## Root cause hypothesis

**Exactly one hypothesis:**

`classify.py._ANALYSIS_SIGNALS` (line 51) is missing the finance/aggregation vocabulary. It captures `analyze|summarize|compare|count|list\s+all|report|describe|explain|how\s+many` but not `how\s+much|total|sum|subtotal|paid|pay|spent|spend|cost|balance|revenue`. A "how much … in total" question on a bill file is the textbook analysis case — it requires reading multiple rows across multiple files, exact transcription, and explicit grounding — yet it falls through every rule and defaults to CRUD. Once in CRUD, the agent gets the wrong prompt fragment (no monetary discipline, no search hygiene, no ALWAYS-read-all-sources guidance), the wrong step budget (15 vs analysis's 25), and no pre-submission monetary gate.

**Evidence chain:**
1. Task text contains only two content words that could possibly route it: `bill` (matches nothing) and `total` (matches nothing). The classifier has zero hooks for currency or aggregation vocabulary.
2. Verifier is null and the step count is 3 out of 15 — a CRUD-style one-and-done trajectory on a task that requires sustained multi-file reasoning. This is the classifier putting the agent on the wrong rail, not the agent failing at the right rail.
3. Under the correct `analysis` routing, the agent would have seen analysis.md lines 11–16 ("Before stating a computed result, cite the source file AND the row or field containing each input value. … For sums or subtotals, read ALL relevant rows first. Do not estimate from a partial read.") — a direct, literal prohibition of the exact failure the agent committed.
4. Root, not symptom: fixing the empty-pattern search symptom (e.g., teaching the agent to reject `search("")`) would not help here, because CRUD would still send the agent down a single-file-write-verify path and the 15-step budget would still short-circuit the aggregation. Only classification can deliver the right fragment.

## Fix proposal (narrow GREEN zone only)

**Selected fix class:** `classify_rule`

**Target file:** `pac1-py/classify.py`

**Exact change:**
```diff
 _ANALYSIS_SIGNALS = re.compile(
-    r"\b(analyze|summarize|compare|count|list\s+all|report|describe|explain|how\s+many)\b",
+    r"\b(analyze|summarize|compare|count|list\s+all|report|describe|explain|"
+    r"how\s+many|how\s+much|total|subtotal|sum|sums|paid|spent|cost|costs|"
+    r"balance|revenue)\b",
     re.IGNORECASE,
 )
```

**Rationale:** This adds the missing monetary and aggregation vocabulary to `_ANALYSIS_SIGNALS`. The classifier already has a correct rule at line 203 (`has_analysis and not has_write → analysis`) that will now fire for t100 because `how\s+much` and `total` both match. Routing to `analysis` loads `workspace/prompts/fragments/analysis.md`, which contains the NUMERIC AND MONETARY DISCIPLINE block the task needs, and raises `max_steps` from 15 → 25 per `_STRATEGY_TABLE` in strategy.py. No Python logic change — only the regex vocabulary widens. Safety is preserved because any write-signal ("create invoice for total X") still short-circuits the analysis branch via `and not has_write` on line 203, falling through to the write-oriented paths.

**Generalizability:** `HIGH`
- Finance aggregation is a recurring task family in the BitGN benchmark: the `50_finance/purchases/` tree alone holds many bills, and the cached task distribution suggests similar "how much / total paid / total spent / subtotal for X" questions across purchases, subscriptions, and payroll. Conservatively expect 5–10 tasks in the 104-task set to contain at least one of `how\s+much|total|sum|paid|spent|cost|balance|revenue`. Widening `_ANALYSIS_SIGNALS` is also the lightest-touch intervention: it doesn't change any existing passing route, it only adds a correct route for currently-misrouted questions. The `how_much|total|paid|spent|cost` cluster is linguistically unambiguous — none of these words carry write semantics or CRUD intent, so false-positive risk into CRUD is near-zero.

**Zone:** `GREEN` — single regex edit in `classify.py`, no touch to security paths, no touch to verification, no strategy table change, no prompt mutation. The `analysis` branch already exists and is exercised by other tasks; this fix just feeds it more traffic.

**Expected impact:** +1 on t100 directly (correct routing → analysis.md loaded → agent reads multiple bill files → sums correctly → OUTCOME_OK with the numeric total). Potentially +1 to +3 on similar finance aggregation tasks elsewhere in the 104-task benchmark. Honest conservative estimate: **+1 to +3 tasks**.

**Risks:** Minor. `total` is a common English word that could appear in write-context ("update the total in config.yaml") — but that case is already gated by `has_write → skip analysis` on line 203, so it falls through to CRUD correctly. `cost`/`paid`/`spent` are similarly safe. The only edge case is "paid" in a past-tense narrative ("the client paid last Tuesday") — but those typically carry other signals (write, communication, multi-step) that take precedence. A targeted regression spot-check on any existing CRUD task containing the word `total` or `paid` is cheap insurance.
