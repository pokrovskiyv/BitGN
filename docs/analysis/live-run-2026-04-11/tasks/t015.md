## Root cause hypothesis

**Exactly one hypothesis:**

`outcomes.md` PROACTIVE AMBIGUITY GATE (lines 25–27) treats any unresolved sub-question at report time as grounds for CLARIFICATION, even when the task's primary success criteria are already met. The gate says *"a concrete date … a specific file path … and that entity is ABSENT after thorough search. Do NOT approximate"* — but in multi-file inbox processing the correct frame is "was the inbox item processed per the workflow?" not "can every stray filename I brainstormed be verified?". When the agent generated a new candidate path (`_2026_...`) from its own speculation and then could not find it, the gate treated that self-invented entity as an authoritative absence signal and overrode the already-completed work. The `inbox_processing.md` fragment has no instruction that says "if all workflow steps succeeded, return OK regardless of trailing exploration" — it leaves the completion rule to `outcomes.md`, which has no clause for "task-already-succeeded, ignore trailing self-generated ambiguity".

**Evidence chain:**
1. Verifier reasoning is explicit: the agent "confused the filename with a leading underscore mentioned in their message with the actual path" — i.e., the agent hallucinated a filename, then let the hallucination's absence drive the outcome.
2. Step 20 (read-verify of file 4 under the canonical non-underscore name) was successful and the verifier explicitly traces `tee` output showing correct frontmatter.
3. Step 26 plan text: *"Report OUTCOME_NONE_CLARIFICATION — 4 of 5 files OCR'd, file 5 with leading unde[rscore]"* — the agent knows 4 files succeeded and still chooses CLARIFICATION purely on a naming doubt, not on an execution failure. That is exactly the "clarification because a sub-question is open" failure mode.
4. Root, not symptom: fixing `inbox_processing.md` to say "delete more aggressively" would not prevent this; the issue is that `outcomes.md` gives CLARIFICATION a wide berth even when OK is clearly earned. The gate needs a completion-guard clause.

## Fix proposal (narrow GREEN zone only)

**Selected fix class:** `prompt_fragment`

**Target file:** `pac1-py/workspace/prompts/fragments/outcomes.md`

**Exact change:**
```diff
 PROACTIVE AMBIGUITY GATE — run BEFORE returning OUTCOME_OK:

 Look at the ORIGINAL task instruction text (not file content). If either marker below is present, return CLARIFICATION with a one-line reason instead of OK:
 - The instruction ends in the middle of a word (e.g., "Create captur"). A stylistic ellipsis "..." at the end of a normal word is NOT truncation.
 - The instruction requires LOOKING UP a specific entity in the filesystem — a concrete date (literal or relative like "36 days ago"), a specific file path, a named person, or a specific amount — and that entity is ABSENT after thorough search. Do NOT approximate or pick the "closest match". This does NOT apply to pure computation ("what date is tomorrow") or to generic collective references ("the inbox", "the next item").

 A hard but unambiguous task is OK. Fire only on a literal marker above.
+
+COMPLETION GUARD (run AFTER the ambiguity gate, BEFORE returning CLARIFICATION):
+If you have already performed the workflow-required writes AND each write was verified by a read-back, the task is OK, not CLARIFICATION. A leftover sub-question you invented yourself (a speculative filename, an alternate path variant, an unchecked related file) is NOT a clarification trigger — it is curiosity, and curiosity does not override completed work. Only the ORIGINAL task instruction text can fire the ambiguity gate; do NOT let a self-generated doubt downgrade an otherwise-successful run.
+Example: inbox task "Handle the next inbox item." — you processed 4 receipts per the workflow, each write read-verified, then noticed a possible "_prefixed" filename variant you never actually saw in a directory listing. Return OK with a summary of the 4 processed files. Do NOT return CLARIFICATION over a phantom path.
```

**Rationale:** The guard is narrowly scoped — it only fires when writes have been completed AND verified, which is exactly the pattern the read-after-write discipline enforces. It does not weaken the existing CLARIFICATION rules for genuine absence (the "March 5th" example stays intact) and it does not touch any SECURITY path. The explicit "self-generated doubt" wording closes the specific hole the agent fell into: the phantom leading-underscore filename was never in any directory listing; it was a hypothetical the agent manufactured during step 21 planning. By requiring the ambiguity to come from the original task text, we force the gate to evaluate only objective signals.

**Generalizability:** `MEDIUM`
- Multi-file inbox and batch-processing tasks are the most likely to hit this pattern: the agent finishes the required items, then spins up one more speculative check, fails it, and downgrades to CLARIFICATION. On a 104-task benchmark, inbox_processing + multi_step tasks with ≥3 items are a meaningful fraction — rough estimate 3–6 tasks. Single-file CRUD tasks are unaffected because they rarely generate speculative sibling paths. Cannot claim HIGH without a broader sweep of cycle logs.

**Zone:** `GREEN` — prompt-fragment edit only, no Python change, no effect on security paths (the completion guard explicitly runs AFTER the ambiguity gate so SECURITY → CLARIFICATION → (guard) → OK path preserves the current security priority). The guard can only UPGRADE CLARIFICATION → OK, never the reverse, so it cannot introduce false positives on genuinely-absent data.

**Expected impact:** +1 on t015 (`OUTCOME_NONE_CLARIFICATION` → `OUTCOME_OK` once the agent reasons that 4 read-verified writes complete the workflow). Potentially +1 to +2 on other multi-file inbox tasks where the agent processes N items and then second-guesses a speculative N+1. Honest conservative estimate: **+1 to +2 tasks**.

**Risks:** Minor regression risk on tasks where the agent prematurely "completes" after writing 2 of 3 required files and then abandons the third — but the guard's text explicitly says "workflow-required writes", so if a genuine workflow step is incomplete the gate still fires CLARIFICATION. Second minor risk: the agent could read the new clause as "just do as many writes as you feel like and call it OK" — mitigated by anchoring to "workflow-required" and "read-back verified", both of which are already binding elsewhere.
