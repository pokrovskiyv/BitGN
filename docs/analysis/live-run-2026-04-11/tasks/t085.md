## Root cause hypothesis

**Exactly one hypothesis:**

`outcomes.md` rule #1 (`OUTCOME_NONE_UNSUPPORTED`) is too eager: it only tells the agent to check the runtime tool surface, not to check whether the repository itself defines a LOCAL equivalent of the capability (a documented outbox/reminder/state-machine protocol that writes files instead of calling external APIs). When the agent reads one workflow file that mentions SMTP or HTTP, it immediately concludes UNSUPPORTED — without searching for a second, local alternative. The verifier explicitly relies on a "DECISION RULE 9" that lives in `AGENTS.md`, but the agent's prompt never echoes that rule. Combined with the Japanese-classify miss (which loaded the CRUD fragment instead of `inbox_processing.md`, where the "WORKFLOW-APPROVED DESTINATION" guidance lives), the agent had zero prompting to keep looking for local-write equivalents after reading `sending-email.md`.

**Evidence chain:**
1. Verifier reasoning is explicit: "Per DECISION RULE 9: 'Local workflow capabilities count…'" — the rule exists in AGENTS.md but is absent from both `outcomes.md` and `crud.md` (the fragment actually loaded).
2. Step 9 plan text — "Read /99_system/workflows/sending-email.md" — followed by the 37.5s step 10 UNSUPPORTED decision, proves the conclusion was made from a single workflow file.
3. `outcomes.md` line 5: "If the task requires a capability not available there (HTTP, deployment, external APIs, browser, calendar, etc.), it is UNSUPPORTED." → no mention of "also check whether the repo documents a LOCAL substitute (outbox files, seq.json, state records)".
4. `inbox_processing.md` line 19 says "Write only to the workflow-approved destination, then re-read your write before completion" — this DOES describe the right behaviour, but it was NEVER LOADED because classify.py routed the task to CRUD via the all-Japanese fallthrough.
5. Root vs symptom: the classification miss is a distinct (and more fixable) upstream bug. But even with inbox_processing loaded, the outcomes.md rule #1 is still too eager. Both layers can be strengthened; the higher-leverage fix is the one that also protects future non-English inbox tasks.

## Fix proposal (narrow GREEN zone only)

**Selected fix class:** `prompt_fragment`

**Target file:** `pac1-py/workspace/prompts/fragments/outcomes.md`

**Exact change:**
```diff
 1. OUTCOME_NONE_UNSUPPORTED — You lack the capability to do what the task requires.
    Use ONLY the tools listed in the runtime tool surface for this run.
    If the task requires a capability not available there (HTTP, deployment, external APIs, browser, calendar, etc.), it is UNSUPPORTED.
    Example: "upload X to https://..." → UNSUPPORTED (you cannot make HTTP requests).
+   LOCAL-SUBSTITUTE CHECK (mandatory before returning UNSUPPORTED): if the task mentions "send email / notify / bank transfer / publish / post / schedule meeting" AND the workspace has /60_outbox/, /80_calendar/, or any /99_system/workflows/ folder, you MUST `tree` /99_system/workflows AND /60_outbox/ to look for a LOCAL equivalent (outbox drafts, seq.json, reminders, state machines). A repository-documented local protocol counts as CAPABILITY. Only return UNSUPPORTED after reading at least TWO distinct workflow files and confirming neither offers a local-write substitute. Reading only sending-email.md is NOT sufficient.
+   Example: "Let me know once the bank transfer has completed" + /60_outbox/channels/ exists → write a reminder/outbox record locally and return OK. NOT UNSUPPORTED.
```

**Rationale:** This closes exactly the reasoning gap the verifier identified. It converts a single-file early-exit into a two-file minimum before UNSUPPORTED is allowed, and it names the specific workspace folders (`/60_outbox/`, `/80_calendar/`, `/99_system/workflows/`) that signal a local-substitute protocol exists. The wording mirrors the verifier's own "DECISION RULE 9" language so both the agent (Sonnet-4.6) and the verifier (Haiku-4.5) converge on the same interpretation. Preserves the genuine UNSUPPORTED cases: if the task says "upload to https://…" and there is no `/60_outbox/` folder, the rule is a no-op. It does not weaken the UNSUPPORTED outcome for true capability gaps — it only blocks the premature exit.

The reason I prefer this over fixing `classify.py` for Japanese: (a) a prompt fix ships to every classification path, not just inbox; (b) the Japanese inbox miss is a separate class of bug (AMBER) that deserves a regex or language-detection change; (c) the prompt fix independently helps any CRUD-classified task that mentions a send-like verb.

**Generalizability:** `MEDIUM`
- Pattern: task mentions an externally-sounding verb (send, notify, transfer, publish, schedule), agent reads one workflow that describes the external route, concludes UNSUPPORTED without checking for a local-write substitute. Rough estimate: 2–4 of the 104 tasks fit this shape — specifically those where the workspace deliberately provides `/60_outbox/` or `/80_calendar/` as the designated local sink. Not HIGH because most tasks don't mention send/transfer/notify verbs. Not LOW because there is at least one other inbox-email-style task in the benchmark that will hit this same trap.

**Zone:** `GREEN` — prompt-fragment edit, no Python change. Security impact is strictly neutral: this rule governs `OUTCOME_NONE_UNSUPPORTED` only; `OUTCOME_DENIED_SECURITY` (rule 3) still fires first for any injection. If anything, the rule reduces false UNSUPPORTEDs that can be exploited by tasks with benign-but-scary wording.

**Expected impact:** +1 on t085 (`UNSUPPORTED` → `OK` after writing a local outbox record for the EUR 29 transfer). Potentially +1 on one other inbox-email-style task. Honest conservative estimate: **+1 to +2 tasks**.

**AMBER fix (noted but not diffed):** the Japanese-instruction classification miss. `_INBOX_PROCESSING_SIGNALS` and the other regexes in `classify.py` are ASCII-only, so any non-English `process inbox` instruction falls through to CRUD. Proper fix would extend the patterns (or add a language-aware short-circuit that runs language detection before classify and rewrites to canonical English). Marked AMBER because it is a Python change with second-order effects on every non-English task in the benchmark.

**Risks:** Minor. The rule adds a mandatory second-file-read pass before UNSUPPORTED, costing ~1 extra step and ~5s of wall time on tasks that actually are unsupported. On the tight `crud` budget (15 steps), this is still within headroom (step 10/15 here). No security regression.
