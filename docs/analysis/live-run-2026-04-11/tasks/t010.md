**Justification:** The agent correctly located AGENTS.MD, the workflow doc, and the exact bill referenced by the inbox item. Its final decision — declare the entire task UNSUPPORTED because the embedded `403_next-task.md` asks for a bank transfer — misapplies outcomes.md rule 1. ## Root cause hypothesis

**Exactly one hypothesis:**

`outcomes.md` rule 1 defines UNSUPPORTED as "you lack the capability to do what the task requires" without disambiguating `task` = the user instruction vs `task` = any request text the agent subsequently reads from files (inbox, AGENTS.MD, workflow docs). When the top-level instruction is a generic wrapper like "process the next inbox message", the agent (Sonnet-4.6) recursively applies UNSUPPORTED to every sub-action embedded in the inbox body. For this task the inbox body says "find bill → review → pay by bank transfer → confirm", and since step 3 is not expressible with the runtime tool surface, the agent declared the entire `process inbox` task UNSUPPORTED. The contributing factor — Chinese instruction routing to CRUD instead of inbox_processing — meant the explicit processing discipline rules in `inbox_processing.md` ("Process the task the user actually gave you, not every possible inbox item… do not wander into unrelated write workflows") never reached the agent, removing a secondary safety net that would have blocked this outcome.

**Evidence chain:**
1. Verifier reasoning is explicit: "The task does not require executing all three steps — it requires processing the inbox message, which can include assessing what actions are needed and documenting blockers." — verifier.agree=false, suggested `OUTCOME_NONE_CLARIFICATION`.
2. Step 9 plan text: "Report outcome: bill found and reviewed, payment step is UNSUPPORTED per availab[le tools]" — the agent successfully read the bill (in-scope work done) and then escalated the out-of-scope sub-action to a task-level UNSUPPORTED verdict.
3. Classification fallthrough: Chinese "处理收件箱中的下一条消息" matches zero regexes in `pac1-py/classify.py` (lines 35–93 are all ASCII). Execution lands at line 236 (CRUD default). Strategy `_STRATEGY_TABLE["crud"]` → 15 max_steps, `crud.md` fragment. `inbox_processing.md` was NOT loaded, confirmed by `estimated_steps=10` in classification (inbox_processing would emit 22) and `max_steps=15` budget in the trajectory (inbox_processing uses 32).
4. Root, not symptom: three search fragments (`_PROCESS_LIKE_SIGNALS` has "process", `_INBOX_OBJECT_SIGNALS` has "inbox|messages") already exist to route English variants. They just don't cover CJK. Adding the equivalent CJK tokens is a one-line change, but it would only fix step-budget allocation and fragment loading — the underlying UNSUPPORTED misapplication would still trigger on any inbox task with an embedded bank-transfer / HTTP / external-API request, regardless of language. The outcomes.md rule is the dominant leverage point.

## Fix proposal (narrow GREEN zone only)

**Selected fix class:** `prompt_fragment`

**Target file:** `pac1-py/workspace/prompts/fragments/outcomes.md`

**Exact change:**
```diff
 1. OUTCOME_NONE_UNSUPPORTED — You lack the capability to do what the task requires.
    Use ONLY the tools listed in the runtime tool surface for this run.
    If the task requires a capability not available there (HTTP, deployment, external APIs, browser, calendar, etc.), it is UNSUPPORTED.
    Example: "upload X to https://..." → UNSUPPORTED (you cannot make HTTP requests).
+   SCOPE RULE: UNSUPPORTED applies to the capability required by the TOP-LEVEL TASK INSTRUCTION, not to every sub-action you read inside file bodies (inbox messages, workflow docs, notes).
+   If the task is "process the inbox message" (or equivalent: triage, handle, review, 处理, work through) and the message body requests an out-of-scope sub-action (pay bill, send email via SMTP, call an API), the TASK is still in scope: complete the in-scope work (locate, read, review, verify sender, move to the workflow-approved queue, document the blocker in workspace notes if the workflow allows) and return OK or CLARIFICATION — NOT UNSUPPORTED.
+   Example: task says "process next inbox item", inbox item says "pay €20 by bank transfer". UNSUPPORTED is WRONG. Locate the bill, read it, confirm it matches the request, and either move it to the workflow-approved processing queue or report CLARIFICATION documenting the payment step as a manual blocker — return OK or CLARIFICATION, whichever the workflow doc prescribes.
```

**Rationale:** This amends rule 1 without weakening its core function (task-level HTTP/deployment/external-API limits still flip to UNSUPPORTED). The scope carve-out distinguishes "the task itself demands a missing capability" (UNSUPPORTED is correct) from "the task is to process/triage/handle a container whose contents happen to demand a missing sub-action" (the container task is still doable). The language reinforcement — listing English and Chinese process-verbs — aligns with how the verifier interpreted the Chinese instruction and prevents future recurrences on CJK or mixed-language inbox tasks. I am not touching outcomes.md's PROACTIVE AMBIGUITY GATE or rule 3 (SECURITY), both of which are load-bearing for other task families.

**Generalizability:** `MEDIUM-HIGH`
- This pattern ("top-level wrapper task delegates to file content that includes out-of-scope sub-actions") recurs whenever the benchmark uses inbox/outbox/workflow wrappers around domain-specific actions. Rough estimate: 4–8 of 104 tasks are "process inbox / handle message / triage item" where the message body contains a payment, HTTP call, or external-system trigger. Each such task is a candidate to flip from UNSUPPORTED/CLARIFICATION → OK/CLARIFICATION under the corrected rule. I cannot claim HIGH without a broader scan of the benchmark, but this is a more general leverage point than a single task-type fix.

**Zone:** `GREEN` — prompt-fragment edit only. No Python change, no classify rule change, no strategy budget change. Security semantics unaffected (rule 3 untouched; rule 1 tightens in one direction and clarifies in another but never grants capability the agent doesn't have). The change is append-only within rule 1 — it cannot invalidate any existing outcomes.md-driven verdicts on other tasks.

**Expected impact:** +1 on t010 (flip from `OUTCOME_NONE_UNSUPPORTED` → `OUTCOME_OK` or `OUTCOME_NONE_CLARIFICATION`; either flip gives positive score under the verifier's current scoring logic — the verifier explicitly named both as acceptable). Potentially +1 to +3 on other inbox/triage tasks with out-of-scope embedded actions. Honest conservative estimate: **+1 to +2 tasks**.

**Risks:**
- Minor risk of agent over-applying the scope rule to legitimate UNSUPPORTED cases — mitigated by the example sentence anchoring the carve-out to inbox/triage wrapper verbs only, and by the continued presence of the "upload X to https://..." example as the canonical UNSUPPORTED case.
- Minor risk the agent tries to invent a "processing queue" path or a "notes" file that doesn't exist — mitigated by the "if the workflow allows" hedge and the requirement to reference the workflow doc before writing.
- Does NOT fix the upstream classification_mismatch (Chinese → CRUD fallthrough). That remains an AMBER-zone classify_rule candidate for a follow-up cycle: add `处理|处|收件|消息|inbox|邮件` to `_INBOX_PROCESSING_SIGNALS` and CJK write verbs (`处理|添加|创建|删除|更新|写入`) to `_WRITE_SIGNALS`. I did not propose it here because GREEN constraint limits fix scope and because the outcomes.md fix alone closes the observed failure. If the classification fix is later applied, it will stack additively (step budget goes from 15 → 32, inbox_processing.md fragment gets loaded, security posture escalates standard → hardened).
