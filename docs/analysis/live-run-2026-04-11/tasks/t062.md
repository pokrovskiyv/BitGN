# t062 — post-mortem analysis

## Instruction
> Find the next birthday from the visible people. If several birthdays land on the same next date, list all matching names. Return only the exact names, one per line, sorted alphabetically.

## Execution profile
- **Task type (classified):** `search` via `_READ_ONLY_DATE_LOOKUP_SIGNALS` (`classify.py` lines 55–59, 181–189). The regex matches "next … birthday"; because the instruction has no write signals (`has_write=False`), control falls into the read-only date-lookup branch at line 181 and returns `task_type="search", estimated_steps=15`. The later `search` branch at line 214 would have matched anyway. `has_analysis=True` ("list all matching names") but is bypassed because the read-only-date rule fires first.

Budget was effectively **exhausted**: the listed step indices jump 1–23 → 27 → 30, so five agent turns (24, 25, 26, 28, 29) were consumed by non-dispatch loop iterations (stagnation retry, recovery, or `report_completion` re-deliberation).
- **Tool calls:** 25
- **Wall time:** 188.9s
- **Tokens:** 763,722 in / 84,665 out (by far the heaviest task in the run)
- **Language:** en
- **Prompt fragment loaded:** `workspace/prompts/fragments/search.md` (+ always-on `outcomes.md`, `reasoning.md`)

2. **steps 2–23** (20–8.6s each): sequential `read` of every file in `/10_entities/cast/` — badger, bix, claudia, elena, foundry, gregor, hanna, ida, jana, juniper, lukas, miles, nina, nora, omar, oskar, pepper, petra, renate, roman, sara, tobias. 22 full reads in a row.

4. **step 27** (12.7s think): `read(/10_entities/cast/claudia.md)` — re-reads claudia.md. Classic stagnation signal; `verify.py` stagnation detector should have nudged after `StagnationDetector` triggered on the repeat.

6. **step 30** (23.8s think): `read(/10_entities/cast/AGENTS.MD)` — the agent finally reads the authoritative header file, but as step 30 instead of step 1. Execution ran out of budget right here.

Notable patterns:
- **`context()` was NEVER called.** `search.md` line 14 explicitly instructs: *"For 'next', 'upcoming', or date-comparison lookups, call `context()` early so you compare against the current date instead of guessing."* The agent ignored this and brute-forced the cast directory without knowing today's date. The 23.8 s think spike on step 30 is almost certainly the agent realising it lacks a reference date.
- **`search` with a field token was NEVER used.** Instead of one `search(pattern='birthday:', root='/10_entities/cast')` that returns every cast file with a birthday line in one shot, the agent did 22 sequential `read`s. `search.md` line 3 allows `search` *when you already have a concrete token* — `birthday:` is exactly that.
- **AGENTS.MD read backwards.** The runtime auto-init already reads the root AGENTS.md, but per-directory AGENTS.MD files still exist. Reading `/10_entities/cast/AGENTS.MD` on step 30 (after exhausting everything else) is the wrong order — it should have been the second action, right after the list.
- **Stagnation nudge fired but did not recover.** Step 27's 12.7 s planning + the missing 24–26 block is the fingerprint of the 2-repetition stagnation detector firing and the agent re-deliberating. It did not find a new productive trajectory.
- **Answer hallucination, not budget-only failure.** The agent eventually submitted "Claudia Reiter" as the next-birthday name, but the verifier sees only a window of tool outputs (the last ~5 cast files: petra, renate, roman, sara, tobias) and so cannot confirm Claudia's birthday at all. Even if Claudia were correct in absolute terms, the agent never read the full benchmark fixture, because the verifier lost the early reads to window trimming.

## Failure category

**Selected:** `budget_exhausted`

**Justification:** The underlying failure is **strategy**, not semantics. The agent picked a brute-force per-file walk, never called `context()` for today's date, and never used `search` with a field token — all three behaviours directly violate `search.md`. By the time it needed to *compare dates* it had already spent 23 of its 24 budgeted steps on data collection, hit stagnation, and ran out of room. The final hallucinated answer "Claudia Reiter" is a symptom of this: step 30 was a desperate AGENTS.MD read, not a reasoning pass, so the agent never actually computed the minimum-delta date across the collected records. `wrong_outcome` would also fit, but root cause is the strategy that left zero cycles for reasoning. `stagnation` is a secondary contributor but fired too late to help.

## Root cause hypothesis

**Exactly one hypothesis:**

`search.md` already lists the correct techniques (early `context()` call, field-token `search`, canonical-folder-first) but phrases them as *advice*, not as *enforced step-ordering rules*. For "next/upcoming" comparison tasks, the optimal protocol is deterministic: **(1) `context()` → (2) `search` for the field token in the canonical dir → (3) read only the matched files → (4) compare dates → (5) report**. Without that protocol stated as a numbered checklist, a thinking model falls back to its default "read everything first" behaviour. Combine that with a 24-step cap for `search` (already tight for 22+ entity files), and any fixture of this size will blow the budget and trigger exactly the trajectory observed.

**Evidence chain:**
1. Step 1 is correct (`list cast`) — so the agent read and understood `search.md`'s *first-action* advice.
2. Step 30 is the late `context()`-equivalent (reading AGENTS.MD) — the agent eventually realised it was missing orientation, proving the gap is *order*, not *knowledge*.
3. Steps 2–23 are 22 consecutive full-file reads with identical plan strings ("Read X.md for birthday field") — the agent saw no reason to use `search` because `search.md` never instructs it to for field-token queries.
4. `classify.py` correctly routes "next birthday" → read-only-date-lookup → `search`. The classification is fine; the downstream *protocol* for that subtype is not strong enough.
5. `strategy.py` line 51: `search` max_steps=24. 22 reads + 1 list + 1 report = 24. Zero slack for stagnation recovery or reasoning — one wrong turn and the budget dies.

## Fix proposal (narrow GREEN zone only)

**Selected fix class:** `prompt_fragment`

**Target file:** `pac1-py/workspace/prompts/fragments/search.md`

**Exact change:** Replace the `DATE / UPCOMING LOOKUPS` section (lines 14–17) with a numbered, enforceable protocol:

```diff
-DATE / UPCOMING LOOKUPS:
-- For "next", "upcoming", or date-comparison lookups, call `context()` early so you compare against the current date instead of guessing.
-- For people/entity date lookups, list the canonical entity directory first, then read the candidate entity files and compute the answer from those records.
-- These tasks are usually read-only lookups, not workflows. Avoid procedural wandering once you have the canonical records.
+DATE / UPCOMING LOOKUPS — MANDATORY PROTOCOL (follow the numbered order, do not skip steps):
+1. `context()` FIRST — you need today's date before you can compare any "next" or "upcoming". Never start with `list` or `read` on this subtype.
+2. `list` the canonical entity directory ONCE to learn the file count.
+3. `search` the canonical directory with the relevant field token (`birthday:`, `dob:`, `anniversary:`, `renewal:`, `due:`) to collect ALL matching records in ONE call. Do not read files individually before doing this.
+4. `read` ONLY the files the search returned as matches. Do NOT read files that had no match.
+5. Compute the minimum positive delta against today's date (cycle year forward for birthdays/anniversaries) and report.
+Budget warning: brute-force per-file reads of the entire directory WILL exhaust the step budget on dirs with 20+ entities. The `search` step in (3) is non-negotiable for this subtype.
```

**Rationale:** The existing text had the right ideas as bullet advice. Turning them into a numbered protocol with an explicit "do not skip" clause converts advice into a checklist the model will actually follow. The explicit "`search` with the field token in ONE call" instruction prevents the 22-file sequential read anti-pattern that caused this failure — that alone would have reduced t062 from ~24 dispatches to ~6. The budget warning closes the loop by telling the model *why* the protocol matters.

**Generalizability:** `HIGH`
- The "find next/upcoming X across N entities" pattern is common: next birthday, next anniversary, next renewal, next deadline, next appointment, next review cycle. Rough count: at least 5+ tasks in the 104-task benchmark plausibly match `_READ_ONLY_DATE_LOOKUP_SIGNALS` or an adjacent "across all entities" compare task. Even tasks that do not strictly match the date-lookup regex benefit from the "`search` with field token before per-file read" rule embedded in step 3 — that applies to almost every lookup over structured entity directories.
- Risk of regression: near zero. The protocol strictly narrows the *first* actions; nothing downstream is forbidden. `context()` is already cheap and already recommended, so promoting it to step 1 cannot hurt other search tasks.

**Zone:** `GREEN` — prompt-fragment edit only, no Python changes, no strategy table bump, no security-path impact.

**Expected impact:** +1 on t062 directly, and plausibly +1 to +3 on sibling "next/upcoming X across entities" tasks whose current-run trajectories would share the same brute-force symptom. Honest conservative estimate: **+1 to +3 tasks**. Impact is gated by how many of those sibling tasks currently fail vs. pass.

**Risks:**
- If a sibling task has an entity dir where the field-name varies per file (e.g., some use `birthday`, some `dob`, some `born`), a single `search` may miss matches. Mitigated because step 4 still allows reading candidates, and the agent will fall back to per-file reads if `search` returns zero hits.
- A `context()` call at step 1 adds ~200 ms of dispatch for search tasks that do NOT need a date — but the existing text already recommended it "early", so the net cost is negligible.

**Alternative fix (NOT proposed, AMBER zone):** bump `strategy.py` `search` max_steps from 24 to 30. This would also allow the current trajectory to finish, but it treats the symptom (too few steps) instead of the cause (inefficient strategy), and globally lengthens every search task. Marking AMBER because it is a `strategy_budget` change; no diff produced per scope constraints.
