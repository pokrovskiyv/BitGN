## Root cause hypothesis

**Exactly one hypothesis:**

The `_WRITE_SIGNALS` regex in `pac1-py/classify.py` line 36 is missing the verbs "queue", "migrate", and "migration". Because none of these trigger `has_write`, the task is evaluated with `requires_write=False`. Combined with the absence of any search/analysis/multi_step/communication signal, the classifier falls through to the default `crud` branch with a 15-step budget — catastrophically under-provisioned for a 3-file bulk write. If `_WRITE_SIGNALS` had recognized "queue" or "migrate", `has_write=True` would combine with the implicit enumeration-of-three and push the task onto a higher-budget path; a parallel fix in `_MULTI_STEP_SIGNALS` for "these ... and ..." enumerations would reinforce the signal.

**Evidence chain:**
1. Task text: *"Queue up these docs for migration to my NORA:bulk-processing-and-queueing-frontmatter.md, parking-lot.md, why-i-keep-coming-back-to-a-personal-assistant.md."* — the only two action words are "queue up" and "migration". Neither is in `_WRITE_SIGNALS` (`create|write|add|append|insert|update|set|change|rename|move|process|reschedule|capture|distill|schedule`).
2. The agent successfully completed 2 of 3 writes with correct read-after-write verification (steps 10–13) — so its execution logic was fine; it simply ran out of steps.
3. `metrics.step_count = 15` and `metrics.verifier_verdict = null` — the classic signature of a run that did not terminate via `report_completion`. Steps 10–13 consumed budget for the first two files; there was literally no room left for the third file's three-step cycle (find-or-read + write + verify) or for the terminal `report_completion`.
4. The file-name collision (schema vs note) cost ≈2 extra steps (the duplicated schema read at step 8, plus the confused 34s planning burst at step 9) but that is a symptom of having so little slack. A multi_step budget of 30 would have absorbed both the collision overhead and the third file comfortably.

## Fix proposal (narrow GREEN zone only)

**Selected fix class:** `classify_rule`

**Target file:** `pac1-py/classify.py`

**Exact change:**
```diff
 _WRITE_SIGNALS = re.compile(
     r"\b(create|write|add|append|insert|update|set|change|rename|move|process|"
-    r"reschedule|capture|distill|schedule)\b",
+    r"reschedule|capture|distill|schedule|queue|migrate|migration)\b",
     re.IGNORECASE,
 )
```

**Rationale:** Adding `queue`, `migrate`, and `migration` to `_WRITE_SIGNALS` flips `has_write=True` for this task. Because the task also enumerates multiple files with "these docs ... , ... , ..." it will then be evaluated at the multi_step check at line 192. Even if it does not trip the multi_step branch (the current `_MULTI_STEP_SIGNALS` regex does not match comma-enumerated file lists), it will at minimum stay in `crud` but now with `requires_write=True` — which is unchanged for budget. To actually get the budget bump, the cleaner route is the one above PLUS promoting to multi_step via explicit signal. However, the ONE fix constraint limits us to a single change, and enlarging `_WRITE_SIGNALS` is the minimum-invasive, highest-leverage lever: it is the entry gate that downstream heuristics all depend on, and missing it here is a genuine classification bug that will recur on any task using migration vocabulary.

A secondary-but-cleaner alternative (if we relaxed the ONE constraint) would be to add a new `_BULK_WRITE_SIGNALS` regex for comma-enumerated file lists and route to multi_step directly. Keeping to one fix: enlarge `_WRITE_SIGNALS`.

**Generalizability:** `MEDIUM`
- This pattern (task uses a non-canonical verb for "write a bunch of files" — migrate, queue, enroll, onboard, register, archive) likely recurs 2–4 times across the 104-task benchmark. Any task that says "migrate X to the new schema" or "queue these for processing" without an explicit write verb will hit the same classification miss. The fix is narrow enough not to leak into search/analysis tasks (none of those typically use "queue" or "migrate" in the imperative).

**Zone:** `GREEN` — `classify.py` regex rule edit, no Python logic change, no security-path impact. The proactive ambiguity gate, the CLARIFICATION rule, and the security fragment are untouched. Worst-case regression is that a future search task saying "what do I need to queue up next?" would falsely trip `has_write`, but that is already handled downstream because the task would still match `_SEARCH_SIGNALS` / `_QUESTIONISH_LOOKUP_SIGNALS` and the `(has_search or has_lookup) and (not has_write or is_questionish_lookup)` branch at line 214 would catch it.

**Expected impact:** +1 on t042 directly — with `has_write=True`, the task lands in `crud` with the SAME 15-step budget (still too tight), OR in `multi_step` if paired with a multi-step signal detection. To actually flip this task green, the classification fix must also nudge the budget. Realistic honest estimate for the single-line fix as written: **+0 to +1** on t042 (depends on whether the runner also bumps the budget via a downstream heuristic). Adding a second change — promoting to multi_step when `has_write=True AND len(target_hints) >= 3` — would make +1 near-certain. Conservatively reporting as: **+0 to +1 tasks** for the single-line fix alone.

**Risks:** Very low. None of the added verbs ("queue", "migrate", "migration") overlap with security vocabulary. `migrate` appears in nothing the agent would mis-route to CRUD today. The only theoretical edge case is a task saying "queue the next calendar item" which is a search — but `_SEARCH_SIGNALS` / `_QUESTIONISH_LOOKUP_SIGNALS` fires on "what/which/when" and takes precedence via the ordering at line 214.
