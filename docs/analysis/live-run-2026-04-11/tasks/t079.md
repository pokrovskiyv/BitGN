## Root cause hypothesis

**Exactly one hypothesis:**

If this task scored < 1.0, the most likely root cause is **format_mismatch at the final submission**, not a reasoning gap. Specifically: the task demands "Answer with a number only" — one of the strictest format constraints in the benchmark. The agent's analysis.md fragment line 6 already says "your completion message must contain ONLY that value — no prefix, no explanation. Just the raw answer." But the sentinel word in the task is "number", not "list" or "email", and the agent's current prompt stack does not explicitly say "a bare integer, no unit, no word, no sentence". A completion like `"1 project"`, `"One"`, `"1."`, or `"Based on my search: 1"` would all fail a strict equals check against `"1"`. Every other lever (classification, step budget, search discipline, counting rule) is already correctly applied for this task.

**Evidence chain:**
1. Trajectory is textbook for a counting analysis: search → read candidates → final count_only verification → report.
2. Step 8's plan ("the only simmering project") demonstrates the agent correctly narrowed the search space.
3. `analysis.md` line 6 handles the generic precision rule, but the word "number" in the task isn't tied to a numeric-only schema check anywhere in the prompt stack.
4. The verifier verdict being null is unusual — in runs where the answer is well-formed, Haiku usually returns a structured agree/disagree; null suggests the verifier was either not run for this task or errored, not that the agent failed the reasoning.
5. In prior PCDRED cycles, "Answer with N only" tasks have been a known format-regression surface (see `docs/analysis/`-dated files referencing outcome/format slippage around counting tasks).

## Fix proposal (narrow GREEN zone only)

**Selected fix class:** `prompt_fragment`

**Target file:** `pac1-py/workspace/prompts/fragments/analysis.md`

**Exact change:**
```diff
 - ANSWER PRECISION: when the task asks for a specific value (email, name, number, list), your completion message must contain ONLY that value — no prefix, no explanation. Just the raw answer.
+- ANSWER PRECISION: when the task asks for a specific value (email, name, number, list), your completion message must contain ONLY that value — no prefix, no explanation. Just the raw answer.
+- NUMERIC ANSWER FORMAT: when the task says "answer with a number only", "return only the number", "just the count", or similar, your completion message MUST be a bare integer/decimal with NO other characters. Not "1 project", not "One", not "1.", not "Based on my count: 1", not "**1**". Just `1`. This applies even if the number is zero — return `0`, not "zero" or "none".
```

**Rationale:** This is a targeted addition to an existing rule that the verifier and the agent already mostly honor. It closes the specific gap where "number" is one word among several in the generic precision rule, but the literal-equals check on numeric answers is stricter than on emails or names. Adding concrete negative examples (`"1 project"`, `"One"`, `"**1**"`) teaches the format directly, matching the pattern proven effective in `outcomes.md` ("Example: …"). No Python change, no effect on security paths, no effect on other task types (this fragment only loads for analysis tasks).

**Generalizability:** `MEDIUM`
- Bare-number answers appear in any `how many` / `count` / `how much` style question. Rough estimate: 3–6 tasks of 104 in the live benchmark ask for a strict numeric answer. This fix would also help on budget-style tasks that require a decimal amount. Cannot claim HIGH without a broader scan of live-run payloads, and cannot claim LOW because this is clearly not a one-off — the analysis fragment exists precisely because these tasks recur.

**Zone:** `GREEN` — prompt-fragment edit to `analysis.md` only. No Python change. No effect on security paths or any other task type. The new line is purely additive — it makes an existing rule stricter, not looser.

**Expected impact:** +0 to +1 on t079 depending on what the actual failure mode was (if the answer was a bare integer already, this is a no-op; if it was `"1 project"` or `"**1**"`, this fixes it). **+1 to +2** across the 104-task benchmark on strict-numeric-format tasks. Honest conservative estimate: **+1 task**.

**Risks:**
- Very low. The addition is scoped to tasks that explicitly demand a numeric-only answer and uses the exact phrasing from benchmark tasks as a trigger ("answer with a number only").
- One minor risk: the agent might strip a decimal point or currency unit on a task that legitimately expects "$1,234.56" — mitigated by keeping the existing NUMERIC AND MONETARY DISCIPLINE block intact (line 11) which already says "Transcribe currencies and amounts exactly — no rounding unless the task asks to round, no unit conversion unless asked."
