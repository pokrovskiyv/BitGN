## Root cause hypothesis

**Exactly one hypothesis:**

The `search.md` prompt fragment tells the agent to call `context()` early for "next/upcoming" lookups (line 15) but this guidance is buried inside a DATE/UPCOMING LOOKUPS paragraph as one bullet among three and without a hard "MUST" or "FIRST" imperative. Meanwhile, the LOOKUP DISCIPLINE block above it strongly emphasizes "identify the canonical directory first, then read only the candidate files needed for the answer". The agent read the latter as a mandate, walked every single file in the canonical cast/ directory exhaustively, and skipped the date-anchoring context() call entirely — because the fragment never establishes context() as a hard precondition for comparative date tasks. The budget-24 strategy was sized for a targeted lookup, not a full-directory walk, so the sequential read pattern guaranteed overflow.

**Evidence chain:**
1. No `context()` call in any of the 28 steps (verifier explicitly notes: "Without an explicit current date provided in the task") — direct evidence the agent never grounded against today.
2. 22 sequential `read(/10_entities/cast/*.md)` calls (steps 2–23) with no early termination after the 5th birthday-bearing file. This is the opposite of `search.md` line 10 ("read only the candidate files needed for the answer") and line 17 ("Avoid procedural wandering once you have the canonical records").
3. `strategy.py` sets `max_steps=24` for `search` — appropriate for a targeted lookup, inappropriate for a full-directory walk. The classification is correct (`_READ_ONLY_DATE_LOOKUP_SIGNALS` routes this branch deliberately at `classify.py` 181–189 to avoid escalating to `multi_step`/`analysis` budgets) but the prompt does not enforce the tight-budget behavior the classifier promises.
4. Root, not symptom: if the agent had called `context()` at step 1 and used a `list`-then-`grep`-for-`birthday` strategy, the entire computation fits in ≤10 steps. The missing gate is a hard ordering requirement in the prompt.

## Fix proposal (narrow GREEN zone only)

**Selected fix class:** `prompt_fragment`

**Target file:** `pac1-py/workspace/prompts/fragments/search.md`

**Exact change:**
```diff
 DATE / UPCOMING LOOKUPS:
-- For "next", "upcoming", or date-comparison lookups, call `context()` early so you compare against the current date instead of guessing.
-- For people/entity date lookups, list the canonical entity directory first, then read the candidate entity files and compute the answer from those records.
-- These tasks are usually read-only lookups, not workflows. Avoid procedural wandering once you have the canonical records.
+- For "next", "upcoming", "coming up", or any date-comparison lookup: **MUST call `context()` as step 1** before any list/read. Without the current date you cannot compute "next" rigorously. This is a hard precondition, not a suggestion.
+- After `context()`, use `search` with a field-name pattern (e.g. `birthday:`, `dob:`, `anniversary:`) against the canonical entity directory to extract ONLY the candidate records. Do NOT read every file in the directory sequentially.
+- Show your work in the final completion message: list all candidates with their dates, the reference date, and the computed "next" winner(s). If two or more share the soonest date, list them all sorted alphabetically.
+- These tasks are usually read-only lookups, not workflows. Avoid procedural wandering once you have the canonical records. Budget is tight (typically ≤15 tool calls for ≤25 entities).
```

**Rationale:** The current wording is passive ("call … early"). The fix promotes `context()` to a **hard step-1 precondition** for any comparative date lookup, explicitly lists the trigger phrases ("next", "upcoming", "coming up"), and replaces the implicit "read all candidate files" pattern with a `search`-based extraction that scales linearly in matches, not files. The "show your work" clause directly addresses the verifier's three complaints (no work shown, no tie-check, no verification). The budget hint inside the prompt teaches the model to self-regulate before hitting the runtime cap.

**Generalizability:** `MEDIUM`
- This pattern (read-only comparative date lookup over an entity directory) is exactly what the `_READ_ONLY_DATE_LOOKUP_SIGNALS` regex was added for in `classify.py`. It fires on tasks matching "next/upcoming/coming up next ... birthday/anniversary/renewal/date". Rough estimate from the 104-task benchmark: 3–6 tasks share this shape (renewal dates, anniversaries, next meeting, next maintenance window). Also catches the generic "exhaustive sequential directory walk" anti-pattern that may recur in other single-value lookups when the canonical directory has >10 files.
- Cannot claim HIGH without a broader scan — the `context()`-as-precondition rule only helps tasks where today's date is load-bearing, and the search-vs-read discipline only helps when the canonical directory is bigger than the step budget.

**Zone:** `GREEN` — prompt-fragment edit, no Python change, no effect on classify.py/strategy.py budgets or security paths. The `context()` requirement strictly adds work, so it cannot cause a regression on tasks that don't need today's date (it just adds one tool call). The search-discipline tightening can only reduce, not increase, the tool-call count on exhaustive walks.

**Expected impact:** +1 on t037 (budget overflow → fits in budget, agent produces computed answer with tie-check, likely OUTCOME_OK). Potentially +1 to +2 on similar comparative-date lookups that currently risk the same sequential-walk trap. Honest conservative estimate: **+1 to +2 tasks**.

**Risks:** Minor — forcing `context()` as step 1 on lookups that happen to have date keywords in them costs one extra tool call for tasks that would have worked without it. Since the trigger regex is narrow (must match "next/upcoming/coming up next" AND "birthday/anniversary/renewal/date"), collateral exposure is small. Second minor risk: the search-over-read pivot may miss birthdays in files where the field is not labeled `birthday:` — mitigated by keeping `read` as the fallback after `search` returns candidates.
