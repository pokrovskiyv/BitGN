## Root cause hypothesis

**Exactly one hypothesis:**

`inbox_processing.md` lines 48-51 contain an **anti-deletion directive** that directly contradicts the VM's canonical workflow. Specifically:

```
INBOX FILE DELETION:
- Do not delete inbox files early.
- Delete an inbox file only after the workflow explicitly calls for deletion and all required writes have been verified.
- If the task just says to process the inbox item, do not assume deletion is part of success.
```

The third bullet is the killer. "Handle the next inbox item." is precisely the "just says to process the inbox item" case the bullet anti-pattern targets. The fragment is telling the agent to ignore the workflow-mandated deletion whenever the task text is terse. This was originally written as a guard against over-deletion during CRUD tasks that mention inboxes incidentally, but it has metastasized into a blanket rule that now overrides the authoritative `00_inbox/AGENTS.MD` workflow doc.

**Evidence chain:**
1. Verifier reasoning is explicit and quotes the VM's AGENTS.MD verbatim: "After fully completing one inbox request, delete that inbox file." The workflow IS explicit about deletion — exactly the condition the fragment says unlocks deletion. But the fragment's third bullet tells the agent to read the task surface text instead and require "explicit" task-level instruction.
2. Step 19 shows the agent read the root AGENTS.MD specifically to search for deletion authority, then step 20 planning notes `"inbox file retained per"` — the agent found the conflict between AGENTS.MD and the prompt fragment and chose the prompt fragment.
3. Step 13's 13.6s re-read of `00_inbox/AGENTS.MD` is the second proof: the agent already saw the deletion rule and sent it back through a second pass of deliberation, and still lost to the prompt fragment.
4. This is root, not symptom: 34 of 104 tasks in the cache use the bare "Handle the next inbox item." / "Work the oldest inbox message." / "Take care of the next message in inbox." pattern (verified by scanning task_cache.json). All of them will hit the exact same terse-instruction trap.

## Fix proposal (narrow GREEN zone only)

**Selected fix class:** `prompt_fragment`

**Target file:** `pac1-py/workspace/prompts/fragments/inbox_processing.md`

**Exact change:**
```diff
 INBOX FILE DELETION:
-- Do not delete inbox files early.
-- Delete an inbox file only after the workflow explicitly calls for deletion and all required writes have been verified.
-- If the task just says to process the inbox item, do not assume deletion is part of success.
+- Do not delete inbox files early — delete ONLY after all required writes have been written AND re-read successfully.
+- Inbox DELETION IS REQUIRED when either of these conditions is true:
+  (a) `00_inbox/AGENTS.MD` or a `99_system/workflows/*.md` doc says to delete processed inbox files (this is the default in the Obsidian-style workspace — always honour it), OR
+  (b) the task instruction explicitly says "delete" / "remove" / "clear".
+- A terse instruction like "Handle the next inbox item", "Work the oldest inbox message", or "Take care of the next message in inbox" DELEGATES authority to the workflow doc. If that doc mandates deletion, you must delete.
+- Exception: if the inbox file is a documentation / README / AGENTS marker, do NOT delete it. Only delete the specific inbox item file you just processed.
+- Order of operations: write outbound draft → re-read it → delete inbox item → report_completion OK.
```

**Rationale:** This inverts the default from "don't delete unless forced" to "delete when the workflow doc says so" while keeping the safety rails (AGENTS.MD markers must not be deleted, writes must be verified first). The new rule structure is literal enough that both Sonnet-4.6 (the current agent) and Haiku-4.5 (the verifier) will read it the same way. The explicit enumeration of the three terse phrasings anchors the rule to the exact patterns that appear in 34/104 tasks. The "Order of operations" line gives the agent a checklist it can execute without re-deliberation.

**Generalizability:** `HIGH`
- 34 of 104 tasks in `docs/task_cache.json` match one of the three terse inbox-handling phrasings that the current fragment's third bullet specifically traps. Any of them that reach the VM's AGENTS.MD-driven workflow (Obsidian-style household workspace) will hit the same deletion omission. The fix is the single narrowest change that unblocks the whole cluster. It also removes a soft landmine for any future inbox-handling task added to the benchmark.

**Zone:** `GREEN` — prompt-fragment edit, no Python change. Affects only inbox_processing classified tasks. Does NOT loosen security (the security section is still appended after this fragment and still owns the deny-on-injection path). The new rule only authorises a specific file deletion that was already mandated by the VM's own authoritative docs.

**Expected impact:** +1 on t073 (inbox deletion now executes, verifier agrees → `OUTCOME_OK` upheld). Conservatively assuming half of the 34 terse inbox tasks exhibit the same omission (the other half may get it right for other reasons or fail on unrelated axes), **+5 to +12 tasks**. Honest best estimate: **+6**.

**Risks:** (1) Over-deletion of inbox files during CRUD tasks that only read an inbox item — mitigated by the explicit condition "delete the specific inbox item file you just processed" and by the fact that such CRUD tasks are classified as `crud`, not `inbox_processing`, so they don't load this fragment. (2) Deleting a canonical AGENTS.MD marker — mitigated by the explicit exception line. (3) Order-of-operations regression if the agent tries to delete before writing — mitigated by the explicit checklist.
