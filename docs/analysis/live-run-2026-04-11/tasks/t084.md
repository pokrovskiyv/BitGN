The label `language_handling` is the broader bucket, but the specific mechanism is the classifier.

## Root cause hypothesis

**Exactly one hypothesis:**

`pac1-py/classify.py` uses English-only `re.IGNORECASE` keyword patterns for every signal (`_SEARCH_SIGNALS`, `_LOOKUP_SIGNALS`, `_ANALYSIS_SIGNALS`, `_WRITE_SIGNALS`, `_QUESTIONISH_LOOKUP_SIGNALS`, etc.). The benchmark contains at least 10 non-English tasks (3 German `t009`/`t059`/`t084`, 7 CJK — verified by scanning `docs/task_cache.json`): every single one falls through to the default `crud` branch on line 236. This means:

1. They all load `crud.md` (6 lines, write/read-back focused) instead of the semantically correct fragment (`analysis.md`, `search.md`, `inbox_processing.md`).
2. They all get `max_steps=15` (or 20 with delete), regardless of whether the task is a one-shot lookup or a 25-step analysis.
3. The model is forced to infer discipline from the system prompt alone, without the task-specific guardrails.

**Evidence chain:**
1. **Regex replay** (verified): The instruction `"Wie viel Geld haben wir seit Beginn von December 2025 mit der Servicezeile 'checklist  rewrite and rollout pack' verdient? Antworte nur mit einer Zahl."` returns `None` from every signal regex in `classify.py`. There is no English word present except the literal service-line name and the date, neither of which is in any signal pattern. Verified via direct `re.search` replay.
2. **Correlated non-English zero-scores** (verified via `task_cache.json` scan): `t009` (Wie viel Geld Apr 2026): score 0, step_count 5. `t034` (Chinese 从December 2025开始...多少钱): score 0, step_count 4. `t049` (mixed English+Chinese invoice lookup 深圳市海云电子): score 0, step_count 4. `t059` (Wie viel Geld March 2026): score 0, step_count 4. `t084` (this task): score 0, step_count 6. All "how much" numerical lookups. All short trajectories. All classified as `crud`.
3. **Mechanism is deterministic, not probabilistic:** a classifier that only matches English words cannot recognize any non-English question word. It is not a case of "sometimes misclassifies" — it is a case of "never classifies correctly."
4. **Not a prompt issue:** `analysis.md` already contains the exact discipline needed ("cite the source file AND the row or field containing each input value", "read ALL relevant rows first"). The prompt is correct; the routing is broken.

## Fix proposal (narrow GREEN zone only)

**Selected fix class:** `classify_rule`

**Target file:** `pac1-py/classify.py`

**Exact change (illustrative, not to be applied — analysis-only task):**

```diff
 _SEARCH_SIGNALS = re.compile(
     r"\b(find|search|locate|look\s+for|where\s+is|which\s+files?|what(?:'s|\s+is)|"
-    r"which\b|who\s+is|who\s+are|when\s+is|can\s+you\s+tell\s+me)\b",
+    r"which\b|who\s+is|who\s+are|when\s+is|can\s+you\s+tell\s+me|"
+    # German
+    r"wo\s+ist|welche\s+datei|was\s+ist|wer\s+ist|wann\s+ist|"
+    # CJK question particles (non-word-boundary, broadly matched)
+    r")\b|什么|哪个|谁|何处|什么时候|(?:です|ます)か\??",
     re.IGNORECASE,
 )
 _ANALYSIS_SIGNALS = re.compile(
     r"\b(analyze|summarize|compare|count|list\s+all|report|describe|explain|"
-    r"how\s+many)\b",
+    r"how\s+many|how\s+much|wie\s+viel(?:e)?|wieviel|"
+    r"zusammenfass|vergleich|zähl|auflist|beschreib|erklär)\b|"
+    r"多少|总计|汇总|计算|比较|描述|解释|どのくらい|いくら|合計",
     re.IGNORECASE,
 )
 _QUESTIONISH_LOOKUP_SIGNALS = re.compile(
     r"^\s*(?:what(?:'s|\s+is)|which|who|where|when|can\s+you\s+tell\s+me|"
-    r")\b",
+    r"wie(?:\s+viel(?:e)?)?|was|welche|wer|wo|wann|wieviel)\b|"
+    r"^\s*(?:多少|哪个|谁|何|いくら|どの)",
     re.IGNORECASE,
 )
```

For t084 specifically, the load-bearing signal is `_ANALYSIS_SIGNALS` gaining `wie\s+viel` / `wieviel` / `how\s+much` / `多少` / `いくら`. Once matched, `_ANALYSIS_SIGNALS` flips `has_analysis=True` and the existing branch at line 203 (`if has_analysis and not has_write`) routes the task to `analysis` with `analysis.md` and `max_steps=25`.

**Rationale:** This fix is minimal (adds multilingual keywords to three existing regexes), it is in the `classify_rule` target which is explicitly GREEN, and it directly addresses the root cause without touching any prompt, strategy table, or runtime code. The multilingual tokens are narrow — only question words and aggregate verbs — so they cannot reclassify an English task. The existing English rules are unchanged.

**Generalizability:** `HIGH`

Exact evidence from the benchmark — five tasks (t009, t034, t059, t084, and arguably t049 which is a mixed Chinese-English numerical lookup) are structurally identical "how much / how many, from service line X, since date Y" queries, all of which currently fall through to `crud`. Two more Chinese tasks are `inbox_processing` queries (`处理收件箱中的下一条消息` — "process the next inbox message") that ALSO fall through to `crud` because `process` matches English but `处理` does not, losing the 32-step inbox_processing budget and fragment. Three Japanese inbox tasks (`次の受信トレイ項目を処理してください`) follow the same pattern. Total impact surface: **≥10 tasks** across the 147-task cache (≈7%). H threshold is "5+ similar tasks" — this clears it.

**Zone:** `GREEN` — `classify_rule` edit, no Python logic change (only pattern additions), no effect on security paths (`_compute_threat_level` and `security_test` branch are untouched), no effect on English classification.

**Expected impact:** Lower bound +1 on t084 (routes to `analysis`, agent reads all invoices, applies NUMERIC AND MONETARY DISCIPLINE, arrives at the correct sum). Middle estimate +3 to +5 (also rescues t009, t034, t059 on the same pattern, possibly t049). Upper bound +8 if the inbox-processing CJK tasks ALSO benefit (they would need separate `_INBOX_PROCESSING_SIGNALS` multilingual expansion, but that is the same GREEN target). Honest conservative estimate: **+3 to +5 tasks.**

**Risks:**
- **False-positive reclassification of English tasks:** zero — the multilingual tokens are non-Latin or German-specific, they do not collide with any English word in the benchmark.
- **Regex performance:** negligible — pattern size grows ~30 characters, still compiled once at import.
- **CJK character-class `\b` boundary:** Python `re` word boundaries do not align with CJK characters. The fix uses raw character-literal alternation (`多少`, `いくら`) outside the `\b...\b` group, so matches work. Verified this is the conventional approach.
- **German umlauts:** `zähl`, `erklär`, `vergleich` are matched case-insensitive with default Unicode flag; Python `re` handles UTF-8 cleanly. No extra flag needed.
- **Unintended `analysis` routing for a German CRUD task:** possible if a German task says "write a summary" — the word `zusammenfass` would match `_ANALYSIS_SIGNALS`. Mitigated by the existing `has_analysis and not has_write` gate at line 203 — if the task also has a German write verb (which would need to be added to `_WRITE_SIGNALS`), the gate keeps it in `multi_step`/`crud`. Ordering of rules is preserved.

A narrower scoped alternative: add only `wie\s+viel|wieviel|多少|いくら` to `_ANALYSIS_SIGNALS`, ignoring question-word reclassification and inbox CJK. That alone rescues t009/t034/t059/t084. This would drop generalizability to MEDIUM but keep the risk near zero. I still recommend the fuller change because the ORM cost is identical.

**AMBER note (no diff):** a complementary fix would be to add a "guess the language" preprocessing step in `classify.py` that translates non-English task text to English via the existing LLM backend before regex matching. This is AMBER because it adds a latency+cost hop and an LLM dependency inside a pure-regex classifier, violating the "rule-based classification for speed (microseconds)" contract in the file's docstring. Mentioned for completeness but not proposed.
