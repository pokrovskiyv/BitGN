## Root cause hypothesis

**Exactly one hypothesis:**

`inbox_processing.md` lines 48–52 (the "INBOX FILE DELETION" block) unconditionally instruct the agent to NOT delete inbox files unless "the workflow explicitly calls for deletion". This block was added defensively to stop premature deletion, but it does NOT mention the authoritative route: `00_inbox/AGENTS.MD` itself counts as the workflow document that can mandate deletion. When `00_inbox/AGENTS.MD` says *"After fully completing one inbox request, delete that inbox file"* (which is what the verifier quoted), the fragment's blanket ban wins in the agent's head because it is bolder and more recent in the system prompt composition (static prompt, right above `outcomes.md` + `reasoning.md`).

**Evidence chain:**
1. Agent read `00_inbox/AGENTS.MD` at step 14 — it knew the ground-truth rule before the write.
2. Agent still wrote the outbox draft at step 15 AND refused to delete, with the reasoning verbatim from the fragment: "task instruction did not explicitly request deletion". No other source in the prompt or the workspace contains this exact phrase.
3. Step 20 (18.8s of thinking) is the agent looking for a "v2 update" workflow to break the conflict between AGENTS.MD and the fragment — it could not, because `inbox-processing-v2-update.md` did not override the fragment.
4. The verifier confirms both halves independently: the write was correct, the deletion was required, and the rule lives in `00_inbox/AGENTS.MD`.
5. Root, not symptom: the classifier and budget were correct (21 < 32, inbox_processing route chosen). The write was correct. The only breakdown is the deletion gate, and that gate lives entirely in the fragment.

## Fix proposal (narrow GREEN zone only)

**Selected fix class:** `prompt_fragment`

**Target file:** `pac1-py/workspace/prompts/fragments/inbox_processing.md`

**Exact change:**
```diff
 INBOX FILE DELETION:
-- Do not delete inbox files early.
-- Delete an inbox file only after the workflow explicitly calls for deletion and all required writes have been verified.
-- If the task just says to process the inbox item, do not assume deletion is part of success.
+- Do not delete inbox files early — delete ONLY after all required writes are done and read-verified.
+- `00_inbox/AGENTS.MD` is a workflow-authority document. If it mandates deletion after completion (e.g., "delete that inbox file" / "remove the processed item"), you MUST delete the processed inbox file as the final action.
+- Other authoritative mandates: any `/99_system/workflows/*.md` that the inbox-processing route points at, and any explicit `delete` verb in the task text itself.
+- If neither AGENTS.MD, the controlling workflow doc, nor the task text mandates deletion, do NOT delete. When in doubt read `00_inbox/AGENTS.MD` first and follow it literally.
+- Ordering is always: (1) write the outbound artifact, (2) read-verify the write, (3) delete the inbox source IF mandated.
```

**Rationale:** The fragment currently treats "no explicit task-level request" as sufficient reason to skip deletion, which contradicts how the benchmark workspace actually encodes authority. `00_inbox/AGENTS.MD` is a stable, explicitly-named ground-truth source in the Obsidian-style workspace, and the fragment already instructs the agent to read it (line 14 of the fragment: *"If the workspace has `00_inbox/AGENTS.MD`, read it before touching inbox items"*). The fix closes the loop: read AGENTS.MD, honor AGENTS.MD, including the deletion clause. It preserves the core guard against premature deletion (still "not early", still "after read-verified writes") and the explicit ordering, so tasks where AGENTS.MD says nothing about deletion remain safe.

**Generalizability:** `MEDIUM` (H=5+ / M=2–4 / L=1)
- Any "Handle / process the next inbox item" task in the Obsidian-style workspace will hit the same gate if `00_inbox/AGENTS.MD` mandates deletion. Looking at the classifier, this route triggers on any task text combining a process-like verb ("handle", "process", "triage", "clear", "work through", "go through", "take care of") with an inbox/mailbox object, AND on the narrower explicit `_INBOX_PROCESSING_SIGNALS` regex. In the 104-task benchmark, inbox-handling tasks are a recurring family. Conservative estimate: 2–4 tasks benefit directly, plus unknown future tasks that re-use the same AGENTS.MD clause. HIGH is not honest without an offline scan of every AGENTS.MD in the task corpus — hence MEDIUM.

**Zone:** `GREEN` — prompt-fragment edit, no Python change, no classifier change, no budget change. Security posture unaffected (still hardened for inbox_processing). The fix only narrows one misalignment between fragment text and workspace ground truth.

**Expected impact:** +1 on t096 (`OUTCOME_OK` accepted instead of verifier-flipped to CLARIFICATION). Plausible +1 to +2 on other "Handle/Process the next inbox item" family tasks where the write was correct but deletion was skipped for the same verbatim reason. Honest conservative estimate: **+1 to +2 tasks**.

**Risks:**
- **Over-deletion risk** on inbox items where the task is read-only triage (e.g., "Summarize the next inbox item"). Mitigated by keeping the "do NOT delete if nothing mandates it" clause and by the task-type fragment only being loaded for `inbox_processing` classification (read-only triage classifies to `analysis` or `search` and does not load this fragment).
- **Conflict risk** if `00_inbox/AGENTS.MD` changes between runs to say "never delete" — mitigated because the fix delegates to AGENTS.MD, so any future wording change is honored automatically.
- **No security impact** — deletion of an already-processed inbox file after a verified write cannot leak data or bypass trust checks. The existing `RiskLevel.HIGH` gate on `delete` still applies (blocks-and-reconfirms), so the agent must still explicitly commit to the delete.
