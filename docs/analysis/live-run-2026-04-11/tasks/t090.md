## Root cause hypothesis

**Exactly one hypothesis:**

`verify.py::pre_completion_gate` at lines 415–424 enforces an inbox post-condition that only holds for the `outbox-send / reminders-create` task family, not for record-keeping workflows. The rule reads: "if `inbox_like` and `outcome == OUTCOME_OK` and `tracker._writes` has no path containing `outbox/` and no path containing `reminders/` and `tracker._deletes` is empty → HOLD: 'perform a write or delete … Read outbox/README.MD and outbox/seq.json, then write the outbox file'". For an ocr-records workflow the valid destination is `50_finance/purchases/*.md` (finance frontmatter application), and the agent's writes land there. The gate treats those writes as if they did not exist, rejects the OK, and the agent loses turns trying to reconcile a HOLD it cannot actually satisfy without violating the task. The gate's failure mode is task-family bias: it was designed for "outbox send" inbox tasks (where the inbox message says "write me a reply and send it") but it fires on every inbox task regardless of workflow.

**Evidence chain:**
1. `verify.py` lines 415–424 literally check only `outbox/`, `reminders/`, and `_deletes`. A write to `50_finance/purchases/2025_12_21__*.md` matches none of these despite being the canonical workflow destination named by `/99_system/workflows/ocr-records.md`.
2. Four tasks in the live run share the exact same 15-step trajectory shape and `verifier_verdict: null` signature: **t022, t040, t065, t090**. t022 ends on a `write(/60_outbox/drafts/reply-oldest-helios-invoice.md)` — an outbox reply — so *its* workflow does match the gate, but the agent still fails (different sub-cause). t040, t065, t090 all end with a `read` of a finance file or `read(/60_outbox/outbox/README.MD)` — they are stuck in the HOLD retry loop. The task cache shows 13 total "Work the oldest inbox message" tasks, all scoring 0.0 in the live run.
3. Step 14 is missing from `metrics.steps`. The only code path in `agent_loop.py` that increments the step counter without appending to `steps_detail` is `continue` after a pre-dispatch rejection (gate HOLD, HOLD `search("")`, inbox pre-write checkpoint, unverified-write HOLD, or verifier disagree). Of those, `pre_completion_gate` is the only one that fires specifically on a `report_completion` attempt.
4. The `inbox_processing.md` fragment (lines 3–19) explicitly authorizes writing to "workflow-approved destination" — there is no textual rule that all inbox tasks must write to outbox. The prompt and the Python gate disagree.
5. The gate's retry cap is `completion_gate_count < 2` (`agent_loop.py:359`). After the 2nd rejection the gate stops firing, but by then the agent is thoroughly confused and would need to retry completion on step 16+. `metrics.step_count = 15` implies the loop exited before a third completion attempt — most consistent with the `job is None` LLM-parse break after the gate spam polluted the conversation context.

## Fix proposal (narrow GREEN zone only)

**Selected fix class:** *none — best fix is AMBER*

**Target file (AMBER, no diff):** `pac1-py/verify.py`, function `pre_completion_gate`, lines 415–424.

**What the AMBER fix would look like (conceptually, not written as code in the GREEN zone):** The current rule compares write paths only to `outbox/` and `reminders/`. It should instead accept any write whose parent directory matches a workflow-declared destination surfaced during the run — e.g., paths the agent *read under `/99_system/workflows/*.md` as write targets*, or, more simply, any write outside `inbox/` itself. A lighter variant: drop the "no outbox → HOLD" rule entirely and rely on the verifier second-opinion for inbox-task OK decisions. That matches how the gate treats non-inbox tasks and removes the false positive without weakening any security check (the security paths are rule 3 in `outcomes.md`, evaluated before OK is even considered).

**GREEN-zone fallback (smaller and honestly weaker):** Edit `pac1-py/workspace/prompts/fragments/inbox_processing.md` to add a defensive paragraph that helps the agent *survive* the gate rather than remove it:

```diff
 INBOX FILE DELETION:
 - Do not delete inbox files early.
 - Delete an inbox file only after the workflow explicitly calls for deletion and all required writes have been verified.
 - If the task just says to process the inbox item, do not assume deletion is part of success.
+
+COMPLETION DISCIPLINE (critical for record-keeping workflows):
+- When the controlling workflow routes output to a non-outbox destination (e.g., `50_finance/`, `10_entities/`, `40_projects/`), that destination IS the valid completion target. You do NOT need to also write to `60_outbox/` or `reminders/`.
+- If a completion gate rejects your OUTCOME_OK with a message about "read outbox/README.MD and outbox/seq.json", and your workflow does NOT require an outbound message, RE-SUBMIT the same OUTCOME_OK on your next turn with an explicit one-line justification in `message`: "Workflow routes to <destination>; no outbox write required." The gate retry cap is 2 — your second attempt will dispatch.
+- Do NOT start reading `60_outbox/` files just because a gate cited them. That wastes steps and does not change the gate's decision — the gate only counts writes, not reads.
+- Your completion message should name the workflow you followed and list each file you touched.
```

**Rationale:** The GREEN-zone fallback does not cure the bug — it teaches the agent to *survive* the gate by re-submitting the same OK. Since `completion_gate_count < 2`, the second attempt will dispatch regardless of gate logic. The fragment edit costs no Python change and no security impact (threats are evaluated in rule 3, before OK is considered). It is strictly weaker than the AMBER fix because it relies on the agent correctly recognising the HOLD pattern, which is a behaviour Sonnet-4.6 might still fumble under the verifier/stagnation pressure of a long trajectory.

**Generalizability:** `HIGH`
- The live run contains **13 tasks** with the exact instruction "Work the oldest inbox message", and the task cache shows the same workflow-mismatched-gate signature on at least four of them (t040, t065, t072, t090). The ocr-records workflow is one of at least two inbox workflows in `/99_system/workflows/` that route to non-outbox destinations; a similar pattern likely affects any `10_entities/` update workflow, any `40_projects/` queue-up workflow (see t092), and any finance-record-ingest workflow. Conservative lower bound on the affected task count: 5+ tasks in this run. Upper bound: all 13 "oldest inbox" tasks plus several "handle the next inbox item" tasks that route to record-keeping destinations.

**Zone:** `AMBER` for the real fix (Python in `verify.py`). `GREEN` for the fragment fallback.

**Expected impact:**
- AMBER fix (Python gate loosening): +1 on t090, with likely +3 to +6 on other non-outbox inbox workflows in this run. The gate removal also removes a known false-positive source for every future inbox task that routes to a non-outbox destination.
- GREEN fallback (prompt fragment only): +0 to +1 on t090 — the agent may still fail to re-emit OK if the first rejection triggers a context-derailing cascade. Honest estimate: marginal benefit without the Python fix.

**Risks:**
- **AMBER**: removing the outbox-write gate could mask a genuine missing-outbox failure on an inbox task whose workflow *does* require an outbox reply (e.g., t022's helios invoice reply). Mitigation: make the gate workflow-aware — accept any write outside `/00_inbox/` OR any read of a workflow doc in the same turn. Or: delegate the "is this OK valid?" decision to the second-opinion verifier (which is already mandatory for inbox_processing — see `second_opinion.py:70`).
- **GREEN**: the "RE-SUBMIT the same OUTCOME_OK" instruction could be read as a jailbreak pattern ("ignore gate"). Mitigation: phrase it as a workflow-specific recovery rule, not a general instruction to override gates; the security gate (outcome rule 3) is unaffected because it fires earlier than any OK path.
