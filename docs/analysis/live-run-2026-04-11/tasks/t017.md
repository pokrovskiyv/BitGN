## Root cause hypothesis

**Exactly one hypothesis:**

`classify.py` has no rule that recognizes "queue / queue up / queue for X" as a workflow-queueing signal. The `_INBOX_PROCESSING_SIGNALS` regex requires `"process inbox"`, `"from inbox"`, `"inbox queue"`, etc. — and the secondary path via `_PROCESS_LIKE_SIGNALS` + `_INBOX_OBJECT_SIGNALS` requires an explicit process verb (`process|triage|clear|handle|work through|go through|take care of`). "Queue up these docs for migration" satisfies neither. As a result the task routes to CRUD, which has no understanding of the `99_system/` workflow discipline and only 15 steps — not enough for the 6-step workflow-discovery prologue this task truly requires.

**Evidence chain:**
1. **The agent's own trace shows it wanted to be an inbox_processing task.** Step 1 immediately targets `99_system/`, step 2 opens a workflow doc, step 3 opens the schema — this is exactly the DEFAULT ROUTE prescribed in `inbox_processing.md` lines 11–14 ("`tree /99_system` to find the relevant workflow or schema… Read the specific workflow doc(s)… Read `/00_inbox/AGENTS.MD`"). The CRUD fragment gave zero hint to do this; the agent discovered it through the file system itself, wasting planning time.
2. **Budget math:** discovery prologue (≈6 steps) + locate (2) + re-read (2) + write-verify cycle (4) = 14 steps. That leaves 1 step for completion. Any slip (an extra `list` drift, a truncated write, an empty-pattern `find`) ejects `report_completion` out of the budget. The trace shows exactly that — step 15 is a drift `list 00_inbox`, not a completion.
3. **Classifier rule gap, not prompt gap:** The `inbox_processing.md` fragment already contains the right workflow guidance — it was simply not loaded because `classify.py` routed to `crud`. Fixing the prompt would be off-target; the fix is in the classification rule that selects which prompt to load.
4. **Queue is a first-class concept in the workspace:** `_INBOX_OBJECT_SIGNALS` already knows `queue` is an inbox-class object (line 86) — the only missing piece is the corresponding queueing-action verb in `_PROCESS_LIKE_SIGNALS` (or a standalone "queue up" rule).

## Fix proposal (narrow GREEN zone only)

**Selected fix class:** `classify_rule`

**Target file:** `pac1-py/classify.py`

**Exact change:**
```diff
 _PROCESS_LIKE_SIGNALS = re.compile(
-    r"\b(process|triage|clear|handle|work\s+through|go\s+through|take\s+care\s+of)\b",
+    r"\b(process|triage|clear|handle|work\s+through|go\s+through|take\s+care\s+of|"
+    r"queue\s+up|enqueue|queue\s+for)\b",
     re.IGNORECASE,
 )
```

**Rationale:** `_INBOX_OBJECT_SIGNALS` already recognizes `queue`, `backlog`, `pending requests`, etc. as inbox-class objects. The two-signal compound check at `classify.py` line 148 — `_PROCESS_LIKE_SIGNALS` AND `_INBOX_OBJECT_SIGNALS` — is the path for tasks that don't use literal "inbox processing" wording but are still workflow-driven queue operations. Adding `queue up|enqueue|queue for` to the process-verb regex closes the exact gap t017 fell through: the object (`queue` via `docs for migration`) is already recognized, but the action verb (`queue up`) wasn't. With this fix, the task routes to `inbox_processing`, loads `inbox_processing.md` (which contains the exact workflow-first discipline the agent reinvented from scratch), and gets a 32-step budget instead of 15. The agent would have spent its discovery-prologue steps guided rather than groping, and had ~20 steps left for the actual write-verify-complete cycle.

**Generalizability:** `MEDIUM`
- "Queue for migration / queue for processing / enqueue this" is a common pattern for any workflow-managed write task, and the `99_system/workflows/` directory in this workspace suggests multiple such workflows exist (migration, bulk-processing, queueing). Rough estimate: 1–3 of 104 tasks use "queue up" or "enqueue" phrasing; a broader class of "workflow-discipline" tasks with other non-standard verbs (`stage`, `flag`, `tag for`, `mark for`) may benefit from similar classifier additions but those are out of scope for this one-fix cycle. I don't want to widen the regex speculatively — conservative: this fix lands t017 and maybe 1–2 sibling tasks with identical wording.

**Zone:** `GREEN` — single regex-literal change in `classify.py`, no strategy change (the 32-step `inbox_processing` budget is already set in `_STRATEGY_TABLE`), no prompt change, no security path touched. The `_PROCESS_LIKE_SIGNALS` regex feeds only the compound `has_inbox_processing` branch, which is ordered above all other branches except `security_test` and the `has_read_only_date_lookup` branch — no collateral reroutes.

**Expected impact:** +1 on t017 (`budget_exhausted` → `OUTCOME_OK` via `inbox_processing` strategy, 32 steps). Potentially +1 on sibling tasks with identical "queue up" phrasing. Honest conservative estimate: **+1 task**, possibly **+2** if the benchmark has one more migration-flavored queue task.

**Risks:** Minor — a task like "queue up a meeting" or "enqueue a reminder" could now route to `inbox_processing` instead of `communication` or `crud`. Mitigations:
1. The `inbox_processing.md` fragment begins with "FIRST ORIENT TO THE ACTUAL WORKSPACE" and explicitly warns against assuming legacy layouts — a misrouted task would still do the right thing by reading the workspace first.
2. The 32-step budget is a ceiling, not a floor; a genuinely simple CRUD task misrouted to `inbox_processing` would finish in 5–8 steps and not hurt.
3. `queue up` and `enqueue` are workspace-layer verbs — they presuppose a queue exists. They don't overlap with calendar/reminder semantics.
