## Root cause hypothesis

**Exactly one hypothesis:**

`classify.py` routes this 4-file migration task to the `crud` default branch (15-step budget) because the instruction verb "Queue up" matches none of the specialized classification signals. The task is effectively an `inbox_processing`-style workflow (read workflow doc → orient → per-file read/write/verify loop → completion) across 4 items, which requires a 25–32 step budget. The fall-through to `crud` gives only 15 steps, which is mathematically insufficient for 4-file execution with mandatory read-after-write verification (minimum 16 steps, realistic 18–22).

**Evidence chain:**
1. Step log shows exactly 14 tool calls, indices 1–14, NO `report_completion` entry. `step_count=15` metric indicates the 15th turn was reserved but the runtime terminated before a tool dispatched. This is the budget-exhaustion fingerprint.
2. `classify_task()` output (verified locally via direct import): `task_type='crud', estimated_steps=10, requires_write=False`. Note that `requires_write=False` is itself wrong — the task clearly requires 4 writes — because `_WRITE_SIGNALS` does not include `queue`. This undercounts step needs.
3. `_STRATEGY_TABLE["crud"] = (15, "standard", True)` at `strategy.py` line 49 sets the hard ceiling. The strategy layer never had a chance to upgrade the budget because the classification came in as `crud` with no flags set.
4. The trajectory itself is competent — correct schema read, correct workflow read, correct landing on `30_knowledge/notes/`, correct frontmatter semantics — so neither prompt fragment content nor reasoning discipline is the bottleneck. Only the step ceiling is.
5. Root, not symptom: a `crud.md` fragment tweak would not help — the fragment content is fine for single-file ops, and there is no prompt text that can increase `max_steps`. Only the classify → strategy routing can raise the budget. The GREEN-zone fix is at the classifier layer where the mis-routing originates.

## Fix proposal (narrow GREEN zone only)

**Selected fix class:** `classify_rule`

**Target file:** `pac1-py/classify.py`

**Exact change:**
```diff
 _WRITE_SIGNALS = re.compile(
     r"\b(create|write|add|append|insert|update|set|change|rename|move|process|"
-    r"reschedule|capture|distill|schedule)\b",
+    r"reschedule|capture|distill|schedule|queue(?:\s+up)?|migrate|enqueue)\b",
     re.IGNORECASE,
 )
```
Plus a companion nudge in `_MULTI_STEP_SIGNALS` so that a comma-listed multi-item action is recognized as multi-step:
```diff
 _MULTI_STEP_SIGNALS = re.compile(
     r"\b(then|after\s+that|also|and\s+then|finally|first.*then|step\s+\d|"
-    r"next\s+(?:step|phase|task|action)|process|when\s+done|accordingly)\b",
+    r"next\s+(?:step|phase|task|action)|process|when\s+done|accordingly|"
+    r"queue\s+up\s+these|migrate\s+these|for\s+migration)\b",
     re.IGNORECASE,
 )
```

**Rationale:** The minimal first-order fix is teaching `_WRITE_SIGNALS` that `queue`, `queue up`, `migrate`, and `enqueue` are write verbs. This alone reclassifies the task as `crud` with `requires_write=True` (the estimated_steps jump to 10 stays in the crud branch though — still 15 max). The second nudge on `_MULTI_STEP_SIGNALS` is what actually rescues the task: the phrase "Queue up these docs for migration" is recognized as multi-step intent, which routes through the `has_multi_step and (has_write or has_search or has_analysis)` branch at line 192, producing `task_type='multi_step'`. With multi_step routing, `strategy.py` line 55 picks `("multi_step": (30, "standard", True))` — a 30-step budget, doubling the available budget and comfortably fitting the observed 16–20 step execution. The regex additions are narrow enough that they will not false-positive on unrelated CRUD tasks: `queue up these` is a distinctive 3-word phrase, `migrate these` and `for migration` are uncommon outside actual migration workflows.

**Generalizability:** `MEDIUM`
- The core pattern "multi-item workflow referring to a comma-separated list of files with a verb that classify.py doesn't recognize" is recurring but not pervasive. Likely-related tasks in the 104-item benchmark: any "queue / migrate / enroll / onboard these N docs" pattern. A fast grep of task_cache.json for "queue" or "migrate" as a leading verb would catch the similar cases. Honest estimate: 2–4 tasks share the exact "N files, no specialized verb" pathology. HIGH would require a broader audit of all ≤ step-budget failures, which is out of scope for this single-task post-mortem. The fix does NOT help a task that is a single-file rename or a single-file simple CRUD — it only rescues the multi-file workflows that currently fall through to the default 15-step crud branch.

**Zone:** `GREEN` — classify.py regex addition, no Python control-flow change, no new state, no security-posture change. Multi-step routing already exists and has been exercised on many tasks; the fix simply expands the set of instructions that reach it. There is no write-path or threat-detection interaction.

**Expected impact:** +1 on t067 (0.0 → 1.0 given a correct completion on path). Potentially +1 to +2 on similar multi-item migration/queue tasks in the benchmark. Honest conservative estimate: **+1 to +2 tasks**.

**Risks:** 
1. A single-file task with the word "queue" in the filename (e.g., "update queue-config.md") could now falsely trigger `_WRITE_SIGNALS` via the new `queue` token. Mitigation: the `queue(?:\s+up)?` variant is preferred over bare `queue` to reduce false positives; standalone `queue` still matches but that's already a write verb in practice ("queue a job" is a write-like action).
2. `_MULTI_STEP_SIGNALS` gaining `for migration` is narrow but could catch "notes for migration planning" — harmless since multi_step only fires when paired with a write/search/analysis signal, so a pure analysis task won't be mis-routed.
3. No interaction with security paths — multi_step posture is "standard", same as crud, so threat detection and outcomes.md behavior are unchanged.
