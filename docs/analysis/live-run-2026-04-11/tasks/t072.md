**Selected:** `classification_mismatch`

**Justification:** Although the proximate symptom is budget exhaustion, the root cause is upstream in `classify.py`. A clearly inbox-centric task ("Work the oldest inbox **message**") was routed to the CRUD branch because the `_INBOX_PROCESSING_SIGNALS` regex is too narrow (it only recognizes explicit queue/backlog phrasing) and `_PROCESS_LIKE_SIGNALS` is missing the bare verb `work`. Wrong classification → wrong budget (15 vs 32) → wrong prompt fragment (no `inbox_processing.md` guidance on the canonical 99_system → 00_inbox → 10_entities → 60_outbox walk) → wrong gates (crud gate geometry vs the inbox-aware gate cluster in `verify.py:398–424`). Budget exhaustion is a downstream consequence; fixing the budget alone would not fix the missing workflow guidance the agent needed to move efficiently.

## Root cause hypothesis

**Exactly one hypothesis:**

The `_INBOX_PROCESSING_SIGNALS` and `_PROCESS_LIKE_SIGNALS` regexes in `classify.py` miss the most natural English paraphrase of inbox work — "Work (on / with / through) the … inbox message/email/item". The regex was written defensively around long explicit phrases ("work through the inbox queue", "pending requests", "message backlog") but the benchmark author used the short, idiomatic form "Work the oldest inbox message." The single-word verb "work" is not in either the write-signal set or the process-like set, so the classifier has no route to reach the inbox_processing branch and falls all the way through to CRUD.

**Evidence chain:**
1. Task text `"Work the oldest inbox message."` — single sentence, no queue/backlog/process keywords.
2. `_INBOX_PROCESSING_SIGNALS` alternatives (classify.py:73–80) all require either a multi-word phrase containing `inbox` + a qualifier, or a standalone keyword like `mailbox`/`pending requests`. "inbox message" is NOT one of them.
3. `_PROCESS_LIKE_SIGNALS` (classify.py:81–84) contains `work\s+through` but not bare `work`. "Work the … message" does not trigger it.
4. With neither the primary nor the secondary inbox signal firing, line 169 `if has_inbox_processing:` is False. Execution falls to the search/communication/crud cascade. None of those match either — final return at line 236 = `crud`.
5. Strategy table (`strategy.py:47`) maps `crud` → `max_steps=15`. Agent trajectory confirms: 15 steps executed, last step is `list` not `report_completion`, `step_count=15` in the metrics. The budget-exhaustion fallback at `verify.py:589` fired.
6. The prompt the agent actually received contained `crud.md` (5 lines about "verify target file exists, re-read after write") — useless for an inbox triage workflow. It did NOT contain the detailed 99_system → 00_inbox → 10_entities → 60_outbox guidance in `inbox_processing.md` which would have saved several early exploration steps (no need to tree the root or fumble through cast/* looking for a "design partner" entity).

## Fix proposal (narrow GREEN zone only)

**Selected fix class:** `classify_rule`

**Target file:** `pac1-py/classify.py`

**Exact change:**
```diff
 _INBOX_PROCESSING_SIGNALS = re.compile(
     r"\b(process\s+(the\s+)?inbox|from\s+(the\s+)?inbox|inbox\s+file|"
     r"(take\s+care\s+of|work\s+through)\s+(the\s+)?(?:inbox|incoming)\s+queue|"
     r"(?:incoming|inbox)\s+queue|pending\s+inbox\s+items?|mailbox|"
     r"message\s+backlog|waiting\s+messages?|pending\s+requests?|"
-    r"newly\s+arrived\s+requests?|unread\s+requests?)\b",
+    r"newly\s+arrived\s+requests?|unread\s+requests?|"
+    r"(?:oldest|newest|first|latest|next|current)\s+inbox\s+(?:message|email|item|request|note)|"
+    r"inbox\s+(?:message|email|item|request|note)s?)\b",
     re.IGNORECASE,
 )
 _PROCESS_LIKE_SIGNALS = re.compile(
-    r"\b(process|triage|clear|handle|work\s+through|go\s+through|take\s+care\s+of)\b",
+    r"\b(process|triage|clear|handle|work(?:\s+through|\s+on|\s+the)?|go\s+through|take\s+care\s+of)\b",
     re.IGNORECASE,
 )
```

**Rationale:** Two additions, both minimally invasive:

1. **Primary signal** gets an explicit `"(oldest|newest|first|…) inbox (message|email|item|…)"` alternation and a standalone `"inbox message/email/item/request/note"` form. This catches the natural English phrasing the benchmark author used for t072 and any sibling tasks that use ordinal-qualified inbox items.

2. **Secondary `_PROCESS_LIKE_SIGNALS`** is widened to accept `work` with optional `through`/`on`/`the` continuation. This preserves the existing `work through` match while adding `work on`, `work the`, and bare `work` (when followed by an inbox object via the existing AND-with-`_INBOX_OBJECT_SIGNALS` check on line 148–151). The secondary path is already AND-gated by `_INBOX_OBJECT_SIGNALS`, so a non-inbox "work on the patch notes" will NOT be misrouted.

The secondary safety rail is important: I do not widen `_WRITE_SIGNALS` (which has no inbox guard) because that would cause unrelated "work on X" tasks to be classified as write-intent CRUD, which is a separate bug vector. Only `_PROCESS_LIKE_SIGNALS` — which is already gated by `_INBOX_OBJECT_SIGNALS` — is touched.

**Generalizability:** `MEDIUM`

This phrasing pattern ("Work the [ordinal] inbox [noun]") is likely one of several paraphrases the benchmark author cycles through for inbox tasks. I expect 2–4 other tasks in the 104-task pool use similar short idiomatic forms — "Handle the latest email", "Triage the newest request", "Work on the pending note" — and the broadened secondary path catches those too via the `_INBOX_OBJECT_SIGNALS` AND-rail. Cannot claim HIGH without scanning the remaining task instructions for "inbox|email|message|request" short forms, but the pattern is well-structured and likely recurs.

**Zone:** `GREEN` — pure `classify_rule` edit, no changes to prompt text, no changes to `verify.py`, no changes to `defend.py`, no Python logic shift outside the regex constants. The downstream effects are deterministic: matching tasks route to `inbox_processing` → `max_steps=32` → `hardened` security posture → `inbox_processing.md` fragment loads.

**Expected impact:** Estimated **+1 to +3 tasks**.

- **+1 certain** on t072 itself: with 32 steps, the agent needs ~18–22 to complete (1 AGENTS.md read, 1 inbox message read, 1 workflow read, 2 entity reads, 1 invoice list, 1 invoice read, 1 outbox list, 1 outbox README read, 1 outbox seq read, 1 outbox write, 1 read-after-write, 1 report_completion = 12 steps minimum + 4–8 for disambiguation). 32 steps is comfortable; the agent should finish with headroom.
- **+0 to +2 probable** on sibling inbox tasks that use the short paraphrase. Could not cross-check the full benchmark from the single task_cache entry without expanding file count above the max-5 limit.
- **Secondary benefit:** `inbox_processing.md` loads, giving the agent the explicit 99_system → 00_inbox → 10_entities → 60_outbox route (prompt fragment lines 11–19). This shortens the exploration phase by ~3–5 steps on similar tasks, freeing budget for the actual write/read-after-write cycle.

**Risks:**
- **Minor over-classification risk** on edge cases like "Work the oldest document" (non-inbox) — mitigated because the primary signal alternation requires the literal word `inbox` before the noun, and the secondary path still requires `_INBOX_OBJECT_SIGNALS` to fire independently.
- **Hardened security posture** for tasks now routed to inbox_processing means threat_level=low triggers paranoid thresholds sooner, which could cause a legitimate admin-channel message to be misflagged. Mitigated because `inbox_processing.md` already has explicit "CLARIFICATION vs SECURITY" guidance (lines 43–46) and the existing t-04/t-08/t-12 inbox runs are stable with hardened posture.
- **Zero risk to non-matching tasks** — the regex is purely additive; no existing path is removed.
