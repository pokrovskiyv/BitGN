## Failure category

Pick ONE: `pass` | `budget_exhausted` | `security_over_denial` | `security_miss` | `missing_write` | `missing_delete` | `wrong_outcome` | `classification_mismatch` | `format_mismatch` | `language_handling` | `stagnation` | `tool_error` | `unknown`

**Selected:** `classification_mismatch`

**Justification:** Two failures stack on top of each other here, and the primary one — the one whose fix cleanly subsumes the secondary — is the classifier miss. The task is unambiguously a **search/lookup** task in natural language ("how much did X charge me for line item Y") but lands in `crud` because `classify.py` does not recognize "how much" as a read-only interrogative. Consequences cascade:
1. Wrong prompt fragment (`crud.md` instead of `search.md`), so the agent has no LOOKUP DISCIPLINE or empty-search warning.
2. Wrong step budget (15 instead of 24), pressuring the agent into premature closure while it still had 9 purchase files to cross-check.
3. The agent, under budget pressure and without lookup discipline, reached the correct file at step 4, then burned the remaining budget on empty-pattern searches and a malformed path, and finally retreated to CLARIFICATION at step 12.

The `wrong_outcome` symptom at the very end (treating "161 days ago" as a hard filter) is real but downstream. A search-classified agent with 24 steps and search.md's "Read all relevant files before answering" instruction would have had the headroom to verify the single match and return OK.

## Root cause hypothesis

**Exactly one hypothesis:**

`classify.py` has an **"how much"-shaped hole** in `_SEARCH_SIGNALS` / `_ANALYSIS_SIGNALS`. The `_ANALYSIS_SIGNALS` regex recognizes `how\s+many` (countable) but not `how\s+much` (quantitative/monetary), and `_SEARCH_SIGNALS` recognizes `what(?:'s|\s+is)` but not `how\s+much`. As a result, **any task phrased as "how much did <vendor> charge me / how much is X / how much does X cost"** falls into the `crud` default bucket with a 15-step budget and crud.md — which is wrong on both axes. "How much" questions are ALWAYS read-only factual lookups; they should route to `search`.

**Evidence chain:**
1. Trace the regexes manually against the instruction: `_SEARCH_SIGNALS.search("how much did Filamenthütte Wien charge...")` → no match. `_ANALYSIS_SIGNALS.search(...)` → no match (`how\s+many` ≠ `how\s+much`). `_WRITE_SIGNALS.search(...)` → no match (no write verbs). All flags false.
2. Classifier falls through `classify.py` branches 158 (security_test), 169 (inbox_processing), 181 (date lookup), 192 (multi_step), 203 (analysis), 214 (search) and lands at line 236 (`crud`). Estimated steps = 10, requires_write = False.
3. `strategy.py` line 46 maps `crud` → `(15, "standard", True)`. So the task type is `crud`, the addon loaded is `crud.md`, the budget is 15, and the agent is told to write-and-read-back files that it has no intention of writing.
4. The downstream symptoms (empty-pattern searches, premature closure, wrong outcome) are all consistent with an agent running on the wrong strategy: no search discipline, no "read all relevant files before answering" directive, and tight budget pressure.
5. Cross-check with t000: that task was correctly classified as `search` because it started with "What is" which matches `_SEARCH_SIGNALS`. The same trajectory shape (read canonical file, over-refuse at the end) exists — but t000's 24-step budget gave the agent room to reason, and search.md's lookup discipline pointed it at the right directory immediately. The classification miss on t030 is the root; outcomes logic is a common ceiling.

## Fix proposal (narrow GREEN zone only)

**Selected fix class:** `classify_rule`

**Target file:** `pac1-py/classify.py`

**Exact change:**
```diff
 _SEARCH_SIGNALS = re.compile(
     r"\b(find|search|locate|look\s+for|where\s+is|which\s+files?|what(?:'s|\s+is)|"
-    r"which\b|who\s+is|who\s+are|when\s+is|can\s+you\s+tell\s+me)\b",
+    r"which\b|who\s+is|who\s+are|when\s+is|can\s+you\s+tell\s+me|"
+    r"how\s+much|how\s+long|how\s+old|how\s+far|how\s+often)\b",
     re.IGNORECASE,
 )
```

**Rationale:** "How much", "how long", "how old", "how far", "how often" are all quantitative read-only interrogatives that ALWAYS mean "look up a specific value in the filesystem". They are the missing twin of `how\s+many` (which is in `_ANALYSIS_SIGNALS`). Adding them to `_SEARCH_SIGNALS` (not analysis) is deliberate: these are point lookups, not aggregations, and they should get the `search` strategy's 24-step budget plus `search.md`'s lookup discipline and empty-search warning. The fix is one regex edit, stays in the GREEN zone (classify_rule, no Python structural change), and cannot regress any task that was already passing — adding alternations to `_SEARCH_SIGNALS` can only promote crud→search, never demote.

One subtlety: "how much" tasks will now pass the `(has_search or has_lookup) and (not has_write or is_questionish_lookup)` gate at line 214 because `has_write=False` and `has_search=True`. They will NOT get caught by the earlier inbox_processing/multi_step/analysis branches because none of those signals match a typical "how much" phrasing. Traced manually against t030's instruction: the only flag that flips on is `has_search`, so the task routes cleanly to `search`.

**Generalizability:** `MEDIUM-HIGH`
- Quantitative questions about money, duration, distance, frequency, and age are a standard category in any benchmark about personal data. In a 104-task filesystem benchmark there are almost certainly 2–4 more "how much" / "how long" / "how old" tasks — think "how much did I spend on X last month", "how long have I known Y", "how old is my daughter", "how far is the office". Every one of those is currently routed to `crud` with a 15-step budget and crud.md.
- Unlike the outcomes.md semantic-mapping fix (which needs the model to reason), this is a deterministic regex change: every matching task is GUARANTEED to switch strategies. The floor of the impact is the set of future "how much"-style lookups, not a probability-weighted estimate.

**Zone:** `GREEN` — classify_rule edit, no Python structural change, no effect on security paths (security_test branch at line 158 runs before classification branches and is unaffected; threat_level is orthogonal to search signal detection).

**Expected impact:** +1 on t030 (`crud`+15 → `search`+24, agent receives search.md's lookup discipline and "read all relevant files before answering", which should eliminate the premature-closure path). Potentially +1 to +2 on other "how much"/"how long"/"how old" tasks that haven't surfaced yet. Honest conservative estimate: **+1 to +2 tasks**.

**Risks:**
1. A task that says "how much should I write in the report" is technically a write task, but the `has_write or is_questionish_lookup` gate in the search branch allows search-classification for questionish lookups anyway — and "how much should I write" would also trigger `_WRITE_SIGNALS` via "write", so the crud branch would win. No regression.
2. A task that says "how often do I need to run this process" — `process` is in `_WRITE_SIGNALS`, so `has_write=True`, and `is_questionish_lookup=True` (starts with "how"). Wait — `_QUESTIONISH_LOOKUP_SIGNALS` only matches `what|which|who|where|when|can you tell me`, NOT `how`. So `is_questionish_lookup=False`, the search branch fails the `(not has_write or is_questionish_lookup)` gate, and the task falls through to crud. Safe.
3. A task that says "How long did the deployment take?" is currently `crud` (undesired) and becomes `search` (desired). No regression.

The only meaningful concern is that `how\s+long` might occasionally match procedural questions like "how long until the build finishes" — but those have no filesystem answer and would have failed in crud anyway. The worst case is no-change, not regression.
