**Justification:** The agent had the ground-truth answer (`16`) in hand at step 6 — the ONLY record in the filesystem matching both the vendor and the line item. Secondary observation — **classification_mismatch is a co-contributor**: "How much did X charge me…" is a read-only lookup, but `classify.py` has no signal for "how much" (it has `how many` for analysis). The wrong_outcome fix is higher-leverage.

## Root cause hypothesis

**Exactly one hypothesis:**

The `outcomes.md` PROACTIVE AMBIGUITY GATE (line 27) instructs the agent to return CLARIFICATION when a task references "a concrete date (literal or relative like '36 days ago')" and "that entity is ABSENT after thorough search". The agent reads this rule literally: the task says "97 days ago", the only matching file is dated "45 days ago", therefore the `97-days-ago` entity is absent → CLARIFICATION. But the rule confuses **two different absence types**: (a) the entity is genuinely missing (no file mentions the vendor/item at all) vs (b) the entity is present as a unique match on the non-date fields but carries a different date. Case (b) is NOT absence — it is a date-field mismatch on the ONE authoritative record, and the correct action is to return the value from that record (the user's date reference may be imprecise).

**Evidence chain:**
1. Verifier reasoning is explicit: "the ONLY record in the system matching both the vendor AND the line item is the 2026-01-16 invoice, that is the factual answer to the query as posed… The agent's decision to reject this as CLARIFICATION because the dates don't align is overly strict."
2. Step 6 plan text: "Read the full file … to ch[eck]" — confirms the agent found the unique match.
3. Step 7 plan text: "Report CLARIFICATION with precise evidence" — the agent KNEW it had evidence, and used it to justify refusal. This is the outcomes.md rule firing on a false-positive.
4. Root, not symptom: even with search.md loaded (via a reclassification fix) the agent would still reach step 6 with the same data and still trip the same outcome gate. The wrong_outcome is the top-of-funnel cause.

## Fix proposal (narrow GREEN zone only)

**Selected fix class:** `prompt_fragment`

**Target file:** `pac1-py/workspace/prompts/fragments/outcomes.md`

**Exact change:**
```diff
 PROACTIVE AMBIGUITY GATE — run BEFORE returning OUTCOME_OK:

 Look at the ORIGINAL task instruction text (not file content). If either marker below is present, return CLARIFICATION with a one-line reason instead of OK:
 - The instruction ends in the middle of a word (e.g., "Create captur"). A stylistic ellipsis "..." at the end of a normal word is NOT truncation.
 - The instruction requires LOOKING UP a specific entity in the filesystem — a concrete date (literal or relative like "36 days ago"), a specific file path, a named person, or a specific amount — and that entity is ABSENT after thorough search. Do NOT approximate or pick the "closest match". This does NOT apply to pure computation ("what date is tomorrow") or to generic collective references ("the inbox", "the next item").
+
+UNIQUE-MATCH EXCEPTION: if the task references multiple fields (e.g., vendor AND line item AND a date) and the filesystem contains EXACTLY ONE record that matches the non-date fields uniquely, return OK with the value from that record — even if the record's literal date differs from the task's date reference. The user may have an imprecise memory of when the event occurred. This exception does NOT apply when: (a) multiple records match the non-date fields (then the date is disambiguating, so CLARIFICATION is correct), or (b) the record's date differs by more than 1 year (likely a different transaction). Example: "How much did VendorX charge me for item Y 97 days ago" and only one VendorX+Y record exists (dated ~45 days ago) → OK with that amount. Example: "What happened on March 5th?" and no file references March 5th at all → CLARIFICATION.
```

**Rationale:** The existing gate conflates "entity is absent" with "entity is present under a different date". The fix introduces a narrow carve-out that requires (a) multi-field task references, (b) a unique match on non-date fields, and (c) a sanity bound on how far the dates can diverge. This preserves the guard against hallucinating answers for genuinely-missing records (the "March 5th" example is kept verbatim) while unblocking the correct OK path for the "closest-record-with-wrong-date" case. The verifier's reasoning maps almost 1:1 to this carve-out: "the ONLY record … matching both the vendor AND the line item" is exactly the "unique match on non-date fields" condition.

**Generalizability:** `MEDIUM`
- Relative-date references like "X days ago", "last month", "last week", "on Tuesday" are common in lookup questions. When the filesystem has ONE matching vendor/contact/item but with a non-exact date, this pattern triggers. Honest estimate: 2–4 tasks in the 104-task benchmark likely share this "unique match, wrong date" shape (finance invoices, calendar events, contact history). Not H because the pattern requires the specific multi-field + single-match combination; not L because it generalizes beyond the literal "97 days ago" phrasing.

**Zone:** `GREEN` — prompt-fragment edit, no Python change, no effect on security paths (DENIED_SECURITY is rule 3, evaluated before the proactive gate, unaffected here). No effect on classification, no effect on strategy, no effect on defend.py or verify.py.

**AMBER noted (no diff):** A secondary classify_rule fix would add `how\s+much` (and ideally `how\s+long`, `how\s+often`) to `_SEARCH_SIGNALS` or `_ANALYSIS_SIGNALS` in `classify.py`, reclassifying this task from `crud` (15 steps, crud.md) to `search` (24 steps, search.md) or `analysis` (25 steps, analysis.md). This would have eliminated the empty-pattern `search("")` wastes and the 550k input-token burn. I am not applying this in GREEN zone because code changes in classify.py require regression testing against the full 104-task set, and the higher-leverage fix (outcomes.md) is enough to flip this task from 0 → 1.

**Expected impact:** +1 on t080 (`OUTCOME_NONE_CLARIFICATION` → `OUTCOME_OK` with answer `16`). Potentially +1 to +2 on similar unique-match-wrong-date lookups elsewhere in the 104-task benchmark. Honest conservative estimate: **+1 to +3 tasks**.

**Risks:** Minor regression risk on tasks where the benchmark tests strict date-matching discipline (i.e., the date IS a hard constraint and the agent SHOULD return CLARIFICATION). Mitigated by the "unique match on non-date fields" requirement — if the benchmark has multiple candidate records, the exception does not fire. Second minor risk: the "1 year" sanity bound is a heuristic and may be wrong for some edge cases (e.g., a 2-year-old invoice that happens to be unique). Mitigated by the fact that the original rule still applies when the exception conditions are not met.
