## Root cause hypothesis

**Exactly one hypothesis:**

The `crud.md` prompt fragment does not contain an **enumeration discipline** rule for "delete ALL files matching X" tasks. It only addresses the single-file write-then-read case. For `crud_delete` tasks that use "every", "all", "each", or similar quantifiers, the agent must (1) enumerate ALL candidate files before deleting any, (2) read each candidate to confirm the literal phrase is present in the content, and (3) only then start deleting. Without that rule, the agent grabs the first hits from a single search and commits to a premature delete, missing files whose phrase is split across lines, appears only in a metadata field, or lives in a sibling folder the initial search didn't cover.

**Evidence chain:**
1. Four tasks with identical structure (`t006`, `t031`, `t056`, `t081`) all score 0.0 with the same 2-delete pattern. A single task could be attributed to a test artifact; four cannot.
2. `t031` step 1 uses `search("")` — empty pattern. The `search.md` rule forbidding empty search is NOT loaded for crud_delete tasks (see `strategy.py:83–90`: only the matching task_type's fragment is loaded into `addons`).
3. `t081` completes in 4 tool calls total (search + 2 deletes + report). It never re-verifies by reading any file before deleting. That is structurally incapable of confirming "every" match — the agent is trusting a single search return.
4. `crud.md` currently contains only four lines, all about single-file write-verify semantics. There is no rule for plural / "every" / "all" deletes.
5. `outcomes.md` and `verify.py::pre_completion_gate` cover `OUTCOME_OK`-only conditions but do not enforce enumeration completeness before permitting the first delete. `pre_completion_gate` checks `unconsulted_target_hints` only against paths mentioned in the task text — it cannot flag unconsulted files the task did not name explicitly.

## Fix proposal (narrow GREEN zone only)

**Selected fix class:** `prompt_fragment`

**Target file:** `pac1-py/workspace/prompts/fragments/crud.md`

**Exact change:**
```diff
 TASK TYPE: Simple CRUD operation.
 - Verify the target file exists (or doesn't) before writing.
 - A write response of "written: path (OK)" means SUCCESS — do NOT repeat the same write. Proceed to re-read for verification.
 - After writing, re-read the file to confirm the write succeeded.
 - Include the modified file in grounding_refs.
+
+DELETE-ALL / FIND-ALL DISCIPLINE (for tasks with "every", "all", "each", "any receipt containing", etc.):
+- First, enumerate the FULL candidate set. Use `search` with a concrete non-empty pattern derived from the task (never an empty pattern). If the phrase has word variants (singular/plural, hyphenation), run a second search with the variant before moving on.
+- Second, `read` each candidate file to CONFIRM the literal phrase is present in the content. A filename match is not sufficient; a single-hit search line is not sufficient without re-reading the file.
+- Third, only after all candidates are confirmed, start deleting. Delete in sorted path order so the final answer list is already sorted.
+- Your completion message must contain EVERY deleted path, one per line, sorted alphabetically, with no prefix, no header, and no explanatory text.
+- If you find fewer than 2 matches after a thorough search, double-check by listing the canonical receipts directory (e.g. `50_finance/purchases/`) and reading each file whose name contains any keyword from the task. "Every" means every — premature completion with an incomplete set scores zero.
```

**Rationale:** The current `crud.md` is silent on the plural-delete case, which is the exact hole four tasks are falling into. The new block enforces (a) enumerate-before-delete, (b) content re-read for each candidate, (c) sorted-order deletion to match the answer contract, and (d) an explicit warning that "every" is a coverage contract. It does not touch Python code, does not affect security paths (`OUTCOME_DENIED_SECURITY` rules in `outcomes.md` are evaluated before OK and unaffected here), and does not change the read-after-write rule for single-file writes.

**Generalizability:** `HIGH`
- This rule applies to every "delete all X" / "find every X" task family. Based on this run, at minimum 4 tasks (t006, t031, t056, t081) hit the pattern. The rule also transfers cleanly to hypothetical "move all X to archive", "rename every file matching X", or "update every receipt with Y" tasks that may exist in the benchmark. The enumerate-then-mutate pattern is standard database-like CRUD discipline.

**Zone:** `GREEN` — prompt-fragment edit only. Python (`classify.py`, `strategy.py`, `agent_loop.py`, `verify.py`) is untouched. Security behavior unchanged. No new tool calls or new risk-level escalation.

**Expected impact:** +1 on t031. Likely +1 each on t006, t056, t081 (same failure family). Conservative honest estimate: **+2 to +4 tasks** across the 104-task run. The rule will also reduce wasted tool calls on `crud_delete` tasks in general (the empty-search violation is addressed in passing).

**Risks:**
- **Regression on single-delete tasks** where the task says "delete file X": the new block starts with "tasks with 'every', 'all', 'each'…" so it will not fire on singular delete tasks. Low risk.
- **Over-reading inflating tokens:** the "read each candidate before deleting" rule could bloat step count for tasks with many candidates, but `crud_delete` has a 20-step budget (only 10 used here), so headroom exists.
- **Answer contract drift:** the "no prefix, no header" wording is already enforced by `output_contract.check_answer_contract` via `pre_completion_gate`; the fragment restates it for the agent's local reasoning, which is redundant but not harmful.
