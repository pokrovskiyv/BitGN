## Failure category

**Selected:** `classification_mismatch`

**Justification:** The task is unambiguously a read-only factual lookup against a single entity file. The correct route is `search`, which ships `LOOKUP DISCIPLINE` ("identify the canonical directory first, then read only the candidate files"), `DATE / UPCOMING LOOKUPS` ("people/entity date lookups, list the canonical entity directory first, then read the candidate entity files and compute the answer from those records"), and most importantly `ANSWER PRECISION` ("When the task asks for a specific value (email, name, number, list), your completion message must contain ONLY that value — no prefix, no explanation, no extra context. Just the raw answer."). None of those reached the model. The agent instead received `crud.md`, which says nothing about how to structure an answer — it talks about write-then-reread verification. The downstream symptom (score=0 for a 3-step trajectory that clearly reached the right file) is format-precision failure, but the root cause is the classifier never routing this task to search. A format-only fix would patch the symptom in a single fragment; a classify fix restores the entire `search` pipeline for "Give me X" tasks in one line.

## Root cause hypothesis

**Exactly one hypothesis:**

The `_SEARCH_SIGNALS` regex at `classify.py:41–45` does not include the imperative-lookup verb phrase `"give me"` (nor the equivalents `"tell me"`, `"show me"`, `"i need"`). These are the most natural English phrasings for a factual question that is not grammatically a question, and they produce silent classification fall-through to `crud`.

**Evidence chain:**
1. **Regex misses a common phrasing.** `_SEARCH_SIGNALS` captures `find / search / locate / look for / where is / which files / what is / which / who is / who are / when is / can you tell me`. It captures `can you tell me` (the polite interrogative) but omits `give me` / `tell me` / `show me` (the bare imperatives). All four phrases are idiomatic equivalents of "please look this up", and the last three would collapse into a single regex alternation.
2. **Two tasks fail identically.** Grep of `task_cache.json` for instructions starting with `"Give me"` returns exactly `[t025, t075]`, and both share the same classifier path, same 3–4 step trajectory, same `score: 0.0`, same `verifier_verdict: null`. No other task in the 104-task set begins with `"Give me"`, but any future task using that phrasing will also fail without the fix.
3. **Correct routing is known-good.** The sibling "Whose birthday is coming up next" tasks (t012, t037, t062, t087) match `_READ_ONLY_DATE_LOOKUP_SIGNALS` and `_SEARCH_SIGNALS` respectively and are routed to `search` — those tasks load `search.md` with its `ANSWER PRECISION` rule. So the pipeline already has the precision wording; it just needs the `"give me"` task to reach it.
4. **The root, not the symptom.** A narrower fix would add format-precision wording to `crud.md`, but that papers over the underlying routing defect: a read-only lookup has nothing to do with the CRUD "write-then-reread" workflow. Any per-fragment patch would have to be repeated on every fragment that could receive a lookup by accident. Fixing the classifier once solves the class of problems.

## Fix proposal (narrow GREEN zone only)

**Selected fix class:** `classify_rule`

**Target file:** `pac1-py/classify.py`

**Exact change:**
```diff
 _SEARCH_SIGNALS = re.compile(
     r"\b(find|search|locate|look\s+for|where\s+is|which\s+files?|what(?:'s|\s+is)|"
-    r"which\b|who\s+is|who\s+are|when\s+is|can\s+you\s+tell\s+me)\b",
+    r"which\b|who\s+is|who\s+are|when\s+is|can\s+you\s+tell\s+me|"
+    r"give\s+me|tell\s+me|show\s+me|i\s+need)\b",
     re.IGNORECASE,
 )
```

**Rationale:** Adds the four most common English imperative-lookup verb phrases to the search signal group. This keeps the regex single-expression, preserves every existing alternative (no behavior change on matched tasks), and is specifically scoped to phrases that introduce a read-only retrieval. `"Give me"` / `"tell me"` / `"show me"` / `"I need"` are all followed by a noun phrase (the value being looked up), never by a file-mutation verb, so the search branch at classify.py line 214 — `(has_search or has_lookup) and (not has_write or is_questionish_lookup)` — is the correct destination. This is the same kind of fix-at-the-signal-layer that t000 needed at the outcomes layer: one tiny textual edit to a single line at the pipeline's entry point.

**Generalizability:** `MEDIUM`
- t075 and t025 are the two current hits. `"give me"` is a natural English phrasing that is likely to keep recurring as the benchmark grows — grading templates for "return X in format Y" are an obvious pattern. `"tell me"` and `"show me"` are not currently present in task_cache but are such close phrasal siblings that including them is free defensive coverage. Impact bound: **2 tasks now, likely 2–4 as the benchmark expands**. Not HIGH because we cannot claim a broad pattern across unrelated task types; not LOW because the fix is structural rather than one-off.

**Zone:** `GREEN` — classify_rule edit, single regex alternation, no strategy table change, no prompt fragment change, no Python logic change, no security path touched. The `crud` branch is the fallthrough default so nothing that currently lands there is displaced except the exact instructions starting with the four added phrases, which by construction are lookups.

**Expected impact:** +2 tasks in the 104-task set (t025 and t075), assuming the underlying cause is indeed loss of the `ANSWER PRECISION` rule and not a deeper grader-format rejection we cannot see. Honest conservative estimate: **+1 to +2 tasks**. If the true failure is format-pedantic (e.g. the agent actually wrote `"1989-11-27"` while the grader expects `"November 27, 1989"`), the `ANSWER PRECISION` rule alone may not convert the score without also an explicit format-echo discipline — but in that case this fix is still necessary and we would stack a fragment edit on top in a follow-up cycle. Reaching search.md is a prerequisite for any format fix.

**Risks:**
- **False-positive classification of `give me some time`, `tell me when you are done`:** the regex is word-bounded and `"give\s+me"` does not match `"gave me"` or `"give-me"`, but phrases like `"Tell me when you are done"` would now match `_SEARCH_SIGNALS`. Mitigation: these phrases are unlikely to appear as standalone task instructions — benchmark tasks do not conversationally ask the agent to report completion. Risk is low in practice.
- **Minor risk on imperative write tasks:** a phrase like `"Show me by writing..."` would hit both `_SEARCH_SIGNALS` and `_WRITE_SIGNALS`. Mitigation: the classifier already resolves this via the `not has_write or is_questionish_lookup` clause at line 214 — a `show me + write` task will bypass the search branch and fall into communication/crud. No regression.
- **No security impact whatsoever:** search fragment does not weaken any guard. `OUTCOME_DENIED_SECURITY` evaluation happens in `outcomes.md` rule 3, which is loaded unconditionally from the always-on fragments (strategy.py line 110). Security posture is unchanged.
