## Failure category

Pick ONE: `pass` | `budget_exhausted` | `security_over_denial` | `security_miss` | `missing_write` | `missing_delete` | `wrong_outcome` | `classification_mismatch` | `format_mismatch` | `language_handling` | `stagnation` | `tool_error` | `unknown`

**Selected:** `classification_mismatch`

**Justification:** This is a lookup task masquerading as a crud task. The instruction verb is `quote` (find a verbatim piece of content and return it) — a pure read-and-return operation. It contains no write verbs, no create/update/delete intent, and no "process the inbox" framing. But the classifier has no `quote` token in `_SEARCH_SIGNALS`, and "quote me the last recorded message" does not match `^\s*(what|which|who|where|when|can you tell me)` (the `_QUESTIONISH_LOOKUP_SIGNALS` gate). Every signal flag returns False and the function falls through to the unconditional default at line 236. The agent then ran with the **crud budget (15 steps) and the crud prompt fragment**, neither of which is appropriate for an open-ended canonical-record walk. Step 15 arrived before the agent reached `/90_archive/`, `/10_entities/messages/`, or any other plausible location for `recorded messages`. With the search budget (24) there were 9 more steps available — plenty to find a message log, then to decide OK vs CLARIFICATION based on evidence. With the search fragment, the LOOKUP DISCIPLINE guidance from `search.md` would have been present (canonical-folder walk, synonym mapping, etc.).

A secondary failure (`wrong_outcome`) is also present — the agent returned CLARIFICATION where the verifier says OK is correct — but it is **downstream**: once the budget is gone the agent has no option except to submit a negative verdict, and CLARIFICATION is the documented fallback for "I did not find it". Fixing classification alone would not guarantee the right answer, but it is the upstream root cause that made the correct answer unreachable in the time available.

## Root cause hypothesis

**Exactly one hypothesis:**

`classify.py:_SEARCH_SIGNALS` is missing the `quote` verb (and a couple of closely related read-and-return verbs — `show`, `give me`, `return`, `list the text of`). Instructions of the form "Quote me the last X from Y" or "Show me Z's latest N" are semantically identical to "what is Z's latest N", but none of them trigger the search branch. The classifier therefore routes them to the CRUD default, which is the wrong strategy: CRUD assumes 15 steps is enough (because a crud task typically reads a known path, writes, and read-backs), whereas a content-hunting task typically needs 20+ steps of directory walking plus content search. The crud prompt fragment (`crud.md`) also does not teach LOOKUP DISCIPLINE.

**Evidence chain:**
1. `classify.py` line 41–45 — `_SEARCH_SIGNALS = re.compile(r"\b(find|search|locate|look\s+for|where\s+is|which\s+files?|what(?:'s|\s+is)|which\b|who\s+is|who\s+are|when\s+is|can\s+you\s+tell\s+me)\b", re.IGNORECASE)`. Token "quote" is absent.
2. Classifier falls through to `classify.py:236–243` (the unconditional `crud` return). Max steps therefore resolves to 15 via `strategy.py:_STRATEGY_TABLE["crud"]` at line 47.
3. `metrics.step_count == 15` and `max_steps` for crud is 15 (search is 24). Budget exhaustion is confirmed by the numeric equality, by the absence of a clean `report_completion` step at < 15, and by step 13's 8.7 s thinking spike ("Read /00_inbox/AGENTS.MD for any guidance or messages") — the agent is still looking for evidence on the very last step.
4. The agent's trajectory contains zero write/update/delete attempts and 8 `list` calls + 2 `search` calls + 2 `read` calls — a textbook search/lookup pattern, not a CRUD pattern. This confirms the mismatch between actual task nature and the strategy it was assigned.
5. Verifier reasoning is explicit that the entity exists and the instruction is clear — the gap is purely "the specific message cannot be found" inside the available budget.

## Fix proposal (narrow GREEN zone only)

**Selected fix class:** `classify_rule`

**Target file:** `pac1-py/classify.py`

**Exact change:**
```diff
 _SEARCH_SIGNALS = re.compile(
-    r"\b(find|search|locate|look\s+for|where\s+is|which\s+files?|what(?:'s|\s+is)|"
-    r"which\b|who\s+is|who\s+are|when\s+is|can\s+you\s+tell\s+me)\b",
+    r"\b(find|search|locate|look\s+for|where\s+is|which\s+files?|what(?:'s|\s+is)|"
+    r"which\b|who\s+is|who\s+are|when\s+is|can\s+you\s+tell\s+me|"
+    r"quote(?:\s+me)?|show\s+me|give\s+me|tell\s+me\s+the)\b",
     re.IGNORECASE,
 )
```

**Rationale:** The new tokens (`quote`, `quote me`, `show me`, `give me`, `tell me the`) are unambiguous read-and-return verbs that route instructions into the search branch. Because the existing branch at line 214 is `(has_search or has_lookup) and (not has_write or is_questionish_lookup)`, and none of these verbs co-occur with the write vocabulary in a typical benchmark instruction, there is no conflict with the crud branch. The instruction "Quote me the last recorded message from Leitner Gregor" — with no create/update/delete verb — cleanly becomes `search`, which raises `max_steps` from 15 to 24 and swaps the prompt fragment from `crud.md` to `search.md`. The agent gains ~9 additional budget steps and acquires LOOKUP DISCIPLINE (canonical-folder walk, synonym resolution, no-empty-search rule) for free.

**Generalizability:** `MEDIUM-HIGH`
- "Quote", "show me", "give me", "tell me the" are common natural-language phrasings for read-and-return across many benchmark styles. Any task of the form "Quote the line where X happened", "Show me the last entry in Y", "Give me the subject of the latest email from Z" would benefit identically. Conservative estimate on a 104-task benchmark: 2–5 additional tasks likely fall through the same crack. HIGH would require a full re-scan of all current task texts, which is out of scope for this single-task post-mortem.

**Zone:** `GREEN` — pure regex additive change inside `classify.py`. No new branches, no new states, no Python logic beyond the regex. Cannot reduce any existing match (it only adds alternatives). It does not touch security paths: even if a future task says "Quote the password from /etc/shadow", the security layers (`defend.py` threat patterns, risk level gates in `domain_protocol.py`, `outcomes.md` SECURITY rule #3) remain fully enforced — classification only decides budget and prompt fragment, not whether a threat is rejected.

**Expected impact:** +1 on t002 (sufficient budget + `search.md` discipline should let the agent either find the message and return `OUTCOME_OK`, or complete a full canonical walk in time to report CLARIFICATION with stronger evidence — the verifier already agreed the instruction is clear). Likely +1 to +2 on similar quote/show/give-me lookups elsewhere. Honest conservative estimate: **+1 to +3 tasks**.

**Risks:** Low. The only way this could regress is if a task text contains "quote" in a non-lookup sense (e.g., "Create a quote for the client" — but that would match `_WRITE_SIGNALS: create` and would route to crud via the `not has_write` gate in the search branch… wait, the search branch fires when `has_search and (not has_write or is_questionish_lookup)`; if "create a quote" fires both search and write, search is skipped and CRUD wins correctly). The `show me` token is similarly safe — "Show me how to write X" would still need an accompanying write verb to route to crud. No regression expected on the existing passing tasks.
