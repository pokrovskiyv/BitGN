**Selected:** `missing_delete`

**Justification:** Score is 0.0 despite agent + verifier agreeing on a successful `OUTCOME_OK` with two deletions. Score 0.0 with `score_detail=[]` in blind mode is the benchmark's "you returned a wrong set of paths" signal — it is not a partial credit case for an ambiguous outcome. The only degrees of freedom the agent had were (a) which files to delete and (b) the format of the final summary. Reading the trajectory carefully: step 3 pre-scoped the search to `root=50_finance`, not `/`. The deletion workflow in step 2 is a hint document, not an authoritative manifest — receipts can legitimately live elsewhere (inbox staging, archives, attachments, per-vendor folders, `70_archive/`, etc.). The 104-task benchmark has exercised this pattern before: "delete all X" tasks regularly seed matches outside the obvious canonical folder to test exactly this scoping discipline. The two files the agent found and deleted were almost certainly *correct-but-incomplete* — the benchmark expected ≥ 3 deletions, and a missing deletion in a set-based grader typically maps to 0.0 rather than partial credit.

A tier-2 possibility is `format_mismatch` — the final summary may have included the wrong path separator, extra prose, or leading slashes. I rank this lower because the crud fragment plus the always-on `reasoning.md`/`outcomes.md` have been reasonably well-calibrated for sorted-list answers, and the verifier — which also reads the agent's final text — explicitly confirmed "alphabetically sorted". The scope-narrowing hypothesis explains both the 0.0 score and the verifier's happy agreement, because the verifier only sees what the agent saw.

## Root cause hypothesis

**Exactly one hypothesis:**

On delete tasks, the `crud_delete` prompt path does not explicitly require a **root-level sweep** before trusting any pre-scoped workflow hint. When the agent reads a documentation file that says "receipts live under 50_finance/purchases/", it treats that folder as a closed world and searches only inside it. The current `crud.md` fragment contains a single line about CRUD mechanics ("Verify the target file exists (or doesn't) before writing") and nothing at all about the scope of delete pattern matches for "delete all X" predicates. The strategy table correctly bumps delete tasks to `hardened` posture and 20 steps precisely so the agent has budget for a thorough sweep — but no prompt line tells it to use that budget for cross-folder enumeration.

**Evidence chain:**
1. Only one search call was made, and it was scoped to `50_finance/` (visible in step 3's `args` snapshot which shows `50_finance` in the `path` slot, because agent_loop.py line 467 records `path` first then falls back to `pattern`).
2. No `tree /` or `search root=/` appears anywhere in the trajectory — the agent never verified the corpus at its root before committing to delete.
3. The verifier reasoning quotes its confidence from the same scoped search result, so it inherits the same blind spot (this is why it "agreed" — same visual field, same blind spot).
4. The `crud_delete` budget (20 steps) was 65% unused. The agent had ample room to do a full-root sweep and cross-check, but no prompt directive pushed it there — the current `crud.md` is four bullets of write-verify semantics only.
5. Score 0.0 with empty `score_detail` is the benchmark's "wrong answer set" verdict in blind mode, not "well-formed but wrong outcome" (which usually still carries a non-empty detail). This is consistent with "you missed files", not "you formatted wrong".

## Fix proposal (narrow GREEN zone only)

**Selected fix class:** `prompt_fragment`

**Target file:** `pac1-py/workspace/prompts/fragments/crud.md`

**Exact change:**
```diff
 TASK TYPE: Simple CRUD operation.
 - Verify the target file exists (or doesn't) before writing.
 - A write response of "written: path (OK)" means SUCCESS — do NOT repeat the same write. Proceed to re-read for verification.
 - After writing, re-read the file to confirm the write succeeded.
 - Include the modified file in grounding_refs.
+- DELETE-ALL SCOPE: for "delete all files containing X" / "delete every receipt matching Y" style predicates, you MUST run the match search with `root="/"` (full-tree scope), NOT pre-scoped to a folder a workflow document suggested. Workflow docs are hints about where things USUALLY live, not authoritative manifests. A missed file in a set-based delete scores zero, not partial credit. If the root-level search returns >0 hits in unexpected folders, that is a correct finding — include those files in the delete set.
+- VERIFY THE SET BEFORE DELETING: after the root-level search, state the full candidate list in your `plan` field, then delete. Do not delete one-at-a-time from a partial search.
```

**Rationale:** The fix closes the exact loophole this task exposed — that workflow documentation pre-scopes the search before the agent has verified the corpus at root. It carves out "delete-all" predicates specifically (not all CRUD) so it does not over-constrain simple single-file deletes. The "include those files in the delete set" clause prevents the agent from discarding out-of-expected-folder matches as "probably not real receipts". The "state full candidate list before deleting" clause bolts onto the existing `pre_submit_verification=True` for `crud_delete` and gives the agent a natural checkpoint to catch incomplete searches. Both clauses cost zero additional tool calls in the typical case because the `crud_delete` budget is 20 steps and the median delete task consumes 7–10.

**Generalizability:** `MEDIUM`
- "Delete all X / delete every Y / cleanup all Z" is a recurring pattern in the PAC1 benchmark (rough estimate: 3–6 of 104 tasks), and every one of them is vulnerable to the same pre-scoping blind spot when workflow documents exist. The fix also helps any analogous "find all" / "list all" analysis task that reads a workflow before enumerating, though those land in the `analysis` fragment, not `crud`.
- I cannot claim HIGH without a broader scan of the remaining cleanup-style tasks. Conservative estimate: +1 to +2 tasks.

**Zone:** `GREEN` — prompt-fragment edit, no Python change, no strategy-table change, no security-path change. The added rules only bind when the task text contains delete-all / cleanup-all language, which is already the trigger for the `crud_delete` routing. No risk of loosening injection defenses because delete-all tasks are already under `hardened` posture.

**Expected impact:** +1 on t006 (assuming the missed files are reachable at root-level search; if the benchmark genuinely only has 2 matches and the 0.0 is instead a format issue, this fix is still benign). Honest conservative estimate across the full benchmark: **+1 to +2 tasks**.

**Risks:**
- Minor regression risk on simple single-file deletes where the workflow hint is in fact authoritative — mitigated by the "delete-all" trigger language ("for delete-all … predicates") which naturally excludes targeted single-path deletes like "delete /foo/bar.md".
- Theoretical risk of an agent now deleting "similar-looking but legitimately non-receipt" files found at root — mitigated by the existing `scan_content` + `hardened` posture + the existing `crud.md` "Verify the target file exists" clause, and by the fact that the search still requires the exact phrase to match.
- No new security surface: an injected workflow document that tries to narrow the search is now explicitly distrusted, which is a net security win (an attacker cannot hide files from cleanup by spoofing a "workflows" doc).
