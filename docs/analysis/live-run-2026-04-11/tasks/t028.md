## Root cause hypothesis

**Exactly one hypothesis:**

`search.md` LOOKUP DISCIPLINE handles single-value lookups ("what is X's email?") but has no guidance for **set-membership lookups** ("in which Ys is X involved?"). A membership question has two complementary authoritative sources: the entity's own back-reference list (petra.md lists her projects) and the project's participant list (project X lists its participants). Answers that use ONLY one side are systematically wrong whenever the two sides disagree — which happens whenever authors forget to update one side after a membership change. The current search.md drives the agent to pick the wrong side: "identify the canonical directory first, then read only the candidate files needed for the answer" (line 10) leads straight to the project-side scan and away from the entity's own back-references, because projects are the thing being listed.

**Evidence chain:**
1. Step 2 reads petra.md and the agent never returns to it, despite 12 steps of headroom. If the fragment had said "for 'which Xs is Y in?' questions, read Y's own file FIRST, then cross-verify against each candidate X", the agent would have had a clear checklist.
2. Step 4 escalates search root to `/` — this is the agent thrashing because the project-side scan wasn't finding a clean hit. That thrashing is a symptom of missing guidance, not of search.md being too loose on root escalation.
3. Steps 5–11 read projects in `list(/40_projects)` order, not in an order filtered by actual petra-mentions. That's the tell: the agent interpreted "exhaustive project scan" as the canonical strategy for a membership question. The fragment provides no alternative pattern.
4. Root, not symptom: a budget increase wouldn't fix this (there's already 50% headroom). A classification tweak wouldn't either (the task IS a search). Only a fragment update that explicitly teaches membership-question doctrine will address the underlying reasoning gap.

## Fix proposal (narrow GREEN zone only)

**Selected fix class:** `prompt_fragment`

**Target file:** `pac1-py/workspace/prompts/fragments/search.md`

**Exact change:**
```diff
 LOOKUP DISCIPLINE:
 - When the task asks for a single factual value (name, date, email, number), identify the canonical directory first, then read only the candidate files needed for the answer.
 - Do not keep searching the whole workspace after you have already found the authoritative folder.
 - If AGENTS.MD names an authoritative source, go there directly instead of doing exploratory global search.
+
+MEMBERSHIP / SET LOOKUPS:
+- For "In which Xs is Y involved?" / "Which Xs does Y own?" / "What Xs is Y a participant in?" the question has TWO complementary authoritative sources:
+  1. Y's own entity file — usually has a back-reference field (related_projects, involved_in, participant_of, owns, member_of). Read it first.
+  2. Each candidate X's file — may list Y in a participants / owners / managed_by / assigned_to field.
+- Cross-verify: the FINAL answer is the INTERSECTION of what Y claims and what each X confirms. If Y claims membership in project X but project X does not list Y, exclude X (Y's file is stale). If project X lists Y as a participant but Y's file does not claim X, include X (Y's file is stale — project is authoritative on its own participants).
+- Never return a set-membership answer from a one-sided scan. A grep hit for "petra" inside a README is NOT proof of participation — it may be an incidental mention ("formerly led by petra", "ask petra for access").
+- If the entity file has an explicit list field, use it as the seed set; otherwise fall back to scanning every candidate X and filtering by a participant-field match (not a free-text grep).
```

**Rationale:** This adds a dedicated doctrine for membership questions without loosening any existing rule. The "INTERSECTION" framing is the critical insight — it forces the agent to consult BOTH sides of the relationship, which is the only way to catch stale data on either side. It also explicitly disallows the single-sided grep strategy the agent used on t028 ("a grep hit is NOT proof of participation"), which should prevent the same pattern on similar tasks. The doctrine is narrow enough not to interfere with single-value lookups (which still follow the earlier LOOKUP DISCIPLINE block) and explicit enough to be actionable by both Sonnet-4.6 and the Haiku verifier.

**Generalizability:** `MEDIUM`
- Membership questions are a recognized PAC benchmark pattern: "in which X is Y a member?", "which projects is person P on?", "what rooms has device D been placed in?", "which channels does user U belong to?". On a 104-task benchmark I'd estimate 3–6 tasks follow this pattern, and they are systematically vulnerable to the same one-sided scan failure. Cannot claim HIGH without explicitly auditing the task list for member-set questions; honest bound is MEDIUM.

**Zone:** `GREEN` — prompt-fragment edit only, no Python change, no classification change, no security path touched. The addition only clarifies strategy for questions that already go through the `search` strategy; no task that previously used a different fragment will be affected.

**Expected impact:** +1 on t028 (agent correctly cross-verifies petra's projects → OUTCOME_OK with the intersection list). Likely +1 to +2 additional tasks with the same membership pattern across the benchmark. Honest conservative estimate: **+1 to +2 tasks**.

**Risks:** Minor risk that the agent over-applies the "cross-verify" rule to single-entity lookups (e.g., "what is Petra's email?" — no cross-verify needed, email is a scalar attribute). Mitigated by the explicit wording "For 'In which Xs is Y involved?' / 'Which Xs does Y own?'" — the trigger phrase is specifically plural-set questions, not scalar-attribute questions. Second minor risk: "entity file is stale → project-side wins" could push the agent to include a project where Y appears in an obsolete `former_members` field — mitigated by requiring the match to be in a "participants / owners / managed_by / assigned_to" field specifically, not any field mentioning the person.
