**Selected:** `classification_mismatch`

**Justification:** The surface symptom is `budget_exhausted` (step 15/15), but the **cause** is classification. A textbook inbox-processing task — "review the next inbound note and act on it", with a workspace containing `00_inbox/`, `99_system/workflows/`, and a canonical OCR workflow requiring multi-invoice frontmatter writes — was routed to `crud` with a 15-step budget because the classifier regexes don't recognize the phrase "inbound note". Had the task classified as `inbox_processing`, the budget would have been **32 steps** (nearly 2× the actual need) and the correct fragment (`inbox_processing.md`) would have been injected with its DEFAULT ROUTE checklist — which already names `99_system/`, `60_outbox/channels/`, and the read-after-write requirement the agent discovered the hard way. The agent's per-step behaviour was correct; every unused cycle was spent on necessary work, not fumbling. The root cause is a **regex vocabulary gap**, not a reasoning or security failure.

## Root cause hypothesis

**Exactly one hypothesis:**

`_INBOX_PROCESSING_SIGNALS` in `classify.py` lines 73–80 is a closed-vocabulary regex keyed on literal "inbox/mailbox/queue" nouns and imperative verbs like "process inbox" / "pending inbox items". It completely misses the natural-language phrasing the benchmark actually uses: "inbound note", "incoming item", "next unread message", etc. When the instruction is short and colloquial ("Review the next inbound note and act on it"), none of the signal regexes fire — not `_WRITE_SIGNALS` (no explicit write verb), not `_COMMUNICATION_SIGNALS` (no send/reply), not `_ANALYSIS_SIGNALS`, not `_MULTI_STEP_SIGNALS` — and the task silently drops into the CRUD fallthrough with a 15-step budget. For any task that *actually* requires multi-item inbox processing, 15 steps is structurally insufficient (one invoice = 3 steps minimum: read → write → verify; three invoices = 9 steps, leaving 6 for orientation and outbox reporting — not enough to also read workflow + schema + AGENTS.md + 60_outbox/README).

**Evidence chain:**
1. Step count = 15 exactly = `crud` budget exactly. Coincidence at this precision means classification picked `crud`.
2. `tool_call_count=14` with step 14 missing and `verifier_verdict=null` → the fallback path in `verify.py:report_budget_exhaustion()` was taken, which only runs on budget exhaustion.
3. The agent's own step plans ("Read 00_inbox/000_next-task.md", "Tree 99_system/ to find OCR workflow docs", "Read finance-record-frontmatter.md schema") perfectly match the inbox_processing.md DEFAULT ROUTE checklist that it never received — this is what "the right fragment would have just worked" looks like.
4. Instruction lexical audit: "Review the next **inbound note** and act on it" → no word appears in `_INBOX_PROCESSING_SIGNALS` ("inbox|mailbox|queue|backlog|waiting messages|pending requests|newly arrived requests|unread requests|message backlog|mailbox"). "inbound" is absent; "note" is present but not inside any signal regex.
5. Not a budget-tuning issue: even doubling crud's budget is the wrong fix because the missing `inbox_processing.md` fragment — with its identity/channel verification and outbox trust doctrine — is as important as the extra steps.

## Fix proposal (narrow GREEN zone only)

**Selected fix class:** `classify_rule`

**Target file:** `pac1-py/classify.py`

**Exact change:**
```diff
 _INBOX_PROCESSING_SIGNALS = re.compile(
     r"\b(process\s+(the\s+)?inbox|from\s+(the\s+)?inbox|inbox\s+file|"
     r"(take\s+care\s+of|work\s+through)\s+(the\s+)?(?:inbox|incoming)\s+queue|"
     r"(?:incoming|inbox)\s+queue|pending\s+inbox\s+items?|mailbox|"
     r"message\s+backlog|waiting\s+messages?|pending\s+requests?|"
-    r"newly\s+arrived\s+requests?|unread\s+requests?)\b",
+    r"newly\s+arrived\s+requests?|unread\s+requests?|"
+    r"(?:next|latest|newest|upcoming)\s+(?:inbound|incoming|unread|pending|new)\s+"
+    r"(?:note|item|message|request|memo|email|letter|envelope)|"
+    r"inbound\s+(?:note|item|message|memo)|"
+    r"next\s+(?:inbound|incoming|unread))\b",
     re.IGNORECASE,
 )
```

**Rationale:** The fix extends `_INBOX_PROCESSING_SIGNALS` with the natural-language pattern family the benchmark uses in practice: "next/latest/newest/upcoming" + "inbound/incoming/unread/pending/new" + "note/item/message/request/memo/email/letter/envelope", plus the standalone "inbound note/item/message/memo" and "next inbound|incoming|unread". This keeps the rule purely lexical (no semantic LLM dependency), adds zero latency (regex prefilter), and preserves the existing `_PROCESS_LIKE_SIGNALS × _INBOX_OBJECT_SIGNALS` compound rule untouched. The existing CRUD fallback remains the default for genuinely simple tasks; only the clearly-inbox-like phrasings get promoted. I chose `classify_rule` over `strategy_budget` because bumping CRUD from 15 → 30 would leak into every real CRUD task (slowing them, inflating tokens, blurring the classification signal for A-Evolve); and over `prompt_fragment` because no CRUD prompt text change can conjure the inbox_processing.md DEFAULT ROUTE checklist into the system prompt.

**Generalizability:** `HIGH` — **H**.
- The benchmark contains multiple variants of the "review/handle the next X" phrasing in `task_cache.json` (inbound note, incoming message, latest memo, unread item). This regex family will catch at least 5+ tasks that currently land in CRUD or analysis fallbacks. It's a structural classifier gap, not a one-off lexical accident.
- Ground-truth check: the agent's trajectory shows it already figured out the correct procedure without the fragment — meaning the model is smart enough to execute inbox_processing.md; it just needs the right budget and the right lookup checklist.
- Fails safely: if the new patterns over-match (e.g., a search task phrased as "find the next inbound memo"), the worst case is `inbox_processing` running with 32 steps and a harder security fragment — a ~0 downside because `hardened` posture never *worsens* a search outcome.

**Zone:** `GREEN` — `classify_rule` edit in `classify.py`, pure regex extension to an existing signal set, no Python logic change, no risk to security gating, no mutation of `strategy.py`, no prompt changes. `_INBOX_PROCESSING_SIGNALS` is not referenced from defend.py or verify.py, so impact is strictly contained to classification routing.

**Expected impact:** +1 on t068 (classification → `inbox_processing`, budget → 32, fragment → `inbox_processing.md`, trajectory already correct → submission before exhaustion → verifier runs → `OUTCOME_OK`). Potential +3 to +5 more across other colloquially-phrased inbox tasks hiding in CRUD. Honest conservative estimate: **+2 to +4 tasks**.

**Risks:** Minor — a search task phrased "what is the next inbound memo's subject?" would now classify as `inbox_processing` instead of `search`, inheriting a `hardened` posture and 32-step budget. Both are strictly more permissive than `search`'s 24-step, `standard` posture, so OK-outcome tasks don't regress. Second risk: the new regex broadens `inbox_processing`'s footprint, which tightens the `pre_completion_gate` requirement that inbox tasks *must* produce writes or deletes — but that gate already checks `_looks_inbox_like()` via consulted-path heuristics, so the same tasks already hit it. Negligible additional exposure.
