**Selected:** `budget_exhausted`

**Justification:** Two failures are visible (semantic misread of "visible people" + blown step budget), but the upstream one is budget. The classification routes this as `search` with `max_steps=24`, and the agent consumed 23 steps on raw cast-file reads before doing ANY computation or date check. By the time it realized it needed `context()` (step 28) and re-reading evidence (step 26), the budget was already gone and the gate was rejecting steps. A `wrong_outcome` label would also fit the semantic miss, but the root cause of *why* the agent never recovered is that the cost of the sequential cast-walk strategy swallowed the budget, leaving no room for the filter step. A 24-step search budget cannot absorb "read N cast files AND call context() AND filter by visibility AND compute next date" when N = 22.

## Root cause hypothesis

**Exactly one hypothesis:**

`search.md` DATE/UPCOMING LOOKUPS guidance is advisory but NOT enforced by ordering: the agent is told to "call `context()` early" but is free to walk the directory first. Combined with the current `search` step budget of 24 and the PAC1 cast directory size (22 people), the agent naturally consumes ~22 steps on reads before it has any budget left for orientation, filtering, or computation. The prompt needs to convert the "early `context()`" guidance into a HARD FIRST-ACTION rule for date-comparison lookups, so the date anchor and the filtering criteria are pinned before the cast walk begins.

**Evidence chain:**
1. `pac1-py/workspace/prompts/fragments/search.md` line 15: "For 'next', 'upcoming', or date-comparison lookups, call `context()` early so you compare against the current date instead of guessing." — advisory language ("early"), no enforcement, no "BEFORE reading any entity files" anchor.
2. metrics.steps step order: `list` (step 1) → 22 reads (steps 2–23) → `context()` (step 28). The agent deferred the advisory action to near-last.
3. `pac1-py/strategy.py` line 52: `"search": (24, "standard", True)`. Budget is 24. 22 reads + 1 list + 1 report = 24 exactly, leaving 0 for any of: visibility filter, date computation, re-read for confirmation. The strategy is numerically impossible for PAC1-scale cast lookups without pre-filtering.
4. The "visible people" semantic miss is a *symptom* — the agent never had budget to investigate what "visible" means because it had already committed to the full-sweep strategy on step 2. An earlier `context()` + earlier prompt-fragment hint about "visible" routing would have pushed the agent toward `list(/00_*)` or a roster lookup instead of mass reads.

## Fix proposal (narrow GREEN zone only)

**Selected fix class:** `prompt_fragment`

**Target file:** `pac1-py/workspace/prompts/fragments/search.md`

**Exact change:**
```diff
 DATE / UPCOMING LOOKUPS:
-- For "next", "upcoming", or date-comparison lookups, call `context()` early so you compare against the current date instead of guessing.
-- For people/entity date lookups, list the canonical entity directory first, then read the candidate entity files and compute the answer from those records.
-- These tasks are usually read-only lookups, not workflows. Avoid procedural wandering once you have the canonical records.
+- MANDATORY FIRST ACTION for "next"/"upcoming"/date-comparison lookups: call `context()` BEFORE any `list`, `read`, or `search`. You cannot compute "next" without knowing today's date — skipping this wastes step budget on files you will have to revisit.
+- SCOPE HINTS IN THE TASK — if the instruction says "visible people", "active contacts", "current roster", or similar qualifier, that word is load-bearing. BEFORE walking `/10_entities/cast/`, check `AGENTS.md` and any top-level index/roster file for a visibility/active filter. If no filter exists, note that and proceed with the full directory.
+- For people/entity date lookups, list the canonical entity directory, then read ONLY the candidate entity files you have budget for. For a 22-person cast and a 24-step budget, reading every file leaves zero room for filtering or computation — triage by the task's scope qualifier first.
+- These tasks are usually read-only lookups, not workflows. Avoid procedural wandering once you have the canonical records.
```

**Rationale:** The fix turns advisory language into a hard ordering constraint (context first, scope qualifier second, reads third). It also explicitly names the budget arithmetic (22 files vs 24 budget) so the agent reasons about cost before committing to the sweep. The "visible people" clause is a prompt-level teaching — we name the exact failure mode so the agent recognizes it in the instruction next time. No Python change, no budget change (budget-raise would be AMBER), no classification rule change.

**Generalizability:** `MEDIUM`
- PAC1 is likely to have multiple "next/upcoming + filter" tasks — renewal dates, contract expiries, subscription anniversaries, etc. — where the filter word (visible, active, pending, open) is the trap. The `context()` ordering rule also helps any task that mentions a relative time. Rough estimate: 3–6 of 104 tasks involve date-comparison lookups where the agent either forgets `context()` or treats a scope qualifier as filler. Cannot claim HIGH without cross-task review.

**Zone:** `GREEN` — prompt-fragment edit only. No Python change, no classification rule, no budget bump, no security path touched. Risk is strictly additive prompt guidance.

**Expected impact:** +1 on t012 (`OUTCOME_OK` with wrong name → `OUTCOME_OK` with correct `Petra Novak` or whatever the alphabetically-sorted next-visible-birthday names resolve to, once the agent filters by visibility and checks date). Potentially +1 to +2 on similar filtered-date-lookup tasks elsewhere. Honest conservative estimate: **+1 to +2 tasks**.

**Risks:** Minor — the new "MANDATORY FIRST ACTION" wording may cause the agent to `context()` even on date-lookup tasks where the current date is irrelevant (e.g., "what was Lukas's birthday"). That is one wasted step in ~1% of cases, trivially acceptable against a 24-step budget. Second minor risk: the "scope hints" clause could push the agent to over-investigate AGENTS.md for tasks with incidental qualifiers ("visible on the site" meaning "live"). Mitigated by the "if no filter exists, note that and proceed" escape hatch.
