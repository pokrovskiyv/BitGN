**Justification:** The root defect observable from evidence is that "Give me the birthday for our ops lead" — a textbook read-only people-date lookup — is not matched by any of the `_SEARCH_SIGNALS` / `_LOOKUP_SIGNALS` / `_READ_ONLY_DATE_LOOKUP_SIGNALS` patterns in `classify.py`. That misrouting has two downstream effects: (a) `search.md` discipline (canonical directory → single read, answer-precision rule, no-empty-pattern rule) is NOT injected into the system prompt, and (b) the CRUD budget/posture is applied instead of the search lane. Whether t025 was a format-mismatch or a suppressed PASS, the classification mismatch is the REAL upstream defect that needs fixing regardless of t025's actual verdict.

## Root cause hypothesis

**Exactly one hypothesis:**

`classify.py._SEARCH_SIGNALS` regex does not cover the imperative/possessive lookup phrasing `"give me the X for Y"` / `"tell me the X of Y"` / `"get me the X of/for Y"` / `"what's our X"`. The closest existing patterns are `what(?:'s|\s+is)` and `can\s+you\s+tell\s+me`, but none of these fire on "give me the birthday for our ops lead". The instruction therefore classifies as `crud` with `requires_write=False`, which is a legal-but-wrong bucket: it applies the 15-step CRUD budget and loads `crud.md` instead of `search.md`. The agent-level symptom (empty `search("")` on step 2) is a direct consequence — the search-lane discipline forbidding empty patterns (search.md line 4) was never in the prompt.

**Evidence chain:**
1. Step 2: `search("")` with plan "Search for 'ops lead' in 10_entities/cast/" — this is the exact pattern `search.md` line 4 forbids, but that fragment was not loaded.
2. `classify.py` lines 41–45 define `_SEARCH_SIGNALS` as `find|search|locate|look for|where is|which files?|what's/what is|which|who is/are|when is|can you tell me`. None match "give me". Line 46–50 `_LOOKUP_SIGNALS` matches specific role nouns (legal entity, account manager, primary contact, owner) — "ops lead" is not in that list either. So both `has_search` and `has_lookup` are False.
3. `classify.py` lines 35–39 `_WRITE_SIGNALS` does not include "give". No other signal fires. Control reaches the default CRUD return at line 236. `requires_write=False` because "give me" is not a write verb, so the task is a read-only CRUD — a bucket that doesn't really exist in the design.
4. Root, not symptom: editing `outcomes.md` or `crud.md` would not fix this — the wrong fragment is loaded in the first place. Fixing the classifier is the only clean repair.

## Fix proposal (narrow GREEN zone only)

**Selected fix class:** `classify_rule`

**Target file:** `pac1-py/classify.py`

**Exact change:**
```diff
 _SEARCH_SIGNALS = re.compile(
     r"\b(find|search|locate|look\s+for|where\s+is|which\s+files?|what(?:'s|\s+is)|"
-    r"which\b|who\s+is|who\s+are|when\s+is|can\s+you\s+tell\s+me)\b",
+    r"which\b|who\s+is|who\s+are|when\s+is|can\s+you\s+tell\s+me|"
+    r"give\s+me\s+(?:the\s+)?|tell\s+me\s+(?:the\s+)?|get\s+me\s+(?:the\s+)?|"
+    r"show\s+me\s+(?:the\s+)?|i\s+need\s+(?:the\s+)?)\b",
     re.IGNORECASE,
 )
```

**Rationale:** Adds the five most common imperative-lookup phrasings ("give me the", "tell me the", "get me the", "show me the", "i need the") to `_SEARCH_SIGNALS`. These are high-signal lookup openers in English — once one of them appears, the task is almost always a read-only retrieval. Adding them makes `has_search=True`, which combined with `has_write=False` hits the search branch at line 214 (`(has_search or has_lookup) and (not has_write or is_questionish_lookup)`). The task then classifies as `search`, loads `search.md` (with the no-empty-pattern rule, canonical-folder rule, and ANSWER PRECISION rule), and uses the 24-step search budget — which is more headroom than the misrouted CRUD budget of 15. The fix does NOT touch any threat/outcome logic and has no security implications: the new phrases are all benign retrieval verbs, not action verbs that could escalate to writes.

**Generalizability:** `MEDIUM`
- Imperative lookup openers ("give me", "tell me", "show me") are extremely common in natural-language benchmark tasks. Rough estimate: 3–8 of 104 tasks use one of these five phrasings as the leading verb for a pure lookup. Every such task currently misroutes to CRUD, loads the wrong fragment, and loses the search-lane discipline. The fix unblocks all of them in one rule change. I cannot claim HIGH without a text-scan of every task instruction, but the pattern is common enough that MEDIUM is honest.

**Zone:** `GREEN` — single-line regex addition in `classify.py`, no Python control-flow change, no effect on security paths (new phrases don't trigger `_DELETE_SIGNALS` or threat patterns), no effect on the strategy table. The branch it fires into (search) is a standard-posture path already exercised by dozens of existing tasks.

**Expected impact:** If t025 was a suppressed PASS, this fix is invisible on t025 itself but prevents future regressions when a harder variant appears. If t025 was actually a format-mismatch (agent emitted `March 15, 2026` but the grader expected `03-15-2026` or vice versa), the fix routes future runs through `search.md`'s ANSWER PRECISION rule ("your completion message must contain ONLY that value — no prefix, no explanation"), which would tighten format compliance. Honest conservative estimate: **+1 to +2 tasks** across the benchmark (task-level fix + one or two sibling tasks with the same phrasing), zero regressions expected on the existing 104.

**Risks:** Very low. The new patterns cannot fire on a write task because "give me X and delete Y" still has an explicit `_DELETE_SIGNALS` hit that takes precedence inside the CRUD branch, and `_WRITE_SIGNALS` still overrides via the `not has_write` guard at line 214 unless the task is questionish (these aren't). The only edge case is "give me access to X" — but that's not currently a task shape in the benchmark, and if it ever appears the search-lane posture is still safe (read-only posture never causes a security breach). No interaction with outcomes.md or defend.py.
