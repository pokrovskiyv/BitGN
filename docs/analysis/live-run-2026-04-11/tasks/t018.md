## Root cause hypothesis

**Exactly one hypothesis:**

`classify.py` regex patterns `_INBOX_PROCESSING_SIGNALS` / `_INBOX_OBJECT_SIGNALS` / `_PROCESS_LIKE_SIGNALS` do not cover the natural-English phrasing "inbound note" + "review … and act on it", so tasks that use those exact words fall all the way through the classification cascade to the `crud` default. The `_INBOX_OBJECT_SIGNALS` regex already enumerates `inbox|mailbox|queue|backlog|…|messages?|requests?|messages/` — the word `note(s)` and the modifier `inbound` are simply missing. Similarly, `_PROCESS_LIKE_SIGNALS` covers `process|triage|clear|handle|work through|go through|take care of` but omits the common synonyms `review|address|action`.

**Evidence chain:**
1. Local classifier run on the exact instruction text returns `task_type='crud'`, confirming the routing mismatch.
2. The first 10 agent steps follow the `inbox_processing.md` playbook almost verbatim (inspect system workflows → read schema → read inbox item → write target → verify) — meaning the agent's behavior was correct for inbox_processing, just starved of budget.
3. `metrics.step_count = 15` exactly equals `_STRATEGY_TABLE["crud"][0] = 15`, and the final step is a `read`, not `report_completion` — this is a hard-cap cut, not a decision failure.
4. `verifier_verdict: null` + empty `score_detail` proves the task never produced a verdict; it was suppressed by the cap.
5. The hallucinated `/60_outbox/outbox/README.MD` path at step 12 is exactly what `inbox_processing.md` line 4 and 22 ("Only use older paths like `outbox/…` if those paths actually exist in the current workspace") explicitly warns against — but that fragment was never loaded.

## Fix proposal (narrow GREEN zone only)

**Selected fix class:** `classify_rule`

**Target file:** `pac1-py/classify.py`

**Exact change:**
```diff
-_PROCESS_LIKE_SIGNALS = re.compile(
-    r"\b(process|triage|clear|handle|work\s+through|go\s+through|take\s+care\s+of)\b",
-    re.IGNORECASE,
-)
+_PROCESS_LIKE_SIGNALS = re.compile(
+    r"\b(process|triage|clear|handle|work\s+through|go\s+through|take\s+care\s+of|"
+    r"review|address|action|act\s+on|deal\s+with|respond\s+to)\b",
+    re.IGNORECASE,
+)
 _INBOX_OBJECT_SIGNALS = re.compile(
-    r"\b(inbox|mailbox|queue|backlog|waiting\s+messages?|pending\s+requests?|"
-    r"newly\s+arrived\s+requests?|unread\s+requests?|messages?|requests?)\b|messages/",
+    r"\b(inbox|mailbox|queue|backlog|waiting\s+messages?|pending\s+requests?|"
+    r"newly\s+arrived\s+requests?|unread\s+requests?|messages?|requests?|"
+    r"inbound\s+(?:note|message|item|mail)s?|inbound\s+\w+|"
+    r"incoming\s+(?:note|message|item|mail)s?|next\s+inbound|next\s+note)\b|messages/",
     re.IGNORECASE,
 )
```

**Rationale:** Narrowly widens two existing regex vocabularies. The first addition ("review|address|action|act on|deal with|respond to") covers the most common English synonyms for "process an inbox item" without pulling in unrelated verbs. The second addition ("inbound note", "next inbound", "incoming message", etc.) covers the noun phrasing used by real-world instructions that describe inbox items without the literal word `inbox`. Together these make the compound rule `_PROCESS_LIKE_SIGNALS AND _INBOX_OBJECT_SIGNALS` (classify.py line 148–151) fire correctly on "Review the next inbound note and act on it", pushing the task into the `inbox_processing` branch with a 32-step budget and the full inbox_processing playbook.

**Why classify_rule and not strategy_budget:** Raising the `crud` budget from 15 to 32 would be a blunt instrument that also affects legitimate CRUD tasks (which currently pass with 10–15 steps comfortably). The right fix is routing-level: give this task the correct playbook, not just more runway.

**Why not a prompt_fragment edit:** The `inbox_processing.md` fragment ALREADY contains the exact guardrails this agent needed (avoid `outbox/README.MD`, read `/00_inbox/AGENTS.MD`, prefer modern canonical paths). The fragment was simply not loaded because classification routed elsewhere. Editing `crud.md` to duplicate inbox_processing content would be the wrong layer.

**Generalizability:** `HIGH`
- Natural-English synonyms for "process an inbox" ("review … and act", "handle the next", "deal with", "respond to the incoming") likely appear in many benchmark tasks. The synonym set is small and linguistically bounded. Conservatively, 2–5 of the 104 tasks use `review|act on|respond to` + `inbound|next note|incoming message` phrasing. Additionally, any future benchmark mutation that uses these synonyms will be covered preemptively. Cannot claim HIGHEST because I have not scanned all 104 task instructions.

**Zone:** `GREEN` — single-file Python regex widening, no semantic behavior change for non-matching tasks, no effect on security paths (`threat_level == "high"` branch at classify.py line 158 still wins over inbox_processing routing), no effect on other task types (the `_WRITE_SIGNALS` / `_SEARCH_SIGNALS` / `_COMMUNICATION_SIGNALS` groups are untouched).

**Expected impact:** +1 on t018 (`budget_exhausted` → `OUTCOME_OK` with both finance records correctly created — the agent had already completed the two writes successfully by step 10, it just needed budget to finalize). Potentially +1 on other tasks with "review/act on inbound" phrasing. Honest conservative estimate: **+1 to +2 tasks**.

**Risks:** Minor regression risk if a non-inbox task uses `review` + `note` in an unrelated sense (e.g., "review the meeting note and summarize"). Mitigation: the compound rule requires BOTH `_PROCESS_LIKE_SIGNALS` AND `_INBOX_OBJECT_SIGNALS` to match — "review the meeting note" has `review` but lacks `inbound|next inbound|next note` modifier. The regex I added for `_INBOX_OBJECT_SIGNALS` requires the `inbound`/`incoming`/`next inbound`/`next note` qualifier, not bare `note`, which keeps this scoped. Second risk: `address` is sometimes used in the sense of "email address" — but `_COMMUNICATION_SIGNALS` already has `email(?!\s+address)` negative lookahead, and the compound rule still requires an inbox object. Third risk: a communication task with "respond to the incoming email" would now match both `inbox_processing` and `communication`, but classification ordering (line 169 before line 225) means inbox_processing wins, which is the right call for any task that says "respond to the incoming email in the inbox".
