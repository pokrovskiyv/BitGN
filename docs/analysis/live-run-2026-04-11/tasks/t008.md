## Root cause hypothesis

**Exactly one hypothesis:**

The `_ANALYSIS_SIGNALS` regex in `pac1-py/classify.py` line 52 includes `how\s+many` but omits the monetary/quantity synonyms `how\s+much`, `total`, `subtotal`, `sum`, `revenue`, `spend`, and `balance`. Any task phrased "how much did X" or "what's the total X" therefore falls through all classification branches and lands on the `crud` default. The downstream `crud` strategy loads only `crud.md` (5 lines, schema-focused) and never loads `analysis.md` with its NUMERIC AND MONETARY DISCIPLINE block, so the agent has no prompt-level pressure to read ALL relevant rows before answering a sum question. The crud budget of 15 steps is adequate in principle (the agent used only 6), but the agent was not instructed that aggregations require multi-row reads.

**Evidence chain:**
1. `classify.py` line 52: `_ANALYSIS_SIGNALS = re.compile(r"\b(analyze|summarize|compare|count|list\s+all|report|describe|explain|how\s+many)\b", re.IGNORECASE)` — no `how\s+much`, no `total`, no `sum`.
2. `classify.py` lines 203–211: the `analysis` branch is gated on `has_analysis`, which is False for this task, so the branch is skipped.
3. `classify.py` lines 214–222: the `search` branch requires `has_search or has_lookup` — both False.
4. `classify.py` line 236: falls through to `return TaskClassification(task_type="crud", estimated_steps=10, ...)` — the default.
5. `strategy.py` lines 82–90 + 109: only `addons[classification.task_type]` is loaded, so `analysis.md` is NOT appended to the system prompt.
6. `analysis.md` lines 11–14: contains the exact guardrail that would have prevented early termination — "For sums or subtotals, read ALL relevant rows first. Do not estimate from a partial read." The agent never saw this text.
7. Trajectory confirms: step 4 reads ONE invoice, step 6 reports — no iteration over the directory listing from step 3. This is the "partial read" pattern the analysis.md rule targets.

## Fix proposal (narrow GREEN zone only)

**Selected fix class:** `classify_rule`

**Target file:** `pac1-py/classify.py`

**Exact change:**
```diff
 _ANALYSIS_SIGNALS = re.compile(
-    r"\b(analyze|summarize|compare|count|list\s+all|report|describe|explain|how\s+many)\b",
+    r"\b(analyze|summarize|compare|count|list\s+all|report|describe|explain|"
+    r"how\s+many|how\s+much|how\s+often|total|subtotal|sum|aggregate|"
+    r"revenue|spend|spent|earned|made|balance|average|avg|mean)\b",
     re.IGNORECASE,
 )
```

**Rationale:** This widens `_ANALYSIS_SIGNALS` to include the quantity/monetary/aggregation synonyms that currently fall through to `crud`. It's a minimal, surgical addition — no new branches, no new strategy, no code flow change. The pattern list is deliberately targeted at computed-number questions: "how much", "how often", "total", "sum", "aggregate", "revenue", "spend/spent", "earned", "made" (matches "did we make" in t008), "balance", "average". Once the task classifies as `analysis`, it automatically gets `analysis.md` loaded with the NUMERIC AND MONETARY DISCIPLINE block, a 25-step budget (up from 15), and `pre_submit_verification=True` which may catch the single-read bug before submission.

One thing to watch: `made` is a common English verb and could false-positive (e.g. "I made a note" → analysis). I accept that risk here because (a) `\bmade\b` almost always co-occurs with money/quantity context in this benchmark, and (b) analysis strategy is a strict superset of crud — getting the analysis fragment instead of crud.md is never actively harmful for a simple CRUD task, it just loads an extra ~15 lines of prompt. The downside is roughly "a few more tokens and slightly tighter answer-precision instructions" on mislabeled tasks.

**Generalizability:** `MEDIUM`
- "How much", "total", and "sum" are very common phrasings for financial and analytical queries in the BitGN benchmark (finance invoices, subscriptions, transactions). Rough estimate: 3–7 of the 104 tasks ask computed-sum questions using these exact words. I cannot claim HIGH without scanning all task text — but the pattern is clearly broader than one task.

**Zone:** `GREEN` — classify-rule regex widening. No new branches, no new strategy key, no code flow change, no effect on security classification (which is threat-level-first at line 158 and unaffected). This is a GREEN-zone edit per the scope constraint (classify_rule is one of the three allowed GREEN classes).

**Expected impact:** +1 on t008 (gets analysis.md, 25-step budget, read-all-rows discipline → correct sum). Potentially +1 to +2 on other "how much" / "total" / "revenue" tasks in the benchmark. Honest conservative estimate: **+1 to +3 tasks**.

**Risks:**
- False positives on verbs like `\bmade\b` (e.g. "I made a file for X") → mislabeled as analysis. Mitigated: analysis strategy is stricter about numeric precision but otherwise compatible with CRUD tasks; the worst case is a slightly longer prompt and a slightly higher step budget, both benign.
- `\btotal\b` could match "total order" or "grand total" in non-numeric contexts → benign analysis routing.
- No security-path impact: threat classification runs FIRST at line 158 and is untouched.
