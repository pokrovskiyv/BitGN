**Selected:** `wrong_outcome`

**Justification:** The agent and verifier DISAGREE, and the verifier is objectively wrong on the facts — the trace shows step 1 reading `00_inbox/AGENTS.MD`, step 2 reading `00_inbox/000_next-task.md` (the next inbox message itself), and step 9 listing `00_inbox`. The agent's concrete actions match exactly what `inbox_processing.md` prescribes (read AGENTS.MD → list inbox → read item → follow workflow → write result → read-after-write). What failed was the **completion report narrative**: the agent's `report_completion` summary evidently led with OCR/invoice language ("No outbox action required — this is not an email task") and omitted the explicit inbox→action chain. The verifier, reading only the completion summary without access to the underlying step trace, saw "finance document processing" and could not verify that the finance document was the direct output of an inbox directive. This is the same class of bug that killed t000: agent does the correct work, report text fails to spell out the semantic linkage, verifier disagrees. Not a security miss, not a budget issue, not a classification mismatch (inbox_processing was the right route) — purely a communication / traceability gap at the reporting step.

## Root cause hypothesis

**Exactly one hypothesis:**

The `outcomes.md` PROACTIVE AMBIGUITY GATE and OK rule do not require the agent to write a **provenance chain** into the completion summary. When the agent successfully completes an inbox→workflow chain, it tends to summarize only the terminal action ("added frontmatter to invoice") rather than citing the triggering inbox message explicitly ("inbox/000_next-task.md directed OCR of invoice X → I added frontmatter per workflow Y"). Verifiers operating on completion summaries alone (with no trace access) can therefore fail to see the causal connection and default to CLARIFICATION. This is a reporting-protocol gap, not a reasoning gap — the agent is correct, but invisible.

**Evidence chain:**
1. Verifier reasoning explicitly lists four things it could not see: "(1) listing inbox contents, (2) reading an inbox message, (3) identifying what 'the next message' actually was, or (4) confirming the inbox was non-empty." ALL FOUR happened in the trace (steps 1, 2, 9). The verifier is judging the completion text only, not the trace.
2. The completion plan text on step 20 reads `"Report OUTCOME_OK with new evidence"` — confirming the agent itself understood this was a second submission, and was gathering "new evidence" (re-read + re-list) specifically to strengthen the report. But the report template does not require naming the source inbox file.
3. `outcomes.md` line 37 says "Inbox has messages but you processed them all successfully → OK, not CLARIFICATION" — this is a decision rule, not a reporting-format rule. Nothing in `outcomes.md` or `inbox_processing.md` tells the agent to cite the triggering inbox file by path in its completion summary.
4. Root, not symptom: a `classify.py` tweak would not help (already routes correctly). A budget bump would not help (already under budget). A new prompt fragment exists in `inbox_processing.md` but only covers process, not reporting. The gap is at the output-report layer.

## Fix proposal (narrow GREEN zone only)

**Selected fix class:** `prompt_fragment`

**Target file:** `pac1-py/workspace/prompts/fragments/inbox_processing.md`

**Exact change:**
```diff
 INBOX FILE DELETION:
 - Do not delete inbox files early.
 - Delete an inbox file only after the workflow explicitly calls for deletion and all required writes have been verified.
 - If the task just says to process the inbox item, do not assume deletion is part of success.
+
+COMPLETION REPORT PROVENANCE (MANDATORY):
+When reporting OUTCOME_OK for an inbox-processing task, the summary MUST contain, in order:
+1. The exact path of the inbox file you processed (e.g. `/00_inbox/000_next-task.md`).
+2. A one-sentence paraphrase of what that file asked for.
+3. The exact path(s) you wrote or modified in response.
+4. Confirmation that you read-after-write verified each written path.
+Example OK summary: "Processed /00_inbox/000_next-task.md which requested OCR of invoice 2025-11-04 northstar backfill. Wrote YAML frontmatter to /50_finance/invoices/2025_11_04__…alpha.m per /99_system/workflows/ocr-records.md schema. Read-after-write verified."
+Without this provenance chain, the verifier cannot confirm the inbox→action linkage and may reject OUTCOME_OK.
```

**Rationale:** This fix forces the agent to embed the causal trace into the completion summary text itself, independent of whether the verifier has access to the step log. It mirrors the "grounding citation" discipline already required in `reasoning.md` (quote-the-source for state transitions), but applied to the terminal reporting step. The four-point template is mechanical and hard to partially follow — either the inbox path appears in the summary or it doesn't. The example line is an actual reconstruction of what t064's successful summary SHOULD have said. The rule is scoped to OUTCOME_OK inside inbox-processing, so it cannot leak into security rejection paths.

**Generalizability:** `MEDIUM`
- This pattern (agent processes inbox correctly, verifier rejects because the summary omits the inbox filename) affects every inbox-processing task where the verifier is blind to the step trace. With ~10–15 inbox/queue-style tasks in a 104-task benchmark, the direct addressable set is 2–5 tasks. It does NOT help pure search or crud tasks (which don't go through the inbox-processing fragment), hence MEDIUM not HIGH. It will also slightly improve the score distinguishability for any eval that re-reads only the completion report — a broader hygiene benefit.

**Zone:** `GREEN` — prompt-fragment edit only. No Python change. No change to classify, strategy, outcomes, or defend. No effect on security decisions (security paths exit the decision tree well before OUTCOME_OK). No effect on stagnation logic.

**Expected impact:** +1 on t064 (verifier will accept OUTCOME_OK once the summary cites `/00_inbox/000_next-task.md`). Conservative extrapolation: **+1 to +3 tasks** across the 104-task benchmark, concentrated in inbox_processing-classified tasks where the verifier is skeptical of OCR/finance/calendar-side writes.

**Risks:** Minor — adding a mandatory template increases tokens in every inbox-processing completion summary by ~60 tokens. Very low risk of regression on existing PASSes (they already cite the inbox path implicitly; making it explicit only helps). One edge case: if the "next message" is a file that does NOT exist (empty inbox), the template cannot be followed — but that branch returns CLARIFICATION, not OK, so the rule does not apply.
