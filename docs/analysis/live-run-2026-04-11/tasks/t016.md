## Root cause hypothesis

**Exactly one hypothesis:**

`_INBOX_PROCESSING_SIGNALS` and its fallback (`_PROCESS_LIKE_SIGNALS` × `_INBOX_OBJECT_SIGNALS`) do not cover the "inbound note / inbound message" vocabulary. "Inbound" is not listed as a process-signal root, and "note" is not listed as an inbox-object. As a result, the common phrasing "Review the next inbound note and act on it." falls through every if-branch in `classify_task()` and lands in the CRUD default bucket with 15 steps and the `crud.md` fragment. This removes the inbox workflow discipline that the verifier explicitly references in its reasoning ("According to the AGENTS.MD rules, entity files in 10_entities/cast/ are authoritative for identity...").

**Evidence chain:**
1. classify.py line 73–79: `_INBOX_PROCESSING_SIGNALS` regex requires literal `inbox`, `mailbox`, `queue`, `backlog`, `messages?`, `requests?`, `pending`, `unread`, etc. — none present in "Review the next inbound note and act on it."
2. classify.py line 81–89: the `_PROCESS_LIKE_SIGNALS` + `_INBOX_OBJECT_SIGNALS` fallback also fails: `_PROCESS_LIKE_SIGNALS` has `process|triage|clear|handle|work through|go through|take care of`; `review` and `act on` are absent. Even if `_PROCESS_LIKE_SIGNALS` matched, `_INBOX_OBJECT_SIGNALS` requires `inbox|mailbox|queue|...|messages?|requests?` and `note` is not in the list.
3. strategy.py line 47: CRUD key maps to `(15, "standard", True)`. The t016 payload shows `step_count=9`, well inside that 15-step envelope — the agent was not budget-constrained, but it also had no inbox playbook to follow.
4. Sibling comparison: t011 ("Handle the next inbox item.") classified to inbox_processing (step_count=13, consistent with the 32-step envelope and the inbox_processing fragment). t016, t014, t018 all show step_count ≤ 15, consistent with the CRUD envelope. The delta between the two families is a single regex gap.
5. Verifier reasoning directly appeals to inbox-specific rules (`10_entities/cast/` authority, `50_finance/` bill location, "clarification first") — exactly the content that lives in `inbox_processing.md` but is absent from `crud.md`.
6. 10 tasks in the benchmark share this exact instruction text and every single one scored 0.0 — this is a systemic suppression, not a per-task incident.

## Fix proposal (narrow GREEN zone only)

**Selected fix class:** `classify_rule`

**Target file:** `pac1-py/classify.py`

**Exact change:**
```diff
 _INBOX_PROCESSING_SIGNALS = re.compile(
     r"\b(process\s+(the\s+)?inbox|from\s+(the\s+)?inbox|inbox\s+file|"
     r"(take\s+care\s+of|work\s+through)\s+(the\s+)?(?:inbox|incoming)\s+queue|"
     r"(?:incoming|inbox)\s+queue|pending\s+inbox\s+items?|mailbox|"
     r"message\s+backlog|waiting\s+messages?|pending\s+requests?|"
-    r"newly\s+arrived\s+requests?|unread\s+requests?)\b",
+    r"newly\s+arrived\s+requests?|unread\s+requests?|"
+    r"(?:next|latest|newest|oldest)\s+(?:inbound|incoming)\s+(?:note|message|item|email)|"
+    r"inbound\s+note|inbound\s+message)\b",
     re.IGNORECASE,
 )
 _PROCESS_LIKE_SIGNALS = re.compile(
-    r"\b(process|triage|clear|handle|work\s+through|go\s+through|take\s+care\s+of)\b",
+    r"\b(process|triage|clear|handle|work\s+through|go\s+through|take\s+care\s+of|"
+    r"review(?:\s+(?:and\s+act|the\s+next))?|act\s+on)\b",
     re.IGNORECASE,
 )
 _INBOX_OBJECT_SIGNALS = re.compile(
     r"\b(inbox|mailbox|queue|backlog|waiting\s+messages?|pending\s+requests?|"
-    r"newly\s+arrived\s+requests?|unread\s+requests?|messages?|requests?)\b|messages/",
+    r"newly\s+arrived\s+requests?|unread\s+requests?|messages?|requests?|"
+    r"inbound\s+note|inbound\s+message|next\s+(?:inbound|incoming))\b|messages/",
     re.IGNORECASE,
 )
```

**Rationale:** Three additions, each conservative and each aimed at one specific vocabulary hole:
1. The primary `_INBOX_PROCESSING_SIGNALS` rule gains an explicit "inbound note / inbound message / next-inbound-X" clause so the common benchmark phrasing classifies directly without relying on the fallback.
2. `_PROCESS_LIKE_SIGNALS` gains `review` and `act on` so the fallback path (process-like-verb × inbox-object-noun) also catches it, as a safety net.
3. `_INBOX_OBJECT_SIGNALS` gains `inbound note` / `inbound message` / `next inbound/incoming` so the fallback's object side also fires. Redundancy is intentional — either branch alone is sufficient, but both firing together is resilient against the exact word order the benchmark author picks.

The new tokens are tight: `inbound` is not common in non-inbox contexts (CRUD/search/analysis tasks don't use it), `review + act on` without an inbox object would still need `_INBOX_OBJECT_SIGNALS` to fire, and the whole edit is in classification (no prompt change, no security-path change).

**Generalizability:** `HIGH`
- 10 tasks in the current task_cache share this exact instruction text verbatim (t014, t016, t018, t036, t041, t068, t086, t091, t094, t097). Every one scored 0.0 in this run. The fix addresses all 10 directly and does so without touching the existing `inbox_processing.md` workflow or the sibling "handle / take care of" path that already works.
- This is one of the largest single-vocabulary gaps in classify.py. Cross-checking the 35 inbox-next-item variants: 25 match via `_PROCESS_LIKE_SIGNALS`+`_INBOX_OBJECT_SIGNALS`, 10 do not. The fix closes the remaining 10.

**Zone:** `GREEN` — classify.py regex addition only. No prompt change, no Python logic change, no security path touched. The new tokens are narrow and do not overlap with security_test, search, or communication signal families. `_INBOX_PROCESSING_SIGNALS` is evaluated before security fallback only when `threat_level != "high"`, so injection tasks with inbox vocabulary still route through security_test first.

**Expected impact:** Conservative **+1 task** (t016 only, if the agent with inbox_processing discipline reaches OK after verifying OCR is unsupported for real files that actually exist). Realistic **+2 to +4 tasks** from the 10-task "inbound note" family, because the inbox_processing fragment's explicit "verify identity and channel first" guidance + 32-step budget gives the agent room to follow the correct workflow before declaring UNSUPPORTED or CLARIFICATION. Honest ceiling is bounded by whatever the underlying inbox content demands — if the benchmark author really does ask for OCR-only work on all 10, UNSUPPORTED remains the right call and the reclassification still helps the agent reach it cleanly instead of waffling at step 9.

**Risks:** Very low. The new tokens are specific:
- `inbound note|inbound message` — no legitimate CRUD/search task uses "inbound" without meaning inbox.
- `review + act on` — only caught when paired with an `_INBOX_OBJECT_SIGNALS` match. A task like "Review the contacts folder" would still route to CRUD (no inbox object).
- `(next|latest|newest|oldest) + (inbound|incoming) + (note|message|item|email)` — the full phrase is required, so incidental occurrences of "next note" or "incoming email" inside an analysis task won't accidentally trip it.
- Worst case false positive: a task like "review the inbound shipment note" — semantically ambiguous, but the inbox_processing fragment's EMPTY/AMBIGUOUS INBOX RULE would trigger CLARIFICATION, which is a safe outcome.
- No regression on t011/t015/t019/etc. because those continue to match via the existing `handle + inbox` path before the new rule is even evaluated.
