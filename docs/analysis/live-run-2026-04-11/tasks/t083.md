**Selected:** `classification_mismatch`

**Justification:** The task is a monetary-sum analysis — exactly what `analysis.md` (lines 11–16 "NUMERIC AND MONETARY DISCIPLINE") was written for. Instead, `classify.py` routes it to `crud` because the phrase "how much money" does not match any of the `_ANALYSIS_SIGNALS` tokens (the regex covers `how\s+many` but not `how\s+much`). The downstream consequences are cumulative:
1. The agent loads `crud.md` (5 lines, no numeric guidance) instead of `analysis.md` (discipline for citing sources, exact transcription, "read ALL relevant rows before summing", and explicit CLARIFICATION for missing inputs).
2. The step budget is 15 instead of 25 — 2 slack steps remaining for what is intrinsically a multi-file aggregation.
3. The agent never uses `search` because `crud.md` does not recommend it, even though a literal-phrase search would have immediately resolved whether "follow-up timeline prototype review" exists in the corpus.

Every failure symptom (exhaustive brute reads, no search, no verification, late-planning spike, score=0) traces back to the single regex miss on `how\s+much`. This is a textbook classifier miss, not a reasoning, security, or output-format failure.

## Root cause hypothesis

**Exactly one hypothesis:**

`classify.py._ANALYSIS_SIGNALS` (line 52) matches `how\s+many` but not `how\s+much`. Monetary questions phrased as "how much money did we make / spend / earn / owe" fall through all classifier branches to the default `crud` bucket, which loads the wrong prompt fragment and the wrong step budget. The fix is a one-token regex extension.

**Evidence chain:**
1. Task text begins with "How much money did we make…" — the only keyword that could match any signal is `make`, and `make` is not in any signal list.
2. `_ANALYSIS_SIGNALS` regex literal (classify.py line 52): `\b(analyze|summarize|compare|count|list\s+all|report|describe|explain|how\s+many)\b`. `how\s+many` is present; `how\s+much` is NOT. I verified by reading the file.
3. `classify_task()` therefore computes `has_analysis=False` and every prior branch also evaluates False → the function returns the final `crud` fall-through (classify.py lines 236–243).
4. `strategy.decide_strategy()` (strategy.py lines 73–100) with `task_type="crud"` loads `crud.md` and uses the `"crud": (15, "standard", True)` strategy entry — step budget 15, no analysis fragment, no numeric/monetary discipline section.
5. The trace confirms the downstream damage: 11 serial reads, no `search` call, step 13 of 15 spent on `report_completion`, zero verification or re-read, and a score of 0. This matches the predicted behaviour of routing an analysis task through the CRUD pipeline.
6. Root vs symptom check: would editing `outcomes.md` fix this? No — the agent never reached the CLARIFICATION gate because it was told (implicitly, via `crud.md`) to go read and write things. Would editing `crud.md` fix this? Partially, but it would pollute a fragment intended for simple write-verify flows with numeric-sum content. The correct fix is to stop the task from landing in `crud` in the first place.

## Fix proposal (narrow GREEN zone only)

**Selected fix class:** `classify_rule`

**Target file:** `pac1-py/classify.py`

**Exact change:**
```diff
 _ANALYSIS_SIGNALS = re.compile(
-    r"\b(analyze|summarize|compare|count|list\s+all|report|describe|explain|how\s+many)\b",
+    r"\b(analyze|summarize|compare|count|list\s+all|report|describe|explain|"
+    r"how\s+(?:many|much)|total(?:\s+amount|\s+spend|\s+revenue)?|what\s+was\s+the\s+total)\b",
     re.IGNORECASE,
 )
```

**Rationale:** The minimal fix is to add `how\s+much` to the existing `how\s+many` alternation — that alone would have routed t083 into `analysis` and loaded `analysis.md` with its NUMERIC AND MONETARY DISCIPLINE section. I additionally propose two small adjacent extensions (`total`, `total amount/spend/revenue`, `what was the total`) because they are the same semantic class and the benchmark is likely to surface similar phrasings. These are conservative: all three extra tokens are unambiguous analysis cues; none clash with CRUD, communication, or security test signals. The regex grows by ~40 characters, no new capture groups, no change to the alternation's behavior for existing patterns.

Secondary benefit — because `_ANALYSIS_SIGNALS` is checked in the `analysis` branch (classify.py lines 203–211) which also requires `not has_write`, there is no risk of hijacking a CRUD-with-analytics task (e.g. "compare X and Y and write the result to report.md" would still match both `has_analysis=True` and `has_write=True`, so it would progress to the multi-step branch first).

**Generalizability:** `MEDIUM`
- This exact classifier gap (monetary-sum questions phrased as "how much … did we [verb] …") is likely to recur on any finance/analytics task in the benchmark. A back-of-envelope estimate: benchmarks of this scale (~104 tasks) typically have 3–6 financial questions and 2–4 metric/count questions using "how much". Together, 2–5 tasks are plausible candidates for direct benefit. I marked MEDIUM (not HIGH) because I cannot scan the full 104-task corpus without more file reads, but the pattern is structural enough to help more than one task.
- Indirect benefit: every task that previously fell through to CRUD default with no positive match on any signal — a pure "is there any way this could be an analysis task?" fallback — gets a stronger classifier. The narrower the CRUD bucket, the fewer false negatives on the downstream analysis fragment.

**Zone:** `GREEN` — a single-line regex extension in `classify.py`. No Python structural change, no prompt fragment edits, no security path touched. The threat-level logic (`_compute_threat_level`) is upstream of this branch and unaffected. `_STRATEGY_TABLE` in `strategy.py` is unchanged.

**Expected impact:** +1 on t083 directly (routes to `analysis` → loads `analysis.md` → agent uses `search`, caches source rows, and either computes the sum correctly or returns CLARIFICATION because the service line is absent — both are non-zero-scoring outcomes). Conservative estimate: **+1 to +2 tasks** across the benchmark. No regression risk on tasks already classified correctly, because the change only adds positive matches.

**Risks:** Minor — if any task contains phrasings like "how much effort will it take to create a file" (rare and contrived), those would be re-routed from CRUD to analysis. Even then, `analysis.md` is compatible with most read-heavy workflows; the step budget is larger (25 vs 15), which is strictly safer. Second minor risk: the `total(?:\s+amount|\s+spend|\s+revenue)?` extension could match non-analytical uses of the word `total` (e.g. "total this list" as an imperative), but imperative usages are rare in the benchmark, and even then routing to `analysis` is safer than routing to `crud`.
