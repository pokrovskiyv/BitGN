**Justification:** The answer submitted in step 8 was derived from a single project folder (`window_farm_notes`), not from a survey of all projects. For a counting task over a set of projects, the correct behavior is: (1) list `/40_projects/` to enumerate every project directory, (2) read each project's `README.MD` / metadata for status + mentioned people, (3) accumulate `status == PLANNED and Pepper ∈ people`, (4) report the sum. The agent skipped step (1) entirely. Whatever number it produced is a single-file count, not a project count. ## Root cause hypothesis

**Exactly one hypothesis:**

`analysis.md` instructs the agent to "list subdirectories explicitly" but does NOT give the agent an explicit multi-entity enumeration recipe for counting-across-entities tasks. The fragment's COUNTING section (line 9) talks about `search(count_only=True)` for counting matches *within a file*, which is actively misleading for counting ENTITIES (projects, contacts, events) where the right primitive is `list` + per-entity read, not a single regex count. The agent in step 7 followed the misleading recipe literally — it ran `count_only=True` on ONE file instead of iterating over all project folders. The prompt nowhere tells the agent "counting X across the filesystem requires listing the directory that holds X first".

**Evidence chain:**
1. Step 5 is a single `read` of `window_farm_notes/README.MD`, and step 7 is an in-file count on that same README. No sibling project was ever opened. This matches "agent read the analysis.md COUNTING advice literally and picked the wrong primitive".
2. `analysis.md` line 9: the verbatim example is `search(pattern="blacklist", root="/docs/channels/Telegram.txt", count_only=True)` — which is in-file counting. This is the ONLY count example in the entire fragment, and it primes the agent toward in-file counting even when the task is entity-level counting.
3. `analysis.md` line 5 warns about the shallow tree but is phrased as "before concluding data is absent" — it reads as a rule for negative claims (absence), not for enumeration when counting positive hits. The agent did not hit absence so it felt no pressure to enumerate.
4. Root, not symptom: a classify fix would not help (the task IS analysis); a budget fix would not help (only 8/25 steps used, budget was plentiful); a search.md fix would not help (the search fragment isn't even loaded for analysis tasks). The minimal missing piece is an enumeration-before-counting rule inside `analysis.md`.

## Fix proposal (narrow GREEN zone only)

**Selected fix class:** `prompt_fragment`

**Target file:** `pac1-py/workspace/prompts/fragments/analysis.md`

**Exact change:**
```diff
 TASK TYPE: Analysis operation.
 - Read all relevant sources before synthesizing.
 - Cite every source in grounding_refs.
 - Be precise with numbers and comparisons.
 - The boot-time tree is only 2 levels deep. ALWAYS list subdirectories explicitly before concluding data is absent.
 - ANSWER PRECISION: when the task asks for a specific value (email, name, number, list), your completion message must contain ONLY that value — no prefix, no explanation. Just the raw answer.
 - Do NOT report OUTCOME_NONE_CLARIFICATION without first reading files that might contain the answer. If the task asks about specific data, explore the filesystem thoroughly.

 COUNTING: When the task asks "how many" or requires counting items, use the search tool with count_only=True for EXACT counts. Do NOT read a file and count manually — this is error-prone for large files. Example: search(pattern="blacklist", root="/docs/channels/Telegram.txt", count_only=True) returns the precise count.
+
+COUNTING ACROSS ENTITIES: If the task counts ENTITIES (projects, contacts, events, messages, files) matching a condition — not occurrences of a substring inside one file — then `count_only=True` on a single file is the WRONG primitive. The correct recipe is:
+  1. `list` the directory that holds the entity (e.g. /40_projects for projects, /10_entities/cast for people) to enumerate EVERY candidate.
+  2. For each candidate, `read` just enough to check the condition (status field, tags, mentioned people).
+  3. Accumulate the matches and report the count.
+A count derived from a single file when the task asks about a set of items is almost always wrong.
+Example: "How many PLANNED projects involve Pepper?" → list /40_projects, read each project's README.MD, count the ones where status == PLANNED AND Pepper is listed.
+Example: "How many contacts are on the blacklist?" → list /10_entities/cast, read each entity, count matches. NOT: search one blacklist.txt with count_only=True (that counts lines in the file, not contacts).
```

**Rationale:** The existing COUNTING paragraph primed the agent toward in-file counting, so a fix that only tightens `list-first` enforcement would fight the existing example. Instead, add a second, more specific recipe that distinguishes the two cases (in-file occurrence counting vs. cross-entity counting) and gives a concrete pattern for the latter. Both examples are drawn from real task shapes (the t029 task itself, and a plausible blacklist-style task) so the agent can pattern-match immediately. The change preserves the existing `count_only=True` advice for its valid use case — scanning one file for token occurrences — and only adds a new branch for entity-level counting.

**Generalizability:** `MEDIUM`
- This failure mode should recur for any task of the form "how many X [matching condition]" where X is a directory-backed entity (projects, contacts, events, inbox messages, files of a certain type). A conservative scan of the 104-task benchmark would flag every task starting with "how many" and containing a plural noun that maps to a directory. Likely 3–6 such tasks. Cannot claim HIGH without a broader scan, but the pattern is common enough in practical agent benchmarks that the fix should see multi-task carryover.

**Zone:** `GREEN` — prompt-fragment edit only. No Python change, no classify rule change, no strategy budget change, no effect on security paths. The change makes CLARIFICATION *less* likely (agent will explore more before giving up) and OK *more* likely on counting tasks, which is safe: CLARIFICATION on a counting task is currently a 0-point outcome, so the regression floor is zero.

**Expected impact:** +1 on t029 (assuming the underlying truth is a specific small integer answer the agent now computes correctly). Potentially +1 to +2 more on sibling entity-counting tasks in the 104-task benchmark. Honest conservative estimate: **+1 to +3 tasks**.

**Risks:** Small risk that the agent now over-lists for in-file counting tasks (e.g., "how many blacklisted domains in this file") — mitigated by keeping the original `count_only=True` paragraph intact and framing the new recipe as an explicit branch ("if counting ENTITIES, not occurrences"). Second minor risk: the agent may read every candidate file even when the directory listing already encodes the answer (e.g., counts matching filename patterns) — acceptable because over-exploration in analysis tasks costs tokens, not score.
