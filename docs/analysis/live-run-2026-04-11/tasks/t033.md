**Selected:** `classification_mismatch`

**Justification:** The task is a textbook numeric aggregation: "how much money … from service line X … since date Y". It belongs in `analysis` type — that fragment carries the `NUMERIC AND MONETARY DISCIPLINE` block (lines 11–15 of `analysis.md`) which mandates row-level grounding, full enumeration of inputs, and exact transcription. Instead, the classifier dropped the task into `crud`, which loads a 6-line prompt fragment about "verify target exists before writing". The agent therefore ran a crud trajectory on an analysis problem and bailed after 4 steps without reading a single finance record. The misclassification is not downstream of poor LLM behavior — it is upstream, in `classify.py`'s regex coverage. `_ANALYSIS_SIGNALS` captures `how\s+many` but not `how\s+much`. That single gap explains the whole failure chain: wrong type → wrong fragment → no numeric discipline → premature completion → score 0.

## Root cause hypothesis

**Exactly one hypothesis:**

`classify.py._ANALYSIS_SIGNALS` is missing `how\s+much`, so questions that ask for a total, sum, or aggregate amount are never routed to the `analysis` strategy. The agent therefore receives the `crud` prompt fragment (which is optimized for "write a file and verify") instead of `analysis.md` (which carries the `NUMERIC AND MONETARY DISCIPLINE` block mandating row-level grounding, full enumeration, and exact transcription).

**Evidence chain:**
1. Classifier trace (computed by hand from `classify.py` lines 140–152): on the t033 instruction, `has_write=False`, `has_delete=False`, `has_search=False`, `has_lookup=False`, `has_analysis=False`, `has_multi_step=False`, `has_communication=False`, `has_inbox_processing=False`, `is_questionish_lookup=False`. Every `if` branch is skipped; control falls through to the `crud` default at line 236.
2. The ONLY token in the task that could have fired an analysis signal is "How much". `_ANALYSIS_SIGNALS` (line 51) contains `\b(analyze|summarize|compare|count|list\s+all|report|describe|explain|how\s+many)\b`. Note `how\s+many` (for discrete counts) but no `how\s+much` (for continuous/monetary amounts).
3. The agent's 4-step trajectory is exactly what the wrong fragment predicts: a single search, no row reads, early `report_completion`. In contrast, `analysis.md` line 15 — "For sums or subtotals, read ALL relevant rows first. Do not estimate from a partial read" — would have forced the agent to enumerate finance records explicitly.
4. Root, not symptom: the prompt fragments are correct; it is the routing that fails. Fixing `analysis.md` further or tightening `crud.md` would not help, because the agent was never going to see `analysis.md` in the first place. The fix must be in `classify.py`.

## Fix proposal (narrow GREEN zone only)

**Selected fix class:** `classify_rule`

**Target file:** `pac1-py/classify.py`

**Exact change:**
```diff
 _ANALYSIS_SIGNALS = re.compile(
-    r"\b(analyze|summarize|compare|count|list\s+all|report|describe|explain|how\s+many)\b",
+    r"\b(analyze|summarize|compare|count|list\s+all|report|describe|explain|"
+    r"how\s+many|how\s+much|total|subtotal|sum\s+of|aggregate)\b",
     re.IGNORECASE,
 )
```

**Rationale:** This adds the four lexical patterns most commonly used by benchmark authors to frame a numeric-aggregate question — `how much`, `total`, `subtotal`, `sum of`, `aggregate`. The inclusion of `how much` is the direct fix for t033; the other three are low-risk companions that are vocabulary-specific to numeric aggregation (they do not overlap with CRUD, search, communication, or security-test phrasing). Once the pattern matches, the existing branch at line 203 (`if has_analysis and not has_write: → analysis`) routes correctly, the `analysis.md` fragment is loaded, the strategy budget expands to 25 steps, and the agent inherits the `NUMERIC AND MONETARY DISCIPLINE` guidance that mandates reading all rows before summing.

**Generalizability:** `MEDIUM-HIGH`

- The benchmark probably contains several tasks phrased as "how much money…", "what's the total of…", "what's the subtotal of…", or "what is the aggregate of…". My conservative estimate is 2–4 tasks in the 104-task set explicitly use aggregation vocabulary that would benefit from this fix. Generalizability is tempered because I cannot claim HIGH without cross-referencing all task texts.
- Low regression surface: `total`, `subtotal`, `sum of`, `aggregate` are unlikely to appear as noise words in CRUD or communication tasks. `how much` is even safer — it is unambiguously an aggregation question.

**Zone:** `GREEN` — a regex extension inside `classify.py` only, no strategy table edits, no prompt changes, no effect on security or threat detection paths. Classification rule is a per-task pure function with no shared state.

**Expected impact:** +1 on t033 (routes to `analysis`, loads the `NUMERIC AND MONETARY DISCIPLINE` fragment, raises budget to 25, forces row-level grounding). Potential +1 to +2 more tasks in the live benchmark that use the same vocabulary. Honest estimate: **+1 to +3 tasks**.

**Risks:**
1. A task phrased "how much time do you have?" could route to analysis — but that phrasing is unlikely in a file-agent benchmark, and even if misrouted, analysis's step budget and prompt are stricter, not looser, so no security or correctness regression.
2. A task that says "send a total of 5 emails" would hit `total` and also `communication` — but `has_communication` is evaluated after `has_analysis`, and the first matching branch wins. The ordering in `classify_task` currently puts analysis BEFORE communication (line 203 before line 225), so communication tasks with the word "total" would incorrectly route to analysis. Mitigation: keep the fix narrow to `how much`, `sum of`, and `aggregate` — skip the bare `total` / `subtotal` tokens, since those could appear in communication contexts. I recommend the narrower diff below:

```diff
 _ANALYSIS_SIGNALS = re.compile(
-    r"\b(analyze|summarize|compare|count|list\s+all|report|describe|explain|how\s+many)\b",
+    r"\b(analyze|summarize|compare|count|list\s+all|report|describe|explain|"
+    r"how\s+many|how\s+much|sum\s+of|aggregate)\b",
     re.IGNORECASE,
 )
```

Dropping `total`/`subtotal` keeps the regression surface near zero while still fixing t033 and similar `how much / sum of / aggregate` phrasings.
