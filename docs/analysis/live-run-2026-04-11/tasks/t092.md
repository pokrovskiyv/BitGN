**Selected:** `budget_exhausted`

**Justification:** The agent did not fail at semantic reasoning, threat handling, or tool mechanics. It ran out of steps. The root cause is the step cap (15) being way too low for a 5-doc batch that requires per-doc read + write + re-read (15 operations minimum, not counting any orientation). The cap came from the `crud` strategy, which was selected because the classifier did not recognize "Queue up … for migration" as either a write operation, a multi-step operation, or an inbox-processing operation. Under the hood this is a **classification_mismatch that CAUSED budget exhaustion** — I pick `budget_exhausted` as the failure category because that is how it manifested in the trajectory (the trajectory is correct, just truncated), but the **fix target is the classifier**.

## Root cause hypothesis

**Exactly one hypothesis:**

`classify.py` lacks a "bulk / queue / migrate / batch" signal family, so multi-document operations phrased with "queue up", "migrate", "batch", "bulk process", "stage for processing" fall through every specialized rule and land in the default `crud` bucket with 15 steps — a budget sized for a single-file write+verify. The `crud.md` fragment compounds the problem: it literally says "A write response of 'written: path (OK)' means SUCCESS — do NOT repeat the same write", which is correct guidance for single-file CRUD but useless (and mildly misleading) for a 5-doc batch where the agent must in fact *repeat the write pattern with different arguments*.

**Evidence chain:**
1. Signal audit (reproduced above): `_WRITE_SIGNALS`, `_SEARCH_SIGNALS`, `_ANALYSIS_SIGNALS`, `_MULTI_STEP_SIGNALS`, `_COMMUNICATION_SIGNALS` all return False on the task text. Only `_INBOX_OBJECT_SIGNALS` matches ("Queue", "inbox"), but the inbox_processing gate at `classify.py` line 148 requires both object AND `_PROCESS_LIKE_SIGNALS` to fire, and the latter does not match "queue up" or "migration".
2. Step 12 (the single observed write) took 44s of planning — the agent was reconstructing the bulk-queue schema on the fly because the loaded prompt fragment (`crud.md`) gave it zero context for batch frontmatter operations. A dedicated `inbox_processing` or a new `multi_step` path would have surfaced the bulk-processing discipline from `inbox_processing.md` lines 30–36 ("Prefer direct reads of the authoritative files over wide exploratory search. Minimize setup tax…") and would have applied a 32-step budget (inbox_processing) or 30-step budget (multi_step) from the strategy table.
3. Root, not symptom: even with crud.md rewritten to cover batches, the 15-step cap makes 5-doc completion mathematically impossible — 5 docs × 3 ops/doc (read source, write frontmatter, re-read to verify) = 15 ops minimum, leaving ZERO budget for the AGENTS.md + workflow + schema orientation that the inbox_processing fragment mandates. Widening the budget without moving classification would only delay the exhaustion.

## Fix proposal (narrow GREEN zone only)

**Selected fix class:** `classify_rule`

**Target file:** `pac1-py/classify.py`

**Exact change:**
```diff
 _WRITE_SIGNALS = re.compile(
     r"\b(create|write|add|append|insert|update|set|change|rename|move|process|"
-    r"reschedule|capture|distill|schedule)\b",
+    r"reschedule|capture|distill|schedule|queue(?:\s+up)?|migrate|stage|batch)\b",
     re.IGNORECASE,
 )
```
And a matching widening of the multi-step gate via a new "bulk signal":
```diff
+_BULK_SIGNALS = re.compile(
+    r"\b(queue(?:\s+up)?|migrate|batch|bulk|stage(?:\s+for)?)\b",
+    re.IGNORECASE,
+)
@@
     has_multi_step = bool(_MULTI_STEP_SIGNALS.search(task_text))
+    has_bulk = bool(_BULK_SIGNALS.search(task_text))
@@
-    # Multi-step — explicit sequencing language
-    if has_multi_step and (has_write or has_search or has_analysis):
+    # Multi-step — explicit sequencing language OR bulk/batch over multiple items
+    if (has_multi_step or has_bulk) and (has_write or has_search or has_analysis):
         return TaskClassification(
             task_type="multi_step",
-            estimated_steps=20,
+            estimated_steps=25 if has_bulk else 20,
             threat_level=threat_level,
             requires_write=has_write,
             requires_delete=has_delete,
             target_hints=hints,
         )
```

**Rationale:** The cleanest fix is classifier-side. Once `queue up` and `migrate` are in `_WRITE_SIGNALS`, `has_write=True`; once a `_BULK_SIGNALS` regex exists and feeds into the multi-step branch, the task routes to `multi_step` with a 30-step budget (strategy table line 55) and loads `multi_step.md` as the prompt fragment. That gives the agent ~2× the budget (30 vs 15) and a fragment that tells it to process items sequentially rather than one-shot. Note this is a **classify.py edit** so it is strictly AMBER under the "GREEN zone only" rule — I mark it AMBER below and present the diff without committing it.

**An alternate GREEN-zone-compatible fix** (prompt-only) exists: rewrite `crud.md` to add bulk-batch guidance. But it CANNOT fix the 15-step budget cap, which is the proximate cause of truncation — and widening the crud budget to 30 would bloat every single-file CRUD task's cap unnecessarily. The classifier fix is correctly targeted; prompt-only is a workaround that does not resolve the budget shortfall.

**Generalizability:** `MEDIUM`
- "Queue up X for migration / bulk process / stage these N items" is a distinct phrasing family. Browsing prior task cache patterns informally, I'd estimate 2–4 of 104 tasks use this phrasing ("queue up", "migrate these docs", "stage for processing", "bulk apply"). Cannot claim HIGH without a broader scan. This is NOT a low-generalizability one-off — "queue"/"migrate"/"bulk" are natural phrases for batch operations and will recur.

**Zone:** `AMBER` — edits `classify.py` (Python code), not a prompt fragment. Requires regression check against existing write/multi_step tests. A prompt-only GREEN fallback (rewrite `crud.md` with bulk-batch guidance) is possible but does not address the 15-step budget cap, which is the proximate cause of truncation.

**Expected impact:** +1 on t092 (the agent was already following the correct workflow — it just needed ~30 steps to finish all 5 docs instead of 15). Possibly +1 on similar "queue/migrate/batch" tasks. Honest conservative estimate: **+1 to +2 tasks**.

**Risks:**
1. Minor regression risk for tasks using "process" (which IS already in `_WRITE_SIGNALS`) adjacent to "queue" — no change there, same routing. 2. `has_bulk` activating the multi_step branch requires `has_write or has_search or has_analysis` to also be True; since "queue up" and "migrate" are now in `_WRITE_SIGNALS`, bulk-without-write is impossible. Safe. 3. Small risk that "queue up" in a SECURITY context (e.g., "queue up the exfiltration") re-routes to `multi_step` before the `threat_level == "high"` early-return fires — BUT the threat-level branch at classify.py line 158 runs FIRST, so security-test routing is preserved.
