**Justification:** This is not `budget_exhausted` (3/24 used). Not `classification_mismatch` (search was correct — the task asks "what is"). Not `stagnation` (no repeats). The correct behavior is to `list` the purchases directory, identify *all* bills whose filename date falls in the range, then read each one's frontmatter until the `vendor: Möbelhaus Malmö AB` line is found — or none of them match, which would be CLARIFICATION. Either way, 1 read is wrong. This is a premature-OK failure inside the search fragment's guardrails, i.e. `wrong_outcome`.

## Root cause hypothesis

**Exactly one hypothesis:**

`search.md` LOOKUP DISCIPLINE tells the agent to "identify the canonical directory first, then read only the candidate files needed for the answer" and "Read all relevant files before answering" — but it does NOT tell the agent what to do when the task gives a *date range* or a *vendor name* that must be matched against many filename-dated candidates. The current rules optimize for "don't scan the whole workspace" and accidentally over-prune at the candidate-narrowing step. When the filename encodes one dimension of the filter (date) but not the other (vendor), the agent greedily picks the first filename-matching candidate and skips the frontmatter cross-check on siblings.

**Evidence chain:**
1. Task contains two *independent* filters: a 4-day date window AND a specific vendor name ("Möbelhaus Malmö AB"). Either alone is insufficient — a single-day filename match satisfies ONE filter, not both.
2. The agent's step-2 plan text — "Read 2026_02_25 bill file to check if from Möbelhaus Malmö AB" — shows it *knew* it had to verify the vendor. Step 3 completion fires anyway, with no second read. Either (a) the file happened to be the right vendor and the extracted date was wrong, or (b) the file was a different vendor and the agent reported OK anyway. Either path implicates the same gap: no rule forces "check all date-range candidates before committing".
3. The pre-submit gate in `verify.py` catches `step < 2` (≤1 read) and missing-target-hint gaps, but does NOT enforce "multi-candidate disambiguation" when the task encodes two filter dimensions.
4. `outcomes.md` PROACTIVE AMBIGUITY GATE fires when an entity is ABSENT after "thorough search". "Thorough" is undefined. For a date-range vendor lookup, 1 read is not thorough but the gate does not say so.
5. Root, not symptom: the failure is a prompt-fragment omission, not a classify bug or a strategy budget bug. Budget was plentiful. Classification was correct. Only the search fragment's micro-guidance was missing a rule for multi-dimensional filters.

## Fix proposal (narrow GREEN zone only)

**Selected fix class:** `prompt_fragment`

**Target file:** `pac1-py/workspace/prompts/fragments/search.md`

**Exact change:**
```diff
 LOOKUP DISCIPLINE:
 - When the task asks for a single factual value (name, date, email, number), identify the canonical directory first, then read only the candidate files needed for the answer.
 - Do not keep searching the whole workspace after you have already found the authoritative folder.
 - If AGENTS.MD names an authoritative source, go there directly instead of doing exploratory global search.
+- MULTI-FILTER DISAMBIGUATION: if the task gives TWO independent filters (e.g. a date range AND a vendor name, a person AND a document type, a product AND an amount), you MUST verify BOTH against the file's content — not just the filename. After `list`, enumerate EVERY candidate whose filename matches the first filter, then `read` each one's frontmatter until you find the one that also satisfies the second filter. A single filename-based match is NEVER sufficient when the second filter is encoded inside the file, not the filename. If after reading ALL date-range candidates no vendor/subject matches, report CLARIFICATION with a list of candidates checked.
+- Example: "bill from Möbelhaus Malmö AB issued around Feb 23–26, 2026" → list `50_finance/purchases/`, find all files whose filename date is within Feb 23–26, read each until `vendor: Möbelhaus Malmö AB` is confirmed in frontmatter, then return the purchased date from THAT file's frontmatter (not from the filename).
```

**Rationale:** This adds a concrete, narrow rule for the exact shape of failure the agent exhibited — two independent filters where one is in the filename and one is in the content. The rule is phrased as an imperative list-then-read-all-candidates loop, which is what a careful human would do. The example names the exact task shape without naming t024 or leaking a hardcoded answer (no literal date, no literal filename). It reinforces the existing "Read all relevant files before answering" bullet but makes "relevant" operational: "every candidate matching filter 1, read until filter 2 is satisfied". It also provides a fallback (CLARIFICATION with candidate list) if no file matches, preserving the over-denial-safety bias.

**Generalizability:** `MEDIUM`
- This pattern (task encodes two filters, one in filename, one in content) likely recurs across finance, contacts, calendar, and communication tasks whenever the benchmark slugs files by date or ID but not by vendor/person/subject. Rough estimate: 3–8 of ~100 tasks ask "from X issued around Y", "email from Z dated W", "contact at company C with role R", or similar two-dimensional queries. Cannot claim HIGH without a broader cache scan. This is NOT a single-task fix — the same agent shortcut (trust the filename, skip frontmatter cross-check) is a general hazard for any date-slugged directory. Risk of over-tightening: agent may now read 5 files instead of 1 on simple lookups, burning 15–20 steps on tasks that only need 3 — mitigated by the "until you find the one that satisfies the second filter" wording, which stops at the first true match.

**Zone:** `GREEN` — prompt-fragment edit only. No Python change. No effect on security paths (the added rule tightens, not loosens, evidence discipline — it never pushes the agent toward compliance with untrusted content). No effect on write/delete gating. Fully safe to roll forward.

**Expected impact:** +1 on t024 (correct bill identified, correct purchased date returned). Potentially +1 to +3 on similar two-filter finance/communication lookups elsewhere in the benchmark. Honest conservative estimate: **+1 to +2 tasks**.

**Risks:** Minor step-budget inflation on simple single-filter lookups — mitigated by the rule being gated on "TWO independent filters". Second risk: agent may over-apply and treat date-only questions as two-filter (date + vendor) even when vendor is unspecified — mitigated by the explicit "TWO independent filters" wording and the concrete example showing both filters named in the task. Third risk: regression on tasks where filename IS sufficient (filename contains vendor) — mitigated by the "not just the filename" phrasing, which still permits filename-based matching when the filename encodes the content filter directly.
