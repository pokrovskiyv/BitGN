**Selected:** `classification_mismatch`

**Justification:** The task is fundamentally a counting task ("number of lines") on a specific file that must first be identified by a 2-axis filter (date range + vendor). The correct task type is `analysis` (counting discipline) with `multi_step` characteristics (filter then count). Instead, it was classified as `search` because (a) the leading "What is" short-circuits to search/lookup and (b) the analysis signal regex has no entry for "**number of**" — only for "count", "how many", "list all", etc. Had it been classified as analysis, the agent would have loaded `analysis.md` and received the explicit COUNTING recipe (`search(count_only=True)` instead of manual counting), the ANSWER PRECISION rule, and the NUMERIC AND MONETARY DISCIPLINE that mandates citing source rows before stating a computed result. It would also have inherited a `max_steps=25` budget and `pre_submit_verification=True`, forcing the agent through a verification step. The agent's 3-step premature stop is the symptomatic tail of this classification miss — with the search fragment's "smallest plausible root" preference and no counting recipe loaded, the shortest path to "done" is "read first date-matching file, report line count, move on". This is a root-cause classification failure, not a search-discipline failure — the search fragment is actually doing the right thing for its task type.

## Root cause hypothesis

**Exactly one hypothesis:**

`_ANALYSIS_SIGNALS` in `classify.py` (lines 51–54) does not recognize the phrase "**number of**" as a counting / analysis marker, so any task worded "what is the number of X" routes to the search branch at line 214 (because `what is` is already in `_SEARCH_SIGNALS`). This strips away the counting recipe (`count_only=True`), the NUMERIC DISCIPLINE gate, and the larger step budget the task actually needs. The downstream effect is that the agent executes a one-shot read-and-report pattern and guesses at the vendor match, because the only fragment loaded (`search.md`) is optimized for single-value factual lookups, not filter-then-count.

**Evidence chain:**
1. **The regex literal gap.** `_ANALYSIS_SIGNALS = r"\b(analyze|summarize|compare|count|list\s+all|report|describe|explain|how\s+many)\b"` (classify.py line 52). The token `number` and the phrase `number\s+of` are absent. Trace: grep for "number" across `classify.py` returns no matches inside signal regexes.
2. **The downstream loss.** `strategy.py` line 89 maps `task_type="analysis"` to `analysis.md`, whose line 9 contains the exact counting recipe the task needs: `search(pattern="...", count_only=True) returns the precise count`. This fragment is never loaded when classification returns `search`.
3. **Scope evidence (this is systemic, not a singleton).** Of 147 cached tasks, 13 use counting language; 6 of those currently score 0.0: t004, t029, t054, t074, t079 all phrase it as "how many X involve Y" or "number of lines" and get misrouted or under-supported. t004, t029, t054, t079 all use the "how many ... involve" phrasing which DOES hit `how\s+many` — so they route to analysis correctly, meaning their 0 scores are a different failure mode (likely analysis-fragment under-specification for PLANNED/ACTIVE/SIMMERING status filters). t074 is the only clean classification miss in this run, and it is the only one using the literal "**number of**" phrasing. The fix is narrow enough to not regress the others.
4. **Agent behavior is consistent with the wrong fragment.** Step 1 does `tree("")` (no root), step 2 picks the first date-matching file, step 3 reports. This is search-discipline "locate authoritative source, read, answer" — it is NOT counting discipline. The agent is doing its classified task competently, but was classified for the wrong task.

## Fix proposal (narrow GREEN zone only)

**Selected fix class:** `classify_rule`

**Target file:** `pac1-py/classify.py`

**Exact change:**
```diff
 _ANALYSIS_SIGNALS = re.compile(
-    r"\b(analyze|summarize|compare|count|list\s+all|report|describe|explain|how\s+many)\b",
+    r"\b(analyze|summarize|compare|count|list\s+all|report|describe|explain|"
+    r"how\s+many|number\s+of|total\s+number|line\s+count)\b",
     re.IGNORECASE,
 )
```

**Rationale:** This adds three phrasal counting markers — `number of`, `total number`, `line count` — to the analysis signal regex. The effect is that any task worded "what is the **number of** X" or "the **total number** of Y" or "the **line count** of Z" now classifies as `analysis` instead of `search`. The classification branch at line 214 still gate-keeps with `(has_search or has_lookup) and not has_write`, but `has_analysis and not has_write` at line 203 runs FIRST (line 203 vs line 214), so the analysis branch takes precedence even though `has_search` is also true. The downstream effect:
- `analysis.md` loads, bringing in the COUNTING recipe and NUMERIC DISCIPLINE.
- `max_steps` jumps from 24 (search) to 25 (analysis) — marginal but non-zero.
- `pre_submit_verification=True` on both branches so no regression there.
- `security_posture=standard` on both, so no regression.

The agent will now receive: "COUNTING: When the task asks 'how many' or requires counting items, use the search tool with count_only=True for EXACT counts. Do NOT read a file and count manually." This directly addresses t074's failure mode. For the vendor-match verification gap, `analysis.md` line 5 adds: "The boot-time tree is only 2 levels deep. ALWAYS list subdirectories explicitly before concluding data is absent." and line 7: "Do NOT report OUTCOME_NONE_CLARIFICATION without first reading files that might contain the answer. If the task asks about specific data, explore the filesystem thoroughly." These encourage multi-file exploration.

**Generalizability:** `MEDIUM`
- Direct hit count: 1 confirmed task (t074). The phrase "**number of**" is a common English counting idiom that the challenge author is likely to use in several tasks; I grep'd the 147 cached instructions and found t074 is the only one using "**number of**" literally, but the broader pattern ("what is the number / total / count of X") is a natural rephrasing style the author might use in the live run tasks we have not cached yet. Also `total number` and `line count` are there defensively for phrasing variance. Scope estimate: **2–4 tasks** plausibly affected across the 104-task live benchmark. Honest conservative estimate: **+1 to +2 tasks**.
- Risk of over-matching: `number\s+of` is narrow enough that it won't catch "write my phone number" or "the number 42" — the regex requires the exact two-word phrase with a word boundary on both sides.

**Zone:** `GREEN` — classify_rule edit, 3-token regex addition, no Python logic change, no security path change, no outcome-decision change. Other tasks that currently hit analysis correctly (via `how_many` / `count`) are unaffected because the addition is purely disjunctive.

**Expected impact:** +1 on t074 (classification flips to analysis, agent loads analysis.md with counting recipe, agent uses `search(count_only=True)` instead of manual line count AND pre_submit_verification gates a sanity check on the vendor match). Potential +1 to +2 elsewhere if the live run has other "number of / total number / line count" phrasings. Honest estimate: **+1 to +2 tasks**.

**Risks:**
- *Minor*: A task like "What is the serial number of X" would now classify as analysis instead of search. Analysis fragment still handles factual lookup reasonably (ANSWER PRECISION rule is there), but the recipe is slightly wrong for non-counting factual lookups. This is a minor regression that loses at most ~0.2 points per affected task and is unlikely to fire — the 147-task cache has zero "serial number" phrasings.
- *Minor*: `total_number` could match "total number of people" where the answer is a simple read, not a count. Analysis.md handles simple reads fine (it's a superset of search for most purposes).
- Not a fix for the underlying "agent terminated at step 3 without verifying vendor match" behavior. The fix routes to a better fragment, which improves the odds but does not guarantee multi-file vendor verification. A stronger fix would also add a "MULTI-AXIS FILTER RULE" to search.md/analysis.md that says "when the task specifies both a date range AND a vendor/entity filter, enumerate ALL candidates in the date range, then filter by vendor, then answer" — but that is outside GREEN scope for a single-cycle fix and would need a separate pass.
