## Root cause hypothesis

**Exactly one hypothesis:**

The `_INBOX_PROCESSING_SIGNALS` regex in `classify.py` (lines 73–80) is lexically too narrow: it requires an explicit noun phrase containing `inbox` (e.g., "process the inbox", "inbox queue", "pending inbox items") OR the `_PROCESS_LIKE_SIGNALS` + `_INBOX_OBJECT_SIGNALS` pair. The fallback pair fails on short imperatives like "Work the oldest inbox message." because `_PROCESS_LIKE_SIGNALS` requires `work\s+through`, not bare `work` followed by a noun phrase. But naturally-phrased one-liners like "Work the oldest inbox message", "Handle the top inbox item", "Open the latest inbox message" all target the inbox object with verbs that would need to be recognized on their own. The current regex treats "work" and "work through" as separate lexical items, which is a false narrowness given English usage.

**Evidence chain:**
1. The instruction text literally contains `inbox`, and the tool trajectory shows the agent correctly followed the inbox_processing.md default route — so the agent itself recognized the task type. Only the classifier missed it.
2. `_PROCESS_LIKE_SIGNALS` at line 81 reads: `\b(process|triage|clear|handle|work\s+through|go\s+through|take\s+care\s+of)\b`. Bare `work` + object (`work the inbox`, `work the message`) is a standard English productivity verb ("work a task", "work a queue") that this regex does not capture.
3. If `_INBOX_PROCESSING_SIGNALS` had matched on its own — e.g., by adding `oldest\s+inbox\s+message` / `(oldest|newest|next|top)\s+inbox\s+(message|item|entry)` / a bare `inbox\s+(message|item)` phrase — the task would have routed to `inbox_processing` at line 169, yielding `max_steps=32` via strategy.py line 54. The trajectory we observed would have finished in 16–17 steps with budget to spare.
4. Root, not symptom: the prompt fragments are fine, the agent's reasoning is fine, the verifier was never involved. The only code decision that mattered was the regex at classify.py:73–80.

## Fix proposal (narrow GREEN zone only)

**Selected fix class:** `classify_rule`

**Target file:** `pac1-py/classify.py`

**Exact change:**
```diff
 _INBOX_PROCESSING_SIGNALS = re.compile(
     r"\b(process\s+(the\s+)?inbox|from\s+(the\s+)?inbox|inbox\s+file|"
     r"(take\s+care\s+of|work\s+through)\s+(the\s+)?(?:inbox|incoming)\s+queue|"
     r"(?:incoming|inbox)\s+queue|pending\s+inbox\s+items?|mailbox|"
     r"message\s+backlog|waiting\s+messages?|pending\s+requests?|"
-    r"newly\s+arrived\s+requests?|unread\s+requests?)\b",
+    r"newly\s+arrived\s+requests?|unread\s+requests?|"
+    r"(?:oldest|newest|latest|top|first|next|last)\s+inbox\s+(?:message|item|entry|mail|email)|"
+    r"inbox\s+(?:message|item|entry))\b",
     re.IGNORECASE,
 )
```

**Rationale:** Adds two targeted alternations:
1. `(oldest|newest|latest|top|first|next|last)\s+inbox\s+(message|item|entry|mail|email)` — catches natural positional references that appear as short imperatives ("Work the oldest inbox message", "Handle the newest inbox item", "Open the latest inbox entry"). This is the exact phrase in t022.
2. `inbox\s+(message|item|entry)` — catches the bare "inbox message / inbox item / inbox entry" noun phrase in any imperative ("Reply to the inbox message from Claudia"). Narrow enough to not overtrigger on search/lookup questions (those already have `_QUESTIONISH_LOOKUP_SIGNALS` / `_SEARCH_SIGNALS` that divert them into search branch earlier — though note that `inbox_processing` check fires BEFORE search, so the routing will prefer inbox_processing, which is the correct behavior for "reply to inbox message" type imperatives).

The alternative — adding bare `work` to `_PROCESS_LIKE_SIGNALS` — is rejected as too broad. Bare `work` is a common English verb ("work out the numbers", "work on this file") that would cause many false positives. The noun-phrase-anchored approach is tighter.

**Generalizability:** `MEDIUM`
- Short imperatives of the form `{verb} the {ordinal} inbox {noun}` are a natural, plausible style for task instructions. I would expect 1–3 tasks in the current 104-task benchmark to use this pattern. The trajectory correction for each is +1 task (moving from budget-exhausted to OK). Cannot claim HIGH without a broader scan of the benchmark corpus. Conservative estimate: **+1 to +2 tasks** in the current benchmark, plus resilience against future benchmark phrasing variations.

**Zone:** `GREEN` — regex-only edit in classify.py; no strategy change, no prompt mutation, no effect on security paths. Security test classification fires before this rule (line 158) and is unaffected. Adding alternations to an existing `or`-branch cannot remove any currently matching task from inbox_processing.

**Expected impact:** +1 on t022 (classification_mismatch → correct inbox_processing routing → max_steps=32 → trajectory completes read-after-write + report_completion with budget to spare → OK outcome). Possibly +1 to +2 on similarly-phrased short-imperative inbox tasks elsewhere. Honest conservative estimate: **+1 to +2 tasks**.

**Risks:**
- **Regression risk: LOW.** The added alternations can only move tasks from some other category INTO `inbox_processing`. For a task to be affected, its instruction must contain the literal substring `inbox message` / `inbox item` / `inbox entry` (with optional positional qualifier). Tasks of the form "search for a specific inbox message" contain `search` or `find`, but since the inbox_processing check fires before the search check at line 214, such tasks would now route to inbox_processing instead of search. This is actually the preferred routing because inbox search tasks benefit from the inbox_processing.md discipline (read workflow, verify sender via cast, etc.). Worst-case regression: a pure-read search of the inbox would get a larger budget (32 vs 12) and a hardened security posture — both strictly safer.
- **Security posture upgrade: INTENTIONAL.** inbox_processing.md is `hardened`, which is stricter than crud's `standard`. No task that currently fires crud will lose security protections.
