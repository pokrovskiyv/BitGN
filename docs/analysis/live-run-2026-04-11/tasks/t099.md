## Root cause hypothesis

**Exactly one hypothesis:**

`search.md` encodes "read only the candidate files needed for the answer" but fails to enforce **compound-key disambiguation** for queries of the form `<field> of <entity> at <date window>`. For finance/purchase lookups, filename-date matches a small set of candidates, but vendor identity lives INSIDE the file. The agent correctly performs the "date gate" (picking files by name-date prefix) but skips the "vendor gate" (reading multiple candidates and checking the vendor field before answering). The prompt nowhere states: *when multiple attributes constrain the answer, verify ALL of them — not just the first one that's cheap to check*.

**Evidence chain:**
1. The step-2 plan "Read the 2025_12_05 bill file" explicitly commits to one file by date alone. The agent used the date as a primary key and treated vendor as an afterthought that would be "in there somewhere".
2. Task cache shows THREE other sister tasks (t024 "Möbelhaus Malmö AB", t049 "深圳市海云电子", t074 "Datenspeicher Köhler GmbH") all scored 0.0, all with 3–4 step trajectories, all read a single date-matched file whose filename slug is NOT the queried vendor. This is a family, not a one-off.
3. `search.md` LOOKUP DISCIPLINE says "identify the canonical directory first, then read only the candidate files needed for the answer" — the agent read the directory, picked the minimum (1 file), and stopped. The prompt rewards frugality without defining when frugality is wrong.
4. `analysis.md` DOES have the right discipline ("Before stating a computed result, cite the source file AND the row or field containing each input value") — but task classification routed this to `search`, not `analysis`, because "quantity" is not in `_ANALYSIS_SIGNALS`. So the stronger rule never reached the LLM.
5. `outcomes.md` PROACTIVE AMBIGUITY GATE covers "entity is ABSENT after thorough search" but does not cover "entity is PRESENT but you read the wrong one".

This is a root-cause problem in search.md, not a symptom. A budget-only fix or a classification-only fix would not stop the same pattern: the agent would still pick the first date-matching file, still not read the vendor field, still commit.

## Fix proposal (narrow GREEN zone only)

**Selected fix class:** `prompt_fragment`

**Target file:** `pac1-py/workspace/prompts/fragments/search.md`

**Exact change:**
```diff
 LOOKUP DISCIPLINE:
 - When the task asks for a single factual value (name, date, email, number), identify the canonical directory first, then read only the candidate files needed for the answer.
 - Do not keep searching the whole workspace after you have already found the authoritative folder.
 - If AGENTS.MD names an authoritative source, go there directly instead of doing exploratory global search.
+
+COMPOUND-KEY DISAMBIGUATION (vendor × date, person × project, entity × period):
+- When the task names BOTH an entity (vendor, person, project) AND a temporal window (date range, month, year), you have TWO constraints. A filename that matches the date is NOT proof the file matches the entity — the entity name lives INSIDE the file, not in the filename slug.
+- Read the file contents and verify the entity field explicitly before answering. If the file's contents do not name the queried entity, it is the wrong file — read the next candidate in the date window.
+- If multiple files match the date window, read all of them until you find the one whose contents confirm the entity. Do not answer from the first date match alone.
+- Example: "bill from Hörnbach Österreich issued Dec 3–6, 2025" → list purchases in that date window, then read each candidate and look for "Hörnbach" in the vendor/supplier field of the file. Answer only from the file that names the queried vendor.
+- If no file in the date window names the queried entity, return OUTCOME_NONE_CLARIFICATION (the bill is absent), not a number from a mismatched file.
```

**Rationale:** This preserves search.md's existing frugality instinct ("read only the candidate files needed") while adding the missing disambiguation rule for compound keys. The example is drawn directly from t099 so the agent can pattern-match on exactly the failing case. The CLARIFICATION fallback closes the loop with outcomes.md rule 2 (absent entity → clarify, not approximate). Critically, the rule is LITERAL about where entity names live ("inside the file, not in the filename slug") — a rule Sonnet-4.6 and Haiku-4.5 can both apply mechanically without judgment.

**Generalizability:** `HIGH`
- Hard evidence, not speculation: t024 (Möbelhaus Malmö AB), t049 (深圳市海云电子), t074 (Datenspeicher Köhler GmbH), t099 (Hörnbach Österreich) — **four** vendor×date compound-key bill lookups, ALL scored 0.0, ALL with identical 3–4 step broken trajectories. Likely also t100/t101/t103 which are structurally related ("Looking at the bill X, how much..."). Rough conservative impact: **+2 to +4 tasks** on the benchmark.
- Rule also applies to person×project queries (e.g., t004 "projects involving NORA", t054 "projects involving Miles Novak") where the person name lives inside project files, not in filenames. Extending the fix to those is a secondary win.
- Counter-scenario: tasks where filename and entity slug align perfectly (e.g., `2026_02_26__hörnbach_receipt.md`) — the new rule adds one extra read before answering but does not fail. Cost is 1-2 extra steps, well within the 24-step budget.

**Zone:** `GREEN` — prompt-fragment edit, no Python change, no effect on security paths (outcomes.md CLARIFICATION rule tightens behavior in the correct direction).

**Expected impact:** +1 on t099 specifically (agent reads multiple Dec 3-6 purchase candidates, finds the Hörnbach bill, reports the correct seal-set quantity). Likely +1 on each of t024, t049, t074 by the same mechanism. Honest conservative estimate: **+2 to +4 tasks**.

**Risks:** Minor regression risk on single-hit lookups where the first date-matched file IS the right one — the agent now reads one extra candidate "just to be sure". Wall-clock cost ~3-6s per lookup, well inside the 24-step search budget. Zero risk to security paths — the rule adds verification before a positive answer, never loosens a rejection.
