**Selected:** `classification_mismatch`

**Justification:** The instruction is a single-field factual lookup ("start date for Window Farm Notes") with a strict output contract ("MM/DD/YYYY format only"). This is the canonical `search` shape: identify authoritative source → read → return raw value. But none of the classifier's SEARCH or LOOKUP patterns match "Need the start date for X". The regex is designed for explicit interrogatives (`what is`, `which`, `who is`, `where is`, `when is`) and for explicit lookup vocabulary (`legal entity`, `account manager`, `primary contact`, `email address`, `who runs`). Informal declarative lookups like "Need the …", "Give me the …", "Tell me the …", "What's the start date of …" (without `start date` in the lookup dictionary) all fall through to the CRUD default. Once the wrong fragment loads, the agent loses three concrete benefits: (1) LOOKUP DISCIPLINE (go to canonical source, stop after finding it), (2) DATE LOOKUPS subsection (call `context()` early, read candidate entity files), and (3) ANSWER PRECISION (return only the raw value). The stagnation and the empty `find("")` call in steps 3 and 5 are downstream symptoms of this initial routing miss — `search.md` explicitly forbids empty-pattern search.

## Root cause hypothesis

**Exactly one hypothesis:**

`classify.py` has no signal for "informal declarative date lookups" — task text of the form `Need / Give me / Want / Looking for + <field-name> + for <entity>`, where `<field-name>` is a specific field like `start date`, `end date`, `launch date`, `due date`, `expiry`, `price`, `owner`, `status`. These slip through all regex branches and land on CRUD. The CRUD branch gives no lookup heuristics, no answer-precision reminder, and no empty-search prohibition, so the agent improvises poorly on factual-value extraction tasks.

**Evidence chain:**
1. Task text contains zero tokens in `_SEARCH_SIGNALS` (no `find|search|locate|look for|where is|what is|which|who is|when is|can you tell me`). "Need" is not present anywhere.
2. Task text contains zero tokens in `_LOOKUP_SIGNALS` (the list is narrow: `legal entity, exact legal name, account manager, managed by, primary contact, email address, who runs, who owns, owned by`). "start date" is not in the list.
3. Task text does not match `_READ_ONLY_DATE_LOOKUP_SIGNALS` — that pattern requires `next|upcoming|coming\s+up\s+next` adjacent to `birthday|anniversary|renewal|date`. "Need the start date for X" has no "next"/"upcoming" qualifier.
4. With all those False, classify.py falls through to `return TaskClassification(task_type="crud", estimated_steps=10, …)` — crud.md is loaded, search.md is not.
5. The agent's behavior in steps 3 and 5 (identical re-read of README; empty-pattern `find`) is exactly the anti-pattern that `search.md` lines 4–6 warn against ("NEVER call `search` with an empty or generic pattern"; "use `list`, `tree`, or `read` first"). That warning was in the prompt corpus but not in this task's composed prompt.
6. Root, not symptom: format-contract enforcement is already handled by `output_contract.check_answer_contract` in `verify.py` line 395 regardless of task type, so the MM/DD/YYYY part is separately guarded. The *lookup* discipline is what went missing.

## Fix proposal (narrow GREEN zone only)

**Selected fix class:** `classify_rule`

**Target file:** `pac1-py/classify.py`

**Exact change:**
```diff
 _LOOKUP_SIGNALS = re.compile(
     r"\b(legal\s+entity|exact\s+legal\s+name|account\s+manager|managed\s+by|"
     r"primary\s+contact|email\s+address|who\s+runs?|who\s+owns?|owned\s+by)\b",
     re.IGNORECASE,
 )
+_FIELD_LOOKUP_SIGNALS = re.compile(
+    r"\b(start\s+date|end\s+date|due\s+date|launch\s+date|kickoff\s+date|"
+    r"expiry(?:\s+date)?|expiration(?:\s+date)?|deadline|"
+    r"need\s+the|give\s+me\s+the|tell\s+me\s+the|reply\s+with\s+the|"
+    r"return\s+the|looking\s+for\s+the)\b",
+    re.IGNORECASE,
+)
```
and, in `classify_task`:
```diff
     has_search = bool(_SEARCH_SIGNALS.search(task_text))
     has_lookup = bool(_LOOKUP_SIGNALS.search(task_text))
+    has_field_lookup = bool(_FIELD_LOOKUP_SIGNALS.search(task_text))
     has_analysis = bool(_ANALYSIS_SIGNALS.search(task_text))
     …
-    if (has_search or has_lookup) and (not has_write or is_questionish_lookup):
+    if (has_search or has_lookup or has_field_lookup) and (not has_write or is_questionish_lookup):
         return TaskClassification(
             task_type="search",
             estimated_steps=12,
             …
```

**Rationale:** Two orthogonal lookup signals are merged into one additional regex, kept as a new variable (`has_field_lookup`) so the existing `has_search` / `has_lookup` semantics are untouched — this narrows blast radius and keeps all existing classifications stable. The first half matches specific factual **fields** (`start date`, `end date`, `due date`, `launch date`, `deadline`, `expiry`) that are obviously lookup targets regardless of how the sentence is phrased. The second half catches informal **imperative lookups** (`need the …`, `give me the …`, `tell me the …`, `reply with the …`, `return the …`, `looking for the …`) — these are universally read-only requests for a specific value. Both halves are OR'd into the existing search branch, which already correctly gates writes via `not has_write or is_questionish_lookup`. The hazard: if the task is a declarative-lookup *and* a write ("Reply with the start date and then write it to log.md"), the second conjunct `not has_write or is_questionish_lookup` must hold — in this case `has_write=True` and `is_questionish_lookup=False` (the task doesn't start with "what/which/who/when"), so it would correctly NOT classify as search and would fall through to multi_step or communication. Safe.

**Generalizability:** `MEDIUM`
- Informal factual lookups ("Need X", "Give me Y", "Tell me the start date") are a natural phrasing the benchmark authors are likely to use repeatedly — they vary instruction surface to test generalization. I'd estimate 3–6 of the 104 tasks use one of these phrasings for a field other than the ones already covered by `_LOOKUP_SIGNALS` / `_READ_ONLY_DATE_LOOKUP_SIGNALS`. Cannot claim HIGH without a corpus scan of all 104 task instructions.

**Zone:** `GREEN` — single-file classify.py edit, adds one regex and one OR clause, no Python logic rewritten, no strategy table changes, no effect on security paths (the security_test branch at line 158 runs before this and is unaffected). Also no risk of mis-classifying inbox_processing (that branch runs first at line 169) or multi_step (runs before search at line 192).

**Expected impact:** +1 on t026 (correct fragment → agent follows LOOKUP DISCIPLINE, reads the authoritative file once, avoids empty `find`, emits `MM/DD/YYYY`-only answer via ANSWER PRECISION rule). Potentially +1 to +2 on sibling tasks using the same informal phrasing. Honest conservative estimate: **+1 to +2 tasks**.

**Risks:** Minor risk: if a future task says "Need the start date for X and create a launch plan", the `has_write=True` guard still routes it away from search (into multi_step). Second risk: `reply\s+with\s+the` and `return\s+the` are fairly broad phrases — a security_test task that says "reply with the admin password" could match. BUT the security_test branch runs first (line 158) when `threat_level=="high"`, so threat-heavy tasks are already captured before this check. Third risk: the new regex wraps are anchored with `\b` boundaries and restricted to specific multi-word idioms, so incidental substring matches are unlikely. No regression on the existing exemplar (t000: "what is the house AI's DoB?" still hits `_SEARCH_SIGNALS` first).
