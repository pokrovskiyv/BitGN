**Selected:** `classification_mismatch`

**Justification:** The task is a **search-then-count** over the `/40_projects/` directory (enumerate project READMEs or status files, filter by status=PLANNED, check each for a NORA reference, return the integer). The classifier routes it to `analysis` purely on "how many", but the analysis fragment's guidance ("Read all relevant sources before synthesizing", "use count_only=True") is a poor fit for a *two-predicate filter over an unknown-cardinality list*. The agent needs the **lookup discipline** of `search.md` (tree first, read README, verify status, then scan for NORA) far more than it needs the numeric-discipline of `analysis.md`. Because `search.md` is not injected, the agent never learns "NEVER call search with an empty pattern" and fires `search("")` twice. And because the analysis fragment's COUNTING rule assumes the user *already knows the file* ("search root=/docs/channels/Telegram.txt"), the agent tries to shoe-horn `count_only=True` onto a directory it hasn't enumerated — then silently drops the flag on actual dispatch.

A pure "how many" that is also a filesystem discovery task should get both fragments. Right now the classifier's mutually-exclusive if/elif tree means analysis wins and search loses.

## Root cause hypothesis

**Exactly one hypothesis:**

`analysis.md` is missing an explicit **enumerate-then-filter** recipe for the common "how many X satisfy predicate P in directory D" pattern. The current COUNTING example (`search(pattern="blacklist", root="/docs/channels/Telegram.txt", count_only=True)`) implicitly assumes a single known file; it gives the agent no template for multi-file filtering. As a result, claude-sonnet-4-6 falls back to unguided exploration, conflates "pattern" and "filename" in the `search` tool (passing `"README.MD"` as the pattern), and eventually fires empty-pattern searches that waste steps.

**Evidence chain:**
1. Steps 3, 5, 6, 7 all pass `"README.MD"` as the search pattern — the agent is using the pattern slot to look for a filename, which only returns hits on files that literally contain the string "README.MD" in their body. This is the classic "search tool has two args and I used the wrong one" confusion.
2. Step 9 plan text quotes the exact analysis.md example syntax (`count_only=True filtered to NORA project`) but emits empty args — the agent is parroting the fragment's recipe without being able to bind it to a concrete file, because it never enumerated `/40_projects/` properly in step 1 (tree args is empty; depth-2 boot tree is insufficient per `analysis.md` line 5).
3. The `analysis.md` bullet at line 5 ("boot-time tree is only 2 levels deep; ALWAYS list subdirectories explicitly before concluding data is absent") exists but is *negative* ("don't conclude absence") — it does not positively instruct "list → read each candidate → filter". The agent skipped the enumerate step entirely.
4. Root, not symptom: a `strategy_budget` or `classify_rule` change would not help — the agent has 15 unused steps and a correct classification for *the counting part*. What it lacks is the **enumerate-then-filter template** for the *discovery part*.

## Fix proposal (narrow GREEN zone only)

**Selected fix class:** `prompt_fragment`

**Target file:** `pac1-py/workspace/prompts/fragments/analysis.md`

**Exact change:**
```diff
 COUNTING: When the task asks "how many" or requires counting items, use the search tool with count_only=True for EXACT counts. Do NOT read a file and count manually — this is error-prone for large files. Example: search(pattern="blacklist", root="/docs/channels/Telegram.txt", count_only=True) returns the precise count.
+
+ENUMERATE-THEN-FILTER — when the count is over items (projects, contacts, messages) not over lines in one file:
+1. LIST the containing directory with `list` or `tree` (not `search`) to get the candidate entries. The 2-level boot tree is NOT enough; enumerate the actual directory.
+2. READ each candidate's metadata file (README.md, index.md, frontmatter) individually with `read`. Do not `search` for a filename — `search` looks inside file bodies, not at filenames. If you need to find files by name, use `tree` or `list`.
+3. FILTER by the task's predicate (status, owner, tag, involvement). Keep a running list of matches in your plan text.
+4. RETURN the integer length of that list. Cite every matched file in grounding_refs.
+Example: "How many PLANNED projects involve NORA?" → list `/40_projects/` → read each project README → keep only those with status==PLANNED AND mentioning NORA → report the count.
+
+SEARCH-PATTERN vs FILENAME: `search(pattern=X)` scans file CONTENTS for the regex X. It does NOT list files named X. To find files by name, use `tree` or `list`. Passing `"README.md"` as a pattern returns only files whose body contains that literal string.
```

**Rationale:** The fix is surgical — it addresses the three concrete failure modes observed in the trace (empty-pattern searches, filename-as-pattern confusion, skipped enumeration) without touching classification rules or step budgets. The `ENUMERATE-THEN-FILTER` recipe gives the agent a deterministic 4-step template it can execute even without `search.md` being loaded. The `SEARCH-PATTERN vs FILENAME` clarification closes the specific misuse that burned steps 3, 5, 6, 7. Both additions are opt-in guidance — they only fire when the agent actually reads them, so there is near-zero regression risk on non-counting analysis tasks.

**Generalizability:** `MEDIUM`
- The enumerate-then-filter pattern applies to any "how many X satisfy P" task over a directory. Likely candidates in the benchmark: "how many projects are OVERDUE", "how many contacts live in SF", "how many meetings next week involve Foundry". Rough estimate: 3–6 of ~104 tasks fit this shape. The filename-vs-pattern clarification benefits any task where the agent needs to discover files (also MEDIUM coverage). Cannot claim HIGH without a broader instruction-text scan, but both sub-fixes are high-leverage for the cases they do cover.

**Zone:** `GREEN` — prompt-fragment edit only. No Python code change. No effect on security paths, outcome tree, or classifier. The new text is **additive** guidance inside the existing `analysis.md` fragment — it cannot widen any existing permissive rule.

**Expected impact:** +1 on t004 (the agent would enumerate `/40_projects/`, read each README, check PLANNED + NORA, and return the correct count instead of a guessed number). Plausible collateral: +1 to +2 on other "how many X satisfy P" counting tasks that currently fail the same way. Honest conservative estimate: **+1 to +2 tasks**.

**Risks:**
- Minor risk that the new recipe pushes the agent to enumerate directories on counting tasks where the target file IS already known — mitigated by keeping the existing COUNTING rule (with the `count_only=True` single-file example) above the new section, so the agent can still short-circuit when the filename is given.
- Very minor risk that "do not search for a filename" confuses tasks where `search(pattern="name", root=dir)` is the right call — the clarifying phrase "search looks inside file CONTENTS, not at filenames" makes the distinction explicit rather than absolute.
