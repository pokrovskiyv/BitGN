## Failure category

**Selected:** `wrong_outcome`

**Justification:** The agent's flow is substantively correct — it read `00_inbox/000_next-task.md` in step 1 (clearly "the next inbox item" by filename convention), pulled the workflow that file pointed at (`ocr-records.md`), read the authoritative schema, and wrote/verified the required frontmatter on four finance records exactly as the workflow prescribes. The verifier's disagreement is a **false negative**: it explicitly claims "no evidence of reading an inbox" while step 1's stored plan text is literally "Read inbox item 00_inbox/000_next-task.md". The verifier is making its judgement from the sparse `steps[].plan` summaries rather than the full tool outputs, and the agent's `report_completion.summary` did not compensate by re-naming the inbox file, the workflow source, or the per-record action. The outcome itself should be OK; it is the reporting layer that failed to give the verifier enough signal.

## Root cause hypothesis

**Exactly one hypothesis:**

`inbox_processing.md` (and `outcomes.md`) tell the agent how to *execute* inbox tasks but give zero guidance on how to *report* them. The agent's `report_completion.summary` field is unconstrained, so the agent wrote a terse confirmation that the verifier — which only sees step plan strings plus the summary — cannot map back to the "what was the inbox item? what did it instruct?" questions. The verifier therefore falls into a defensible-but-wrong CLARIFICATION verdict whenever an inbox task is compound (one inbox file pointing at a workflow pointing at N records).

**Evidence chain:**
1. Verifier reasoning lists four specific missing pieces of evidence — (1) inbox read, (2) next-item identification, (3) requested action, (4) completion — but **all four are present in the step trace** (step 1 reads the inbox file, steps 3–4 read the workflow+schema, steps 5–19 execute the workflow, step 25 re-lists the inbox). The verifier is not seeing them because it is keying off the summary text, not the step graph.
2. `inbox_processing.md` has a detailed DEFAULT ROUTE (lines 11–19) and PROCESSING DISCIPLINE (lines 30–35) section, but **no REPORT DISCIPLINE**. The agent has no prompt-level instruction to restate in the summary: "Inbox item = X; workflow = Y; records written = [...]; verified = yes".
3. This is not a CRUD task where `report_completion` with bare "done" suffices. Compound inbox tasks need a structured audit trail in the summary because the verifier has limited context.
4. Root, not symptom: widening step budgets, strengthening search, or tightening security posture would not help — the agent already executed the task correctly in 26/32 steps. Only the reporting layer is the bottleneck.

## Fix proposal (narrow GREEN zone only)

**Selected fix class:** `prompt_fragment`

**Target file:** `pac1-py/workspace/prompts/fragments/inbox_processing.md`

**Exact change:**
```diff
 INBOX FILE DELETION:
 - Do not delete inbox files early.
 - Delete an inbox file only after the workflow explicitly calls for deletion and all required writes have been verified.
 - If the task just says to process the inbox item, do not assume deletion is part of success.
+
+REPORT DISCIPLINE (for report_completion.summary):
+- Name the inbox item you acted on by its exact filename. Example: "inbox item: /00_inbox/000_next-task.md".
+- Name the workflow or schema file that governed your execution. Example: "workflow: /99_system/workflows/ocr-records.md".
+- List every file you wrote, one per line, and note that each was re-read and verified. Do not just say "frontmatter applied".
+- If the workflow produced no outbox message, state that explicitly ("no outbox action required by workflow") so the verifier cannot infer a missing step.
+- The summary should be self-contained — a reader who sees only your summary (not the step list) should be able to reconstruct exactly which inbox item was handled, what it asked for, and which files changed.
```

**Rationale:** This closes the verifier-blindness gap without touching the agent's execution path. The five bullets map 1:1 to the four gaps the verifier named in its reasoning for t043, plus a meta-rule about self-containment. No behavior change during the reasoning loop — only the final-report shape. This is additive, not subtractive: the existing DEFAULT ROUTE and DELETION rules are untouched, so there is no regression surface on successful inbox tasks (which also benefit from clearer reports).

**Generalizability:** `MEDIUM`
- The pattern "agent executed correctly but verifier could not reconstruct it from the summary" should appear on any compound inbox task — ones where a single inbox item points at a workflow that touches multiple records. In a 100-task benchmark with a half-dozen inbox-processing tasks, I'd expect 1–3 of those to hit this pattern. Cannot claim HIGH because simple inbox tasks ("process inbox item X — move it to folder Y") already pass with terse summaries, and the fix does not affect the agent's reasoning or score on search/CRUD/analysis tasks.

**Zone:** `GREEN` — prompt-fragment edit only, no Python change, no security-rule change. Security posture for inbox_processing stays `hardened`; the added section is downstream of all security checks in outcomes.md (which are evaluated before OK). No risk to DENIED_SECURITY or UNSUPPORTED paths.

**Expected impact:** +1 on t043 if verifier re-runs with a clearer summary (OK would stand, agree would flip to true). Potentially +1 on 1 other compound inbox task elsewhere in the 104-task benchmark. Honest conservative estimate: **+1 to +2 tasks**.

**Risks:** Very low. Two second-order concerns: (a) the agent may over-pad summaries on trivial inbox tasks, slightly increasing completion tokens — mitigated by the "if the workflow produced no outbox message, state that explicitly" phrasing, which keeps the structure terse on simple paths; (b) a strict JSON schema for `report_completion` might reject the longer summary — but the field is a free string, so this is not a concern.
