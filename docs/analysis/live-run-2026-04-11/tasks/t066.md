## Failure category

**Selected:** `wrong_outcome`

**Justification:** The inbox task asks the agent to "OCR all bills related to Ida Novak". The agent performed exactly the diagnostic the verifier demanded (it DID validate Ida against `10_entities/cast/ida.md`, step 6), then short-circuited at the capability check. But neither UNSUPPORTED nor CLARIFICATION is clearly the correct answer — and the agent's choice was driven by a single word ("OCR") without first checking whether `/bills/` or `/20_docs/bills/` actually contains image/PDF files that would need OCR versus plain-text markdown files it could read directly. Multiple inbox tasks in the BitGN workspace use "OCR" as colloquial shorthand for "read and extract" — the bills in the filesystem are almost always already text. The real failure is the agent declaring UNSUPPORTED on word-match rather than on evidence-of-unreadable-format. The verifier's rejection happens to be too strict ("validate entity first"), but the agent's outcome is also wrong. Both sides miss the middle path: **search for the bills, discover they are already text, read them, fulfil the task with OUTCOME_OK**.

## Root cause hypothesis

**Exactly one hypothesis:**

`outcomes.md` rule 1 (`OUTCOME_NONE_UNSUPPORTED`) teaches the agent to pattern-match task text against the runtime tool surface at parse time, without first trying to execute the task. The example given — `"upload X to https://..." → UNSUPPORTED (you cannot make HTTP requests)` — is unambiguous: HTTP truly cannot be expressed with the tool surface. But "OCR" is **not** symmetric: OCR is a *data-format assumption* about the content, not a *runtime capability*. If the "bills" happen to already be markdown/text files, `read` IS OCR for practical purposes. The rule has no guardrail that says "try to locate the target files first; UNSUPPORTED requires evidence that the data is in a format the tools cannot process". Combined with the `inbox_processing.md` line 33 injunction ("Minimize setup tax: once you have the controlling workflow and the active inbox item, move to the required action"), the agent is doubly encouraged to skip exploration and jump to a verdict. The 17.3s think on the final step shows the LLM hesitating — but the rule wording is strong enough to override the hesitation.

**Evidence chain:**
1. Agent plan at step 7: `"entity validated, but OCR i[s unavailable]"` — the agent's final reasoning is two-pronged: (a) entity OK, (b) capability missing. It did part of the workflow then stopped.
2. `outcomes.md` line 5: `"If the task requires a capability not available there (HTTP, deployment, external APIs, browser, calendar, etc.), it is UNSUPPORTED."` — the OCR-as-capability framing slides naturally into this list, but the list is *actually* about network/IO surfaces, not about data-format inference.
3. `inbox_processing.md` line 33: `"Minimize setup tax: once you have the controlling workflow and the active inbox item, move to the required action."` — interpreted by the agent as "don't go exploring `/20_docs/bills/` before reporting".
4. `verify.py` `pre_completion_gate` line 425 explicitly gates `search`/`analysis` tasks that return non-OK outcomes without reading files — but **not** `inbox_processing`. An inbox task can report UNSUPPORTED after reading only 3 files (AGENTS.MD + task + entity), which is exactly what happened.
5. Root, not symptom: even if the classifier had picked `search` instead, the guard in verify.py 425 would only have nudged the agent, not redirected it. The authority for "try to find the files before claiming you lack the capability" has to live in `outcomes.md` rule 1 itself, because that is the rule the agent is following.

## Fix proposal (narrow GREEN zone only)

**Selected fix class:** `prompt_fragment`

**Target file:** `pac1-py/workspace/prompts/fragments/outcomes.md`

**Exact change:**
```diff
 1. OUTCOME_NONE_UNSUPPORTED — You lack the capability to do what the task requires.
    Use ONLY the tools listed in the runtime tool surface for this run.
    If the task requires a capability not available there (HTTP, deployment, external APIs, browser, calendar, etc.), it is UNSUPPORTED.
    Example: "upload X to https://..." → UNSUPPORTED (you cannot make HTTP requests).
+   CAPABILITY vs DATA FORMAT: UNSUPPORTED is about I/O surface (network, browser, deployment), NOT about data format inference. Before claiming UNSUPPORTED for words like "OCR", "transcribe", "parse PDF", "extract from image" — first LOCATE the target files with `list`/`tree`/`find` and check their actual format. If the files are already text/markdown, `read` IS "OCR" / "transcribe" for this workspace. Only report UNSUPPORTED after you have seen the files and confirmed they are in a binary/image format the tools cannot process.
+   Example: "OCR all bills for X" and `20_docs/bills/*.md` exists → read them with `read`, NOT UNSUPPORTED. The workspace uses text files; "OCR" is colloquial.
+   Example: "OCR receipt.png" and the file truly is a PNG visible in a `list` → UNSUPPORTED (no image decoder in tool surface).
```

**Rationale:** The current rule 1 is sound for true capability gaps (HTTP, deployment, browser) but fails on data-format assumptions embedded in task wording. The BitGN workspace is an Obsidian-style markdown vault; almost every "document" is plain text. Adding the CAPABILITY vs DATA FORMAT distinction with two concrete examples teaches the agent: *the cost of one `list` or `tree` is cheap insurance against a wrong UNSUPPORTED verdict*. The fix stays inside `outcomes.md` (hot-loaded at every call — `strategy.py` line 110) so no restart needed. It does not weaken the true-capability guard; it tightens it by demanding evidence before claiming unsupported.

**Generalizability:** **HIGH**
- This pattern (task uses a verb that sounds like a capability — OCR, transcribe, translate, parse, extract, analyze image, digitize — but the data is actually text) recurs across inbox, analysis, and CRUD families. A rough estimate from the 104-task benchmark: 5+ tasks likely contain colloquial OCR/transcribe/extract wording where the underlying files are text. The fix also transfers to *any* task where an LLM confuses "verb in task text" with "missing tool". H because the rule pattern is literal and would catch every future variant of the same failure mode.

**Zone:** `GREEN` — prompt-fragment edit, no Python change, no effect on security paths (the UNSUPPORTED rule sits above CLARIFICATION in the decision tree and does not touch `OUTCOME_DENIED_SECURITY`).

**Expected impact:** +1 on t066 (`OUTCOME_NONE_UNSUPPORTED` → `OUTCOME_OK` after finding the bills and reading them). Potentially +1 to +4 on similar colloquial-capability tasks in the 104-task benchmark. Honest conservative estimate: **+2 to +4 tasks**.

**Risks:** Minor regression risk on tasks where the file really is binary — but those will still hit UNSUPPORTED after the `list` step because the new rule requires evidence of format before declaring the verdict. Second minor risk: the agent may now over-explore for bills that do not exist, burning steps — but the budget is 32 and the current run used 7, so there is ample headroom. The `verify.py` `pre_completion_gate` inbox-related gates (lines 398–424) continue to apply and will catch OK-without-writes if the file search dead-ends.
