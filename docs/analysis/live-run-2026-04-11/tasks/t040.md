## Root cause hypothesis

**Exactly one hypothesis:**

`classify.py` misses the phrase "work the X inbox/message/request" because `_PROCESS_LIKE_SIGNALS` and `_INBOX_PROCESSING_SIGNALS` both require the verb form `work\s+through` (never the bare imperative `work the`). The instruction "Work the oldest inbox message." uses the bare imperative — a natural user phrasing — so neither branch fires, and the classifier falls through to `crud`. The dual-signal fallback (`_PROCESS_LIKE_SIGNALS` AND `_INBOX_OBJECT_SIGNALS`) specifically exists for cases like this, but it is defeated because `_PROCESS_LIKE_SIGNALS` does not list bare `work` as a process-like verb.

**Evidence chain:**
1. Regex audit (verified via local Python eval): all 7 signal families return False on the instruction except `_INBOX_OBJECT_SIGNALS` (which fires on `inbox` and `message`). Specifically, `_PROCESS_LIKE_SIGNALS = r'\b(process|triage|clear|handle|work\s+through|go\s+through|take\s+care\s+of)\b'` — the only `work` variant is `work\s+through`, and the instruction has no `through`.
2. The fall-through to `crud` at `classify.py` line 236 gives `estimated_steps=10`, and the strategy table in `strategy.py` line 48 sets `crud` to `max_steps=15`. The agent's `step_count` is exactly 15 with no `report_completion` step — it hit the wall.
3. The agent's own behavior confirms the wrong-fragment hypothesis: steps 1–2 (read AGENTS.MD, open the inbox pointer) and steps 5–7 (tree 99_system, read workflow, read schema) are exactly the `inbox_processing.md` DEFAULT ROUTE. The model intuited the right route from `/00_inbox/AGENTS.MD` content alone — but without the fragment's explicit "Minimize setup tax" discipline and without the 32-step budget, it could not close the loop.
4. Root, not symptom: fixing the truncated paths at step 8/10/11 would not change the outcome because the agent still only has 15 steps. Fixing `outcomes.md` would not help because the agent never reached an outcome decision. Only extending `_PROCESS_LIKE_SIGNALS` (or `_INBOX_PROCESSING_SIGNALS`) to match "work the inbox/message" reroutes the task to `inbox_processing` and unlocks the 32-step budget + correct fragment.

## Fix proposal (narrow GREEN zone only)

**Selected fix class:** `classify_rule`

**Target file:** `pac1-py/classify.py`

**Exact change:**
```diff
 _PROCESS_LIKE_SIGNALS = re.compile(
-    r"\b(process|triage|clear|handle|work\s+through|go\s+through|take\s+care\s+of)\b",
+    r"\b(process|triage|clear|handle|work\s+through|go\s+through|take\s+care\s+of|"
+    r"work\s+(?:the\s+)?(?:oldest|newest|first|next|latest|top)|"
+    r"work\s+(?:the\s+)?(?:inbox|message|request|queue))\b",
     re.IGNORECASE,
 )
```

**Rationale:** The combined `_PROCESS_LIKE_SIGNALS AND _INBOX_OBJECT_SIGNALS` gate is the intended fallback for exactly this kind of colloquial inbox phrasing. The original list covered formal phrasings (`process the inbox`, `work through the queue`, `take care of pending requests`) but missed the bare imperative `work the X`. The two alternatives added are surgical: (a) `work\s+(?:the\s+)?(oldest|newest|first|next|latest|top)` catches positional language common in user inbox instructions; (b) `work\s+(?:the\s+)?(inbox|message|request|queue)` catches direct object language. Both require the object form — neither matches `work from home`, `work on the report`, or `work day` — because the object set is enumerated. Because the gate still requires `_INBOX_OBJECT_SIGNALS` to also fire, the compound precondition (process-like verb + inbox object) stays strict. After this change, "Work the oldest inbox message." matches `work\s+(?:the\s+)?oldest` → `_PROCESS_LIKE_SIGNALS` fires → combined with `_INBOX_OBJECT_SIGNALS` → routes to `inbox_processing` → loads `inbox_processing.md` with 32-step budget and the Obsidian-workspace DEFAULT ROUTE.

**Generalizability:** `MEDIUM`
- Directly fixes one task (t040). Potentially fires on other inbox tasks where the user writes colloquially ("handle the next inbox request", "take the top inbox item" — the first already matches `handle` + `inbox`, the second would still miss). Conservative estimate: this unlocks 1 task with HIGH confidence (t040), with modest spillover to 0–2 additional inbox-style tasks phrased with bare imperatives. Cannot claim HIGH without a broader benchmark scan. The two added alternatives are cheap enough that even a single task unlock is worth it given the fix complexity (3-line regex edit, no new branches).

**Zone:** `GREEN` — classify_rule edit, single regex extension, no effect on any other task type. The compound gate (process-like AND inbox-object) prevents spurious matches on non-inbox tasks that happen to contain the word "work". No security-path impact: the classifier runs BEFORE threat-level computation, so routing to `inbox_processing` still honors high-threat override to `security_test` at line 158.

**Expected impact:** +1 on t040 (0.0 → expected ~1.0 if the OCR workflow can complete in 32 steps; ~0.5 partial if the agent processes 3/5 purchases). Potentially +1 on colloquially-phrased inbox tasks elsewhere in the 104-task benchmark. Honest conservative estimate: **+1 task**. The Sonnet path-truncation issue would still exist at step 8/10/11, but with 32 steps instead of 15 the agent has headroom to re-read the parent directory after each failed read and recover the correct filename.

**Risks:** Very low. The added alternatives only fire when followed by an explicit inbox-object noun (`oldest`, `newest`, `inbox`, `message`, etc.), which is why the compound gate is still safe. Minor risk: a task like "work the oldest draft" would now classify as CRUD → inbox_processing IF "draft" ever ends up in `_INBOX_OBJECT_SIGNALS`, but it does not today. Zero impact on security tasks (threat_level=high still overrides).
