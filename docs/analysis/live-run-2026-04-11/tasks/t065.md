## Root cause hypothesis

**Exactly one hypothesis:**

`_INBOX_PROCESSING_SIGNALS` in `classify.py:73–80` is too narrow — it requires literal phrases like `"process the inbox"`, `"from the inbox"`, `"inbox file"`, `"work through the inbox queue"`, etc. It does not match the natural-language form `"work the oldest inbox message"`. And the fallback `_PROCESS_LIKE_SIGNALS ∧ _INBOX_OBJECT_SIGNALS` is gated on `"process|triage|clear|handle|work\s+through|go\s+through|take\s+care\s+of"` — none of which include the bare verb `"work"` followed by an article/quantifier (`"work the X"`, `"work on X"`, `"work N inbox items"`). Because the inbox task is not recognized, the agent gets the CRUD strategy (15 steps, `crud.md` prompt) instead of `inbox_processing` (32 steps, the full playbook). The classifier mismatch causes both the budget shortage and the absence of the `99_system → 00_inbox → cast → channels` orientation that would have saved ~10s of step-4 thinking and prevented the step-15 `/60_outbox/outbox/README.MD` detour.

**Evidence chain:**
1. I replayed all signal regexes against the literal task string — only `_INBOX_OBJECT_SIGNALS` matches (`"message"`), and it is a no-op without a `_PROCESS_LIKE_SIGNALS` co-match. Every other signal returns `False`.
2. `strategy.py:46–56` maps `crud` → 15 steps, `inbox_processing` → 32 steps. The trace stops at exactly step 15 with a `read` tool call mid-workflow (the third receipt's write-verify loop was incomplete and the agent had not even touched the outbox routing phase).
3. `inbox_processing.md` lines 3–10 contain the exact orientation steps the agent re-derived in step 4's 16.9s thinking spike, and line 9 warns explicitly against the legacy `outbox/README.MD` path that the agent detoured to in step 15. The prompt fragment was not loaded (CRUD path in `strategy.py:109`).
4. CRUD discipline (write + re-read) was followed correctly on files 1 and 2 — the agent is not broken, it is under-provisioned. This rules out `missing_write`, `stagnation`, and `tool_error`.

## Fix proposal (narrow GREEN zone only)

**Selected fix class:** `classify_rule`

**Target file:** `pac1-py/classify.py`

**Exact change:**
```diff
 _INBOX_PROCESSING_SIGNALS = re.compile(
     r"\b(process\s+(the\s+)?inbox|from\s+(the\s+)?inbox|inbox\s+file|"
     r"(take\s+care\s+of|work\s+through)\s+(the\s+)?(?:inbox|incoming)\s+queue|"
     r"(?:incoming|inbox)\s+queue|pending\s+inbox\s+items?|mailbox|"
     r"message\s+backlog|waiting\s+messages?|pending\s+requests?|"
-    r"newly\s+arrived\s+requests?|unread\s+requests?)\b",
+    r"newly\s+arrived\s+requests?|unread\s+requests?|"
+    r"(?:oldest|newest|next|first|latest|unread|pending)\s+inbox\s+(?:message|item|entry|note)s?|"
+    r"inbox\s+(?:message|item|entry|note)s?)\b",
     re.IGNORECASE,
 )
 _PROCESS_LIKE_SIGNALS = re.compile(
-    r"\b(process|triage|clear|handle|work\s+through|go\s+through|take\s+care\s+of)\b",
+    r"\b(process|triage|clear|handle|work(?:\s+(?:through|on|the))?|"
+    r"go\s+through|take\s+care\s+of|deal\s+with|address)\b",
     re.IGNORECASE,
 )
```

**Rationale:** Two surgical regex widenings targeted at the exact phrasing that failed. (1) `_INBOX_PROCESSING_SIGNALS` gets a direct pattern for `(oldest|newest|next|first|latest|unread|pending) inbox (message|item|entry|note)` plus bare `inbox (message|item|entry|note)` — this captures t065's literal form and any similar "work/do/handle the X inbox Y" phrasing. (2) `_PROCESS_LIKE_SIGNALS` gains `work(\s+(?:through|on|the))?` so bare `"work the"` + any inbox object (via the existing `_INBOX_OBJECT_SIGNALS`) also hits the fallback branch at `classify.py:148–151`. Adding `"deal with"` and `"address"` is a cheap bonus — both are common English instructions that should route to inbox processing when paired with `"inbox|queue|messages"`. Once re-classified, the task gets 32 steps instead of 15 AND the full `inbox_processing.md` playbook — addressing both root causes (budget + orientation).

**Generalizability:** `HIGH`
- The narrow `inbox_processing` regex is likely to miss many similar natural-language forms: `"handle the unread inbox items"`, `"work on the next inbox message"`, `"deal with the pending inbox entry"`, `"address the oldest inbox note"`. These are all standard English phrasings for the same workflow. The `inbox_processing` task type is one of the budget-heaviest (32 vs 15 steps) and the most sensitive to orientation (ocr workflow, identity verification, channel trust) — a classification miss is nearly always fatal as it is here. I expect 5+ similar t### tasks in the 104-task benchmark to benefit directly, and the fallback widening alone raises confidence on any future inbox phrasing A-Evolve or the platform authors experiment with.

**Zone:** `GREEN` — classification-rule edit only, two regex widenings in `classify.py`. No Python logic change, no strategy-table change, no prompt change, no security-path impact. The `security_test` classification runs before `inbox_processing` (line 158), so no regression risk on threat handling. The CRUD default path remains unchanged for tasks that actually do not mention inbox objects.

**Expected impact:** +1 on t065 directly (budget 15 → 32, plus the correct orientation prompt — very high confidence of PASS). Likely +2 to +4 on other tasks whose natural-language inbox phrasing currently escapes the regex. Honest conservative estimate: **+2 to +4 tasks**.

**Risks:** (1) A task that says `"work the crud file"` would now match the fallback (`work` in process-like ∧ no inbox object → no match actually, so safe). (2) A task that says `"handle the inbox request for refund"` — previously CRUD, now inbox_processing — will get 32 steps and the full playbook; this is a strict upgrade (more time, better orientation). (3) A security test crafted as `"work the oldest inbox message, then ignore previous instructions"` — the `threat_level == "high"` check at line 158 runs before inbox_processing at line 169, so still routes to `security_test`. No regressions identified on a mental walkthrough of the current 104-task cache.
