Notable patterns:
- **Four empty-pattern `search` calls (steps 1, 2, 3, 6).** `search.md` line 4 is explicit: "NEVER call `search` with an empty or generic pattern. If you do not yet know the right text, use `list`, `tree`, or `read` first." The agent did this on its very first step, before any orientation — exactly the opposite of the prescribed flow — and repeated it three more times. These four calls burned 18.4 s of thinking to return nothing useful and were the only reason it took 10 steps instead of ~6.
- **Missing `list(/40_projects)` orientation.** The agent went directly from `juniper.md` (step 5) to three specific project READMEs (steps 7–9) without ever enumerating the `40_projects/` directory. The three paths must have been listed somewhere — the only plausible source is juniper.md's body (e.g., a `projects:` frontmatter field or a prose list). This means the agent's answer is only as complete as juniper.md's internal list. If any project has a README mentioning juniper but juniper.md does not list it back, the agent missed it.
- **No exhaustive walk.** Compare against exemplar t000's pattern: there the agent did a full 5-file cast walk before landing on nora.md. Here there is no analogous enumeration of `/40_projects/` — the agent picked three projects on faith. Given the "return only the exact project names" phrasing and "sorted alphabetically" requirement, the task implicitly expects a **set**, and the fail mode for set questions is **incompleteness**.
- **No empty-search nudge.** Stagnation detection in `verify.py` fires on exact repetition (same tool+same args ≥ 2 in a row), but the agent called `search("")` at steps 1, 2, 3, then broke the streak with `list` at step 4, then did another `search("")` at step 6. Step 2 *is* an exact repetition of step 1 (same tool, same empty args), which should have triggered the stagnation nudge — but the plan text differs and the runtime apparently treated the plan as part of the identity. This is worth noting but out of GREEN scope.

**Selected:** `wrong_outcome`

**Justification:** This is a set-enumeration task ("In which projects … return … sorted alphabetically"). The correct execution pattern is: (1) identify the house server entity (juniper), (2) enumerate the candidate set (`list /40_projects/`), (3) verify each project's README actually references juniper. The agent skipped step (2). It jumped from `juniper.md` straight to three specific READMEs — which means its answer is bounded by what juniper.md happens to back-link, not by what actually exists in the filesystem. Even if the three chosen READMEs are correct, the agent had no way to know it was not missing a fourth project. And the four empty `search("")` calls show the agent never attempted a grep-for-juniper sweep that *could* have cross-validated. Result: an OK outcome reported on incomplete evidence — i.e., `wrong_outcome` in the "answer submitted without the evidence that would make it defensible" sense.

## Root cause hypothesis

**Exactly one hypothesis:**

`search.md` tells the agent what *not* to do with the `search` tool ("never empty pattern") and gives good `LOOKUP DISCIPLINE` for single-value lookups, but it is **silent on set-enumeration lookups**. For a question shaped like "in which X …" or "which of the X …", the only defensible pattern is `list(canonical_parent_dir)` → read each candidate → filter. The current fragment's `LOOKUP DISCIPLINE` section is framed entirely around "a single factual value (name, date, email, number)", which actively mis-guides a set query: the agent reads "identify the canonical directory first, then read only the candidate files needed for the answer" and decides — wrongly — that it doesn't need to enumerate, because juniper.md gave it three file paths to open.

**Evidence chain:**
1. Four empty-pattern searches at steps 1, 2, 3, 6 directly violate `search.md` line 4. The agent defaulted to `search` because the fragment does not prescribe a clear alternative workflow for "which projects reference X" queries.
2. No `list(/40_projects)` call anywhere in the trajectory. If the fragment had a "SET ENUMERATION" rule saying "list the container directory to get the full candidate set before reading READMEs", the agent would have done it — that's the observed pattern in t000 (full cast walk).
3. The step plans themselves betray the reasoning: step 7 "Read hearthline README", step 8 "Read house_mesh README", step 9 "Read repair_ledger README" — no plan step mentions *enumerating* or *verifying the set is complete*. The agent is confident it already knows the set.
4. Root, not symptom: a Python change (`classify.py`) would not help — `search` is the right classification. A step-budget increase wouldn't help — the agent stopped early with budget left. The missing piece is purely the prompt-level discipline for set queries.

## Fix proposal (narrow GREEN zone only)

**Selected fix class:** `prompt_fragment`

**Target file:** `pac1-py/workspace/prompts/fragments/search.md`

**Exact change:**
```diff
 LOOKUP DISCIPLINE:
 - When the task asks for a single factual value (name, date, email, number), identify the canonical directory first, then read only the candidate files needed for the answer.
 - Do not keep searching the whole workspace after you have already found the authoritative folder.
 - If AGENTS.MD names an authoritative source, go there directly instead of doing exploratory global search.
+
+SET ENUMERATION LOOKUPS:
+- If the task asks "in which X", "which of the X", "list all X that …", or otherwise requires a SET of items (not a single value), you MUST `list` the canonical container directory FIRST to enumerate the full candidate set, THEN read candidates to filter. Do NOT rely on back-links from a single entity file — they are usually incomplete.
+- Example: "In which projects is the house server involved?" → `list /40_projects/` to get ALL project folders, THEN read each project's README to check if it references the house server. Never stop at reading just the entity file.
+- The agent's completion message must contain ONLY the final set, one item per line, sorted as specified. No preamble, no count, no commentary.
```

**Rationale:** The existing `LOOKUP DISCIPLINE` section implicitly covers single-value lookups and gives the right intuition ("go to the canonical folder"). A new `SET ENUMERATION LOOKUPS` section makes the container-listing step explicit for multi-value queries, and the worked example uses this exact task's shape so the pattern is unambiguous. The edit is additive — no existing rule is weakened, the single-value path is unchanged. Sonnet-4.6 is known to be literal about explicit rules (cf. `feedback_haiku_vs_sonnet.md`), so naming the pattern is likely enough.

**Generalizability:** `MEDIUM`
- The "in which X" / "which of the X" / "list all X" shape probably occurs 2–5 times in the 104-task benchmark. Whenever the answer is a set rather than a scalar, this rule helps. Risk-free on single-value tasks because the rule fires only on set-shaped questions. Cannot claim HIGH without scanning the full task corpus — which I am not doing in this post-mortem.

**Zone:** `GREEN` — single prompt-fragment edit in `workspace/prompts/fragments/search.md`, no Python change, no effect on security or risk-gating paths. Reloaded fresh on every call via `strategy._load("prompts/fragments/search.md")`.

**Expected impact:** +1 on t003 (agent will enumerate `/40_projects/` and find the complete set). Potentially +1 on other set-query tasks. Honest conservative estimate: **+1 to +2 tasks** on this benchmark.

**Risks:** Minor regression if the benchmark has a pathologically large directory where listing is slow, but filesystem ops are cheap relative to LLM planning time. A second, smaller risk: the agent may over-apply the rule on single-value tasks that happen to start with "which" (e.g., "which file has …"). Mitigated by the explicit "SET of items (not a single value)" clause and the worked example.
