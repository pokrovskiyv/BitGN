## Root cause hypothesis

**Exactly one hypothesis:**

`classify.py` does not recognize "inbound note / inbound message / incoming note" phrasing as inbox processing. The current `_INBOX_PROCESSING_SIGNALS` regex (lines 73–80) expects literal "inbox", "mailbox", "queue", "backlog", "messages", or "pending requests". The term "inbound note" is a natural-English paraphrase of "inbox note" that the benchmark uses in this task and would plausibly reuse. More importantly, "Review the next inbound note and act on it" is a meta-inbox instruction — it tells the agent to go find AND process whatever is sitting in the inbound lane. That is the **canonical inbox_processing task shape** (variable-content, variable-length, requires workflow discovery). Routing it to CRUD with 15 steps is systematically wrong and will repeat every time the benchmark uses "inbound" instead of "inbox".

**Evidence chain:**
1. Task instruction "Review the next inbound note and act on it" uses "inbound" not "inbox". `_INBOX_PROCESSING_SIGNALS` on line 73 has no "inbound" token.
2. `_PROCESS_LIKE_SIGNALS` line 81 has `process|triage|clear|handle|work\s+through|go\s+through|take\s+care\s+of` — none of which match "review" or "act on".
3. `_WRITE_SIGNALS` line 36 does NOT contain "review" or "act". `has_write=False`.
4. With all gate flags False, classification falls through to the CRUD default at line 236 with `estimated_steps=10`, which maps to `crud` → 15 max steps in the strategy table.
5. The agent's trajectory proves the correct task type: read inbox note → find workflow → find schema → write frontmatter to bills → re-read. This is textbook inbox_processing. With the inbox_processing budget of 32 steps it would have finished comfortably.
6. Root, not symptom: a budget bump for crud would harm real crud tasks (increasing hallucination surface area and cost). The right fix is classifying this task as what it is.

## Fix proposal (narrow GREEN zone only)

**Selected fix class:** `classify_rule`

**Target file:** `pac1-py/classify.py`

**Exact change:**
```diff
 _INBOX_PROCESSING_SIGNALS = re.compile(
     r"\b(process\s+(the\s+)?inbox|from\s+(the\s+)?inbox|inbox\s+file|"
     r"(take\s+care\s+of|work\s+through)\s+(the\s+)?(?:inbox|incoming)\s+queue|"
     r"(?:incoming|inbox)\s+queue|pending\s+inbox\s+items?|mailbox|"
     r"message\s+backlog|waiting\s+messages?|pending\s+requests?|"
-    r"newly\s+arrived\s+requests?|unread\s+requests?)\b",
+    r"newly\s+arrived\s+requests?|unread\s+requests?|"
+    r"inbound\s+(?:note|message|item|mail|request)s?|"
+    r"next\s+inbound\b|next\s+inbox\s+item|review\s+(?:the\s+)?(?:next|latest)\s+(?:inbound|inbox|incoming))\b",
     re.IGNORECASE,
 )
```

**Rationale:** Adds three new token families to the inbox_processing classifier: (1) "inbound note/message/item/mail/request" — the literal phrase that appears in this task and is a natural paraphrase the benchmark is likely to reuse; (2) "next inbound" and "next inbox item" — the meta-inbox instruction shape of "go find and process whatever is sitting in the inbound lane"; (3) "review the next inbound/inbox/incoming" — covers the "review + process next" pattern without firing on pure "review document X" reads. This is surgical: it adds keywords to an existing allowlist, so there is zero risk to tasks already classified correctly, and the pattern is specific enough that it won't cross-fire on unrelated "review" or "inbound" usage. The routing effect: this task now classifies as `inbox_processing` → 32-step budget, `inbox_processing.md` prompt fragment loaded, `hardened` security posture. The prompt fragment explicitly tells the agent to find `/99_system` workflows, read `/00_inbox/AGENTS.MD`, verify identities against `/10_entities/cast`, write one concrete output with read-after-write. All of which the agent actually did correctly — it just ran out of steps.

**Generalizability:** `MEDIUM`
- The "inbound note" phrasing is almost certainly reused in other benchmark inbox tasks with different content (different bills, different senders, different workflows). Rough estimate: 1–3 additional tasks in the 104-task set use "inbound" or "next inbound" phrasing instead of "inbox". Cannot claim HIGH without grepping all task instructions, but it's clearly above LOW — the pattern is too obviously useful for the benchmark authors to have used it only once.
- Minor cross-benefit: the "review the next X" shape is also a common household-assistant instruction, so adding it to the inbox routing reduces the chance of similar mis-routing on neighbor tasks.

**Zone:** `GREEN` — `classify_rule` edit, single regex in `classify.py`, no Python logic changes, no effect on security paths (threat_level is computed separately and unaffected), no effect on already-classified tasks (only new keywords added, none removed).

**Expected impact:** +1 on t041 (`OUTCOME_NONE_UNSUPPORTED` → `OUTCOME_OK` because the 32-step budget allows completion of all 3 bills, plus the inbox_processing.md fragment actively guides the agent to `/99_system` workflow discovery, which shortcuts steps 4–8). Possible +1 to +2 on similar "inbound / review the next" tasks elsewhere in the 104-task benchmark. Honest conservative estimate: **+1 to +2 tasks**.

**Risks:** Minor false-positive risk on tasks like "review the next inbound e-mail from a specific contact" where the user wants a pure read-and-summarize, not a write. Mitigation: the inbox_processing.md fragment explicitly says "If the task is read-only triage, do not wander into unrelated write workflows" (line 34) — so even if mis-routed, the agent will not write unnecessarily. Second minor risk: the "review the next inbound/inbox/incoming" alternation could cross-fire on "review the next inbound flight" in a travel-planning task — but there is no travel domain in the current benchmark, and the word "inbound" in airline contexts is paired with "flight", not "note/message/item/mail/request", so the specific sub-pattern won't match.
