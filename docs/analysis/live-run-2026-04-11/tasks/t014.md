**Justification:** The failure presents as `budget_exhausted` (step 15 / 15), but the root is classification. The task "Review the next inbound note and act on it" is semantically an inbox-processing task — the agent's own trajectory confirms this: it read `/00_inbox/000_next-task.md`, read the ocr-records workflow, read the finance schema, wrote the invoice frontmatter, and then fumbled the rest of the inbox-processing workflow (channel verification, seq.json/README.MD lookup, inbox file deletion). Fix the classification and the budget exhaustion goes away automatically — 22 actionable steps completed in an inbox task would very likely finish within 32 steps.

## Root cause hypothesis

**Exactly one hypothesis:**

`_INBOX_PROCESSING_SIGNALS` (and its auxiliary pair `_PROCESS_LIKE_SIGNALS` + `_INBOX_OBJECT_SIGNALS`) in `classify.py` lines 73–89 do not cover the "review inbound note" phrasing. Specifically: (i) "review" is not in `_PROCESS_LIKE_SIGNALS` (which only captures `process|triage|clear|handle|work through|go through|take care of`); (ii) "inbound note" is not in `_INBOX_OBJECT_SIGNALS` (which captures `inbox|mailbox|queue|backlog|messages?|requests?` but not `note|notes|item|items|entry|entries`); and (iii) "next inbound" is a canonical household-workspace phrasing visible in the actual inbox filename `000_next-task.md` — it is not a one-off synonym but the exact terminology the benchmark's inbox directory uses. The classifier does not know the benchmark's own folder vocabulary.

**Evidence chain:**
1. Replayed classifier locally against the verbatim task text: every signal regex returns False, default `crud` branch taken, strategy key `crud`, `max_steps = 15` (confirmed against `_STRATEGY_TABLE` in `strategy.py` line 50).
2. The agent's very first action (`read(/00_inbox/000_next-task.md)`) and its workflow choices (`ocr-records.md`, `finance-record-frontmatter.md`, `process-next-inbox-item.md`) are exactly the steps `inbox_processing.md` lists as the canonical route. The agent correctly *understood* the task as inbox processing; only the strategy layer was lied to.
3. `metrics.step_count = 15` exactly matches `_STRATEGY_TABLE["crud"][0]`. Budget exhaustion is the direct proximate cause, classification mismatch is the root.
4. `metrics.verifier_verdict = null` plus absence of any `report_completion` step confirms the loop exited via max_steps guard in `agent_loop.py`, not via a completion decision.
5. The crud fragment carries no warning about legacy outbox paths — so steps 9, 10, 15 (the ghost chase) are unpreventable with the wrong fragment loaded. The inbox_processing fragment explicitly warns against `outbox/seq.json` (line 22).

## Fix proposal (narrow GREEN zone only)

**Selected fix class:** `classify_rule`

**Target file:** `pac1-py/classify.py`

**Exact change:**
```diff
 _PROCESS_LIKE_SIGNALS = re.compile(
-    r"\b(process|triage|clear|handle|work\s+through|go\s+through|take\s+care\s+of)\b",
+    r"\b(process|triage|clear|handle|work\s+through|go\s+through|take\s+care\s+of|"
+    r"review|act\s+on)\b",
     re.IGNORECASE,
 )
 _INBOX_OBJECT_SIGNALS = re.compile(
     r"\b(inbox|mailbox|queue|backlog|waiting\s+messages?|pending\s+requests?|"
-    r"newly\s+arrived\s+requests?|unread\s+requests?|messages?|requests?)\b|messages/",
+    r"newly\s+arrived\s+requests?|unread\s+requests?|messages?|requests?|"
+    r"inbound\s+(?:note|item|message|request)s?|next\s+(?:inbound|inbox|incoming)\s+\w+|"
+    r"(?:inbound|incoming)\s+notes?)\b|messages/",
     re.IGNORECASE,
 )
```

**Rationale:** The combined rule at `classify.py` line 148 is `has_inbox_processing = has_INBOX_PROCESSING or (has_PROCESS_LIKE and has_INBOX_OBJECT)`. Adding "review" and "act on" to `_PROCESS_LIKE_SIGNALS` plus "inbound note", "next inbound _", and "inbound/incoming notes" to `_INBOX_OBJECT_SIGNALS` makes the AND branch fire for the exact task text seen here. Both halves of the edit are narrowly scoped: "review" requires a matching inbox-object word to trigger the branch, and "inbound note" is a noun phrase that only appears in inbox contexts. No other task type loses coverage — `crud` and `search` do not share these tokens (the search regex has "review" neither in `_SEARCH_SIGNALS` nor `_LOOKUP_SIGNALS`). The inbox_processing branch precedes multi_step and crud in the `classify_task()` decision order (`classify.py` lines 169–177), so adding signals there has no downstream collision risk.

**Generalizability:** `MEDIUM-HIGH`
- "Review the next inbound X" is exactly the kind of natural phrasing a benchmark author uses when the inbox contains an actionable note. The benchmark's own filename convention (`000_next-task.md`) suggests the word "next" is part of the canonical vocabulary. Other likely near-misses: "Handle the next inbound", "Triage the incoming note", "Act on the pending note" — the last two already match via existing tokens, so only "review + inbound note / next inbound" are new surface area. Estimate 2–4 tasks in the 104-task benchmark use "review" as the lead verb in an inbox context; each represents a potential +0.5 to +1.0 points if routing improves. Cannot claim HIGH without scanning all task texts.

**Zone:** `GREEN` — classify.py rule additions, pure regex edit, no Python logic change, no effect on the decision-order semantics. The multi_step rule precedes the inbox rule but fires only on explicit sequencing tokens ("then", "after that", "and then", etc.) which are NOT in this task, so no regression on tasks currently classified as multi_step.

**Expected impact:** +1 on t014 (`crud`/15 budget → `inbox_processing`/32 budget, allowing the agent's existing correct trajectory to finish — it completed the critical write by step 7 and needed only 3–5 more steps to satisfy workflow verification and completion). The inbox_processing fragment's "legacy fallback" warning would also have blocked the `/60_outbox/outbox/` and `seq.json` ghost hunt, recovering ~30s of wall time. Potentially +1 on 1–3 similar "review the inbound X" or "next inbound X" tasks elsewhere. Honest conservative estimate: **+1 to +2 tasks**.

**Risks:** Minor risk that "review" triggers inbox routing on tasks like "Review the contacts/ folder and list the entities" — mitigated by the AND with `_INBOX_OBJECT_SIGNALS`, which requires an inbox-object token. A "review" task that does not mention inbox/inbound/queue/note will still fall through to the default. Second minor risk: a task like "Act on the pending feature request" — the word "requests" already matches `_INBOX_OBJECT_SIGNALS`, so "act on" would now route it to inbox_processing instead of crud. That is arguably the correct behavior for a "pending request" (inbox semantics), so this is a neutral-to-positive side effect, not a regression. Third: the new `next\s+(?:inbound|inbox|incoming)\s+\w+` token is very specific and unlikely to collide — it requires the exact "next inbound/inbox/incoming <word>" structure.
