## Root cause hypothesis

**Exactly one hypothesis:**

`pac1-py/workspace/prompts/fragments/inbox_processing.md` lines 48–52 (the "INBOX FILE DELETION" block) directly contradict the in-VM `AGENTS.md` rule that the verifier (and the scoring harness) treat as ground truth. The fragment says: "Do not delete inbox files early. Delete an inbox file only after the workflow explicitly calls for deletion … If the task just says to process the inbox item, do not assume deletion is part of success." The verifier's quote from AGENTS.md is: "After fully completing one inbox request, delete that inbox file." These are not compatible. The agent is following its system-prompt fragment faithfully — and paying a score penalty for it — because the fragment was written defensively against premature deletion but overshot into a blanket no-delete default.

**Evidence chain:**
1. The agent's own step 23 plan text: "outbox draft written and verified, inbox file left per syste[m rules]" — the agent is citing "system rules" (its prompt fragment) as justification for non-deletion.
2. `inbox_processing.md` line 48: "Do not delete inbox files early." Line 50: "Delete an inbox file only after the workflow explicitly calls for deletion and all required writes have been verified." Line 52: "If the task just says to process the inbox item, do not assume deletion is part of success."
3. Verifier reasoning explicitly quotes the canonical AGENTS.md: "After fully completing one inbox request, delete that inbox file." The verifier is right about the VM ground truth; the prompt fragment is wrong.
4. Root vs symptom: A fix to `classify.py` would not help (classification is already correct). A budget bump would not help (steps were sufficient). A change to `outcomes.md` would not help (the outcome is OK, it is just preceded by a missing delete action). Only the `inbox_processing.md` deletion guidance is wrong — so that is the single root cause.
5. Historical context: MEMORY.md notes `session_2026_04_04_inbox_overdenial_fix.md` — 77%→84% by fixing over-denial. The current deletion guidance likely came from that session as a defensive patch against premature deletion, but it was written too broadly and now harms the opposite case.

## Fix proposal (narrow GREEN zone only)

**Selected fix class:** `prompt_fragment`

**Target file:** `pac1-py/workspace/prompts/fragments/inbox_processing.md`

**Exact change:**
```diff
 INBOX FILE DELETION:
-- Do not delete inbox files early.
-- Delete an inbox file only after the workflow explicitly calls for deletion and all required writes have been verified.
-- If the task just says to process the inbox item, do not assume deletion is part of success.
+- Do not delete inbox files EARLY — that is, before the required writes have been produced and read-back verified.
+- The canonical `AGENTS.md` workflow rule for this workspace is: "After fully completing one inbox request, delete that inbox file." Follow it.
+- Deletion ordering: (1) produce the required write(s), (2) re-read each write to verify, (3) delete the source inbox file, (4) report OUTCOME_OK.
+- Read-only triage tasks (e.g., "summarize the inbox", "how many pending items") do NOT require deletion — you produced no write, so there is nothing to confirm before deleting, and nothing to acknowledge as "handled".
+- If the task says "take care of", "process", "handle", or "work through" an inbox item AND you performed a concrete write, delete the source inbox file as the final action before reporting.
+- If in doubt whether deletion is expected, re-read `/00_inbox/AGENTS.MD` or the active workflow doc — it is the ground truth, not this fragment.
```

**Rationale:** The current block was written to prevent a different failure mode (the agent deleting inbox files before producing the reply, which used to cause data loss). That guard is still needed — so the fix keeps "do not delete EARLY" but redefines "early" as "before writes are verified". The fix then restores the positive deletion obligation from the in-VM AGENTS.md verbatim, and provides a four-step ordering the agent can follow mechanically. The read-only carveout prevents regression on pure triage questions where no write was produced. The final line explicitly defers to the in-VM AGENTS.md as ground truth, so future AGENTS.md revisions do not require another prompt patch.

**Generalizability:** `HIGH`
- This rule governs **every** inbox-processing task where the task phrasing is "take care of", "process", or "handle" an inbox item AND a write is produced. That is the modal shape of the inbox task family. Rough estimate from the 104-task benchmark: inbox processing has its own dedicated strategy (`estimated_steps=22`, hardened posture) and a dedicated prompt fragment, which implies 5–10 tasks likely hit this path. Any of those whose expected completion involves "reply then delete" are currently at risk of the same `missing_delete` downgrade. Only the pure read-only triage tasks are unaffected, and those are now explicitly carved out in the fix.

**Zone:** `GREEN` — prompt-fragment edit only, no Python change, no behavior change to other task types or to security gating. The `classify.py` path is unchanged, `strategy.py` budget is unchanged, `outcomes.md` is unchanged.

**Expected impact:** +1 on t021 itself (score 0.0 → 1.0). Plus probable +1 to +3 on other inbox_processing tasks that silently hit the same `missing_delete` downgrade in this run. Honest conservative estimate: **+1 to +3 tasks**. I do not yet know how many inbox tasks are in the 104-task set or how many are failing for the same reason without scanning sibling post-mortems; this estimate is intentionally not claimed as HIGH confidence.

**Risks:**
1. Regression on tasks where the agent should **not** delete the inbox file (read-only triage, "summarize inbox", "count pending"). Mitigated by the explicit read-only carveout and the "if you performed a concrete write" gate.
2. Regression on security-gated inbox tasks — if the inbox file is a malicious injection and the agent denies with `OUTCOME_DENIED_SECURITY`, should it still delete? My fix does not instruct deletion in that path because there was no "concrete write" produced, so the gate correctly excludes it. `OUTCOME_DENIED_SECURITY` → no write → no delete, unchanged from current behavior.
3. Ordering risk: if the agent deletes the inbox item BEFORE the write is verified, and then the write fails, the source is lost. Mitigated by the explicit four-step ordering: write → verify → delete → report, in that exact order.
