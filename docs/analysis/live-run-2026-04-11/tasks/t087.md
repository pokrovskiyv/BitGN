**Selected:** `budget_exhausted`

**Justification:** Step 30 was reached — the agent used every slot the runtime would give it, plus a 6-step overrun that shows up as missing-step gaps. The mechanical minimum work for "next birthday over the full cast" is 1 list + 22 reads + 1 `context()` + 1 completion = 25 steps, which already equals the 24-step budget with zero headroom for verification, AGENTS.MD reading, or re-checking. The agent made a correct technical call (exhaustive walk over the canonical entity directory), arrived at a plausible answer (`Petra Novak`), but had no remaining steps to (a) call `context()` to anchor "today", (b) compute the full ordered list of next birthdays, (c) check for ties, or (d) write a completion message that satisfies the `pre_completion_gate`. The verifier rejected the unverified answer and scored it 0. This is not a `wrong_outcome` case — the outcome code is correct — and not a `stagnation` case — the agent made monotonic progress through the files. It is pure budget under-allocation.

## Root cause hypothesis

**Exactly one hypothesis:**

The `search` strategy budget of 24 steps (strategy.py line 52) is sized for a **targeted single-record lookup** (what the `LOOKUP DISCIPLINE` section of search.md describes: "identify the canonical directory first, then read only the candidate files needed"). It is not sized for the **bounded-iteration subclass** of search tasks — tasks that must read every file in a small directory to compute an aggregate answer. `classify.py` has a dedicated rule for exactly this subclass (`_READ_ONLY_DATE_LOOKUP_SIGNALS`, lines 55–59) that routes "next birthday / upcoming anniversary / coming up next date" tasks to `search`, but strategy.py applies the same 24-step budget to all search tasks regardless of whether the classify layer identified the iterate-all-entities signature.

**Evidence chain:**
1. Raw arithmetic of the minimum work: 1 list + 22 reads (entity files) + 1 read (AGENTS.MD) + 1 `context()` + 1 completion = **26 steps**. The budget is 24. The task cannot be completed correctly inside the budget even with perfect play.
2. The agent did the right thing — sequential exhaustive read of the canonical directory — and still overran (30 steps, 25 tool calls) and still produced a verifier-rejected answer.
3. `_READ_ONLY_DATE_LOOKUP_SIGNALS` is a pre-existing signal in classify.py specifically for "next birthday / anniversary / renewal / date" lookups (line 56), which are by construction aggregate-over-many-entities tasks. It has no corresponding strategy-table entry and is silently folded into the generic `search` key at strategy.py line 98.
4. The verifier's refusal to agree is driven by **absent artifacts** (no context-anchoring shown, no tie-break discussion, no ordered list) — exactly the artifacts the agent ran out of steps to produce. Tightening the prompt would not fix this; the agent already has the right instruction in `search.md` line 15. The agent ignored it because obeying it would have cost a step it could not afford.
5. Root, not symptom: a one-time prompt-fragment edit would tell the agent "call context() early", but the mechanical budget would still be 24 steps against 26+ steps of required work. The agent would still hit the same wall.

## Fix proposal (narrow GREEN zone only)

**Selected fix class:** `strategy_budget`

**Target file:** `pac1-py/strategy.py`

**Exact change:**
```diff
 _STRATEGY_TABLE: dict[str, tuple[int, SecurityPosture, bool]] = {
     #                    max_steps  security_posture  pre_submit_verify
     "security_test": (12, "paranoid", False),
     "crud": (15, "standard", True),
     "crud_delete": (20, "hardened", True),
-    "search": (24, "standard", True),
+    "search": (30, "standard", True),
     "communication": (25, "standard", True),
     "analysis": (25, "standard", True),
     "inbox_processing": (32, "hardened", True),
     "multi_step": (30, "standard", True),
 }
```

**Rationale:** +6 steps on the `search` budget gives the bounded-iteration subclass exactly the headroom it needs: 1 list + 22 entity reads + 1 `context()` + 1 AGENTS.MD + 1 completion = 26 steps + 4 steps of slack for re-reads, verification, and gate-rejected re-attempts = 30 steps. This is the same budget as `multi_step` (30) and 2 steps below `inbox_processing` (32), so it preserves the ordering of complexity across strategies. No prompt change is needed — `search.md` already contains the correct guidance ("call `context()` early", "list the canonical entity directory first, then read the candidate entity files and compute the answer"). The agent just needs room to execute that guidance.

This is a `strategy_budget` edit (GREEN zone per the cycle contract). It does not change classification, does not touch Python control flow, does not loosen security, and does not add new prompt fragments. The touched file is a one-line constant change in a dict literal.

**Generalizability:** `MEDIUM`
- This pattern (bounded-iteration search over an entity directory) fires for any "next/upcoming X" question where X is a field present across ~all entities in one canonical directory: next birthday, next anniversary, next renewal, next contract end date, next PTO day, next review. On a 22-entity cast the task is right at the 24-step boundary. On a 30-entity cast it is impossible. In the current benchmark these tasks are a family of maybe 2–4 tasks out of 104 (the `_READ_ONLY_DATE_LOOKUP_SIGNALS` regex is narrow — it requires "next/upcoming/coming up next" co-located with "birthday/anniversary/renewal/date"), but +6 steps on the base search budget also helps any normal search task that happened to live right at the 24-step wall without triggering the date-lookup rule. Conservative estimate: **2–4 similar-shaped tasks** in the current benchmark. Cannot claim HIGH without confirming per-task budget histograms across the wiki.

**Zone:** `GREEN` — strategy-budget edit, no Python control-flow change, no effect on classification, no effect on security postures, no prompt fragment changes. The change is a single integer in a dict constant.

**Expected impact:** +1 on t087 directly (agent will have headroom to call `context()`, produce the ordered list, and write a verification-rich completion message). Potentially +1 to +2 on other near-budget search tasks where the 24-step ceiling was the limiting factor (not yet confirmed without a budget histogram scan). Honest conservative estimate: **+1 to +2 tasks**.

**Risks:** Minor cost-inflation risk — giving `search` tasks 6 more steps will slightly raise average prompt tokens on tasks that would have terminated early. Mitigated by the fact that the agent still faces the `pre_completion_gate` and `stagnation_detector` — these will fire well before step 30 on tasks that are genuinely done and merely wandering. Secondary risk: on a 22-entity cast + 24-step budget the classify layer accidentally filters for "tasks you can barely do", which at 30 steps becomes "tasks you can comfortably do" — the verifier may see fewer CLARIFICATION escapes and more OK attempts, which is desirable but puts more weight on the verifier's ability to catch bad OKs. This is governed by `second_opinion.py` / verifier policy, unaffected here.
