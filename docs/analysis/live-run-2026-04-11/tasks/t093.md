## Root cause hypothesis

**Exactly one hypothesis:**

`strategy.py:_STRATEGY_TABLE["inbox_processing"] = (32, "hardened", True)` sets a 32-step budget that is too tight for inbox items containing batch workflows (N × {read, write, verify} + setup overhead). The mandatory read-after-write discipline (CLAUDE.md: "every `Req_Write` must be followed by a `Req_Read` of the same path") multiplies per-item cost by 3x, and the inbox_processing setup tax (next-task + tree + workflow + schema + AGENTS.MD) is a flat 5 steps before any per-item work begins. The math: 5 + 3N + 1 (for `report_completion`) ≤ 32 solves to N ≤ 8.67 — so at N=8 the agent has exactly one step of slack, and t093's 8-document OCR workflow blew through that slack on the step-5 exploratory batch-read plan plus the two steps 6/7 that never reached dispatch (most likely retry attempts after the step-5 read surfaced 80-char truncation).

**Evidence chain:**
1. **Step arithmetic:** 8 items × 3 (read+write+verify) = 24; setup = 5; completion = 1; minimum = 30. Budget = 32. Observed step_count = 32, with no `report_completion` call — the agent used the 2-step slack plus the completion slot and ran off the end.
2. **Missing steps 6/7/31:** absent from `metrics.steps` entirely. `tool_call_count: 29` vs `step_count: 32` confirms 3 slots were consumed by attempts that did not produce a dispatched tool call. That alone shaved the slack to zero.
3. **No stagnation nudges fired:** `verify.py:StagnationDetector` (lines 225-261) would have surfaced `zero_match_streak`, `not_found_streak`, or `no_new_evidence` if the agent had been looping. None fired — the agent was making steady linear progress through the 8-item list.
4. **Structural, not content:** the agent executed `inbox_processing.md` discipline correctly (tree 99_system → workflow → AGENTS.MD → per-item read-write-verify). The breakdown is at `strategy.py:_STRATEGY_TABLE` where the budget is hardcoded too low for realistic batch sizes.

## Fix proposal (narrow GREEN zone only)

**Selected fix class:** `strategy_budget`

**Target file:** `pac1-py/strategy.py`

**Exact change:**
```diff
-    "inbox_processing": (32, "hardened", True),
+    "inbox_processing": (40, "hardened", True),
```

**Rationale:** The minimum for an N-item read-write-verify inbox workflow is `5 (setup) + 3N + 1 (completion)`. At N=8 that is 30, and the current 32-step budget leaves only 2 steps of real slack. Anything that costs an extra step — an exploratory batch-read, a path-retry, a gate nudge, a `list` call to recover from not_found — blows the budget. A 40-step budget supports N=10 with 4 steps of honest headroom (5 + 30 + 1 = 36) and N=11 with 1 step (5 + 33 + 1 = 39). Zero Python logic touched, zero prompt text touched, posture still `hardened`, `pre_submit_verification` still True — a single integer change.

**Generalizability:** `MEDIUM`
- Budget-class fix, not a content fix. Helps any `inbox_processing` task whose workflow bundles ≥6 items with read-write-verify discipline. Rough estimate: 2-4 tasks per benchmark run touch batch-style inbox workflows (OCR, frontmatter, triage, batch categorize). Not HIGH because single-item inbox tasks already complete in 10-15 steps and never approach the ceiling. Not LOW because this failure will repeat whenever an inbox item bundles N ≥ 6 sub-writes. Honest midpoint: MEDIUM.

**Zone:** `GREEN` — `_STRATEGY_TABLE` is an explicit GREEN target (strategy_budget fix class). No classify logic, no prompt text, no posture change, no control flow change. Only risk surface is marginally longer wall-clock time on affected tasks, mitigated by `pre_submit_verification=True` and an unchanged `StagnationDetector`.

**Expected impact:** +1 on t093 (with 40 steps the agent completes 30 steps of work with 10 steps of cushion — `report_completion` fires comfortably). Potentially +1 to +2 on similar batch-inbox tasks elsewhere. Honest conservative estimate: **+1 to +2 tasks**.

**Risks:** Minor — (a) slightly larger prompt tokens on short inbox tasks (negligible since those complete early); (b) a pathological stagnation could burn extra steps, but `StagnationDetector` fires at repetition threshold 2 and semantic signals at streak length 3, so escape is unlikely. No security-path risk — `hardened` posture preserved, `security_addon` still injected, `cumulative_threats` still gated in `pre_completion_gate`.
