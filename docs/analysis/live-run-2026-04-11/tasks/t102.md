**Selected:** `classification_mismatch`

**Justification:** The task asks the agent to sum line items across multiple bills from a specific vendor and return a single number — textbook `analysis` (the `analysis.md` fragment literally opens with "ANSWER PRECISION" and contains a dedicated `NUMERIC AND MONETARY DISCIPLINE` block). But because the classifier regex `_ANALYSIS_SIGNALS` only matches `how\s+many` and not `how\s+much`, and because "how much" is also absent from `_SEARCH_SIGNALS`, the task walks all the way down to the default `crud` branch and picks up `crud.md`. This is a single-character regex gap that silently degrades the system prompt for an entire class of currency/quantity questions. The agent's trajectory is the direct symptom: it read only two of potentially N vendor bills, committed an empty-pattern search (which it would have been warned against under search.md), and reported a total with no visible citation of which rows were summed.

## Root cause hypothesis

**Exactly one hypothesis:**

`classify.py._ANALYSIS_SIGNALS` at line 52 matches `how\s+many` but omits `how\s+much`. Natural-language questions about monetary totals ("how much did I pay", "how much did this cost", "how much do I owe") are the single most common phrasing for finance-analysis tasks, and they currently skip the entire analysis branch and land in CRUD. Consequence: the task inherits a 15-step budget (fine), CRUD security posture (fine), AND `crud.md` as its prompt fragment (**not fine**) — losing all numeric/monetary discipline rules.

**Evidence chain:**
1. Direct replay of `classify_task()` on the instruction returns `task_type='crud'`, `estimated_steps=10`, which confirms the regex gap, not a downstream bug.
2. Inspection of `_ANALYSIS_SIGNALS` pattern literal (`classify.py` lines 51–54) shows `how\s+many` is the only "how …" alternative in the alternation. No `how\s+much`, no `how\s+long`, no `how\s+far`.
3. Inspection of `_SEARCH_SIGNALS` pattern literal (`classify.py` lines 41–45) shows "how" is absent entirely from the search alternation. So "how much" falls through _both_ the analysis and search rules — the two branches that would have loaded a useful prompt fragment.
4. `crud.md` is six lines. `analysis.md` contains the `NUMERIC AND MONETARY DISCIPLINE` block (lines 11–16) that is the exact body of rules the agent needed for this task. The observed trajectory (two reads + empty-pattern search + quick completion) is consistent with an agent operating under the six-line CRUD guidance, not the analysis one.
5. Root, not symptom: fixing the symptom at the prompt layer (e.g., cross-pollinating MONETARY DISCIPLINE into crud.md or reasoning.md) would bloat every CRUD task with irrelevant guidance. The cause is the classifier.

## Fix proposal (narrow GREEN zone only)

**Selected fix class:** `classify_rule`

**Target file:** `pac1-py/classify.py`

**Exact change:**
```diff
 _ANALYSIS_SIGNALS = re.compile(
-    r"\b(analyze|summarize|compare|count|list\s+all|report|describe|explain|how\s+many)\b",
+    r"\b(analyze|summarize|compare|count|list\s+all|report|describe|explain|"
+    r"how\s+many|how\s+much|how\s+long|total\s+(?:amount|cost|spent|paid)|"
+    r"sum(?:\s+up)?|subtotal)\b",
     re.IGNORECASE,
 )
```

**Rationale:** Adds the three missing "how …" interrogatives that typically introduce aggregation questions ("how much did I pay", "how long does X take", "how many" already covered) plus explicit aggregation nouns (`total amount`, `sum`, `subtotal`). This is the minimal surface area to promote t102 and its siblings into the `analysis` branch, where they pick up `analysis.md` (25-step budget, `ANSWER PRECISION`, `NUMERIC AND MONETARY DISCIPLINE`). The pattern stays inside `\b…\b` word boundaries and uses non-capturing groups, so it won't accidentally match inside longer words. No change to the branch ordering: `has_analysis and not has_write` still fires at line 203 before search/crud, so the task type resolves to `analysis`. No Python logic change.

**Generalizability:** `HIGH`
- "how much" is one of the most common English question openers for currency and aggregation tasks. Across the 104-task benchmark, any task that asks the agent to sum, total, average, or compare monetary line items in `/50_finance/*` or `/20_ops/*` is exposed to the same classification gap. A conservative estimate of 5–10 sibling tasks share the exact failure mode (monetary total + "how much" phrasing), and another handful use `total …` or `sum …` phrasing that the extended regex also catches. This is a broad, shape-level fix rather than a one-off prompt tweak.

**Zone:** `GREEN` — classify rule edit only, no Python logic change, no new branch, no behavioral change for any task that already matches the current `_ANALYSIS_SIGNALS`. Security paths are untouched (threat classification runs before type classification at line 158). Existing `analysis` strategy settings (25 steps, `standard` posture) are known-safe.

**Expected impact:** +1 on t102 (moves from `crud` → `analysis`, loads `analysis.md`, enforces cite-all-rows and currency transcription before `report_completion`, raising the probability of a correct total). Potentially +1 to +3 on similar finance-computation tasks elsewhere in the 104-task benchmark where "how much" / "total paid" / "sum of" currently degrade into CRUD. Honest conservative estimate: **+1 to +3 tasks**.

**Risks:** Minor over-classification risk for tasks that use "how much" rhetorically without needing analysis (e.g., "how much does this matter" in a description). Mitigations: (a) the analysis branch is gated by `not has_write`, so any task that also contains a write verb still escapes to `multi_step` or `crud`; (b) even a false-positive analysis classification is benign — it adds 10 steps of budget and a slightly larger prompt, with no security-posture change; (c) the added tokens are all content-words that do not collide with common file/path vocabulary the classifier already sees. A grep across the existing task instructions for unintended matches would take a minute and is recommended but not blocking.
