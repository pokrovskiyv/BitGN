## Root cause hypothesis

**Exactly one hypothesis:**

`_ANALYSIS_SIGNALS` in `classify.py` line 51–54 recognises `how\s+many` for counting but not `how\s+much` for monetary totals. A financial summation question ("How much did I pay in total?") is semantically an analysis/aggregation task, but the regex only fires on "how many". Every other analysis signal (analyze/summarize/compare/count/list all/report/describe/explain) is either a verb or an explicit "how many" count — none of them match the natural English phrasing of a money total. Tasks phrased as "how much did I spend / pay / owe / charge / earn / receive / invoice" all slip through to the `crud` default, which is the wrong strategy both in terms of prompt fragment (no numeric discipline) and in terms of step budget (15 vs 25).

**Evidence chain:**
1. Regex trace (run in a Python shell with the exact task text): all 8 signal groups return False. The only matching branch is the final `return TaskClassification(task_type="crud", ...)` on line 236.
2. Strategy table maps `crud` → `(15, "standard", True)` and loads `prompts/fragments/crud.md` — a 5-line write-focused fragment with zero numeric guidance.
3. `analysis.md` line 11–16 contains the exact rules this task needed ("cite source file AND the row", "read ALL relevant rows first", "do NOT invent or approximate") — these never reached the agent's context.
4. The trajectory shows a symptomatic under-read: only 3 bill files touched (one of them via a malformed path that likely failed), no row-by-row citation in the final plan, no visible grounding_refs in the cache payload. Exactly what the analysis fragment was designed to prevent.
5. Root, not symptom: a fix to `outcomes.md` or `crud.md` would leave other "how much did I spend" tasks still misrouted. A fix to the classifier regex routes ALL such tasks to the `analysis` branch in one place.

## Fix proposal (narrow GREEN zone only)

**Selected fix class:** `classify_rule`

**Target file:** `pac1-py/classify.py`

**Exact change:**
```diff
 _ANALYSIS_SIGNALS = re.compile(
-    r"\b(analyze|summarize|compare|count|list\s+all|report|describe|explain|how\s+many)\b",
+    r"\b(analyze|summarize|compare|count|list\s+all|report|describe|explain|"
+    r"how\s+many|how\s+much|total(?:\s+spent)?|subtotal|"
+    r"balance|(?:total|sum|aggregate)\s+(?:spend|spent|cost|costs|paid|payments?|revenue|income))\b",
     re.IGNORECASE,
 )
```

**Rationale:** The added alternates (`how\s+much`, `total`, `subtotal`, `balance`, and the sum-of-X phrases) cover the universe of natural English formulations for monetary aggregation questions. `how\s+much` alone fixes t103 directly. The `total / subtotal / balance` additions cover phrasings like "What's the subtotal for...", "Show the balance for...", "Total revenue from...". All terms are anchored with `\b` word boundaries, so "accounting" will NOT match `\bcount\b` and "cleanup" will NOT match `\bclean\b` (cleanup is not in the pattern anyway — irrelevant here). This keeps the false-positive surface minimal.

Once the regex fires, the classifier falls through to the `if has_analysis and not has_write` branch at line 203, returning `task_type="analysis"`, which loads `analysis.md` with the NUMERIC AND MONETARY DISCIPLINE section and bumps the step budget from 15 to 25.

**Generalizability:** `MEDIUM`
- The specific "how much did I pay / spend / owe" pattern is extremely natural for any accounting, budget, or expense-tracking task in the PAC benchmark. Rough estimate: 2–4 of the 104 tasks in this run are phrased as money totals without using "how many". The fix also catches the "total X for Y" phrasing which likely appears in a further 1–2 tasks. Cannot claim HIGH without an actual grep of all 104 instructions — would need to broaden the scan to verify.
- Collateral benefit: the analysis fragment's "cite every row" rule also defends against wrong-number hallucinations in tasks that were already borderline analysis (e.g., "report how much I owe vendor X", currently ambiguous).

**Zone:** `GREEN` — pure regex addition in `classify.py`, no Python logic change, no strategy-table change, no new branch. The regex only widens the `analysis` trigger surface; it cannot narrow any existing branch, because analysis is evaluated only AFTER write/delete/search/multi_step guards. The only observable effect is that "how much" questions now route to analysis instead of falling through to crud — which is strictly more prompt context, not less.

**Expected impact:** +1 on t103 if the downstream issue is indeed "agent missed a row because it had no 'read all relevant rows' instruction". +1 to +2 on similar money-total tasks in the current benchmark. Honest conservative estimate: **+1 to +2 tasks**. The fix does NOT guarantee a correct total if the agent still mis-transcribes a path like in step 6 — that's a separate tool-error class that would need a `find`-result-verification nudge, which is out of scope here.

**Risks:** Very low. The regex addition can only widen the analysis branch. Tasks that contain "total" in a non-aggregation sense (e.g., "total war campaign notes", "subtotal field of the form") would be routed to analysis and get a larger step budget + numeric discipline prompt — the worst case is a slightly higher planning cost, not a wrong outcome. No security paths touched. No effect on CRUD write/read-after-write semantics because the analysis branch is `not has_write`-gated. If "total" gets false-positive hits, the fix can be narrowed to `total(?:\s+(?:spent|paid|spend|cost|costs|payment|payments|revenue|income|balance))` — but this also reduces catch rate.
