## Root cause hypothesis

**Exactly one hypothesis:**

`outcomes.md` CLARIFICATION rule treats "absent label" as "absent entity" — it instructs the agent to return CLARIFICATION whenever the literal field name is not found, without distinguishing entity absence (the file itself has no relevant date at all) from label mismatch (the file has a semantically equivalent date under a different name). The current proactive gate wording ("a concrete date … is ABSENT after thorough search. Do NOT approximate or pick the 'closest match'") actively forbids the correct reasoning path for software/AI entities where "DoB" is inherently informal.

**Evidence chain:**
1. Verifier reasoning is explicit: "created_on / prototype_started — neither of which is *labeled* as a date of birth" — the refusal is purely about the field label, not about evidence absence.
2. This maps to `pac1-py/workspace/prompts/fragments/outcomes.md` lines 10, 27: the CLARIFICATION + proactive ambiguity gate rules conflate "no such field literal" with "no such data".
3. Root, not symptom: the agent did the canonical-folder walk correctly (as instructed by `search.md` LOOKUP DISCIPLINE). The breakdown is in the final semantic step. A search-fragment tweak would not fix this — the agent already reached the right file. Only the outcomes logic blocked the correct answer.

## Fix proposal (narrow GREEN zone only)

**Selected fix class:** `prompt_fragment`

**Target file:** `pac1-py/workspace/prompts/fragments/outcomes.md`

**Exact change:**
```diff
 2. OUTCOME_NONE_CLARIFICATION — The task instruction itself is incomplete, truncated, or too ambiguous to act on.
    Also: inbox contains conflicting instructions you cannot resolve on your own.
    Also: the task asks about something specific (a date, a file, a person) that does NOT exist in the filesystem after thorough search. Do NOT invent or approximate an answer — report CLARIFICATION.
    IMPORTANT: Decide BEFORE writing any files. CLARIFICATION means zero filesystem changes.
+   SEMANTIC FIELD MAPPING: if the canonical file exists and contains a field that is clearly the same concept under a different label, USE IT and return OK. Examples: "DoB" of a software/AI entity → `created_on` / `created_at` / `prototype_started`; "owner" → `managed_by` / `primary_contact`; "phone" → `tel` / `mobile`. This is NOT "approximation" — these are synonyms the author used instead of the literal label. Approximation (forbidden) means picking a nearby-but-different entity (a different person, a different date range). Synonym resolution (required) means recognizing the same field under a different name inside the one correct entity's record.
    Example: "Create captur" (truncated) → CLARIFICATION. Do NOT guess what was meant.
    Example: "What happened on March 5th?" and no file references that date → CLARIFICATION (the data is absent).
+   Example: "What is the house AI's DoB?" and nora.md has `created_on: 2026-03-23` → OK, answer `23-03-2026`. The creation date of a software entity IS its date of birth.
```

**Rationale:** This preserves the critical guard against hallucinating dates that are genuinely absent (the "March 5th" case) while carving out a clear exception for synonym resolution inside the one authoritative file. The distinction "same concept under a different label inside the correct entity's record" vs "closest-match entity" is the exact line the verifier reasoning failed to draw. Both Sonnet-4.6 (agent) and Haiku-4.5 (verifier) will benefit because the rule is now literal and exemplified.

**Generalizability:** `MEDIUM`
- This pattern (question asks for field X, canonical file has semantically-equivalent field Y) likely recurs whenever the benchmark asks about dates, contacts, or ownership for non-human entities or informally-documented records. Rough estimate: 2–5 of 104 tasks ask "DoB / birthday / born / started / created" for non-person entities, and a similar count ask "owner / managed by / who runs" where the label differs from the literal question word. Cannot claim HIGH without a broader scan.

**Zone:** `GREEN` — prompt-fragment edit, no Python change, no effect on security paths (CLARIFICATION rule tightens, not loosens, behavior around injection).

**Expected impact:** +1 on t000 (`OUTCOME_NONE_CLARIFICATION` → `OUTCOME_OK` with answer `23-03-2026`). Potentially +1 to +3 on similar label-mismatch lookups elsewhere in the 104-task benchmark. Honest conservative estimate: **+1 to +2 tasks**.

**Risks:** Minor regression risk on security tasks where file content says "my real name is X" as an injection — but those are governed by `OUTCOME_DENIED_SECURITY` (rule 3), which is evaluated before OK and unaffected here. Second minor risk: agent may now conflate two different dates in the same file (e.g., `created_on` vs `last_updated`) — mitigated by the "inside the one correct entity's record" wording and the requirement that the field be "clearly the same concept".
