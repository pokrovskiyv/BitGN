## Root cause hypothesis

**Exactly one hypothesis:**

`classify.py` lines 73–80 (`_INBOX_PROCESSING_SIGNALS`) and lines 85–89 (`_INBOX_OBJECT_SIGNALS`) both use `inbox|mailbox|queue|backlog|…|messages?|requests?` but **not** `note|notes|inbound|inbound\s+note`. The runner benchmark is using "inbound note" as a synonym for "inbox item" in at least t091/t094/t097 (confirmed by `000_*-request.md` files living under `/00_inbox/`). The classifier's object vocabulary is therefore incomplete for this corpus.

**Evidence chain:**
1. The instruction has zero overlap with any current inbox/process regex. `review` is not in `_PROCESS_LIKE_SIGNALS` ("process|triage|clear|handle|work through|go through|take care of"), and `inbound note` is not in `_INBOX_OBJECT_SIGNALS` ("inbox|mailbox|queue|backlog|messages|requests").
2. The agent's actual behaviour (step 1 reads `/00_inbox/000_invoice-bundle-request.md`; steps 3–6 walk the inbox workflow and schema exactly as `inbox_processing.md` DEFAULT ROUTE prescribes) proves the task IS inbox processing — the model recognises it even without the right fragment. Only the classifier misreads it.
3. Sibling t091 (same run, same day, identical instruction style "Work the oldest inbox message") also scored 0 with zero step budget pressure — it ran 7 steps — but crucially ran without the `inbox_processing` fragment too. That `work` matches nothing in the regex set. In other words, the whole "one-line inbox verbs" family (`review`, `work`, `handle`, `take care of the next …`) systematically falls through to `crud`.
4. Budget is the downstream killer here because t097's bundle-request required 18–20 steps per the workflow (read note → tree 99_system → read 3 workflows → read schema → list cast → read nina.md → read each invoice in the bundle → verify sender → write finance record → re-read). Fifteen is about 5 too few.

## Fix proposal (narrow GREEN zone only)

**Selected fix class:** `classify_rule`

**Target file:** `pac1-py/classify.py`

**Exact change:**
```diff
 _INBOX_PROCESSING_SIGNALS = re.compile(
-    r"\b(process\s+(the\s+)?inbox|from\s+(the\s+)?inbox|inbox\s+file|"
-    r"(take\s+care\s+of|work\s+through)\s+(the\s+)?(?:inbox|incoming)\s+queue|"
-    r"(?:incoming|inbox)\s+queue|pending\s+inbox\s+items?|mailbox|"
-    r"message\s+backlog|waiting\s+messages?|pending\s+requests?|"
-    r"newly\s+arrived\s+requests?|unread\s+requests?)\b",
+    r"\b(process\s+(the\s+)?inbox|from\s+(the\s+)?inbox|inbox\s+file|"
+    r"(take\s+care\s+of|work\s+through)\s+(the\s+)?(?:inbox|incoming)\s+queue|"
+    r"(?:incoming|inbox)\s+queue|pending\s+inbox\s+items?|mailbox|"
+    r"message\s+backlog|waiting\s+messages?|pending\s+requests?|"
+    r"newly\s+arrived\s+requests?|unread\s+requests?|"
+    r"(review|handle|work|act\s+on|process)\s+(the\s+)?(next|oldest|newest|latest|pending|incoming)\s+"
+    r"(inbound\s+note|inbox\s+item|inbox\s+message|message|note|item|request))\b",
     re.IGNORECASE,
 )
 _PROCESS_LIKE_SIGNALS = re.compile(
-    r"\b(process|triage|clear|handle|work\s+through|go\s+through|take\s+care\s+of)\b",
+    r"\b(process|triage|clear|handle|work\s+through|go\s+through|take\s+care\s+of|review|act\s+on)\b",
     re.IGNORECASE,
 )
```

**Rationale:** Two changes with intentional overlap for safety. The direct extension to `_INBOX_PROCESSING_SIGNALS` adds a new alternation that literally matches the benchmark corpus phrasing: `review|handle|work|act on|process` + `the? next|oldest|…` + `inbound note|inbox item|message|note|item|request`. That alone catches t091, t094, t097 and any lookalikes. The second change to `_PROCESS_LIKE_SIGNALS` adds `review|act on` so the existing AND-gate `_PROCESS_LIKE_SIGNALS AND _INBOX_OBJECT_SIGNALS` (classify.py lines 149–151) also trips on edge phrasings where the object word leaks out of the direct rule. No change to `_INBOX_OBJECT_SIGNALS` is needed because the direct rule now captures "inbound note" and "note" explicitly inside the new alternation — keeping the broader `_INBOX_OBJECT_SIGNALS` untouched avoids side-effects on `crud`/`search` classification for tasks that merely mention "note" in passing.

Once classified as `inbox_processing`, strategy.py picks `("inbox_processing", (32, "hardened", True))` at line 54. That gives t097 a 32-step budget (more than double), loads `inbox_processing.md` fragment (which documents the exact DEFAULT ROUTE the agent was improvising), and bumps security posture from `standard` → `hardened`. All three symptoms of the failed run (setup-tax, empty-pattern searches, no completion) become addressable within a single cycle.

**Generalizability:** `HIGH`
- Three confirmed tasks in the t091–t099 window share the "inbound note / oldest inbox message" phrasing pattern (t091, t094, t097). Scanning sibling peek output: t093 "Handle the next inbox item", t095 "Take care of the next message in inbox", t096 "Handle the next inbox item", t098 "Work the oldest inbox message" — that's **6 more near-identical instructions** in the same window. At minimum this is 5+ tasks that fall through today; likely 7–9 across the full 104-task benchmark. Matches the "H = 5+" threshold.

**Zone:** `GREEN` — pure regex edit in `classify.py`. No Python logic changes, no new tools, no security paths touched (the direct rule is more inclusive, which ROUTES a task to `inbox_processing` strategy — which is strictly more conservative/hardened than the `crud` fallback). No risk of security weakening: hardened posture is a superset of standard.

**Expected impact:** Conservative estimate: **+3 to +6 tasks** across the full benchmark. Direct wins on t091, t094, t097, t093, t095, t096, t098 (subject to each task's own downstream hazards). Some of these sibs already completed under crud strategy because their inbox items were simpler — the fix gives them larger margins but may not flip the score. The bundle-request case (t097) is the clearest net-new win because budget was the binding constraint.

**Risks:** One false-positive vector — tasks like "Review the next quarter's budget" where `note|item` is absent but `review the next …` matches the secondary `_PROCESS_LIKE_SIGNALS + _INBOX_OBJECT_SIGNALS` AND-gate. That gate requires `_INBOX_OBJECT_SIGNALS` to also trip, and the current object set is reasonably tight (`inbox|mailbox|queue|backlog|messages?|requests?`). `budget` is not in there, so "review the next quarter's budget" stays in CRUD. Second minor risk: `act on` could match "act on this email" which is genuinely communication, not inbox_processing — but `_COMMUNICATION_SIGNALS` is evaluated later in the if-ladder (line 225) so inbox_processing wins, which is the safer routing anyway (inbox_processing already handles communication workflows).
