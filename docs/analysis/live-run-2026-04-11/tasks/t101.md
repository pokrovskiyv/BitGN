**Justification:** The task is a numeric aggregation over filesystem data — the exact shape `analysis.md` was designed for. `analysis.md` contains the full NUMERIC AND MONETARY DISCIPLINE block (cite rows, transcribe amounts exactly, read ALL relevant rows, return CLARIFICATION if inputs missing). The root defect is upstream of behaviour — it is the classification decision itself.

## Root cause hypothesis

**Exactly one hypothesis:**

`_ANALYSIS_SIGNALS` in `classify.py` is missing the numeric-monetary phrases that describe the most common benchmark pattern ("how much did X cost / pay / charge", "what is the total", "subtotal / balance / spend / revenue"). Only "how many" is captured, so integer-count aggregations route to `analysis` but monetary-sum aggregations route to the CRUD default. The prompt fragment architecture correctly places the numeric discipline in `analysis.md`, but the classifier never opens that door for "how much" questions.

**Evidence chain:**
1. The instruction text contains "How much did I pay … in total" and "Number only". None of "how much", "pay", "total", "amount" appear in any signal regex in `classify.py` (lines 41–72). Direct confirmation from a live `classify_task()` call: `t005`, `t008`, `t100`, `t101` all return `task_type=crud, estimated_steps=10`, while `t004` ("how many planned projects") correctly returns `task_type=analysis, estimated_steps=15`.
2. `analysis.md` lines 11–16 already contain the exact prescription that would have prevented this failure: "cite the source file AND the row or field containing each input value", "read ALL relevant rows first", "If a required input value is NOT present … return OUTCOME_NONE_CLARIFICATION naming the missing item. Do NOT invent or approximate". The `crud.md` fragment loaded instead (5 lines, file-write verification only) contains none of this.
3. A census of the 104-task cache finds 11 "how much"-style monetary-sum tasks (`t005`, `t008`, `t030`, `t033`, `t055`, `t058`, `t080`, `t083`, `t100`, `t101`, `t102`, `t103` — overlapping groups). Every one of them is currently misrouted to CRUD. This is systemic, not task-specific.
4. Root, not symptom: fixing the agent's output for t101 (e.g., a more generous crud.md) would help this one task; fixing the classifier fixes the entire monetary-sum family in one line and unlocks the NUMERIC AND MONETARY DISCIPLINE block that already exists but is not being routed to.

## Fix proposal (narrow GREEN zone only)

**Selected fix class:** `classify_rule`

**Target file:** `pac1-py/classify.py`

**Exact change:**
```diff
 _ANALYSIS_SIGNALS = re.compile(
-    r"\b(analyze|summarize|compare|count|list\s+all|report|describe|explain|how\s+many)\b",
+    r"\b(analyze|summarize|compare|count|list\s+all|report|describe|explain|"
+    r"how\s+many|how\s+much|total\b|subtotal|balance\b|revenue|spend\b|"
+    r"paid\s+(?:to|for)|pay\s+(?:to|for))\b",
     re.IGNORECASE,
 )
```

**Rationale:** The fragment architecture is already correct — `analysis.md` has the numeric discipline, the `analysis` strategy gets 25 steps (vs CRUD's 15), and the classifier is the one broken link. Adding "how much" and the small set of monetary keywords that recur in the benchmark routes all 11 misclassified tasks into the right strategy in a single line change. `total\b` is word-bounded so it will not collide with "the total file list" or similar; `balance\b` and `spend\b` are likewise conservative. `paid to / pay to / pay for` captures the t101 variant "how much did I pay to these guys" without needing the literal "total". This is a pure widening of the analysis branch — it adds tasks to `analysis`, never removes from it, and `crud` loses only these monetary-sum tasks that should never have been CRUD in the first place.

**Generalizability:** `HIGH`
- The cache census above found **11 tasks** in the `how much / total / paid` family that are currently misrouted: `t005, t008, t030, t033, t055, t058, t080, t083, t100, t101, t102, t103`. That is ~10% of the 104-task benchmark. Every one of these would pick up `analysis.md`'s numeric discipline AND a 25-step budget instead of 15, and every one would be executed with the correct "cite every source row, do not approximate, return CLARIFICATION if inputs missing" rules. The upside across this family substantially exceeds the 1-task impact of most prompt-fragment edits.

**Zone:** `GREEN` — single regex widening in `classify.py`, no Python logic change, no change to security paths (threat detection runs before classification routing), no change to the default `crud` fallback for truly generic operations.

**Expected impact:** +1 on t101 directly. Realistic lift on the rest of the family is bounded by ground-truth availability (each task still requires the agent to find the right vendor's bills and sum them correctly), but loading `analysis.md` provides the explicit instruction "read ALL relevant rows first" and "do NOT invent or approximate" — exactly the two disciplines t101 violated. Conservative estimate: **+3 to +6 tasks** across the 11 misclassified family members, depending on how many were already passing by luck.

**Risks:** Very low. The widening only reroutes monetary-sum tasks away from the CRUD default into the analysis strategy. `analysis.md` is strictly stricter than `crud.md` (numeric discipline, explicit clarification-over-invention rule), so a task that currently passes under CRUD will not fail under analysis. The one concrete risk: a task mentioning "total" in an unrelated sense (e.g., "create a total.md file") could now be classified as analysis and skip the CRUD write/read verification. Mitigated by the word-boundary `\b` on `total` and the fact that the `analysis` branch requires `not has_write` (line 203) — any task with `create / write / update / add` still routes to CRUD first. No security-path impact because threat_level="high" check runs before all other branches.
