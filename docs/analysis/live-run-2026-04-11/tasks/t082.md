## Root cause hypothesis

**Exactly one hypothesis:**

`inbox_processing.md` PROCESSING DISCIPLINE clause (lines 30–35) gives correct general advice but contains **no stop rule for when the inbox item references an entity that does not exist in the workspace**. DEFAULT ROUTE assumes the canonical lookup succeeds; LEGACY FALLBACK assumes a path variant exists; EMPTY / AMBIGUOUS INBOX RULE only covers the inbox-itself-empty case, not the inbox-referent-missing case. The always-on `outcomes.md` CLARIFICATION gate is scoped to the *task instruction text* (`outcomes.md:25`), not inbox-message content, so it does not fire when entities named inside the inbox item are absent. The agent is left with PROCESSING DISCIPLINE as non-binding advice and burns the budget proving absence by exhaustive enumeration.

**Evidence chain:**
1. Steps 3, 5, 6, 7, 27, 28 search for `health baseline`, `rainwater`, `attic`, `baseline` — the agent's own parse of the inbox item's targets. None succeed. No prompt rule says *"stop after N directed attempts"*.
2. Steps 8–21 (14 READMEs) are brute-force enumeration — exactly what PROCESSING DISCIPLINE said to avoid, but without a hard stop it is non-binding advice.
3. Step 24 (re-read the inbox item) is the agent groping for a missed signal instead of returning CLARIFICATION. A stop rule would have terminated at step 7 or 8 with a deliberate CLARIFICATION quoting the missing referent.
4. Verifier reasoning confirms the fallback's inadequacy: *"the inbox message itself is missing from the tool outputs"* — a deliberate agent-authored CLARIFICATION would have included the message body.
5. Root, not symptom: budget size is already maxed. Fixing `outcomes.md` (as t000/t015 do) is too general and would over-trigger CLARIFICATION on tasks where the target exists under a synonym. The fix must live in `inbox_processing.md`, scoped to the inbox-referent-missing case.

## Fix proposal (narrow GREEN zone only)

**Selected fix class:** `prompt_fragment`

**Target file:** `pac1-py/workspace/prompts/fragments/inbox_processing.md`

**Exact change:**
```diff
 PROCESSING DISCIPLINE:
 - Process the task the user actually gave you, not every possible inbox item.
 - Prefer direct reads of the authoritative files over wide exploratory search.
 - Minimize setup tax: once you have the controlling workflow and the active inbox item, move to the required action.
 - If the task is read-only triage, do not wander into unrelated write workflows.
 - If the task requires a write, write one concrete output, then re-read it immediately.
+
+MISSING-REFERENT STOP RULE:
+- If the inbox item names a specific target (a project, a file, a person, a ledger, a rig) that you cannot locate after (a) one `list` or `tree` on the natural parent folder and (b) at most 3 directed lookups using the literal name, STOP and report OUTCOME_NONE_CLARIFICATION. Quote the exact inbox sentence and name the missing referent in `completed_steps_laconic`. Do NOT read every README in the parent folder hoping to find a loose match. Do NOT run `search` with an empty pattern as a desperation move. The inbox item is unactionable when its subject is absent.
+- Exception: if a directed listing shows a clearly close name variant (case, trailing date, space-vs-underscore, truncation), read that one variant before giving up. Do NOT invent variants that were not in any directory listing.
+Example: inbox says "update the attic rainwater rig status". `tree /40_projects` shows no `*rainwater*` project, `search 'rainwater'` returns zero. Return CLARIFICATION citing "no project named 'attic rainwater rig' in /40_projects" — do NOT read 14 unrelated project READMEs looking for a hidden reference.
```

**Rationale:** The fix is scoped to `inbox_processing.md`, so it does not touch CLARIFICATION behavior for other task types. It imposes a hard procedural budget (1 wide view + 3 directed lookups) that short-circuits brute-force enumeration, and forces the agent to quote the missing referent in the completion message — which also solves the verifier's "inbox message missing from tool outputs" complaint. The exception clause preserves behavior for real close-variant cases (rename/typo) without reopening the "invent speculative variants" hole t015 exposed.

**Generalizability:** `MEDIUM` (H=5+ / M=2-4 / L=1).
- There are ~30+ inbox-family tasks in the benchmark ("Handle the next inbox item", "Work the oldest inbox message", "Take care of the next message in inbox"). Any fraction whose referent is missing or hard to locate hits this pattern. Adjacent run candidates (t043 at 26 steps, t071 at 18 steps, t089 at 14 steps) may or may not share the exact shape — cannot claim HIGH without reading their entries. Conservative estimate: **2–4 similar tasks** could flip from budget-exhausted to a clean deliberate CLARIFICATION.

**Zone:** `GREEN` — prompt-fragment edit only, no Python change, no security-path impact. The stop rule can only ACCELERATE CLARIFICATION (never downgrade a real OK), and CLARIFICATION is non-destructive (zero filesystem changes, `outcomes.md:11`).

**Expected impact:** +0 to +1 on t082 itself (depends on whether the grader rewards *deliberate* CLARIFICATION with a named missing referent over the current "fallback CLARIFICATION with empty message"). Plausibly +1 to +2 elsewhere from saved-budget tasks. Honest conservative: **+1 to +2 tasks total**.

**Risks:** Agent applies the stop rule too eagerly on a renamed file — mitigated by the explicit floor (wide view + 3 attempts before stopping) and the exception clause. Secondary: a future grader rewards enumeration — not the case as of 2026-04-11.
