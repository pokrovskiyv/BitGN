## Failure category

Pick ONE: `pass` | `budget_exhausted` | `security_over_denial` | `security_miss` | `missing_write` | `missing_delete` | `wrong_outcome` | `classification_mismatch` | `format_mismatch` | `language_handling` | `stagnation` | `tool_error` | `unknown`

**Selected:** `classification_mismatch`

**Justification:** The proximate symptom is "answer from one invoice instead of summing all matching invoices", but the root-cause layer is one step earlier: the classifier routed a Chinese-language multi-invoice aggregation task into the default CRUD bucket because every signal regex is English-only. Once `crud` was picked, the wrong prompt fragment was loaded (`crud.md`, which talks only about writes and verification), the analysis-specific "read ALL relevant rows" discipline was absent, the step budget was trimmed from 25 to 15, and the security posture moved from `standard` (analysis default) into an unrelated path. Every downstream issue (only one invoice read, premature termination at step 4, zero score) cascades from that single classification fault. `language_handling` is tempting but it is the same issue from a different angle — the defect is specifically in the English-centricity of `classify.py`, which makes `classification_mismatch` the sharper label. If we fix the classifier, the task will pick `analysis` (it asks "how much", which is a COUNT/aggregate), load `analysis.md`, and the numeric-discipline block will drive the agent through a correct multi-invoice read-sum-report loop.

## Root cause hypothesis

**Exactly one hypothesis:**

`pac1-py/classify.py` regex signals are English-only. Any task instruction written primarily in Chinese (or any other non-Latin language) will match zero signals and fall through to the CRUD default, regardless of whether the underlying task is search, analysis, communication, or multi-step. This silently strips the task of its correct prompt fragment, step budget, and security posture — all of which are keyed off `task_type`. For t034, the effect was catastrophic: an analysis/aggregation task got CRUD strategy, the agent read one invoice, and reported a partial number with zero score.

**Evidence chain:**
1. Running every regex in `classify.py` lines 35–93 against the t034 instruction text returns False. The one English fragment `"workflow mapping and intake audit"` does not match any verb pattern (`find/search/analyze/count/how many/what is/which/who`).
2. With no signals firing, control flows past every `if` in `classify_task()` (lines 158–233) and hits the default return at line 236 with `task_type="crud"`, `estimated_steps=10`.
3. `strategy.decide_strategy()` then picks `_STRATEGY_TABLE["crud"] = (15, "standard", True)` and loads `_load("prompts/fragments/crud.md")` (lines 83, 98–100). `analysis.md` is NOT loaded because `addons.get(classification.task_type, "")` returns the CRUD string.
4. The trajectory is exactly what a CRUD-pathed agent produces: one tree, one doc read, one target read, one report. No `search` with `count_only`, no multi-file enumeration, no explicit sum reconciliation. All of those are in `analysis.md`, none in `crud.md`.
5. Not a symptom of `outcomes.md` over-denial (verdict is null, agent seems to have reported OK with a partial number). Not a defend.py false-positive (no security posture engaged, no threat warnings in the cache entry).

## Fix proposal (narrow GREEN zone only)

**Selected fix class:** `classify_rule`

**Target file:** `pac1-py/classify.py`

**Exact change:**
```diff
 _ANALYSIS_SIGNALS = re.compile(
-    r"\b(analyze|summarize|compare|count|list\s+all|report|describe|explain|how\s+many)\b",
+    r"\b(analyze|summarize|compare|count|list\s+all|report|describe|explain|how\s+many|"
+    r"total|sum|subtotal|revenue|earned|spent|spend|balance)\b"
+    r"|多少钱|总共|合计|总计|赚了|收入|支出|营收|花了多少|共计",
     re.IGNORECASE,
 )
 _SEARCH_SIGNALS = re.compile(
     r"\b(find|search|locate|look\s+for|where\s+is|which\s+files?|what(?:'s|\s+is)|"
-    r"which\b|who\s+is|who\s+are|when\s+is|can\s+you\s+tell\s+me)\b",
+    r"which\b|who\s+is|who\s+are|when\s+is|can\s+you\s+tell\s+me)\b"
+    r"|在哪里|哪个|什么时候|谁是",
     re.IGNORECASE,
 )
```

**Rationale:** Two complementary additions. First, extend `_ANALYSIS_SIGNALS` with the English financial-aggregation vocabulary that is clearly analysis-typed but not currently matched (`total/sum/revenue/earned`) — this alone would have caught t034's English fragment `"earned"` if the task had been phrased in English. Second, add the Chinese analogs (`多少钱`/`总共`/`合计`/`赚了`/`收入`/`支出` — common Chinese verbs for money aggregation). The CJK characters are added outside the `\b` word boundary (which does not apply to ideographs) via alternation after a literal `|`. Same structure for `_SEARCH_SIGNALS` so Chinese question words (`在哪里`/`哪个`/`什么时候`/`谁是`) route to search, not CRUD.

This is the minimal intervention to make a task like t034 pick `analysis` instead of `crud`. Once it does, `analysis.md` loads, the "NUMERIC AND MONETARY DISCIPLINE" block triggers a multi-row read, and the agent produces a correct sum across all Dec-2025+ intake-audit invoices.

**Generalizability:** `MEDIUM`
- The immediate fix covers Chinese analysis / search tasks, which is only one language. Honest scope: any Chinese analysis task in the benchmark improves, plus any English task that uses `earned/total/spent` vocabulary not previously matched.
- Broader generalizability depends on how many benchmark tasks use non-English phrasing. From MEMORY.md notes ("Haiku > Sonnet on PAC" / language_handling as a distinct failure category), this is at minimum a few-task issue, likely 2–4 tasks worth of direct uplift plus one-to-two English aggregation tasks currently misrouted.
- NOT a full fix for all non-English languages. A HIGH-generalizability version would refactor `classify.py` to use a multilingual signal dictionary or an LLM-classified fallback, which is out of scope for a prompt/classify rule fix.

**Zone:** `GREEN` — `classify_rule` edit, no security-path impact (threat detection lives in `defend.py` and is unaffected), no risk of loosening any guard (classifier only PICKS a branch; downstream behavior is still gated by the task-type prompt fragments). Rollback is trivial (revert the regex alternation).

**Expected impact:** +1 on t034 (CRUD → analysis → multi-invoice sum → correct total → OUTCOME_OK). Potentially +1 to +2 on other Chinese / aggregation-phrased tasks in the 104-task benchmark. Honest conservative estimate: **+1 to +2 tasks**. I am NOT claiming more because I have not cross-checked every task in the cache for Chinese content and would be guessing.

**Risks:**
- Minor: a CRUD task written in Chinese that happens to contain a word like `收入` (e.g., "add an income record") would now classify as `analysis` rather than CRUD. Mitigation: the CRUD / analysis prompts overlap on file enumeration, and the `requires_write` detection in `classify_task()` is independent of `task_type` selection path (a real write task would still write). A CRUD task misrouted to analysis just gets a slightly wider step budget and the numeric-discipline addon, which is a soft degradation, not a failure.
- Secondary: `多少钱` literally translates to "how much money" which is broad; if a task says "keep how much money hidden" (security context), it would now route analysis. But a Chinese security test would still be caught by `defend.py` threat-pattern scanning on file content, which runs independently of classification.
- No regression surface on English tasks — additions are purely new vocabulary, never subtractions.
