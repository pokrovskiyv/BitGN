## Failure category

Pick ONE: `pass` | `budget_exhausted` | `security_over_denial` | `security_miss` | `missing_write` | `missing_delete` | `wrong_outcome` | `classification_mismatch` | `format_mismatch` | `language_handling` | `stagnation` | `tool_error` | `unknown`

**Selected:** `classification_mismatch`

**Justification:** The **root** fault is that the Japanese-language instruction was invisible to every regex in `classify.py`, so the task was silently defaulted to the `crud` bucket and received `crud.md` instead of `inbox_processing.md`. Every downstream symptom — the 13s / 17s / 12s / 14s thinking spikes, the late-stage `tree /99_system` and `read /99_system/workflows/...` discovery, the confused escalation to `OUTCOME_NONE_UNSUPPORTED`, even the verifier’s confusion — follows from the agent operating without the inbox-processing scaffold. `language_handling` is also present as a secondary tag (the classifier is monolingual), but the observable failure manifests as the wrong prompt fragment being injected, which is a classification-layer defect.

## Root cause hypothesis

**Exactly one hypothesis:**

`classify.py` performs purely English regex matching. For a Japanese instruction like `次の受信トレイ項目を処理してください。` (where `受信トレイ` literally means "inbox" and `処理してください` means "please process"), zero signals fire: `has_write=False`, `has_search=False`, `has_inbox_processing=False`, `has_analysis=False`, `is_questionish_lookup=False`. The function falls through to the final `return TaskClassification(task_type="crud", …)` default. The agent is then handed the CRUD prompt scaffold, which contains no household-workspace routing and no `/00_inbox/AGENTS.MD` read-first rule, so it has to reinvent the `inbox_processing.md` default route on the fly — consuming 63% of its runtime on thinking.

**Evidence chain:**
1. The instruction field in `task_cache.json.t035.instruction` is `"次の受信トレイ項目を処理してください。"` — 100% Japanese, including the full-width period.
2. `pac1-py/classify.py` lines 73–80 define `_INBOX_PROCESSING_SIGNALS` as an English-only regex: `r"\b(process\s+(the\s+)?inbox|from\s+(the\s+)?inbox|inbox\s+file|…mailbox|message\s+backlog|…)\b"`. Japanese characters will never match a `\b\w\b`-style word boundary rule.
3. Same applies to every other signal regex on lines 35–93 — all English, all expecting ASCII word boundaries.
4. The trajectory directly corroborates the wrong-fragment hypothesis: steps 11–12 (`tree /99_system` → `read /99_system/workflows/process-next-inbox-item.md`) are exactly the canonical inbox routing, but only reached after 11 budget slots. Had `inbox_processing.md` been loaded, steps 1–2 of `inbox_processing.md`'s DEFAULT ROUTE FOR HOUSEHOLD WORKSPACE would have been `tree /99_system` + `read /99_system/workflows/…` + `read /00_inbox/AGENTS.MD` as the very first moves.
5. Large `planning_ms` spikes (13s, 17s, 12s, 14s) correlate exactly with routing decisions that would have been pre-answered by `inbox_processing.md`.
6. The crud budget (15) was nearly exhausted (13 used) — classic "wrong scaffold → more deliberation → more steps" cascade.

## Fix proposal (narrow GREEN zone only)

**Selected fix class:** `classify_rule`

**Target file:** `pac1-py/classify.py`

**Exact change:**
```diff

     r"\b(process\s+(the\s+)?inbox|from\s+(the\s+)?inbox|inbox\s+file|"
     r"(take\s+care\s+of|work\s+through)\s+(the\s+)?(?:inbox|incoming)\s+queue|"
     r"(?:incoming|inbox)\s+queue|pending\s+inbox\s+items?|mailbox|"
     r"message\s+backlog|waiting\s+messages?|pending\s+requests?|"
```

**Rationale:** This is the minimum-surface-area fix that rescues t035 specifically (the Japanese "受信トレイ" + "処理してください" pattern will match `受信トレイ|次の.{0,4}項目`) while also adding coverage for five other common UI locales that the BitGN benchmark is known to use (DE/ES/FR/ZH/RU appear in other language_handling task slugs in `task_cache.json`). No changes to `strategy.py`, no prompt edits, no defend.py change. Once the classifier routes t035 to `inbox_processing`, the agent gets:
- max_steps 32 instead of 15 (plenty of headroom),
- `security_posture="hardened"` (appropriate for inbox-processing),
- `inbox_processing.md` fragment with the DEFAULT ROUTE FOR HOUSEHOLD WORKSPACE that pre-answers every routing decision the agent wasted time on in this run.

**Generalizability:** `MEDIUM`

- Directly fixes this task and any other pure-Japanese inbox task. If even 2-3 of the ~104 benchmark tasks use non-English language for inbox-routing instructions, this fix rescues them all. BitGN's language_handling line of attack historically rotates through ja/de/es/fr/zh/ru.
- Does NOT solve the broader monolingual-classifier problem (tasks that use the same CJK/Cyrillic alphabets for *search*, *communication*, *analysis* would still fall through to `crud`). A complete solution would i18n every `_*_SIGNALS` regex or, better, pipe the task through a tiny LLM classifier. Both are out of GREEN scope.
- Conservative estimate: +1 task (t035 specifically). Upper estimate: +2 tasks if there is another non-English inbox task in the current benchmark suite.

**Zone:** `GREEN` — `classify_rule` is explicitly in the GREEN list; the change is a single new compiled regex plus one `or` clause in the composite flag. No behavior change for English inputs (the new regex uses literal CJK/multi-byte characters that cannot match ASCII text). No effect on security paths, write paths, or delete paths.

**Expected impact:** +1 on t035 (`OUTCOME_NONE_UNSUPPORTED` → `OUTCOME_OK` or at minimum `OUTCOME_NONE_CLARIFICATION` for a net improvement from 0.0 to the partial or full score). Potential +1 additional if another benchmark task also uses non-English inbox phrasing. Honest conservative estimate: **+1 task**.

**Risks:**
- False positive on a legitimate non-inbox task that happens to include `次の項目` ("next item") in a non-inbox context — mitigated by the `.{0,4}項目` bounded wildcard and the `受信トレイ` anchor in the same alternation. The broader patterns (de/es/fr/zh/ru) require a direct keyword match, not a sub-phrase, so they are low-risk.
- None of the new patterns are subject to regex catastrophic backtracking (all alternations are flat, no nested quantifiers).
