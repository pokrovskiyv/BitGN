### Root Cause
**Classification**: EDGE_CASE — wrong check order in _fallback_outcome
**File**: `pac1-py/verify.py` lines 212-231 (GREEN zone)
**Generalizability**: HIGH — affects any communication task that exhausts budget after reading files

R85 lesson explicitly says: "UNSUPPORTED overuse is caused by _fallback_outcome() when the model exhausts its step budget. Fixing this requires changing the fallback outcome logic."

Current `_fallback_outcome()` check order:
1. No tracker → ERR_INTERNAL
2. High threats → SECURITY
3. **Communication + no writes → UNSUPPORTED** ← fires BEFORE reads check
4. Has writes → OK
5. Has reads → CLARIFICATION
6. Default → CLARIFICATION

Bug: step 3 returns UNSUPPORTED for communication tasks that READ files but didn't WRITE. This is semantically wrong — UNSUPPORTED means "I lack this capability." If the agent read files, it tried to execute; CLARIFICATION is correct.

### Why this is NOT a repeat of previous cycles
- Cycle 2026-04-02-21 changed the DEFAULT return (step 6) from ERR_INTERNAL to CLARIFICATION
- Cycle 2026-04-03-12 added a pre_completion_gate to intercept model-initiated UNSUPPORTED
- THIS fix reorders the EXISTING checks so has_writes/has_reads are checked before the communication case

### Recommended Fix
Reorder `_fallback_outcome()` checks:
1. No tracker → ERR_INTERNAL
2. High threats → SECURITY
3. Has writes → OK
4. Has reads → CLARIFICATION
5. Communication + no reads + no writes → UNSUPPORTED
6. Default → CLARIFICATION
