**Task**: t01
**Category**: STAGNATION
**Points lost**: 1.0

## Observation

t01 is a `crud_delete` task that has never passed (0.00 across all 3 cycles). The eval report
notes a "delete-after-delete pattern wastes 4 steps" and the Optimizer confirmed 2 stagnation
events in the run.

The agent calls `delete /path`, receives an empty `{}` response (protobuf DeleteResponse has no
fields), then on the next step calls `delete /path` again — identical tool+args → stagnation
detector fires after 2 identical calls. The nudge message does not resolve the confusion because
the agent has no confirmation that the first delete succeeded.

## Root Cause

`_format_result` in `agent.py` has no case for `Req_Delete`. It falls through to:
```python
return json.dumps(MessageToDict(result), indent=2)
```

`DeleteResponse` is an empty protobuf message → `MessageToDict` returns `{}` → the agent
sees `{}` and does not know if the delete operation succeeded. With no success signal, it
retries the same delete, triggers stagnation after 2 identical calls, gets a generic nudge,
and wastes 4 steps before eventually time-running-out or recovering by accident.

## Recommended Fix

Add a `Req_Delete` case to `_format_result` that returns a human-readable Unix-style
confirmation matching the agent's existing output style (like `_format_read_response`,
`_format_search_response`, etc.).

The confirmation message should mirror the `rm` command so the agent can clearly identify
the operation succeeded:
```
rm /path/to/file
deleted: /path/to/file
```

**Risk**: VERY LOW. Only affects the tool output seen by the LLM for delete operations.
Does not change dispatch logic, stagnation detection, or any other behavior.

**Expected impact**: +1 point (t01). Possibly reduces non-deterministic delete-related
failures in other tasks that involve delete operations (t08, t11 are non-deterministic
crud tasks — may benefit).
