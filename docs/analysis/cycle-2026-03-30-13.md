# Analyst Report: Cycle 2026-03-30-13

## Target Failure

**Task cluster**: t12, t13, t14 (CRM), t17 (outbox), + timeout headroom for t06/t07/t08
**Category**: TOOL_ERROR — subprocess timeout at 120s hard limit
**Points at risk**: ~7 tasks that were passing at 68% baseline but vulnerable to any prompt growth
**Previously attempted**: NOT attempted — only identified as "Phase 1 prerequisite" in cycle-2026-03-30-11 analyst report. No prior cycle has touched the timeout value.

## Observation

The `_call_cli()` function in `pac1-py/agent.py` line 222 passes `timeout=120` to `subprocess.run()`.
When the `claude -p` subprocess does not return within 120 seconds, Python raises `subprocess.TimeoutExpired`,
the function catches it (or propagates), and the calling code receives an empty/no result.
The agent then retries up to 3 times — all three retries also time out — and ultimately returns
empty JSON, which causes `Invalid JSON: EOF while parsing a value at line 1 column 0`.

Evidence from cycle-11 eval report:
- t08: "all 3 attempts timed out after 120 seconds"
- t07: "Command timed out after 120 seconds"
- t12/t13/t14: "CRM empty JSON — subprocess timeout at step_1"

These tasks have longer conversation history (CRM context is larger) and take longer per LLM call.
They were passing at 68% but are vulnerable: adding any prompt content tips them over 120s.

## Root Cause

`subprocess.run(timeout=120)` in `agent.py:222` is the single point of failure.
The value 120s is not documented as a deliberate limit — it appears to be a default choice.
CRM tasks need ~110-130s for the first `claude -p` call. At 120s they are borderline.

**This is a systemic fragility**: any future prompt addition risks cascading timeouts in CRM tasks.
The fix is a ONE-LINE change with zero prompt impact and zero logic change.

## Root Cause Classification

**TOOL_ERROR** — hard timeout limit in subprocess invocation is too low for CRM-class tasks.

## Recommended Fix

In `pac1-py/agent.py` line 222:
```python
# Before
timeout=120,

# After
timeout=150,
```

**Risk**: VERY LOW.
- No prompt changes → no LLM behavior change.
- No logic changes → no side effects.
- 150s is still a safety net against runaway calls; 30 extra seconds is modest.
- No other code depends on this value.

**Expected impact**: Recovers t12, t13, t14, t17 (CRM/outbox tasks borderline at 120s).
Also provides headroom so future prompt additions don't cascade into timeout regressions.
Baseline should rise from 68% → ~72% if t12-t14+t17 recover, or at minimum confirm 68% is stable.
